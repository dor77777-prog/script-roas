### [HIGH] Hero Net-Profit delta mixes fair-share cur with full-burden prev — D4 threading missed prevAggFromPrevData

**Evidence:** e290dc4 added store-scope fixed-cost threading to filtered.curAgg/prevAgg (dashboard-web/src/components/Dashboard.tsx:540-553 — scopedStoreNames + revenueByStoreFor), and c39fcc8 propagated it to AiReportButton, but the hero comparison baseline `prevAggFromPrevData` (Dashboard.tsx:1185-1199) still calls `aggregate(prevCur, prevRange, undefined, undefined, ...)` on STORE-FILTERED rows. `toHeroDelta` then computes `netProfit: cur.trueNetProfit - prev.trueNetProfit` (dashboard-web/src/lib/home/adapters.ts:146) — cur charges the store its fair share of All-scoped fixed costs while prev charges it the FULL amount (analytics.ts aggregate(): scopedStoreNames/revenueByStore drive billingForRange → fixedCosts → trueNetProfit). Pre-batch both sides were full-burden (consistent); the batch changed one side only, so every store-filtered hero Net-Profit delta is now systematically overstated whenever All-scoped fixed costs exist. Its own comment claims it must 'match filtered.curAgg'. No test pins cur/prev threading parity (only billing.test.ts / aggregateByStoreAllRowSplit.test.ts cover the aggregate internals).

**Suggested fix:** Hoist the scopedStoreNames/revenueByStoreFor helper out of the filtered memo and thread it into prevAggFromPrevData: `aggregate(prevCur, prevRange, scopedStoreNames, revenueByStoreForRows(dataPrev.rows, prevRange), salariesForRange(...))` (revenue split computed over dataPrev.rows with store='All'). Add a DOM/unit test asserting that with a store filter + an All-scoped billing row, toHeroDelta's netProfit delta equals the delta computed with both sides threaded.

### [MEDIUM] Meta FX adapter's batch-uniformity claim fails under Promise.all — heterogeneous *_cad keys break the whole bulk upsert (PGRST102)

**Evidence:** getFxCadAdapterForStore's per-currency cache is check-then-act across an await (dashboard-web/src/lib/fetchers/metaAccountConfig.ts:111-130: `rateCache.get` → `await getFxRate` → `rateCache.set`), but fetchMetaHotMetricsForStore builds ALL adset rows concurrently (dashboard-web/src/lib/fetchers/metaHotMetrics.ts:132-133 `Promise.all(adsetRaw.map(...))`). Every row misses the empty cache and fires its own Frankfurter call (getFxRate has no internal cache/dedupe — fx.ts:47-73). Under a flapping/timeout-variance outage (the realistic mode P1-11 targets), some rows get a rate and some get null → rows mix {spend_cad present/absent} × {conversion_value_cad present/absent} (a row's 2nd call can even read another row's cached result). metaWorker upserts the whole array in ONE call (metaWorker.ts:829-835 `.upsert(rows, {onConflict: ...})`); PostgREST bulk upsert requires uniform keys across all objects → 'All object keys must match' → the ENTIRE tick fails with transient_error, freezing today's Meta metrics including the non-CAD ones the doctrine explicitly promises 'still refresh' (metaHotMetrics.ts P1-11 comment). The comment's guarantee ('one worker invocation produces a CONSISTENT null-vs-number answer for every row of the same currency') only holds sequentially — TikTok's sequential for...of loop is safe; Meta's Promise.all is not. Test gap: fxAdapterAlert.test.ts:59 ('per-currency result is cached...') only exercises sequential repeated calls; no concurrent-flap test, no batch-key-uniformity assertion.

**Suggested fix:** Cache the in-flight Promise per currency instead of the resolved value (Map<string, Promise<number|null>>; first caller's resolution becomes authoritative for the whole invocation) in BOTH adapters, or pre-resolve the needed rates once before row building. Optionally add a belt-and-suspenders uniformity pass in the workers (if any row in a batch omits a *_cad key, strip that key from all rows of that batch) and a test that runs the adapter under Promise.all with a flapping getFxRate asserting identical key-sets across rows.
