# Phase 05.4: Unmapped Active Campaigns Indicator — Context

**Gathered:** 2026-05-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Operator-facing UX in the Campaigns view: a strip of small chips, one per (store, platform) bucket, each showing the count of campaigns that are currently **`status = ACTIVE` in the Ads Manager** AND have **no entry in the `campaign-product-map`** (cloud-synced operator map). Click a chip → table inline-filters to that bucket's unmapped active campaigns; click a row's `map` button → the existing `ProductPickerModal` opens, pre-scoped to that campaign's `storeId` so only that store's products are selectable. When every active campaign across all (store, platform) buckets is mapped, the strip collapses to a single green confirmation chip "✓ כל הקמפיינים הפעילים ממופים למוצר".

**What this phase delivers:**
1. A new persisted column in `{store}-campaigns` sheet — `Status` (col P) — sourced from Meta's `effective_status` and Google Ads' `status` field, refreshed by every `runLiveUpdate` (~15 min cadence).
2. Apps Script collector changes (MetaAds.gs + GoogleAds.gs + SheetBuilder.gs) to fetch and persist that column.
3. Dashboard `CampaignRow` type + parser update to read the new column.
4. A new aggregator that computes per-(store, platform) `unmappedActiveCount` from the latest available status row per campaign + the live `productMap`.
5. A new `<UnmappedCampaignsStrip>` component placed between `<Filters>` and `<CampaignsTable>` (or directly under `<KpiCards>`) that renders the chip strip, the green confirmation chip, the click-to-filter behaviour, and the per-row `map` button hook into `ProductPickerModal`.
6. A new in-table filter state ("show only unmapped active for X store + Y platform") wired into `CampaignsTable.tsx` and reset when the user clears the filter.

**What this phase does NOT deliver** — handled by other phases or out of scope:
- Backfilling historical status onto pre-existing rows (status starts populating from the deploy date forward — legacy rows get an empty string, which the aggregator treats as "unknown / not active").
- A "campaign needs review" workflow beyond the `ProductPickerModal` flow that already exists.
- Search analytics for which unmapped campaigns the operator visited most.
- Mobile or non-desktop layout for the new strip (dashboard is desktop-first per the architecture).

</domain>

<decisions>
## Implementation Decisions

### "Active" definition + source of truth (D-01..D-03)

- **D-01:** "Active" = the campaign's `effective_status` in Meta or `status: ENABLED` in Google Ads v20 — i.e. the literal Ads Manager toggle, NOT a proxy derived from recent spend. This excludes brand-new just-launched campaigns from being missed (the FIX-26 lastActiveDate proxy would silently skip them until spend lands ~24h later).
- **D-02:** Status MUST be persisted to the sheet at write-time, not derived live on the dashboard. Two reasons: (a) the dashboard is read-only against telemetry tabs (Architecture §"Reverse write path"), so the dashboard can't query Meta/Google itself; (b) writing once per Apps Script execution keeps the live trigger budget honest.
- **D-03:** New sheet column `Status` (col P) in `{store}-campaigns`:
  - Type: `'ACTIVE' | 'PAUSED' | 'ARCHIVED' | 'DELETED' | ''`
  - Value source — Meta: `getMetaBudgets` already fetches `effective_status` ([MetaAds.gs:213,235](MetaAds.gs#L213)); propagate that field through `updateCampaignDataForStoreDate_` into the row written by `writeCampaignRowsForDay`.
  - Value source — Google: extend `GoogleAds.gs` to query `campaign.status` from Google Ads v20 (`SELECT campaign.status FROM campaign WHERE ...`) and join into the existing `getGoogleAdsAdGroupInsights` output.
  - Cell format: `setNumberFormat('@')` (text) — matches the convention for non-numeric ID columns elsewhere in the file.
  - Idempotency: the standard "clear-and-write per date" pattern already covers this column when it's part of the row tuple.

### Granularity of the indicator strip (D-04)

- **D-04:** Per (`storeId`, `platform`) — up to 6 chips (3 stores × 2 platforms). Chips render ONLY when their count > 0. Sort order in the strip: stable by `(storeId asc, platform asc)` so the chip a user looks at yesterday is in the same slot today (no chip-shuffle on re-render).
  - Example present-state: `uzoshop·Meta: 2 · zolplus·Meta: 1 · usmile360·Google: 1`.
  - Each chip's data: `{ storeId, storeName, platform, count, campaignIds[] }` (the campaignIds payload feeds the click-to-filter without a refetch).

### Visual placement (D-05..D-06)

- **D-05:** The `<UnmappedCampaignsStrip>` lives in the Campaigns tab between `<Filters>` and `<CampaignsTable>` (or directly under `<KpiCards>` if KpiCards is the first child of the tab — verify in `Dashboard.tsx`/`CampaignsTable.tsx` during planning). It is a narrow horizontal row — NOT a full banner. Tone: subtle, info-amber for unmapped chips, soft-green for the clean-state chip.
- **D-06:** Two render modes:
  - **Dirty (at least one count > 0):** N chips visible (N ≤ 6), each clickable.
  - **Clean (all counts = 0):** single chip "✓ כל הקמפיינים הפעילים ממופים למוצר" — small, green, non-interactive, with a tooltip showing the total active count e.g. "8 קמפיינים פעילים, כולם ממופים".

### Drill-down + per-store product isolation (D-07..D-09)

- **D-07:** Click on a chip = the `CampaignsTable` enters a transient filter state: show only campaigns where `(storeId, platform, status='ACTIVE', no productMap entry)`. The filter is reflected as a clear pill above the table ("מסנן: לא ממופים — uzoshop·Meta", with an "X" to clear). Re-click the same chip clears the filter.
- **D-08:** Each filtered row gets a `מפה למוצר` button (small, primary tone). Click → opens the existing `<ProductPickerModal storeId={row.storeId} platform={row.platform} campaignId={row.campaignId} />`. After the operator picks one or more products and saves, the modal closes → `productMap` updates via `setMappedProducts` → the row disappears from the filtered view (because the unmapped predicate flips) → if it was the last unmapped active in that bucket, the chip disappears from the strip. If it was the last unmapped active across ALL buckets, the strip flips to the green ✓ confirmation chip. This is the "feels great" loop the user is investing in.
- **D-09:** **PER-STORE PRODUCT ISOLATION (LOAD-BEARING INVARIANT — the user explicitly called this out and it is a hard requirement, not a nice-to-have):** when the strip opens `<ProductPickerModal>` from a chip's row, the `storeId` prop MUST be the row's `storeId`, never `null` and never a different store. The picker's existing internal filter at [ProductPickerModal.tsx:122](dashboard-web/src/components/ProductPickerModal.tsx#L122) (`if (r.storeId !== storeId) continue;`) and [:139](dashboard-web/src/components/ProductPickerModal.tsx#L139) (`catalogRows.filter(c => c.storeId === storeId)`) then enforces that ONLY that store's products appear in the picker list. Cross-store contamination MUST be impossible by construction (no global "pick any store's product" path). Planner: add a regression test that opens the picker via the chip drill-down with a known wrong `storeId` and verifies products from other stores are absent from the picker's option list.

### Edge cases (D-10..D-13)

- **D-10:** Legacy rows (written before the deploy of this phase) have `status === ''`. The aggregator treats empty status as "unknown — exclude from active count". Conservative: no false-positive alerts on legacy data. The aggregator's docstring must call this out.
- **D-11:** A campaign with multiple ad-set rows (one per ad-set per day) has the same `(storeId, platform, campaignId)` repeated N times in the sheet. The aggregator deduplicates to ONE row per campaign, using the LATEST `date` in the filter range, and reads `status` from THAT row. Rationale: status is a campaign-level attribute, not an ad-set-level attribute — capturing it per ad-set is fine (Meta's effective_status is the same across ad-sets of a campaign), but the count must not double-count.
- **D-12:** A campaign that was ACTIVE earlier in the filter range but is PAUSED today: the aggregator reads the latest available status (today's row says PAUSED → not counted as active). This matches the operator's mental model — "what's running RIGHT NOW that needs my attention".
- **D-13:** No spend yet today for a just-launched campaign: because the parser at [campaigns.ts:140](dashboard-web/src/lib/campaigns.ts#L140) drops rows with `spend === 0 && impressions === 0 && conversions === 0`, Meta/Google may not yet have a row in the sheet. In that case the chip will under-count by one until the next live sync writes a row with some early impressions. This is acceptable: the operator gets the alert within ~15 minutes of any real activity, which is the typical lag in their workflow anyway. Document this in the strip's tooltip if it's not too noisy.

### Claude's Discretion

- Exact chip CSS — colour, border-radius, padding, hover state — gsd-ui-researcher will lock during `/gsd-ui-phase 05.4`. The design contract there will reference the existing chip patterns in `CampaignsTableRow.tsx` (Trust chip, CBO/ABO chip, FIX-26 "currently off" chip) so the new chip family stays visually consistent.
- Whether to expose the in-table filter as a URL param (`?unmappedFilter=uzoshop::Meta`) for bookmarkability: defer to planner — low-cost addition if existing `urlState.ts` infrastructure makes it cheap, otherwise skip.
- Exact placement detail (between `<Filters>` and `<KpiCards>` vs between `<KpiCards>` and `<CampaignsTable>`): planner can pick based on which gives the cleanest visual rhythm. The constraint is "above the table, in the Campaigns tab".

</decisions>

## Existing Code Insights

### Reusable Assets
- **`ProductPickerModal`** — already per-store-scoped; takes `storeId`, `platform`, `campaignId` and a list of `existingProductIds`. The unmapped-strip drill-down opens this with `existingProductIds: []` (new mapping).
- **`setMappedProducts`** (campaignProductMap.ts:122) — single-call update path. Triggers the standard cloud-sync chain (localStorage + custom event + pushCloudKey). The chip strip will subscribe to `roas-campaign-product-map-changed` to live-refresh its counts when the operator finishes mapping in the modal.
- **FIX-26 chip styling** (`CampaignsTableRow.tsx:238`) — colour, size, padding pattern to mirror.
- **`campaignsAggregator.ts`** — the latest-day-per-campaign pattern. The new aggregator can extend or sit alongside.
- **`Filters.tsx` + `urlState.ts`** — if the new transient filter goes to URL, integrate via the existing read/write helpers.

### Established Patterns
- **Per-day clear-and-write idempotency** (`SheetBuilder.gs` §writeCampaignRowsForDay) — the column-P addition must preserve this. Existing rows without status get empty string on read; new rows for the same date overwrite cleanly.
- **`setNumberFormat('@')` on non-numeric columns** (CONVENTIONS.md §Defensive Coding) — status is text, must format as text or Sheets will reinterpret 'PAUSED' inconsistently.
- **`useMemo` discipline** (CONVENTIONS.md §React Patterns) — the new aggregator MUST be memoized on `[campaignsResp, productMap]` — recomputing on every render of `CampaignsTable` would be expensive.
- **Cloud-sync subscribe pattern** — the strip listens for `roas-campaign-product-map-changed` to live-update when the picker modal saves.
- **`<bdi dir="ltr">` for RTL numeric** (CONVENTIONS.md §Hebrew RTL) — chip count uses `bdi(count)` from `format.ts`.

### Integration Points
- **`CampaignsTable.tsx`** — hosts the strip; hosts the new transient filter; passes `storeId/platform/campaignId` to the new "map" button.
- **`DailyUpdate.gs` §`updateCampaignDataForStoreDate_`** — the orchestration hook where Meta budgets (already fetched) + Google status (newly fetched) get merged into the row tuple before `writeCampaignRowsForDay`.
- **`Dashboard.tsx`** — already wires `/api/campaigns` via SWR; no new endpoint, the new column comes through the existing payload. No new STATE_KEYS, no new cloud-sync registrations.

<specifics>
## Specific Ideas

- **"Meta: 3 · Google: 1"** — the user's original phrasing for the strip; the final design lands at 6 buckets (per store, per platform) instead of 2 (per platform aggregated), so the example becomes "uzoshop·Meta: 2 · zolplus·Meta: 1 · usmile360·Google: 1".
- **"כל הקמפיינים במערכת ממופים למוצר"** — the operator's literal phrasing for the clean-state confirmation. Use this string verbatim (or near-verbatim "כל הקמפיינים הפעילים ממופים למוצר" — slightly more accurate because the indicator is scoped to active campaigns). gsd-ui-researcher will lock the final Hebrew copy in UI-SPEC.md.
- **The user is explicitly NOT looking for an "all-time mapped" check** — they care about "what's running NOW that I haven't tagged". This is why the active-status filter is load-bearing; an all-time-mapped strip would be noisy with dead historical campaigns.

</specifics>

<deferred>
## Deferred Ideas

These came up during discussion (or are obvious adjacent surfaces) but belong outside this phase's scope:

- **Backfill historical status onto pre-deploy rows** — would require a one-off Apps Script that walks every existing row and re-queries Meta/Google for status. Cost is in the API quota, not the code. Defer until/if an operator workflow needs it (today they don't — the indicator is forward-looking).
- **A separate "orphan products" indicator** — products with no campaign mapping. The mirror of this phase. Could be useful but is a separate question with a separate aggregator. Captured here so we don't forget.
- **Per-campaign last-mapped-by audit log** — who-mapped-what-when. The cloud-sync write path already overwrites without history. Out of scope.
- **A bulk-map action ("map all these uzoshop·Meta campaigns to product X")** — power-user feature. Today's flow is one-at-a-time via `ProductPickerModal`. Defer.
- **Status filter in the main `Filters.tsx`** (e.g. "show only ACTIVE campaigns" / "only PAUSED") — natural extension once the column exists, but not part of THIS phase's UI scope. Defer to a future polish phase.
- **Mobile/narrow layout for the new strip** — dashboard is desktop-first by architecture decision. Defer.
- **URL persistence of the transient unmapped-filter pill** — Claude's Discretion item; planner may include if it's cheap given existing `urlState.ts`, otherwise defer.

</deferred>
