```sql
--   - Never edit this file after `supabase db push` succeeds.

--   'ACTIVE' | 'PAUSED' | 'ARCHIVED' | 'DELETED' | '' at read time.

ALTER TABLE campaigns_daily
  ADD COLUMN IF NOT EXISTS status TEXT;

COMMENT ON COLUMN campaigns_daily.status IS
  'Campaign status as reported by the ad platform on the row''s date. '
  'Meta = effective_status (ACTIVE / PAUSED / ARCHIVED / DELETED / IN_PROCESS / WITH_ISSUES / etc.). '
  'Google = campaign.status (ENABLED / PAUSED / REMOVED / UNKNOWN). '
  'TikTok = secondary_status (e.g. CAMPAIGN_STATUS_DELIVERY_OK / CAMPAIGN_STATUS_DISABLE / CAMPAIGN_STATUS_DELETE). '
```

```
GET /open_api/v1.3/campaign/get/

```

The SDK confirms (`filtering_campaign_get.py`):

- `secondary_status` — leaf state, e.g. `CAMPAIGN_STATUS_DELIVERY_OK`, `CAMPAIGN_STATUS_DISABLE`, `CAMPAIGN_STATUS_DELETE`

The Ads-Manager-facing statuses (per `ads.tiktok.com/help/article/campaign-statuses-and-definitions`) are **Active / Paused / Pending / Deleted / Not delivering**, plus sub-statuses for the "not delivering" branch (Out of budget, Account suspended, etc.).

**Why a separate fetcher (not folded into `fetchTikTokAdInsights`):**
The reporting endpoint `/report/integrated/get/` does NOT return status — it returns spend-/impressions-aware metrics tied to a date. Campaign metadata lives on the campaign-management endpoint (`/campaign/get/`), called once per day with no date arg. Same pattern Meta uses (`/insights` vs `/act_/campaigns`).

Three edits:

1. **Add a new type** (alongside `TikTokAdvertiserInfo`):

   ```ts
   export type TikTokCampaignStatus = {
     campaignId: string;
     campaignName: string;
     /** Raw `secondary_status` from /campaign/get/ — e.g.
      *  CAMPAIGN_STATUS_DELIVERY_OK, CAMPAIGN_STATUS_DISABLE, CAMPAIGN_STATUS_DELETE.
      *  Downstream normalizer maps to ACTIVE/PAUSED/ARCHIVED/DELETED/''. */
     secondaryStatus: string;
     /** Raw `operation_status` — ENABLE | DISABLE | DELETE. The user-controlled
      *  on/off toggle (vs. the platform-controlled secondary_status). */
     operationStatus: string;
   };

   export type TikTokCampaignsResponse = {
     storeId: string;
     campaigns: TikTokCampaignStatus[];
   };
   ```

2. **Add `fetchTikTokCampaignStatuses(storeId)`** (mirror `fetchMetaBudgets`'s shape — one-shot per cron run, paginated):

   ```ts
   /**
    * Phase 05.4 — fetch every campaign's status from /campaign/get/.
    *
    * TikTok's reporting endpoint (/report/integrated/get/) returns no status
    * field — status lives on the campaign-management endpoint. We call it
    * once per cron-daily run, paginated, mirroring fetchMetaBudgets.
    *
    * SDK reference: github.com/tiktok/tiktok-business-api-sdk
    *                python_sdk/business_api_client/api/campaign_creation_api.py
    * Endpoint: GET /open_api/v1.3/campaign/get/
    * Filtering object: FilteringCampaignGet (primary_status / secondary_status).
    */
   export async function fetchTikTokCampaignStatuses(
     storeId: string,
   ): Promise<TikTokCampaignsResponse> {
     const { advertiserId, accessToken } = getTikTokCreds(storeId);
     type CampaignRow = {
       campaign_id?: string | number;
       campaign_name?: string;
       operation_status?: string;
       secondary_status?: string;
     };
     type Payload = {
       list?: CampaignRow[];
       page_info?: { total_page?: number; page?: number };
     };
     const out: TikTokCampaignStatus[] = [];
     let page = 1;
     while (page <= 50) {
       const data = await tiktokGet<Payload>('/campaign/get/', accessToken, {
         advertiser_id: advertiserId,
         fields: JSON.stringify([
           'campaign_id',
           'campaign_name',
           'operation_status',
           'secondary_status',
         ]),
         page: String(page),
         page_size: '200',
       });
       for (const r of data.list ?? []) {
         out.push({
           campaignId: String(r.campaign_id ?? ''),
           campaignName: String(r.campaign_name ?? ''),
           secondaryStatus: String(r.secondary_status ?? ''),
           operationStatus: String(r.operation_status ?? ''),
         });
       }
       const totalPages = Number(data.page_info?.total_page ?? 1);
       if (page >= totalPages) break;
       page++;
     }
     return { storeId, campaigns: out };
   }
   ```

   Pagination cap: 50 matches the Meta + Google pattern. Page size 200 is conservative (TikTok max is 1000).

3. **Status fetch is unconditional only for `STORES_WITH_TIKTOK`.** The cron writer will skip the call for non-TikTok stores — see §2.5.

**Normalization rule** (applied at parse boundary in postgresReaders — §2.5):
- `operation_status === 'DISABLE'` → `'PAUSED'`
- `operation_status === 'DELETE'` → `'DELETED'`
- `operation_status === 'ENABLE'` AND `secondary_status` starts with `CAMPAIGN_STATUS_DELIVERY_OK` (or has `DELIVERY_OK`/`OK` substring) → `'ACTIVE'`
- `operation_status === 'ENABLE'` AND `secondary_status` indicates pending/not-delivering → `'PAUSED'` (conservative — operator can investigate)
- empty/null → `''`

The normalization lives in `postgresReaders.ts` so the persisted DB value stays the **raw** TikTok string (for debugging), while the dashboard parses it consistently.

2. **Add a normalizer** (top of file or in a sibling helper):

   ```ts
   /**
    * Normalize Meta / Google / TikTok platform-specific status strings to the
    * unified CampaignRow.status value space. Centralized here so the dashboard
    * never sees raw enum names like CAMPAIGN_STATUS_DELIVERY_OK.
    *
    * Phase 05.4 — D-01 source-of-truth value set:
    *   ACTIVE   = currently serving / scheduled to serve
    *   PAUSED   = operator-paused, technically off but resumable
    *   ARCHIVED = retired (rare; Meta has it as ARCHIVED, Google has REMOVED)
    *   DELETED  = soft-deleted, will never re-activate
    *   ''       = unknown (legacy NULL rows; no read from API yet)
    */
   function normalizeStatus(
     platform: string,
     raw: unknown,
   ): 'ACTIVE' | 'PAUSED' | 'ARCHIVED' | 'DELETED' | '' {
     const s = String(raw ?? '').trim().toUpperCase();
     if (!s) return '';
     // Meta `effective_status`: ACTIVE / PAUSED / DELETED / ARCHIVED /
     //   PENDING_REVIEW / DISAPPROVED / PREAPPROVED / PENDING_BILLING_INFO /
     //   CAMPAIGN_PAUSED / ADSET_PAUSED / IN_PROCESS / WITH_ISSUES
     // Google `campaign.status`: ENABLED / PAUSED / REMOVED / UNKNOWN
     // TikTok stored as `<operation_status>|<secondary_status>`:
     //   ENABLE|CAMPAIGN_STATUS_DELIVERY_OK / DISABLE|... / DELETE|...
     if (platform.toLowerCase() === 'google') {
       if (s === 'ENABLED') return 'ACTIVE';
       if (s === 'PAUSED') return 'PAUSED';
       if (s === 'REMOVED') return 'DELETED';
       return '';
     }
     if (platform.toLowerCase() === 'tiktok') {
       const [op, sec = ''] = s.split('|');
       if (op === 'DELETE') return 'DELETED';
       if (op === 'DISABLE') return 'PAUSED';
       if (op === 'ENABLE') {
         // ENABLE + delivering = ACTIVE; ENABLE + pending/issue = PAUSED
         if (sec.includes('DELIVERY_OK') || sec.includes('CAMPAIGN_STATUS_DELIVERY_OK')) {
           return 'ACTIVE';
         }
         return 'PAUSED';
       }
       return '';
     }
     // Meta + default fallback
     if (s === 'ACTIVE') return 'ACTIVE';
     if (s.includes('PAUSED')) return 'PAUSED'; // CAMPAIGN_PAUSED / ADSET_PAUSED
     if (s === 'ARCHIVED') return 'ARCHIVED';
     if (s === 'DELETED') return 'DELETED';
     // PENDING_REVIEW / DISAPPROVED / IN_PROCESS / WITH_ISSUES — treat as
     // "not currently active". Conservative: don't accidentally count a
     // disapproved or under-review campaign as active.
     return 'PAUSED';
   }
   ```

## 3. Aggregator — `unmappedActiveByBucket`

**File:** `dashboard-web/src/lib/campaignsAggregator.ts` (extend; do NOT create a new file — pattern parity with the existing `aggregate` function).

**Function signature:**

```ts
/**
 * Phase 05.4 — per-(store, platform) buckets of currently-active campaigns
 * that have no entry in `productMap`. Drives the chip strip in CampaignsTable.
 *
 * Latest-row-per-campaign rule (CONTEXT.md D-11): a campaign with N adset/day
 * rows is deduplicated. The status read is from the row with the LATEST date
 * in the input set (typically today; D-12 — "what's running RIGHT NOW").
 *
 * Empty/unknown status (CONTEXT.md D-10): rows with `status === ''` are
 * treated as not active. Conservative — no false alerts on legacy rows.
 *
 * Memoization key: pass `[campaignsResp.rows, productMap, productMap.__rev]`
 * to useMemo from the calling component. Same shape as the existing
 * `aggregated` memo at CampaignsTable.tsx:334.
 */
export type UnmappedBucket = {
  /** Unique key for stable React render: `${storeId}::${platform}`. */
  key: string;
  storeId: string;
  storeName: string;
  /** 'Meta' | 'Google' | 'TikTok' — TitleCased at the postgresReaders
   *  boundary so it matches CampaignsTable's platform filter values. */
  platform: string;
  /** Number of unmapped ACTIVE campaigns in this bucket. */
  count: number;
  /** Campaign IDs in this bucket — feeds the click-to-filter without a
   *  refetch (CONTEXT.md D-04). Empty when count===0 (chip not rendered). */
  campaignIds: string[];
  /** Total active campaigns in this bucket (mapped + unmapped) — used for
   *  the clean-state tooltip "8 campaigns active, all mapped". */
  totalActive: number;
};

export function unmappedActiveByBucket(
  rows: CampaignRow[],
  productMap: ProductMap,
): UnmappedBucket[] {
  // Step 1: dedupe to one row per campaign, keeping the LATEST date.
  type CampKey = string; // `${storeId}::${platform}::${campaignId}`
  type Latest = {
    storeId: string;
    storeName: string;
    platform: string;
    campaignId: string;
    date: string;
    status: CampaignRow['status'];
  };
  const latestByCampaign = new Map<CampKey, Latest>();
  for (const r of rows) {
    const key = `${r.storeId}::${r.platform}::${r.campaignId}`;
    const prev = latestByCampaign.get(key);
    if (!prev || r.date > prev.date) {
      latestByCampaign.set(key, {
        storeId: r.storeId,
        storeName: r.storeName,
        platform: r.platform,
        campaignId: r.campaignId,
        date: r.date,
        status: r.status,
      });
    }
  }
  // Step 2: filter to ACTIVE-only + check productMap, bucket by (storeId, platform).
  type BucketKey = string;
  const buckets = new Map<BucketKey, UnmappedBucket>();
  for (const c of latestByCampaign.values()) {
    if (c.status !== 'ACTIVE') continue; // D-10 + D-12
    const bKey = `${c.storeId}::${c.platform}`;
    if (!buckets.has(bKey)) {
      buckets.set(bKey, {
        key: bKey,
        storeId: c.storeId,
        storeName: c.storeName,
        platform: c.platform,
        count: 0,
        campaignIds: [],
        totalActive: 0,
      });
    }
    const b = buckets.get(bKey)!;
    b.totalActive++;
    const mapKey = campaignKey(c.storeId, c.platform, c.campaignId);
    const mapped = (productMap[mapKey] ?? []).length > 0;
    if (!mapped) {
      b.count++;
      b.campaignIds.push(c.campaignId);
    }
  }
  // Step 3: stable sort — storeId asc, then platform asc (D-04).
  return Array.from(buckets.values()).sort((a, b) => {
    if (a.storeId !== b.storeId) return a.storeId.localeCompare(b.storeId);
    return a.platform.localeCompare(b.platform);
  });
}
```

Imports required in the same file:
```ts
import { campaignKey, type ProductMap } from './campaignProductMap';
```

**Why an array (not a map) on return:** the strip renders in stable order and React needs an iterable. The `BucketKey` is the React `key` prop.

## 6. Risks + pitfalls (specific to current code)

| Risk | Impact | Mitigation |
|---|---|---|
| **Historical Postgres rows have `status = NULL`** (~6 weeks since 2026-05-01) | Aggregator treats NULL/'' as not-active → underreports until next cron-daily tick re-writes each campaign. | D-10 acceptance; document in tooltip ("might miss campaigns until next daily sync ~24h"); user can manually trigger `cron-daily-*` via Inngest "Run now" if needed. |
| **The cron-daily writer is not idempotent for the new column on stores without TikTok** | The TikTok status fetch only runs for `STORES_WITH_TIKTOK` (uzoshop) — but `zolplus` + `usmile360` TikTok rows shouldn't exist anyway (no platform='tiktok' rows). Safe. | No action — short-circuit already in place. |
| **Meta `effective_status` for ad-set-level rows** | A campaign with one ACTIVE ad-set and one PAUSED ad-set gets written N times with the same campaign-level effective_status. Dedup at aggregator (latest date) handles it; if two ad-sets for the same date have different statuses (shouldn't happen at campaign-level, but possible in theory), behavior is undefined which one wins. | Test with a snapshot; document that campaign-level status is the single source of truth (Meta's `effective_status` is campaign-scoped — not ad-set-scoped). |
| **Google Ads `campaign.status` UNKNOWN** | Rare but possible response value. Normalizer maps to '' → not counted. | Documented in normalizer comment. |
| **TikTok `secondary_status` enum drift** | TikTok adds new sub-states regularly (e.g. new "not delivering" reasons). The normalizer's "ENABLE + DELIVERY_OK = ACTIVE" rule should hold but new statuses default to PAUSED (conservative). | The normalizer comment + open question 1 in §8. Add a console.warn when a tiktok status doesn't match a known prefix, so we catch drift in Inngest logs. |
| **Aggregator perf at scale** | The aggregator is O(N) over `data.rows`. With ~30 days × 3 stores × 3 platforms × ~10 ad-sets/campaign × ~50 campaigns = ~45K rows, the loop is fine (~5ms). | No issue at current scale. |
| **`productMap` race with chip rendering** | If picker save fires `roas-campaign-product-map-changed` while React is mid-render, the strip may briefly show the just-mapped campaign in the count. Cheap fix: CampaignsTable already re-renders on the event. | No new code; rely on existing listener. |

## 8. Open questions for the user (≤3)

1. **Should Google campaigns appear in the strip even though we can't map them in this view?**
   The chip is informational ("you have N active Google campaigns that aren't mapped"), but the per-row "מפה למוצר" button is disabled for Google. Three options:
   (a) Show Google chips, disabled-style row button (current §4 recommendation). Operator sees the count, knows to handle Google via a different surface.
   (b) Hide Google entirely from the strip. Cleaner UX but the operator might never realize Google campaigns exist that aren't mapped (they aren't mappable anyway).
   (c) Show Google chip with a `(N/A — PMax)` suffix and no underline (non-clickable). Most explicit.
   **Recommendation: (a) per §4.4.** If the operator confirms (b) is preferred, the implementer can simply skip Google buckets in `unmappedActiveByBucket`.

2. **Should `cronLive.ts` also write status (10-min cadence) or only `cronDaily.ts` (24h cadence)?**
   Live cron currently doesn't touch `campaigns_daily` at all (only `data_daily` + `products_daily` + `orders_attribution`). Adding campaign-status refresh to cron-live means a new HTTP call per cron-live tick per platform (~3-5s wall-clock). Trade-off: faster freshness (~10 min from operator-flipping-the-toggle) vs Inngest free-tier budget impact (+8.6K execs/month = ~17% of free tier). The operator's words ("the indicator should fire as soon as I turn ON a campaign") argue FOR cron-live. The 24h-acceptable note in CONTEXT.md D-13 argues against.
   **Recommendation: ship daily-cadence first (this plan); revisit after one week of production data.** If operators report painful staleness, add it to cron-live in a follow-up phase (1-day implementation).

3. **Should we wait for one full cron-daily cycle before declaring "legacy NULL rows safe to ignore"?**
   The aggregator already treats NULL/'' as not-active (D-10). But on first deploy, the strip will UNDERREPORT for ~24h because every campaign reads back with `status=NULL` until the cron-daily writes the new value. Two options:
   (a) Ship as-is — strip is empty until the next cron tick. Subtle visual no-op, but technically an under-report.
   (b) After the migration ships, manually trigger `cron-daily-*` via Inngest Cloud UI for all 3 stores → status fills in within minutes → ship the UI code right after.
   **Recommendation: (b).** Adds a 5-minute manual step at deploy time, eliminates the 24h under-report window.
