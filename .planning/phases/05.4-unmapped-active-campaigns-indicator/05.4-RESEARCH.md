## 1. Phase Summary

Add a strip of per-(`storeId`, `platform`) chips above the campaigns table that count campaigns whose `status = ACTIVE` in Ads Manager AND have no entry in the cloud-synced `campaign-product-map`. Clicking a chip filters the table to that bucket's unmapped-active rows; each filtered row gets a `מפה למוצר` button that opens the existing per-store-scoped `ProductPickerModal`. When every active campaign across all (store, platform) buckets is mapped, the strip collapses to a single green confirmation chip "✓ כל הקמפיינים הפעילים ממופים למוצר". The originally locked Apps-Script implementation path (CONTEXT.md D-02/D-03) is dead — Phase 05.7.0 made `READ_FROM=postgres` permanent, so status MUST now be persisted via the TS fetchers into `campaigns_daily` (additive `status` column).

**Primary recommendation:** Single additive migration adding `campaigns_daily.status TEXT NULL`; re-use the `effective_status` already fetched by `fetchMetaBudgets` (currently dropped); extend Google's existing GAQL `SELECT` (no new round-trip); for TikTok, add ONE new dedicated `/campaign/get/` call per cron-daily run (reporting endpoints cannot return status). Aggregator + chip-strip are pure UI work over existing infrastructure — no new SWR endpoint, no new cloud-sync key.

## 3. TikTok Status Fetch — Definitive Answer

**This is the single load-bearing question for this phase. The implementer cannot guess.**

### 3.1 What the existing TikTok fetcher does today

`dashboard-web/src/lib/fetchers/tiktok.ts:308-426` (`fetchTikTokAdInsights`) calls `POST /report/integrated/get/` with `data_level=AUCTION_AD` to get per-ad metrics. **The `/report/integrated/get/` endpoint cannot return campaign status — it returns metrics and dimensions (spend, impressions, conversion, campaign_id, ad_id, etc.), not state.** `FilteringReportIntegratedGet` is a generic `{field_name, filter_type, filter_value}` filter — there is no status field exposed as a dimension or metric. [VERIFIED via SDK source: `python_sdk/business_api_client/models/filtering_report_integrated_get.py` lines 25-32]

### 3.2 Where status actually lives

TikTok's canonical endpoint for campaign metadata (including status) is:

```
GET https://business-api.tiktok.com/open_api/v1.3/campaign/get/
```

Required params:
- `advertiser_id` (numeric string, no quotes-in-string issue like `/advertiser/info/` had — this one is just a regular query param)

Optional params relevant to us:
- `filtering`: JSON-encoded object accepting `primary_status` and `secondary_status` filter parameters [VERIFIED: `filtering_campaign_get.py:25-42`]
- `fields`: JSON-encoded array — request `["campaign_id","secondary_status","primary_status","operation_status"]`
- `page` / `page_size` (default 10, max 1000)

### 3.3 What status field to read

TikTok exposes **three** status-like fields, with subtly different semantics:

| Field | Source endpoint | Meaning | What it returns |
|-------|----------------|---------|-----------------|
| `operation_status` | `/campaign/get/` response field; also the body field on `/campaign/status/update/` | **The user-set toggle in Ads Manager** — the literal "play/pause" state the operator flips. Values: `ENABLE` / `DISABLE` (and `DELETE` for deleted campaigns). [VERIFIED via Java SDK doc + WebSearch corroboration: `js_sdk/docs/CampaignStatusUpdateBody.md` references the `/campaign/status/update/` endpoint accepting `operation_status`; v1.2 example in kitchn.io blog shows `"opt_status":"DISABLE"` returned (v1.2 used `opt_status`; v1.3 renamed to `operation_status` per the v1.3 portal docs landing page id=1739665422787585).] | Plain string: `ENABLE` \| `DISABLE` \| `DELETE` |
| `secondary_status` | `/campaign/get/` response field | **The fine-grained delivery state**, including reasons for non-delivery (out of budget, account suspended, etc.). | Tagged enum: `CAMPAIGN_STATUS_DELIVERY_OK`, `CAMPAIGN_STATUS_CAMPAIGN_PAUSE`, `CAMPAIGN_STATUS_BUDGET_EXCEED`, `CAMPAIGN_STATUS_DELETE`, etc. [VERIFIED structure from v1.2 example response in [kitchn.io](https://www.kitchn.io/blog/tiktok-ads-api-introduction): `"status": "CAMPAIGN_STATUS_DISABLE"` — the `status` field was renamed to `secondary_status` in v1.3.] |
| `primary_status` | `/campaign/get/` response field (also a filter param) | **Coarse-grained rollup** — a higher-level "is this delivering" summary. Less granular than `secondary_status`. | Tagged enum (e.g. `STATUS_ALL`, `STATUS_DELIVERY_OK`, `STATUS_NOT_DELIVERING`). |

**Recommendation: use `operation_status === 'ENABLE'` as the "active toggle" signal.** This is the closest TikTok equivalent of Meta's `effective_status === 'ACTIVE'` semantic ("did the operator toggle it on") and Google's `campaign.status === 'ENABLED'`. The fine-grained `secondary_status` is a "is it actually delivering" signal — useful but a different question (and it would falsely exclude campaigns the operator just turned on but TikTok hasn't started delivering yet, which is exactly the case CONTEXT.md D-01 calls out as critical to capture).

**Rationale for not using `secondary_status`:** A just-launched campaign that the operator turned ON 30 seconds ago will have `operation_status='ENABLE'` but `secondary_status` may still report `CAMPAIGN_STATUS_NOT_START` or similar transitional state. The whole point of D-01 ("capture the Ads Manager toggle, not a delivery proxy") is to surface those campaigns ASAP. `operation_status` is the right pick.

### 3.4 Normalization to the unified `'ACTIVE' | 'PAUSED' | ...` shape

Per-platform → unified status string mapping:

| Platform | API field read | Raw value | Unified `status` written to `campaigns_daily.status` |
|----------|---------------|-----------|------------------------------------------------------|
| Meta | `effective_status` (from `fetchMetaBudgets` campaigns endpoint) | `'ACTIVE' \| 'PAUSED' \| 'ARCHIVED' \| 'DELETED' \| 'CAMPAIGN_PAUSED' \| 'IN_PROCESS' \| 'WITH_ISSUES' \| ...` | `'ACTIVE'` iff raw === `'ACTIVE'`; otherwise pass through raw value as-is (TEXT column tolerates any string) |
| Google | `campaign.status` (extend existing GAQL `SELECT` in `fetchGoogleAdsAdGroupInsights`) | `'ENABLED' \| 'PAUSED' \| 'REMOVED' \| 'UNKNOWN'` | `'ACTIVE'` iff raw === `'ENABLED'`; otherwise pass through |
| TikTok | `operation_status` (from new `/campaign/get/` call) | `'ENABLE' \| 'DISABLE' \| 'DELETE'` | `'ACTIVE'` iff raw === `'ENABLE'`; map `DISABLE → 'PAUSED'`, `DELETE → 'DELETED'` |

**Aggregator's "is active" predicate:** `row.status === 'ACTIVE'`. Single string equality — no per-platform branching in the aggregator. The normalization happens once at write-time in `cronDaily.ts`.

### 3.5 New round-trip cost for TikTok

- `fetchTikTokAdInsights` (existing): paginated `/report/integrated/get/` calls, runs per-day.
- `fetchTikTokCampaignStatuses` (NEW): single paginated `/campaign/get/` call, **per cron-daily run, not per-day**. Campaign status is not date-scoped — the campaign's "current operation_status" is the same regardless of which date's metrics we're writing. We fetch ONCE per cron run and apply to every per-day batch.

This means the cron-daily exec budget stays bounded: `1` new `step.run` (or fold into the existing `fetch-tiktok` step). No per-day, no per-ad multiplication.

## 4. Schema Decision

### 4.1 Column vs. New Table

**Recommendation: add `campaigns_daily.status TEXT NULL`. Do NOT create a new table.**

Rationale:
1. **Status is a campaign-level attribute persisted alongside daily metrics.** Every existing row already carries `campaign_id` + per-row data; adding one TEXT column is the smallest possible delta.
2. **A separate `campaign_status_current` table** (alternative considered) would require: (a) a new fetcher write path, (b) a new postgres reader, (c) a new JOIN in `fetchCampaignsFromPostgres`, (d) handling the "latest status wins" logic via either ORDER BY date DESC LIMIT 1 in SQL or a CTE — vs. inlining the same logic in the existing aggregator (which already does latest-date-per-campaign for `lastActiveDate`). The JOIN path adds complexity without payoff because (b) TikTok adds a NEW round-trip anyway, and (a) status changes daily on most campaigns so per-day rows aren't materially more expensive than a single "current" row.
3. **Pitfall avoidance:** A `campaign_status_current` table would need its own staleness story (when does a deleted-from-Ads-Manager campaign get pruned?). The per-day column inherits the existing `campaigns_daily` retention policy — no new lifecycle question.
4. **Migration discipline (per `supabase/MIGRATION-DISCIPLINE.md:18`):** adding a TEXT NULL column is purely additive — no `-- DESTRUCTIVE` marker required, no downstream code breaks. [VERIFIED]

Tradeoff acknowledged: per-day duplication means `~N rows × store_count × platform_count` carry the same status string. Storage cost is negligible (TEXT column with ~7-byte values × few-thousand-rows/day < 100 KB/day). The query cost stays bounded because the existing index `idx_campaigns_daily_store_date` already covers the access pattern.

### 4.2 Column shape

| Property | Value | Rationale |
|----------|-------|-----------|
| Column name | `status` | Direct, matches the platforms' naming. |
| Type | `TEXT` | Variable-length, accommodates any platform's raw enum or our normalized form. Aligns with `campaigns_daily.platform`, `campaigns_daily.budget_type` already being TEXT. |
| Nullability | `NULL` allowed | Required: legacy rows (6+ weeks pre-deploy) and Google-platform rows for non-uzoshop stores both naturally have no status to write. |
| Default | None (no DEFAULT clause) | We want NULL to mean "we didn't fetch this" — adding `DEFAULT ''` would lose the distinction between "fetched and got empty" (which never happens given our normalization) and "not fetched". |
| Check constraint | None | Defensive; lets us write any platform's raw value if we choose, without coupling the schema to our app-layer normalization. |
| Index | None | The aggregator filters in app-layer JS, not SQL — adding an index would not be used. |

### 4.3 Draft migration SQL

```sql
-- supabase/migrations/{YYYYMMDDHHMMSS}_add_campaigns_daily_status.sql
-- Phase 05.4 — add status column to campaigns_daily for the Unmapped Active
-- Campaigns Indicator. Additive — no DESTRUCTIVE marker required per
-- supabase/MIGRATION-DISCIPLINE.md.
--
-- D-01: Status is the operator-set toggle in Ads Manager (NOT a spend proxy).
-- D-10: Legacy rows pre-deploy have status IS NULL — aggregator must treat
--       NULL/empty as "unknown, exclude from active count".

ALTER TABLE campaigns_daily ADD COLUMN status TEXT;

COMMENT ON COLUMN campaigns_daily.status IS
  'Ads Manager status, normalized: ACTIVE iff Meta effective_status=ACTIVE OR '
  'Google campaign.status=ENABLED OR TikTok operation_status=ENABLE. NULL for '
  'legacy pre-2026-05-22 rows and for Google rows from stores without Google '
  'Ads. Phase 05.4. See dashboard-web/src/inngest/functions/cronDaily.ts for '
  'the write path.';
```

The filename follows the existing pattern: `YYYYMMDDHHMMSS_add_campaigns_daily_status.sql`. The next free timestamp at write time is `20260522{HHMMSS}` based on the latest existing migration `20260522102151_add_tiktok_platform_check.sql`.

### 5.3 TikTok — NEW `fetchTikTokCampaignStatuses` — `dashboard-web/src/lib/fetchers/tiktok.ts`

`fetchTikTokAdInsights` (already in tiktok.ts) cannot return campaign status — `/report/integrated/get/` is metrics-only. A new dedicated fetcher must call `/campaign/get/`.

**New function signature:**
```ts
/**
 * Returns a Map of campaign_id → operation_status for the advertiser.
 * Calls TikTok's /campaign/get/ endpoint with pagination. operation_status
 * is the user-set "play/pause toggle" — what the operator sees in Ads
 * Manager. We pick this (vs. secondary_status) because a just-turned-ON
 * campaign briefly has operation_status='ENABLE' but secondary_status
 * still in a transitional state — and capturing just-launched campaigns
 * is exactly the operator's stated need (CONTEXT.md D-01).
 *
 * Reference: TikTok Marketing API v1.3 /campaign/get/
 * SDK: tiktok-business-api-sdk/python_sdk/business_api_client/models/
 *      filtering_campaign_get.py (verified secondary_status, primary_status
 *      filter params exist).
 *
 * Returns { campaignId → 'ACTIVE' | 'PAUSED' | 'DELETED' | <raw value> }.
 */
export async function fetchTikTokCampaignStatuses(
  storeId: string,
): Promise<Map<string, string>>;
```

**Implementation outline:**
- URL: `GET ${TIKTOK_API_BASE}/campaign/get/`
- Params: `advertiser_id` (plain string, NOT JSON-array — `/campaign/get/` accepts a single advertiser, not a list like `/advertiser/info/` does. This is a different quirk from the one fixed in Phase 05.7.8 — verify against TikTok's docs in plan execution.)
- `fields`: `JSON.stringify(['campaign_id','operation_status'])`
- `page`/`page_size`: standard pagination (max 1000, cap 50 pages like the existing fetcher).
- Filter: omit — we want ALL campaigns regardless of their current status, so the aggregator can see PAUSED ones too (they just don't get counted as active).
- Normalize: `ENABLE → 'ACTIVE'`, `DISABLE → 'PAUSED'`, `DELETE → 'DELETED'`, anything else passes through.
- Returns: `Map<campaignId, normalizedStatus>`.

**Cost: 1 new HTTP call per cron-daily run (paginated, but probably 1 page for any account with <1000 campaigns).** Importantly: NOT per-day, NOT per-ad — once per cron-daily run, applied to every day's UPSERT batch. The exec budget stays at the same number of step.run calls; this just adds to the work inside the existing `fetch-tiktok` step.

## 9. Pitfalls (Numbered)

1. **Legacy `status === null` rows (6+ weeks of pre-deploy data).** Every `campaigns_daily` row written before the new migration has no `status` column to read; after the migration the column exists but old rows have `status IS NULL`. The aggregator MUST treat `null` and `''` identically as "unknown — exclude from active count" (conservative). Failure mode: showing inflated unmapped-active counts on historical rows that are no longer actually active. Mitigation: pure predicate `isUnmappedActive(row, productMap) := row.status === 'ACTIVE' && !productMap[campaignKey(...)]`.

2. **TikTok pagination edge case — `advertiser_id` quoting.** The Phase 05.7.8 bug in `fetchTikTokAdvertiserInfo` (`tiktok.ts:221-228`) was that `/advertiser/info/` required `advertiser_ids` to be a JSON-array-of-STRINGS. `/campaign/get/` takes a SINGLE advertiser_id as a plain query string param — a different shape. The new `fetchTikTokCampaignStatuses` must NOT replicate the JSON-array bug-fix pattern; it should pass `advertiser_id: advertiserId` as a plain string. Confirm during plan execution by trial: a 40002 response with "advertiser_id" in the message indicates wrong shape.

3. **`productMap` is localStorage + cloud-pull-in, not a single read.** The strip subscribes to `roas-campaign-product-map-changed` to refresh after the picker saves. BUT it must also re-read on cloud-pull-in events. Verify the cloud pull-in chain at `cloudSync.ts:271` — does the polling read also dispatch the change event? (Spot check during implementation.) If not, the strip would briefly show stale counts after a teammate's edit propagates from cloud. The `migrateProductMapKeys` effect at `CampaignsTable.tsx:269-273` runs whenever SWR `data` refreshes, so as long as the strip lives inside `CampaignsTable` (which re-runs the effect), the productMap is always current.

4. **Per-store invariant in `ProductPickerModal`** — verified at `ProductPickerModal.tsx:122` and `:139`. CONTEXT.md's claim about exact line numbers stands. The user explicitly called this out in D-09 — DON'T let the strip pass `storeId={null}` or any cross-store fallback. The chip's bucket carries the storeId; thread it through to the picker.

5. **Google rows in strip are shown but per-row map button must be disabled.** `CampaignsTableRow.tsx:319` already provides the tooltip text ("Google PMax לא תומך במיפוי לפי מוצר — הפיד מנהל את ההצגה"). Reuse verbatim. **Critical UX subtlety:** the chip count for a Google bucket is still useful (operator can use it as a signal to investigate manually in the Ads Manager UI), so DON'T hide Google chips from the strip — just disable the per-row mapping button.

6. **`fetchMetaBudgets`'s soft-fail pattern.** When the per-store Meta currency fetch or per-page fetch fails, `fetchMetaBudgets` logs a `console.warn` and proceeds with a partial map (see `meta.ts:687-694`, `meta.ts:725-732`). A campaign present in `meta.adsetRows` but absent from `meta.budgets.campaigns` (e.g. created after the budgets fetch started or behind the partial-map cliff) would get `effectiveStatus: undefined` → status written as `null` → aggregator correctly excludes it. **This is the desired behavior** — but it means the operator's strip will silently under-count during a partial-API-failure cron run. Document this in the strip's tooltip.

7. **The empty-row filter at `postgresReaders.ts:581` drops zero-activity rows.** A freshly-flipped-ACTIVE campaign that has not received any impressions in its first 24h has `spend=0, impressions=0, conversions=0` and is dropped during the read. **The strip will under-count this campaign** until any impression lands. CONTEXT.md D-13 calls this out for the Sheets reader; it applies to the Postgres reader equally. Mitigation: **acceptable lag** per CONTEXT.md decision; document in the strip tooltip if it's not too noisy ("הסטטוס מתעדכן כל ~15 דקות").

8. **TikTok `/campaign/get/` rate limit.** `business-api.tiktok.com` per-app rate limits exist. The new fetcher adds ONE call per cron-daily run per store. With 3 stores and once-a-day cadence the QPS is negligible — but if a backfill ever batches multiple days against the same `/campaign/get/` endpoint, it will hit the same data each time (status is not date-scoped). Add an in-memory cache like `tokenCache` (in `googleAds.ts:91`) keyed by `storeId` with a short TTL (e.g. 60s), so a backfill that processes 7 days hits TikTok once not 7 times.

9. **CronLive does NOT update `campaigns_daily.status`.** Only cron-daily writes campaigns_daily. The operator's mental model is "I just toggled this OFF and the strip should clear within a few minutes." With cron-daily at 00:05 IL (~24h cadence), the worst-case lag is **~24h**. If the operator wants near-real-time, that's a separate phase (extend cron-live to refresh statuses). For 05.4, accept the lag and surface it in the tooltip.

10. **Aggregator memoization — `productMap` reference identity.** `setProductMap(readProductMap())` (`CampaignsTable.tsx:274`) returns a NEW object on every change-event, so `useMemo([data, productMap])` correctly invalidates. **But** if the strip re-derives its own `productMap` from `readProductMap()` independently of the parent's state, two `useMemo`s in two places will fight each other. The strip should accept `productMap` as a prop from the parent, not re-read it.

11. **Status normalization at fetch-time vs. UI-time.** If we normalize `'ENABLED' → 'ACTIVE'` at write-time in `cronDaily.ts`, every reader sees the unified shape. If we instead store raw platform values (`'ENABLED'`, `'ACTIVE'`, `'ENABLE'`) and normalize at read-time, the aggregator gets uglier. **Recommendation: normalize at write-time** — single source of truth, smaller aggregator, easier to query in adhoc SQL. (Note: this means a future migration to a different normalization scheme would require a backfill — acceptable cost.)

12. **`STORE_NAME_BY_ID` in postgresReaders has a stale name.** `postgresReaders.ts:541-545` hardcodes `uzoshop: 'uzoshop'` (lowercase). The stores seed in the DB carries the actual display name. This is unrelated to 05.4 but worth flagging if the strip's "storeName" display has any inconsistency.
