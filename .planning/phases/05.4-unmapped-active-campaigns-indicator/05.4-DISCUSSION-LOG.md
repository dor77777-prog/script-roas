## Area 1 — "Active" definition

| Option | Description | Selected |
|--------|-------------|----------|
| Recent spend (7d window) | Has spend > 0 in the last 7 days regardless of date filter. Stable, doesn't fluctuate when the user changes filter. Misses campaigns launched today before any spend lands. | |
| Filter-range spend | Has spend > 0 within the user's selected date range. Cleanest filter contract but the chip number jumps as the filter changes. | |
| Hybrid recent + filter-range | Two separate sub-counters. Heavier UX. | |
| **Real Meta/Google status (operator clarification)** | Literal `effective_status = ACTIVE` from Meta + `status = ENABLED` from Google. Source of truth. Captures just-launched campaigns. | ✓ |

**User's choice:** "קמפיין פעיל פשוט קמפין שנמצא בסטטוס פעיל/active בפייסבוק במנהל מודעות, ולא ממופה זה שפשוט אין לו מיפוי למוצר עדיין." → forced a follow-up trade-off between (A) persist status via API, (B) reuse FIX-26 lastActiveDate proxy, (C) hybrid.

### Sub-question — Source of truth for "Active"

| Option | Description | Selected |
|--------|-------------|----------|
| **(A) Persist `effective_status` from Meta/Google APIs into a new column P in `{store}-campaigns`** | Source of truth. Captures just-launched campaigns. Cost: Apps Script collector changes + sheet schema + dashboard parser. | ✓ |
| (B) Reuse FIX-26 `lastActiveDate` proxy ("no spend in last 2 days = off") | Zero new collector code. Misses just-launched campaigns with no spend yet. | |
| (C) Hybrid: persist real status going forward, fall back to lastActiveDate for legacy rows | More code, same end-state as (A) after one sync cycle. Not needed because the indicator is forward-looking. | |

**User's choice:** (A) — match the Ads Manager toggle exactly, not a derived proxy.

**Notes:** the user wants the indicator to fire as soon as they turn ON a campaign in the Ads Manager, even before any spend lands — that's the exact moment when mapping is most actionable. The FIX-26 proxy would skip that moment.

## Area 2 — Granularity of the indicator strip

| Option | Description | Selected |
|--------|-------------|----------|
| Per platform aggregated across stores (2 slots: Meta total · Google total) | Matches the user's original phrasing "Meta: 3 · Google: 1". | |
| **Per (store, platform), max 6 chips, render only when count > 0** | More granular. Matches a multi-store mental model (each store has its own ad accounts). Drill-down also more useful. | ✓ |
| Per store aggregated across platforms (3 slots: uzoshop · zolplus · usmile360) | Useful if the operator works by store; less useful for platform-specific debugging. | |
| Single global counter | Minimalist. Forces a drilldown to get any platform context. | |

**User's choice:** per (store, platform), up to 6 chips.

**Notes:** the user's original example "Meta: 3 · Google: 1" was per-platform-aggregated, but on reflection they preferred per-(store, platform) so they immediately know which ad account needs attention without a click.

## Area 3 — Visual placement

| Option | Description | Selected |
|--------|-------------|----------|
| **Strip above the table — between `<Filters>` and the table top (or under `<KpiCards>`)** | High visibility without dominating. Subtle until count > 0. Easy retrofit into `CampaignsTable.tsx`. | ✓ |
| Inline in the table title bar | Discreet, but easily missed during scroll. | |
| Always-visible banner at the top of the Campaigns tab | More prominent. Risk of attention-fatigue. | |
| Composite — strip in Campaigns tab + a small badge in the header `<SyncIndicator>`-style chip | Cross-tab visibility. Higher implementation cost (cross-tab fetch + map subscription in `Dashboard.tsx`). | |

**User's choice:** strip above the table.

## Area 4 — Click behaviour + drill-down

| Option | Description | Selected |
|--------|-------------|----------|
| (A) Drawer with list of unmapped campaigns + "map" button → opens ProductPickerModal | Cleanest separate surface. 2 clicks to map. | |
| (B) Click chip = in-place filter the existing table to unmapped active for that (store, platform) | Uses existing table UX. Easy to scan many. | |
| (C) Popover / dropdown with names + click row to scroll-to-row + open existing CampaignDrawer | Natural to scroll-and-skim. ~3 clicks before reaching ProductPicker. | |
| **(D) Composite (A) + (B): first-click filters table to the bucket; "map" button on each filtered row opens ProductPickerModal directly** | Both modes useful (filter for survey, button for quick map). | ✓ |

**User's choice:** (D), with an explicit invariant: per-store product isolation in the ProductPickerModal.

**User's exact words:** "אופציה d נשמע טוב אבל חייב לוודא שאם אני ממפה מוצר לקמפיין ממנהל המודעות של זול פלוס אני ממפה אך ורק מוצרים של זול פלוס ומתוך הדאטא ביס של זול פלוס ונכון כך לכל החנויות שלא יהיה בילבול בין מוצרים של חנויות שונות לקמפיינים של חנות ספציפית"

**Notes:** verified during discussion that `ProductPickerModal` is already per-store-scoped at [ProductPickerModal.tsx:122,139](dashboard-web/src/components/ProductPickerModal.tsx#L122). The invariant is therefore preserved by-construction — the chip's bucket carries the storeId and that's what gets passed to the modal. Captured as load-bearing D-09 in CONTEXT.md so the planner adds a regression test for it.
