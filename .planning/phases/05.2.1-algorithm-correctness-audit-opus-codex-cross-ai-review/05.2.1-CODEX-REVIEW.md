# Phase 5.2.1: Cross-AI Peer Review (codex / GPT-5)

## Executive Summary

Opus's audit is high-signal overall: it correctly identifies the most obvious Phase 5.2 regression, the broken organic source whitelist in `buildReconciliation`, and several useful missing tests. I disagree with the severity of several P0s: some are real but are presentation or defensive-math issues, while `AUDIT-P0-04` would be made worse by the proposed dedupe fix because Google ad-group rows are meant to sum. The most important Opus finding I agree with is `AUDIT-P0-01`; the most important disagreement is `AUDIT-P0-04`. My top new finding is the hard-coded Shopify `+03:00` day window, which silently shifts winter Shopify revenue/orders by one hour despite the project using `Asia/Jerusalem`.

## Verdict on Each Opus Finding

### P0 Findings

#### AUDIT-P0-01 (ORGANIC_SOURCES set bug)
**Verdict:** PARTIALLY AGREE
**Reasoning:** The issue is real. `dashboard-web/src/components/MetaShopifyReconciliation.tsx:166-174` includes impossible source labels (`organic-search-engine`, `meta-other`, `other`) and omits the real writer-emitted `google-organic` value from `Shopify.gs`. This undercounts organic and inflates `darkTrafficPercent`.

Opus overstates one part: `r(Organic)` is not structurally guaranteed to be `0`; `direct`, `email`, `meta-organic`, and `other-referral` can still create variance. The fix should also decide what to do with `source === ''` legacy/unknown rows. I prefer an inverted paid-exclusion predicate over another whitelist: skip deterministic paid (`meta-paid`, `google-paid`, `fbclidPresent`, `gclidPresent`), count the rest as non-platform/organic for this chart.
**Severity if changed:** P1, not P0. Wrong financial chart, but not corrupting stored data or core true-revenue allocation.

#### AUDIT-P0-02 (dailyMeta cross-store/long-ID collision)
**Verdict:** PARTIALLY AGREE
**Reasoning:** The cross-store leak as described is false. `useCampaignTrueRevenue.ts:264-275` checks `r.storeId !== a.storeId` before comparing campaign IDs, so a lossy campaign ID cannot make a row from another store enter `dailyMeta`.

The underlying ID-format risk is real: `SheetBuilder.gs:789-798` formats metrics columns but not campaign/ad-set ID columns, and `writeAdsRowsForDay` has the same gap. Existing text formatting in `writeOrdersAttributionForDay` is applied before `setValues`, which is the safer pattern. If Sheets coerces long numeric IDs, same-store matching and mapping can break.
**Severity if changed:** Reclassify to P2. Fix by formatting ID columns as text before writes and adding a one-time migration; do not frame this as a cross-store bug.

#### AUDIT-P0-03 (negative organic/refund orders skipped)
**Verdict:** PARTIALLY AGREE
**Reasoning:** The defensive point is valid: `mappedRevenue <= 0` drops negative mapped contributions if they ever appear. But the stated production path is weak. The writer uses Shopify order `current_total_price` for orders created in that day; Shopify normally does not emit a negative current order total, and older-order refund events are not modeled as separate negative rows in this pipeline. The proposed `=== 0` change is harmless only if the chart's Y-axis and interpretation can handle signed channel values.
**Severity if changed:** P3/P2 defensive edge case, not P0 production corruption based on current writer behavior.

#### AUDIT-P0-04 (Google duplicate aggregation)
**Verdict:** DISAGREE
**Reasoning:** Summing multiple Google rows for the same campaign/date is expected because `{store}-campaigns` stores one row per ad group. Dedupe by `(date, campaignId)` would undercount normal Search/Display campaigns with multiple ad groups. The Google writer's fallback is mutually exclusive in a single run: it either pushes real ad-group rows or synthesizes one campaign-level row. The sheet writer replaces the whole date slice, so stale fallback + real rows should not coexist unless the sheet was manually corrupted.
**Severity if changed:** Not a bug. Do not apply the proposed dedupe fix.

#### AUDIT-P0-05 (Google campaign gets Meta-specific r/narrative)
**Verdict:** PARTIALLY AGREE
**Reasoning:** Real issue. For a Google campaign, `metaByDate` stays empty and `r` becomes `0`; the UI then uses the Meta-specific primary narrative even though `rGoogle` may be the relevant value. This is misleading for uzoshop Google drawers, and lag detection is also Meta-only.
**Severity if changed:** P1/P2 UI decision-risk, not P0 stored-data corruption. The fix should make the primary correlation channel-aware: Google campaigns should lead with `rGoogle`, Meta campaigns with `r`, and all-channel views with `rCombined`.

#### AUDIT-P0-06 (Pearson zero variance returns 0)
**Verdict:** PARTIALLY AGREE
**Reasoning:** Correct diagnosis: zero variance is "not applicable", not measured no-correlation. The function documents returning `0`, so the math helper is internally consistent; the bug is that the reconciliation UI renders that sentinel as a real measurement.
**Severity if changed:** P2. Prefer returning a richer result (`{ value, status: 'ok' | 'no-variance' | 'too-few-points' }`) or gating the UI with a variance check rather than changing every caller to `number | null` blindly.

### P1 Findings

#### AUDIT-P1-01 (Bayesian CI population variance)
**Verdict:** EXTEND
**Reasoning:** Dividing by `N` instead of `N - 1` does understate uncertainty for small samples. But this is only the shallow problem. The interval is not Bayesian, not Wilson, and does not model conversion-count uncertainty; it only models observed AOV dispersion while treating the matched order count as fixed. The current zero-variance behavior (`roasInterval = null`) is also not statistically satisfying: identical AOVs still leave uncertainty about future order count.
**Severity if changed:** P2 as currently displayed. A one-line Bessel correction helps but does not make the tooltip's "95% credibility" claim true.

#### AUDIT-P1-02 (Pearson non-finite inputs)
**Verdict:** PARTIALLY AGREE
**Reasoning:** The helper can return `NaN` if given non-finite inputs. Current parsers mostly coerce non-finite Sheets values to `0`, so this is defensive rather than active production wrong-math. The proposed "return 0 if any pair is non-finite" throws away valid pairs; pairwise finite filtering is better.
**Severity if changed:** P3 defensive hardening.

#### AUDIT-P1-03 (negative metaClaim)
**Verdict:** PARTIALLY AGREE
**Reasoning:** The branch is sign-naive: negative `metaClaim` plus positive deterministic revenue falls through to coverage `1`. That said, Meta `action_values` should be non-negative in this collector, so this is unlikely on current data.
**Severity if changed:** P3/P2. Add an explicit negative/invalid claim guard, but this is not a Phase 6 blocker.

### P2 Findings

#### AUDIT-P2-08 (current productMap applied to historical ranges)

#### AUDIT-P2-09 (forecastMonthEnd partial fleet days)
**Verdict:** PARTIALLY AGREE

#### AUDIT-P2-10 (zero-spend mapped campaigns)
**Verdict:** DISAGREE

The edge cases do not promise an epsilon floor for paused campaigns. Adding one would be a new attribution policy, not a correctness fix.
**Severity if changed:** Not a bug.

## New Findings (Opus missed these)

### CODEX-NEW-P0-01: Shopify collection uses hard-coded `+03:00`, corrupting winter day windows
**Algorithm:** Shopify daily/order windows in `Shopify.gs:59-60`, `Shopify.gs:147-148`, `Shopify.gs:521-522`

**Issue:** The project timezone is `Asia/Jerusalem`, but all Shopify order queries use literal `T00:00:00+03:00`. Israel is UTC+03 in daylight time and UTC+02 in winter. On winter dates, the collector reads `23:00 previous day -> 23:00 current day` in local Israel time, not the intended local calendar day.

**Evidence:**
```gs
const dayStart = `${dateStr}T00:00:00+03:00`;
const dayEnd   = `${nextDayStr_(dateStr)}T00:00:00+03:00`;
```

This appears in all three Shopify daily algorithms: total revenue, product sales, and orders attribution.

**Impact:** Winter revenue, products, and deterministic order attribution are silently shifted by one hour. Orders from 23:00-24:00 Israel time land on the next day's analysis, and orders from the previous day 23:00-24:00 leak into the current day. Daily ROAS, attribution windows, reconciliation, and outlier detection can all be wrong.

**Fix sketch:** Generate Shopify bounds using the actual `TZ` offset for `dateStr`, or format local midnight through `Utilities.formatDate` with `XXX/Z` offset. Do not hard-code `+03:00`.

### CODEX-NEW-P0-02: `products-daily` shared-tab writer can lose rows under overlapping per-store triggers
**Algorithm:** `writeProductSalesForDay_` in `SheetBuilder.gs:1110-1150`

**Issue:** `products-daily` is shared by all stores. The writer reads all rows, filters out only the target `(date, storeId)`, clears the entire data range, and writes `keptRows + newRowsArr`. There is no `LockService` around the read-clear-write sequence. If two independent per-store triggers overlap, the later writer can restore a stale snapshot and delete the other store's just-written product rows.

**Evidence:**
```gs
const allExisting = sh.getRange(2, 1, lastRow - 1, PRODUCTS_DAILY_HEADERS.length).getValues();
...
sh.getRange(2, 1, lastRow - 1, PRODUCTS_DAILY_HEADERS.length).clearContent();
sh.getRange(2, 1, combined.length, PRODUCTS_DAILY_HEADERS.length).setValues(combined);
```

**Impact:** Silent product-row loss corrupts `useCampaignTrueRevenue`, `allocateProductRevenue`, product channel analysis, and reconciliation. Phase 5 intentionally split stores into independent executions; offset scheduling lowers the chance but does not remove overlap during slow API days.

**Fix sketch:** Use `LockService.getScriptLock()` around shared-tab read/clear/write operations, or split `products-daily` into per-store tabs like campaigns/orders. At minimum, add lock protection for `writeProductSalesForDay_`.

### CODEX-NEW-P1-01: Phase 5.2 Meta channel does not sum all mapped Meta campaigns
**Algorithm:** `buildReconciliation` in `dashboard-web/src/components/MetaShopifyReconciliation.tsx:135-143`

**Issue:** ROADMAP Phase 5.2 requires the Meta series to be the sum of Meta-claimed revenue for campaigns mapped to the same products. The implementation uses only the current drawer campaign's `summary.dailyArr` when `summary.platform === 'Meta'`. Google, by contrast, sums all mapped Google campaigns in the store.

**Evidence:**
```ts
if (summary.platform === 'Meta') {
  for (const d of summary.dailyArr) {
    metaByDate.set(d.date, d.value);
  }
}
```

**Impact:** If two Meta campaigns promote the same mapped product, the reconciliation undercounts Meta while summing Google more broadly. `r(Meta)`, `rCombined`, and `darkTrafficPercent` become inconsistent with the Phase 5.2 spec.

**Fix sketch:** Mirror the Google path for Meta: walk `campaignsData.rows`, filter `platform === 'Meta'`, same `storeId`, mapped product overlap, and sum by date. For a current-campaign-only chart, rename the semantics and do not call it all-channel reconciliation.

### CODEX-NEW-P1-02: Shopify true revenue allocation changes when the platform filter changes
**Algorithm:** `useCampaignTrueRevenue` + `CampaignsTable.aggregate`; `CampaignsTable.tsx:124-132`, `CampaignsTable.tsx:390-404`, `useCampaignTrueRevenue.ts:182-187`

**Issue:** `campaignSpend` is built from `aggregated`, and `aggregated` has already applied the UI platform filter. `allocateProductRevenue` then shares product revenue across all productMap campaigns, but campaigns hidden by the current platform filter have spend `0`.

**Evidence:**
```ts
// CampaignsTable aggregate filters first:
if (platformFilter !== 'all' && r.platform !== platformFilter) continue;

// useCampaignTrueRevenue later uses only that filtered list:
for (const a of aggregated) {
  campaignSpend.set(campaignKey(a.storeId, a.campaignId), a.spend);
}
```

**Impact:** A Meta campaign sharing a product with a Google campaign can receive 100% of the product revenue when the UI is filtered to Meta, but only its spend-proportional share when the UI is set to all platforms. A campaign's true ROAS should not change just because the operator hides another platform.

**Fix sketch:** Build allocation spend from all campaign rows in the selected store/date range, independent of the visible platform filter. Apply UI filtering only after allocation.

### CODEX-NEW-P2-01: Reconciliation mixes incompatible revenue bases
**Algorithm:** `buildReconciliation` and Shopify line-item writer; `MetaShopifyReconciliation.tsx:122-188`, `Shopify.gs:618-649`

**Issue:** Shopify actual uses `products-daily` product net revenue (`netRevenue ?? revenue`). Organic uses `orders-attribution.lineItems[].revenueCad`, which is a proportional split of order `current_total_price`. Those are not the same basis: `current_total_price` can include order-level effects such as shipping/tax allocation, while product net revenue is computed from line gross minus discounts/refunds.

**Impact:** The organic series can be higher or lower than the Shopify product series even when it is describing the same mapped products. Pearson and dark-traffic calculations then compare mixed accounting definitions.

**Fix sketch:** Pick one canonical basis for reconciliation. Either derive Shopify actual from the same order line-item model or derive organic from product-net-compatible line data.

### CODEX-NEW-P2-02: Lag detection picks strongest absolute correlation, including inverse correlations
**Algorithm:** `buildReconciliation` lag loop in `MetaShopifyReconciliation.tsx:220-230`

**Issue:** The code chooses a lag when `Math.abs(r2) > Math.abs(bestR)`. A shifted negative correlation can win and produce a lag banner, even though inverse correlation is not an attribution-window delay.

**Evidence:**
```ts
if (Math.abs(r2) > Math.abs(bestR)) {
  bestR = r2;
  bestLag = lag;
}
```

**Impact:** The UI can report "Meta reports conversion N days before Shopify" for a lag that is actually a stronger inverse relationship.

**Fix sketch:** For attribution lag, prefer positive correlation only (`r2 > bestR + threshold`) or render negative shifted correlations as an anomaly, not a lag.

### CODEX-NEW-P2-03: Ad-set fallback promised in docs is not implemented
**Algorithm:** `analyzeAttributionForAdSet` in `attributionAnalysis.ts:551-581`

**Issue:** The docstring says the ad-set analyzer falls back to campaign-level analysis if `utm_term` is unconfigured. The implementation only matches `utmTerm === adSetId`; it has no campaign fields and cannot fall back.

**Evidence:**
```ts
return o.utmTerm && o.utmTerm.trim() === adSet.adSetId.trim();
```

**Impact:** Stores that configure only campaign-level UTMs can show useful campaign attribution while every ad-set row appears unknown/misconfigured. That may be acceptable, but the current documentation says otherwise.

**Fix sketch:** Either implement an explicitly labeled campaign-level inherited fallback or correct the docstring and UI copy to say ad-set attribution requires `utm_term={{adset.id}}`.

### CODEX-NEW-P2-04: `campaignKey` has no platform namespace
**Algorithm:** `campaignProductMap.ts:28-29` and all product-map consumers

**Issue:** The campaign-product map key is `${storeId}::${campaignId}`. The table aggregation key includes platform, but product mapping does not. Meta and Google IDs are usually different shapes, so collisions are unlikely, but the model does not prevent them.

**Impact:** A same-store Meta/Google campaign ID collision would merge mappings and true-revenue allocation. This is a low-probability but high-confusion edge case, and Phase 5.2 now intentionally maps both Meta and Google campaigns.

**Fix sketch:** Version the map key to include platform, e.g. `${storeId}::${platform}::${campaignId}`, with a migration for existing keys.

## Overall Verdict

The algorithm stack is not ready to move straight into Phase 6 if Phase 6 assumes the financial numbers are already trustworthy. The must-fix items before security work are: `AUDIT-P0-01`, `AUDIT-P0-05/P0-06` as channel-aware reconciliation presentation, `CODEX-NEW-P0-01`, `CODEX-NEW-P0-02`, `CODEX-NEW-P1-01`, and `CODEX-NEW-P1-02`. Opus's audit is useful, but its P0 count is inflated: I would treat two of its P0s as true P0/P1 blockers, one as a real but lower-severity presentation bug, and one (`AUDIT-P0-04`) as a false positive with a harmful proposed fix. Phase 6 can proceed in parallel only if these algorithm fixes are explicitly tracked and not deferred behind security hardening.

## Disagreements with Opus

- `AUDIT-P0-02`: the claimed cross-store leak is blocked by the existing `storeId` check. The related long-ID formatting risk is real but not cross-store as described.
- `AUDIT-P0-03`: negative refund-row corruption is not demonstrated by the current Shopify writer; current severity should be much lower.
- `AUDIT-P0-04`: disagree. Dedupe by `(date, campaignId)` would undercount legitimate multi-ad-group Google campaigns.
- `AUDIT-P0-05`: agree with the bug, disagree with P0 severity. It is channel-inappropriate UI interpretation, not stored data corruption.
- `AUDIT-P0-06`: agree with "no signal vs zero correlation", disagree that the pure helper itself is the main bug. The rendering contract is the problem.
- `AUDIT-P2-10`: disagree. Zero-spend campaigns receiving zero share when another mapped campaign spent money is consistent with spend-proportional allocation.
