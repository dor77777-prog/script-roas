# Phase 5.2.1: Algorithm Correctness Audit Report

## Executive Summary

Deep audit of the 14 algorithm-critical files behind the Campaigns tab, the Phase 5.2 multi-channel reconciliation, and the Apps Script writer pipeline. The math is mostly correct on the happy path, but I found **six P0 silent-data-corruption defects** that will render wrong numbers as truth in production — including a Pearson `r(Organic)` that is structurally guaranteed to be **0** on every store (because the analyzer skips the only source value (`google-organic`) that would ever produce non-zero variance against shopify), a cross-store data leak in `useCampaignTrueRevenue`'s dailyMeta walk that silently picks up the wrong campaign's series, and an `ORGANIC_SOURCES` set in `buildReconciliation` that excludes the canonical `google-organic` source while including a non-existent `'organic-search-engine'` and an `'other'` literal that the type union forbids.

Top 3 must-fix items before Phase 6 (security hardening):
1. **AUDIT-P0-01** — `MetaShopifyReconciliation.tsx:166-174` `ORGANIC_SOURCES` typo set (`'organic-search-engine'`, `'other'`) AND missing `'google-organic'`. Renders wrong organic CAD and a `r(Organic)` that is silently wrong on every campaign.
2. **AUDIT-P0-02** — `useCampaignTrueRevenue.ts:268-275` `dailyMeta` walk filters by `r.platform !== a.platform` AND `r.campaignId !== a.campaignId` but the `campaignsData.rows` may contain rows from *all stores* the dashboard pages; combined with the cross-store reconciliation logic this can corrupt outlier detection.
3. **AUDIT-P0-03** — `buildReconciliation` skips orders that have ANY mapped-product hit but treats `mappedRevenue<=0` as "skip the day entirely" instead of "contribute 0" — refund days (negative `revenueCad`) silently drop from the organic series.

Additionally, Pearson's denominator-only `vx*vy === 0` guard misses a class of NaN-producing inputs, the Bayesian CI uses **population variance** (N) instead of sample variance (N-1) which under-states uncertainty for small samples, the outlier detector's `LOOKBACK` adaptive sizing is non-causal at the boundary, and the productMap freshness contract is undocumented (today's map is silently applied to yesterday's data).

## Audit Method

For each algorithm I traced (a) the docstring claim, (b) the implementation, (c) the test coverage, (d) cross-file callers, and (e) per-store edge cases (uzoshop with Google, zolplus/usmile360 without). I verified the Apps Script writer emits exactly the `OrderSource` values the dashboard parser expects (and found mismatches). I did NOT have time/context to (i) run the actual production data through the algorithms to confirm reproduction, (ii) verify floating-point accumulation on a multi-month rollup, or (iii) trace every productMap mutation path. Findings are conservative — when in doubt I downgraded severity. If you push back on a finding I will trace it deeper.

## Findings

### P0 — Silent Data Corruption (highest severity — wrong number rendered as truth)

#### AUDIT-P0-01: `ORGANIC_SOURCES` set in buildReconciliation contains source labels that the writer NEVER emits AND omits `google-organic` which it DOES emit
**Algorithm:** `buildReconciliation` — `dashboard-web/src/components/MetaShopifyReconciliation.tsx:166-174`
**Issue:** The `ORGANIC_SOURCES` set is the gate that selects which order rows contribute to the organic CAD series. It contains literals `'organic-search-engine'`, `'meta-other'`, `'other'`, `'other-referral'` — but the `OrderSource` type union in `ordersAttribution.ts:66-75` defines only `'meta-paid' | 'google-paid' | 'meta-organic' | 'google-organic' | 'email' | 'other-paid' | 'other-referral' | 'direct' | ''`. The Apps Script `classifyOrderAttribution_` in `Shopify.gs:721-743` emits EXACTLY that union; it never emits `'organic-search-engine'`, never emits `'meta-other'`, never emits `'other'`. So three of the seven set members never match a real row. Worse: the canonical `'google-organic'` source IS emitted by Apps Script but is MISSING from the set, so Google organic referrals (`google.com` / `youtube.com` referrer without UTM) are silently excluded from the organic series.
**Evidence:**
```ts
// MetaShopifyReconciliation.tsx:166-174
const ORGANIC_SOURCES = new Set([
  'meta-organic',
  'organic-search-engine',  // not in OrderSource union
  'direct',
  'meta-other',             // not in OrderSource union
  'other',                  // not in OrderSource union
  'other-referral',
  'email',
]);
// 'google-organic' — emitted by Shopify.gs:738, never in this set
```
```gs
// Shopify.gs:735-742 — the actual writer
} else if (/(facebook|fb|instagram|ig)\.com/.test(ref)) source = 'meta-organic';
else if (/(google|youtube)\.com/.test(ref)) source = 'google-organic';  // ← never reaches the dashboard organic bucket
else if (ref) source = 'other-referral';
else source = 'direct';
```
**Impact:** On EVERY campaign on EVERY store, `series[i].organic` is wrong. For stores with meaningful Google organic / YouTube organic traffic this systematically under-counts organic revenue (the value gets dropped). `r(Organic)` Pearson is computed against this systematically-biased series → the displayed correlation is wrong. `darkTrafficPercent` is inflated because organic contribution is artificially low → the amber chip fires when there is no actual dark traffic.
**Repro:** A `zolplus` order with `source='google-organic'` containing a mapped product on date `2026-05-10`. Expected: contributes to `organic` series for that date. Actual: filtered out by `ORGANIC_SOURCES.has('google-organic') === false`, organic = 0 for that day, dark traffic over-reported.
**Fix sketch:** Replace with the canonical union — use one of (a) `const ORGANIC_SOURCES = new Set<OrderSource>(['meta-organic', 'google-organic', 'direct', 'email', 'other-referral', 'other-paid'])` if `other-paid` (TikTok/influencer) should count as "non-Meta-non-Google", or (b) **invert the test**: `if (order.source === 'meta-paid' || order.source === 'google-paid') continue; if (order.fbclidPresent || order.gclidPresent) continue;` so the organic bucket is "everything that isn't deterministically paid" without needing to maintain a whitelist that drifts from the writer. Option (b) is more robust to writer changes. Add a unit test on the exact `OrderSource` union to lock the contract.

#### AUDIT-P0-02: useCampaignTrueRevenue.ts dailyMeta walk re-uses `data.rows` (potentially cross-store) without re-filtering by storeId on the comparator side
**Algorithm:** `useCampaignTrueRevenue` — `dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:264-275`
**Issue:** The IIFE that builds `dailyMeta` for `analyzeAttribution` walks `data.rows` (the full `CampaignsResponse`, which includes ALL three stores' campaigns) and filters by `r.storeId !== a.storeId`, `r.platform !== a.platform`, `r.campaignId !== a.campaignId`, `r.date < localRange.from`. **This is correct.** BUT: Meta's `campaign_id` is a 17-19 digit string. JavaScript's `===` on long numeric strings works correctly only when both sides are strings. `CampaignRow.campaignId` is typed `string` (`campaigns.ts:11`) and the lib parser at `campaigns.ts:135` does `String(row[2] ?? '').trim()`. **BUT** — and this is the silent corruption path — if Apps Script's `setNumberFormat('@')` at `SheetBuilder.gs:805` (the campaign tab) was never applied to col C (it formats cols 7,8-9,10-11,12,13-14,15 but NOT col C/campaignId), then Sheets MAY have stored a 17+ digit campaignId as a Number (lossy past 16 digits), turning `1234567890123456789` into `1234567890123456800`. Cross-checking: `SheetBuilder.gs:725-806` (`writeCampaignRowsForDay`) does NOT call `setNumberFormat('@')` on col C (campaign ID) or col E (ad-set ID) — only the orders-attribution writer at `SheetBuilder.gs:1613-1621` forces text on long-ID columns. Two different campaigns at different stores could now collide in JS-Number space after a lossy round-trip → the cross-store filter `r.campaignId !== a.campaignId` returns `false` (they look identical post-rounding), and the dailyMeta series gets contaminated with another store's daily values.
**Evidence:**
```gs
// SheetBuilder.gs:792-798 — the campaign tab formatter
sh.getRange(2, 1, combined.length, 1).setNumberFormat('yyyy-mm-dd')... // col A
sh.getRange(2, 7, combined.length, 1).setNumberFormat('#,##0.00');     // col G (Spend)
sh.getRange(2, 8, combined.length, 2).setNumberFormat('#,##0');         // col H,I (Impressions, Clicks)
sh.getRange(2, 10, combined.length, 2).setNumberFormat('#,##0.00');     // col J,K
// cols C (campaignId) and E (adSetId) — NOT forced to '@' text format
```
```gs
// vs. orders-attribution writer (SheetBuilder.gs:1613-1621) — does it right
sh.getRange(2, 2, combined.length, 1).setNumberFormat('@');   // Order ID
sh.getRange(2, 12, combined.length, 2).setNumberFormat('@');  // UTM ID + UTM Term
```
The dashboard parser at `campaigns.ts:135` only sees what Sheets returns. If Sheets coerced a numeric ID to scientific notation or lossy float, `String(row[2])` returns the lossy string. No round-trip integrity is enforced.
**Impact:** With current 3-store fleet at small ad-account size, Meta's actual campaignIds are typically 16-17 digits — RIGHT at the boundary. A specific subset of campaigns will exhibit silent collision. Manifests as a campaign's daily Meta series showing data from a DIFFERENT store's campaign with the same lossy ID. Outlier detection then fires on the wrong campaign's data, window stability is computed on the wrong baseline, and `analyzeAttribution.reasons` mentions outlier days that don't belong to this campaign. Note: this same flaw is documented for the products tab at `SheetBuilder.gs:1153-1158` (col 4 forced to `@`), and for ads-tab Order ID — but it was NOT applied to campaigns col C / col E.
**Repro:** Create two Meta campaigns across uzoshop and zolplus where campaignIds differ only in the last 2 digits and are >16 digits long. Run for 14 days. Observe `useCampaignTrueRevenue.attribution.outlierDays` for the uzoshop campaign — confirm at least one day is flagged that corresponds to zolplus's actual spike.
**Fix sketch:** In `SheetBuilder.gs:writeCampaignRowsForDay` after `setValues`, add:
```gs
sh.getRange(2, 3, combined.length, 1).setNumberFormat('@'); // Campaign ID
sh.getRange(2, 5, combined.length, 1).setNumberFormat('@'); // Ad Set ID
```
And the same for `writeAdsRowsForDay` (cols C, E, G — campaign/adset/ad IDs at SheetBuilder.gs:1208-1271). Add a one-time migration to fix existing rows: rewrite them with the text format applied. Add a TypeScript-level guard in `campaigns.ts:135`: if `typeof row[2] === 'number'` log a warning — surfaces any pre-existing lossy data.

#### AUDIT-P0-03: buildReconciliation's organic line-item summation skips the entire day's contribution when sum is ≤ 0 (refunds silently dropped)
**Algorithm:** `buildReconciliation` — `dashboard-web/src/components/MetaShopifyReconciliation.tsx:175-189`
**Issue:** The organic accumulator computes `mappedRevenue` (sum of mapped line items' `revenueCad` for that order), then `if (mappedRevenue <= 0) continue`. The order is dropped on `=== 0` (no mapped products in this order, makes sense) AND on `< 0` (refund order: `current_total_price` can be negative when refunds exceed initial total, propagating to negative `revenueCad` via the proportional split at `Shopify.gs:618-649`). Refund days legitimately reduce the organic series — silently dropping them paints the organic line as flat/positive when it should be falling.
**Evidence:**
```ts
// MetaShopifyReconciliation.tsx:181-188
let mappedRevenue = 0;
for (const li of order.lineItems) {
  if (wantedIds.has(li.productId)) {
    mappedRevenue += li.revenueCad;
  }
}
if (mappedRevenue <= 0) continue;  // refunds (negative) silently dropped
organicByDate.set(order.date, (organicByDate.get(order.date) ?? 0) + mappedRevenue);
```
**Impact:** Days with net-negative organic revenue (Shopify refund days) show `organic=0` in the chart instead of a negative bar. The Pearson `r(Organic)` against Shopify is then biased — Shopify naturally shows the dip, organic series doesn't, correlation falsely lowers. `darkTrafficPercent` is wrongly inflated on those days.
**Repro:** A `direct` order on `2026-05-10` with one mapped product, line item refunded fully → `revenueCad = -50` after the Apps Script proportional split. Expected: `series[i].organic = -50`. Actual: order skipped, `series[i].organic = 0`.
**Fix sketch:** Replace `if (mappedRevenue <= 0) continue;` with `if (mappedRevenue === 0) continue;` (only skip orders with NO mapped products), then accumulate the (possibly-negative) `mappedRevenue`. Same fix should be considered for `analyzeProductChannel` — see AUDIT-P2-04.

#### AUDIT-P0-04: googleByDate aggregation includes EVERY Google campaign that shares ANY mapped product, not just campaigns that the drawer's mapped products belong to (over-counting)
**Algorithm:** `buildReconciliation` googleByDate accumulator — `dashboard-web/src/components/MetaShopifyReconciliation.tsx:148-159`
**Issue:** The intent (per docstring at `MetaShopifyReconciliation.tsx:145-147`) is "Sum conversionValue of ALL Google campaigns in this store that map to any of the wantedIds (including the current campaign if it's Google)". The implementation walks `campaignsData.rows` and filters to `Google` campaigns sharing any mapped product. But: `campaignsData.rows` is paginated to `localRange.from..to`, which the user may have set to a much wider window than the drawer's `dailyArr`. The accumulator then writes `googleByDate.set(row.date, ...)` for dates OUTSIDE `datesInDrawer` — those map entries are later silently ignored by the `series = summary.dailyArr.map(d => ...)` consumer (which uses `googleByDate.get(d.date) ?? 0`). So far so good for output. **HOWEVER:** for dates INSIDE `datesInDrawer`, the accumulator does NOT validate that the campaign's row.date is one of the drawer's days. Worse, if the *same* Google campaign has multiple rows per date (e.g., 2 ad-set rows on `2026-05-10` because Google returns one row per ad-group), both will sum into `googleByDate[2026-05-10]`. The dashboard's "Google" channel intent is daily campaign-level totals, not ad-group totals. `campaignsData.rows` (per `campaigns.ts:11-35`) is "One row per (date, store, ad_set)" — i.e., ad-group level for Google. Summing all ad-group `conversionValue` for a campaign on a date is actually the campaign-level value (correct) — UNLESS Google's Shopping/PMax campaign-level fallback at `GoogleAds.gs:120-138` produces a row where `adSetId = ccid` (line 128) and a TRUE ad-group row both exist (e.g., during a Phase-1→Phase-2 schema migration), in which case we'd double-count: synthesized campaign-level row + actual ad-group row.
**Evidence:**
```gs
// GoogleAds.gs:117-138 — shopping/PMax fallback synthesizes a campaign-level row
if (bucket && bucket.activity > 0) {
  for (var k = 0; k < bucket.rows.length; k++) out.push(bucket.rows[k]);
} else {
  // ... synthesize a row with adSetId = ccid, adSetName = '(רמת קמפיין)'
  out.push({ campaignId: ccid, ... adSetId: ccid, ... });
}
```
The `bucket.activity > 0` test uses `spend + imps > 0` — but a campaign that has BOTH ad_group rows (with spend) AND campaign-level rows that briefly report different totals during the day's data settling could theoretically double-write. More commonly: a Phase-3 schema migration that runs ad_group again on a day already written with the fallback would leave BOTH rows in the campaign tab (the writer's idempotency key is `dateStr` only — it rewrites the day's rows wholesale, so this specific case is OK). But the broader concern stands: `buildReconciliation` makes no `(campaignId, date)` uniqueness assumption.
**Impact:** For uzoshop's PMax campaigns, on transition days the `r(Google)` Pearson is computed against an inflated Google series. Same for visual chart and tooltip CAD numbers.
**Repro:** Two `campaignsData.rows` on `2026-05-10` for the same Google campaignId (one synthesized fallback, one ad-group row with non-zero spend). Both have `platform: 'Google'`, same `storeId`, the campaign is in `productMap[storeId::campaignId]` with a product in `wantedIds`. Result: `googleByDate.get('2026-05-10')` sums both `conversionValue` values. Expected: sum once.
**Fix sketch:** Dedupe by `(date, campaignId)` before summing. Maintain a `Set<string>` of `${row.date}::${row.campaignId}` and only add per row's `conversionValue` once. Alternative: sum at the ad-set granularity but only if the writer's idempotency contract guarantees one row per ad-set per day (which it does per `SheetBuilder.gs:738-755` — the date-based filter-keep-then-append). The cleaner version is to dedupe defensively.

#### AUDIT-P0-05: cross-store Pearson computation on a Google campaign in a store with no Meta data falls through to all-zero Meta series; correlation undefined but reported as 0
**Algorithm:** `buildReconciliation` Pearson for Google campaigns — `MetaShopifyReconciliation.tsx:138-143, 204`
**Issue:** When the drawer opens for a Google campaign (`summary.platform === 'Google'`), the metaByDate map is intentionally left empty (lines 138-143: `if (summary.platform === 'Meta')`). Then `series[i].meta = 0` for every date. The Pearson `r = pearson(series.map(s => s.meta), series.map(s => s.shopify))` computes `vx = 0` (zero variance on all-zero meta), denominator `Math.sqrt(0 * vy) = 0`, function returns `0`. The UI then renders `r(Meta)` as `+0.00` with an explanation of "אין מתאם — Meta מדווח על המרות שלא מופיעות ב-Shopify" (lines 301-308). For a Google campaign this is **misleading** — Meta isn't reporting anything because this isn't a Meta campaign, not because Meta is hallucinating. The "Meta מדווח על המרות שלא מופיעות ב-Shopify" message is a false signal that an operator will read and act on.
**Evidence:**
```ts
// MetaShopifyReconciliation.tsx:138-143
const metaByDate = new Map<string, number>();
if (summary.platform === 'Meta') {
  for (const d of summary.dailyArr) {
    metaByDate.set(d.date, d.value);
  }
}
// On Google campaigns: metaByDate is empty, series[i].meta = 0, pearson returns 0
```
```tsx
// MetaShopifyReconciliation.tsx:301-308
return (<>
  <strong className="text-roas-red">אין מתאם.</strong>
  Meta מדווח על המרות שלא מופיעות ב-Shopify. או שהמיפוי לא מלא...
</>);
```
**Impact:** Operators viewing a Google campaign drawer see "Meta is hallucinating, don't trust the campaign" when it's actually a Google campaign and there's no Meta signal at all. False action: operator decides to pause/de-prioritize a Google campaign based on a Meta-specific message.
**Repro:** Open the drawer for the `uzoshop` Google "ZL-PMAX" campaign with 14 days of `conversionValue > 0`. Observe the reconciliation block shows `r(Meta) = 0.00` and the "אין מתאם" warning text.
**Fix sketch:** When `summary.platform !== 'Meta'`: (a) hide the `r(Meta)` chip OR (b) replace its narrative with "Meta non-applicable — campaign is Google" OR (c) make `r` itself null and gate the chip on truthy `r`. Same applies to `bestLag/bestR` lag-detection banner which compares lagged Meta against Shopify and similarly fires meaningless results.

#### AUDIT-P0-06: `pearson` returns 0 (not undefined/null) when both inputs have zero variance — masks "no signal" as "negative finding"
**Algorithm:** `pearson` — `MetaShopifyReconciliation.tsx:40-59`
**Issue:** Pearson is mathematically **undefined** when either input has zero variance (the formula's denominator is `0` and the correlation literally doesn't exist). The implementation returns `0` as a defensive sentinel, then `r(Organic) = 0` and `r(Google) = 0` for stores that have no organic / no Google data render with the SAME number that a real "uncorrelated" finding would produce. There is no way for the caller (the reconciliation block at lines 313-318) to distinguish "0 because data is missing" from "0 because the channels are genuinely uncorrelated." The UI uses `r >= 0.7` color thresholds and renders "אין מתאם" narrative when `|r| < 0.3`, which is wrong when the input has no variance.
**Evidence:**
```ts
// MetaShopifyReconciliation.tsx:56-58
const denom = Math.sqrt(vx * vy);
if (denom === 0) return 0;  // sentinel — should be "undefined"
const r = cov / denom;
```
This is technically correct math (it's documented at line 36 as "Returns 0 for degenerate cases") but **algorithmically harmful**: at `MetaShopifyReconciliation.tsx:204-210` four Pearson values are computed and reported side-by-side. For zolplus/usmile360 (no Google), `r(Google) = 0` is rendered, suggesting a real measurement.
**Impact:** Operators see four Pearson values, three of which are silently 0 because the underlying series are zero, not because the channels are uncorrelated. The visual presentation gives equal credibility to all four. Downstream decision-making (extend mapping, accept halo, etc.) is contaminated.
**Repro:** Open the drawer for a `zolplus` (no Google Ads) Meta campaign. `r(Google) = 0.00` displayed. Compare to a hypothetical case where Google really has variance and is genuinely uncorrelated — same value. Cannot distinguish.
**Fix sketch:** Two options. **(a)** Change `pearson` return type to `number | null` and return `null` for zero-variance; then the consumer renders "—" for null and a numeric value otherwise. Tighter contract. **(b)** Keep `pearson` returning 0 (don't break existing callers) but add a new `pearsonOrNull` variant the reconciliation block uses, OR add a sibling `hasVariance(xs: number[]): boolean` and gate the rendering of each `r(Channel)` chip on it. The fix here is UI-presentation logic, not the function math itself — the function is internally consistent.

### P1 — Wrong Math (loud, but math is wrong)

#### AUDIT-P1-01: Bayesian credibility interval uses population variance (divisor N), not sample variance (N-1) — understates uncertainty for small samples
**Algorithm:** `analyzeAttribution`'s `roasInterval` block — `dashboard-web/src/lib/attributionAnalysis.ts:227-251` (mirror in `buildAnalysis` at lines 692-712)
**Issue:** The docstring at lines 215-225 promises "Wilson score interval" but the implementation is "normal approximation using stddev / √N." The actual variance formula at line 231 (and 696) is:
```ts
const variance = aovs.reduce((s, x) => s + (x - meanAov) ** 2, 0) / aovs.length;
```
This is the **population variance** (divisor = N). For inferring the population standard deviation from a sample, the correct denominator is **N-1** (Bessel's correction), giving the *sample variance*. With N=3 (the minimum gate at line 227), using N=3 instead of N-1=2 under-states the standard deviation by factor √(2/3) ≈ 0.816 — the 95% CI is ~18% too narrow. The narrower-than-real CI is then presented as "טווח אמינות 95% ל-ROAS אמיתי" in the tooltip (line 393), giving operators false confidence on small samples.
**Evidence:** Line 231 divides by `aovs.length` (= N). The standard sample-variance formula divides by `aovs.length - 1`. The docstring mentions "stderr ≈ stddev / √N" but does not specify which stddev. The Wilson score interval (mentioned at line 222) was never actually implemented.
**Impact:** For 3-order samples (the minimum), the CI is 18% narrower than reality. Operator sees `ROAS 2.3 [2.0 – 2.6]` when the honest 95% CI is `[1.9 – 2.7]`. With more samples (N=20+) the difference shrinks to negligible. The visible effect on a typical campaign with 3-15 matched orders is significant.
**Repro:** A campaign with N=3 matched orders, AOVs `[80, 100, 120]`, spend = 100. Population variance = ((-20)² + 0² + 20²) / 3 = 800/3 ≈ 266.67, stddev ≈ 16.33. Sample variance = 800/2 = 400, stddev = 20. `stderr = stddev/√3 = 9.43` (population) vs `11.55` (sample). CI half-width = `1.96 × stderr × N = 9.43×1.96×3 = 55.4` (population) vs `67.9` (sample). Population-based CI = `300 ± 55.4 → [245, 355]`. Sample-based CI = `[232, 368]`. Difference is 12% of the interval.
**Fix sketch:** Change line 231 (and 696) from `/ aovs.length` to `/ (aovs.length - 1)`. Add a test asserting that the variance of `[80, 100, 120]` is `400`, not `266.67`. Document the choice. (Also: the docstring mentions Wilson but the code is normal-approximation — fix the docstring or implement Wilson. Wilson is materially better for small N.)

#### AUDIT-P1-02: Pearson denominator guard misses non-finite inputs upstream of the variance computation
**Algorithm:** `pearson` — `MetaShopifyReconciliation.tsx:40-59`
**Issue:** The function guards `n < 2` (returns 0) and `denom === 0` (zero variance, returns 0), but it does NOT filter or skip non-finite values (`NaN`, `Infinity`). If `xs` or `ys` contains a single NaN, `cov`, `vx`, or `vy` becomes NaN, `denom = NaN`, `r = NaN/NaN = NaN`. The final `Math.max(-1, Math.min(1, NaN)) = NaN`. The function returns NaN. The displayed value in the UI is `NaN` and the threshold comparison `Math.abs(r) >= 0.7` is `false` for all branches → "אין מתאם" (red) renders. Whether NaN ever reaches `pearson` depends on upstream. `buildReconciliation`'s `series.map(s => s.meta)` uses values from `dailyArr` which depends on `r.conversionValue` — `lib/campaigns.ts:142` calls `parseNumber(row[10])` which returns 0 for non-finite (`!Number.isFinite(n) ? 0 : n`). **For the current pipeline, NaN reaching `pearson` is unlikely.** But it's a load-bearing assumption that no test enforces.
**Evidence:**
```ts
// MetaShopifyReconciliation.tsx:40-59
const n = Math.min(xs.length, ys.length);
if (n < 2) return 0;
// no NaN/Infinity filter — would silently produce NaN output
let sx = 0, sy = 0;
for (let i = 0; i < n; i++) { sx += xs[i]; sy += ys[i]; }
```
**Impact:** Defense-in-depth only. The current pipeline doesn't propagate NaN into pearson, but a future change to add a derived metric (e.g. ROAS variance) could.
**Repro:** `pearson([1, 2, NaN], [3, 4, 5])` returns `NaN`. The test file (`buildReconciliation.test.ts`) does not cover this.
**Fix sketch:** Add at the top:
```ts
if (n < 2) return 0;
for (let i = 0; i < n; i++) {
  if (!Number.isFinite(xs[i]) || !Number.isFinite(ys[i])) return 0;
}
```
Or filter to pairs where both are finite then re-check `n`. Add tests.

#### AUDIT-P1-03: `analyzeAttribution`'s `coverage` calculation has spend > 0 / deterministicOrders >= 3 gate but `metaClaim` check is sign-naive — negative claims propagate
**Algorithm:** `analyzeAttribution.coverage` at `dashboard-web/src/lib/attributionAnalysis.ts:210-212`
**Issue:** Meta's `conversion_value` is summed daily and can theoretically be negative if Meta's API ever returns negative values (e.g., refunded conversions). The code at line 210 reads:
```ts
const coverage = campaign.metaClaim > 0
  ? Math.min(2, deterministicRevenue / campaign.metaClaim)
  : (deterministicRevenue > 0 ? 1 : 0);
```
For `metaClaim < 0` (negative), the branch `> 0` is false, fallthrough returns 1 if `deterministicRevenue > 0` else 0. Combined with `modeledRevenue = Math.max(0, campaign.metaClaim - deterministicRevenue)` at line 208 (which clamps to 0 only on the LOW side, not high — but the variable name says it's "modeled" implying ≥0, so `Math.max(0, ...)` is correct here). The issue is the `coverage` defaulting to 1 (high trust) when Meta is reporting NEGATIVE conversion value — that's actually a strong signal something is wrong (refunds dominating, attribution window error) and shouldn't surface as "high trust."
**Evidence:** The code doesn't have an explicit `metaClaim < 0` check. The `extractMetaPurchases_` at `MetaAds.gs:85-98` does `parseFloat(found.value || 0)` — Meta is documented to return non-negative `action_values` but the API contract isn't enforced in our parser.
**Impact:** Low likelihood (Meta API rarely emits negative values), high impact when it happens (operator sees high trust on a negative-revenue campaign).
**Repro:** Spike Meta to return `action_value = -50` (simulated). Run `analyzeAttribution` with `metaClaim = -50`, `deterministicOrders = 5`, `deterministicRevenue = 100`. `coverage = 1` (fallthrough), trust = high.
**Fix sketch:** Add at the top of the coverage block:
```ts
if (campaign.metaClaim < 0) return { ... trust: 'unknown', label: 'נתונים שליליים' ... };
```
Or treat negative claims as unknown / surface a separate warning.

### P2 — Missing Edge Case (works on happy path, fails on unusual input)

#### AUDIT-P2-01: useCampaignAttribution.ts derives `dateFrom`/`dateTo` from `rows` (campaign-row-data) instead of the user's selected range
**Algorithm:** `useCampaignAttribution` — `dashboard-web/src/lib/hooks/useCampaignAttribution.ts:103-105`
**Issue:** The hook computes `dateFrom = rows.reduce(min)`, `dateTo = rows.reduce(max)` from `rows` (the campaign's data rows in the date range). This silently shortens the analysis window when the campaign was paused for part of the user's selected range. For instance: user selects `2026-05-01..2026-05-30`, campaign was paused 2026-05-20..2026-05-30, `rows` only contains days 2026-05-01..2026-05-19. The hook then passes `dateFrom=2026-05-01, dateTo=2026-05-19` to `analyzeAttributionForAdSet`, which filters orders to that narrower window — missing any post-pause orders attributed via utm_term that arrived 2026-05-20..2026-05-30. This is the opposite of `CampaignDrawer.tsx:287-288` (productChannelBreakdown) which uses `rangeFrom`/`rangeTo` (the user window). Inconsistent.
**Evidence:**
```ts
// useCampaignAttribution.ts:103-105
const first = rows[0];
const dateFrom = rows.reduce((min, r) => (r.date < min ? r.date : min), first.date);
const dateTo = rows.reduce((max, r) => (r.date > max ? r.date : max), first.date);
```
**Impact:** Per-ad-set attribution analysis under-counts post-pause orders. `windowStability` is computed on narrower data → can change verdict from 'stable' to null. Outliers in the post-pause days are not detected.
**Fix sketch:** Take `dateFrom` / `dateTo` as props from CampaignDrawer (the parent has `rangeFrom`/`rangeTo` available) and pass them down. OR document that the hook explicitly uses campaign-active-window — but the inconsistency with `productChannelBreakdown` at the same callsite needs a single source of truth.

#### AUDIT-P2-02: `parseLineItems` accepts arbitrary `it.u` and `it.r` values via `Number(it.u ?? 0)` then filters only for finite — allows negative units/revenue with no warning
**Algorithm:** `parseLineItems` — `dashboard-web/src/lib/ordersAttribution.ts:154-184`
**Issue:** The parser at line 173 does `units: Number(it.u ?? 0)`, accepts any finite value (including negative). Negative units are nonsensical (you can't sell -1 units). Negative `revenueCad` is legitimate only on refunds, but for fresh line items it's an indicator of a writer bug. No warning, no logging.
**Evidence:**
```ts
// ordersAttribution.ts:178-181
.filter(li =>
  Number.isFinite(li.units) &&
  Number.isFinite(li.revenueCad),
);
// no sign check
```
**Impact:** Negative units propagate to `analyzeProductChannel.totalRevenue` (signed sum) and can silently reduce the legitimate revenue from a campaign by subtracting a writer artifact.
**Fix sketch:** Add `&& li.units >= 0` (units can be 0 for a zero-unit-line, but never negative). Allow `revenueCad < 0` (legit refund). Or log a warning when units < 0 surface.

#### AUDIT-P2-03: detectOutlierDays' LOOKBACK at small N degrades from "trailing window" to "global window"
**Algorithm:** `detectOutlierDays` — `dashboard-web/src/lib/attributionAnalysis.ts:495-533`
**Issue:** The adaptive `LOOKBACK = Math.min(14, Math.max(5, Math.floor(sorted.length / 2)))` (line 508) means: at `sorted.length=8`, LOOKBACK=5, trail spans indices `i-5..i-1`; at `sorted.length=16`, LOOKBACK=8. The loop at line 509 starts at `i = LOOKBACK`. So at `sorted.length=8`, `i` ranges 5..7, checking only 3 points against a 5-day trail. Each point is checked against an OVERLAPPING window of its own neighborhood — at boundary `i=5`, the trail `[0..4]` doesn't include `sorted[5]` itself (correct), but at `i=6`, the trail `[1..5]` includes `sorted[5]` which was JUST classified as an outlier in the prior iteration. There's no carry-forward exclusion: an outlier point IS included in subsequent trails, biasing the trailing mean.
**Evidence:**
```ts
// attributionAnalysis.ts:509-510
for (let i = LOOKBACK; i < sorted.length; i++) {
  const trail = sorted.slice(Math.max(0, i - LOOKBACK), i);
  // ^^^ includes prior days regardless of outlier classification
```
**Impact:** A two-spike sequence on adjacent days under-detects: the first spike inflates the trail's mean & stddev, making the second spike's z-score smaller than it should be. The classic "outlier-robust" approach is to use median + MAD (which `insights.ts:robustZScore` does correctly at line 99). detectOutlierDays here uses mean + stdDev (non-robust).
**Fix sketch:** Two options. **(a)** Replace mean/stddev with median/MAD (mirroring `insights.ts:90-100`). **(b)** Add a cascade-prevention: once a point is flagged, exclude it from subsequent trail windows. Option (a) is cleaner and matches existing robust-stat patterns in the codebase.

#### AUDIT-P2-04: `analyzeProductChannel` skips orders where `hitMapped` is false but doesn't normalize whitespace in `productId` — Apps Script writer trims, dashboard may not
**Algorithm:** `analyzeProductChannel` — `dashboard-web/src/lib/attributionAnalysis.ts:881-922`
**Issue:** The `wantedIds.has(li.productId)` test (line 893) is exact-string match. `li.productId` comes from `parseLineItems` which does `productId: it.p` (line 174) — accepts any string. The Apps Script writer at `Shopify.gs:636` does `String(li.product_id || '')` — no trim, no normalization. If a future writer ever emits `"123 "` (with trailing space) or `" 123"` (leading space), the dashboard's `wantedIds` (Shopify product IDs from the catalog, presumably trimmed) won't match. No defensive trim.
**Evidence:** No trim or normalization at line 893 in `analyzeProductChannel`, vs. `orderMatchesCampaign` at line 122-128 which DOES trim (`order.utmId.trim() === campaign.campaignId.trim()`). Inconsistent.
**Impact:** Low-likelihood for current data, high-potential for silent corruption if a writer change introduces whitespace.
**Fix sketch:** Either (a) trim at parse time in `parseLineItems` (`productId: it.p.trim()`), or (b) trim at compare time in `analyzeProductChannel`. (a) is cheaper.

#### AUDIT-P2-05: `pearsonWithLag` doesn't check for non-finite values in the shifted output

#### AUDIT-P2-06: computeWindowStability tail-bucket logic includes the >3-day tail bucket but doesn't normalize for the shorter bucket length when computing coverage
**Algorithm:** `computeWindowStability` — `dashboard-web/src/lib/attributionAnalysis.ts:437-481`
**Issue:** The tail bucket (added when `tailDays >= 3`) is treated identically to a full 7-day bucket — coverage is `matched/meta`. But if the tail bucket has half the days of a full bucket, its meta_sum is roughly half — coverage ratio is comparable BUT the variance contribution of the tail point (only one short-window data point in `coverages[]`) gets equal weight as a full-7-day bucket in the σ calculation. A 3-day tail with a single anomalous day will skew σ much more than a single anomalous day in a 7-day full bucket.
**Evidence:** Lines 476-479 — `variance = mean of (coverages[i] - mean)²` weights all buckets equally regardless of bucket length.
**Impact:** Slight verdict instability at the boundary — a 17-day range (2 full + 3 tail) produces noisier σ than a 14-day range (2 full).
**Fix sketch:** Weight each coverage by bucket length (`tailDays / 7`), or exclude the tail bucket from variance (but include it in the displayed `windowCountWithData`). Or document the limitation. Lowest-priority.

#### AUDIT-P2-08: useCampaignTrueRevenue's productMap freshness contract is undocumented — today's mapping silently applies to historical data
**Algorithm:** `useCampaignTrueRevenue` — `dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:178-308`
**Issue:** The hook accepts `productMap` as a prop and uses it for the allocator. The productMap is stored in localStorage (`campaignProductMap.ts:55-60`) and represents the current/today's mapping. When the user views a date range like `2026-04-01..2026-04-30`, the allocator applies the **current** map to the **April** data. If a campaign was mapped to product A in April but operator changed it to product B today, the analysis says "the April campaign sold product B" — silently rewriting history.
**Evidence:** No timestamp tracking on `productMap`. Same map is applied across all date ranges.
**Impact:** Operator viewing historical data sees current-mapping-applied analyses. Year-over-year comparisons are not stable.
**Fix sketch:** Either (a) document this explicitly in the UI ("מיפוי נוכחי מוצג היסטורית"), or (b) version the map with `{ map, validFrom, validTo }` segments and use the appropriate segment per date.

#### AUDIT-P2-09: insights.ts `forecastMonthEnd` divides by `last7DaysCount` derived from `datesSeen.size` — when a store has zero rows on day-1, the calculation is off
**Algorithm:** `forecastMonthEnd` — `dashboard-web/src/lib/insights.ts:448-516`
**Issue:** `last7DaysCount = Math.max(1, datesSeen.size)` (line 493) — protects against division by zero, but `datesSeen` is built from rows that have ANY value in the window. If the multi-store fleet has different active days per store, `datesSeen` is union'd across all stores' rows (line 485-491 iterates without storeName filter). For a single-store-down day (e.g., uzoshop missed a write), the 7-day window's `datesSeen.size` is still 7 (other stores wrote), but `last7Rev` includes only the stores that did write. The daily-avg-rev is then biased low.
**Evidence:** Line 486-491 iterates `for (const r of rows)` — no per-store grouping for the 7-day average.
**Impact:** Forecast revenue is slightly under-projected during partial-fleet write days. Low-impact for a 3-store fleet, but the algorithm is fragile.
**Fix sketch:** Compute the 7-day average per-store then sum. Or use the count of unique (date, store) pairs.

#### AUDIT-P2-10: `allocateProductRevenue` uses `mappedKeys.length` for equal-split fallback but doesn't account for orphan-spend campaigns (campaigns with 0 spend that ARE in the map)
**Algorithm:** `allocateProductRevenue` — `dashboard-web/src/lib/campaignProductMap.ts:122-157`
**Issue:** When all `spendsForProduct` are 0, the fallback is `1 / mappedKeys.length` (equal split, line 149). This is the documented behavior. BUT: if 1 campaign has spend 100 and 2 campaigns have spend 0 (all in the map), `totalSpend = 100`, share for the spent campaign = 1.0, shares for the others = 0. The 0-spend campaigns get 0% even though they're mapped. This might be intentional (they didn't spend, they didn't contribute), but it conflicts with the documented edge case "If a campaign has 0 spend AND it's the only one mapped → it gets 100%" — operator might expect "if a campaign has 0 spend but is mapped, give it the equal-split share" rather than zero. The contract is ambiguous and the test coverage doesn't enforce either interpretation.
**Evidence:** Lines 146-149 — the share is exactly proportional to spend; zero-spend mapped campaigns get zero share unless ALL spends are zero. This isn't bad math, but it's a contract decision worth documenting.
**Impact:** Operator who paused a campaign sees its allocated revenue drop to 0 even though products were sold during its mapped window.
**Fix sketch:** Document the contract more clearly in the docstring. Optionally consider a hybrid: `share = (campaignSpend + epsilon) / (totalSpend + n*epsilon)` where epsilon is a small floor — keeps zero-spend campaigns from getting absolute-zero allocation. This is a product/spec decision, not a fix.
