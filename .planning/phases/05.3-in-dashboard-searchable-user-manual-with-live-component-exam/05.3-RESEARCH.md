## 3. MDX pipeline choice + rationale

**Decision: `next-mdx-remote-client/rsc@2.1.10`.** [VERIFIED: `npm view next-mdx-remote-client version` → `2.1.10`, published 2026-04-04 per `time.modified`.]

### Decision matrix

| Candidate | Version (2026-05-22) | Status | Peer deps | Bundle (client) | Verdict |
|---|---|---|---|---|---|
| **`next-mdx-remote-client/rsc`** | 2.1.10 | Active fork. ESM-only. | `react >= 19.1.0`, `react-dom >= 19.1.0`, node ≥ 20.9 | 1.3 KB gz client runtime (3.7 KB raw) [VERIFIED: bundlephobia API] | **CHOSEN** |
| `next-mdx-remote` | 6.0.0 (archived) | **Archived 2026-04-09** by hashicorp [CITED: README banner]. No further React 19 / Next 15 fixes. | `react >= 16` | 8.3 KB gz | Rejected — stale, archived |
| `@next/mdx` | 16.2.6 | Active. Next-native. File-extension-based (`.mdx` files become pages). | `@mdx-js/react >= 0.15`, `@mdx-js/loader >= 0.15` | 0 KB on client (compiled at build) | Rejected — see below |
| `mdx-bundler` | 10.x | Active. Heavier — uses esbuild at runtime. | varies | ~30 KB+ runtime | Rejected — overkill |
| `@mdx-js/mdx` (raw) | 3.x | Active. Lower-level. Build your own pipeline. | — | varies | Rejected — re-inventing the wheel |

### Why not `@next/mdx`

`@next/mdx` is more "Next-native" but the fit is worse for our specific case:

1. **It treats `.mdx` files as pages or imports.** Our manual lives at `/Users/dorperetz/script-roas/docs/ROAS-Dashboard-User-Manual.md` — outside `src/`. To use `@next/mdx`, the manual would need to be moved into `src/` (or imported by relative path) AND renamed to `.mdx` OR `next.config.ts` would need `extension: /\.(md|mdx)$/` regex [CITED: Next.js MDX guide §"Handling `.md` files"]. The manual is also referenced from the GSD pre-push gate ("update manual when behaviour changes") — moving the file breaks every grep operators do today.
2. **It requires `mdx-components.tsx` at project root.** Required convention [CITED: Next.js MDX guide §"Add an mdx-components.tsx file"]. That file is a global component registry — putting our 5 `Manual*Example` components in a global registry pollutes the project for one feature.
3. **Frontmatter is NOT supported out of the box.** Either `gray-matter` (extra package) or a remark plugin chain is needed [CITED: Next.js MDX guide §"Frontmatter"].
4. **Tables require `remark-gfm`** anyway. Same as next-mdx-remote-client.

`@next/mdx` makes sense for projects with MANY MDX pages (a docs site, a blog with dozens of posts). For ONE long manual that lives outside `src/`, `next-mdx-remote-client` is leaner.

### Why `next-mdx-remote-client` over the archived `next-mdx-remote`

Identical API for our use case (`<MDXRemote source={...} options={...} components={...} />`), but:
- React 19 + Next 15 are explicitly supported [VERIFIED: README §"Important Caveats"]
- `parseFrontmatter: true` option built in — no need to install `gray-matter` or chain `remark-frontmatter` [VERIFIED: README §"Handling Frontmatter"]
- Maintainer (ipikuka) ships updates approximately every 6 weeks per npm publish history

### Architecture: server-renders-MDX, client-hosts-tab

`MDXRemote` from `/rsc` is an **async React Server Component** [CITED: next-mdx-remote-client README]. Our `Dashboard.tsx` is `'use client'` (line 1; verified all 41 components in `dashboard-web/src/components/` are client components — `grep -ln "'use client'" *.tsx | wc -l` returns 41 of 41). A client component **cannot directly render** a server async component. The required topology:

```
app/page.tsx                            (Server Component — has access to fs)
 │
 ├─ read docs/ROAS-Dashboard-User-Manual.md from disk
 ├─ parse frontmatter via next-mdx-remote-client's parseFrontmatter:true
 ├─ <Suspense>
 │   <MDXRemote source={mdString} components={components} options={...} />
 │  </Suspense>                         (renders the prose as ReactNode on server)
 │
 └─ <Dashboard manualSlot={the-prose-react-node} />
       │                                (Client Component)
       │
       └─ when activeTab === 'manual':
              <ManualTab manualSlot={manualSlot} />
                 │
                 ├─ <ManualSearchBar />  (filters DOM via Fuse.js)
                 ├─ {manualSlot}         (the pre-rendered prose)
                 └─ <ManualFooter />
```

This pattern requires modifying `app/page.tsx` from its current 5-line shape (`return <Dashboard />`) to a 30-50 line server component. Existing `app/page.tsx`:

```tsx
// /Users/dorperetz/script-roas/dashboard-web/src/app/page.tsx (current — full file)
import { Dashboard } from '@/components/Dashboard';

export default function Home() {
  return <Dashboard />;
}
```

Becomes (proposed shape; final spelling deferred to plan):

```tsx
// app/page.tsx (new — Server Component reads MD + invokes MDXRemote, passes node down)
import { readFile } from 'node:fs/promises';
import path from 'node:path';
import { MDXRemote } from 'next-mdx-remote-client/rsc';
import remarkGfm from 'remark-gfm';
import rehypeSlug from 'rehype-slug';
import rehypeAutolinkHeadings from 'rehype-autolink-headings';
import { Dashboard } from '@/components/Dashboard';
import { manualComponents } from '@/components/manual-examples/manualComponents';

export default async function Home() {
  const mdPath = path.join(process.cwd(), '..', 'docs', 'ROAS-Dashboard-User-Manual.md');
  const source = await readFile(mdPath, 'utf-8');
  const manualNode = (
    <MDXRemote
      source={source}
      components={manualComponents}
      options={{
        parseFrontmatter: true,
        mdxOptions: {
          remarkPlugins: [remarkGfm],
          rehypePlugins: [rehypeSlug, [rehypeAutolinkHeadings, { behavior: 'wrap' }]],
        },
      }}
    />
  );
  return <Dashboard manualSlot={manualNode} />;
}
```

Note: the `..` in `path.join(process.cwd(), '..', 'docs', ...)` is because the dashboard runs from `/Users/dorperetz/script-roas/dashboard-web/`, and the manual lives at `/Users/dorperetz/script-roas/docs/`. **Verify this path resolution on Vercel** — Vercel may run the build from `dashboard-web/` with `process.cwd()` pointing inside it, OR from the repo root. (Pitfall #7.)

## 4. Fuzzy search choice + rationale

**Decision: `Fuse.js@7.3.0`.** [VERIFIED: `npm view fuse.js version` → `7.3.0`, modified 2026-02-12.]

### Bundle size — hard numbers from Bundlephobia API (2026-05-22)

| Library | Version | gz | Raw min | Dependencies | Hebrew support |
|---|---|---|---|---|---|
| **Fuse.js** | 7.3.0 | **8.3 KB** (8259 B) | 23.7 KB (23662 B) | 0 | Yes (Bitap, Unicode-aware) [CITED: fusejs.io]. CJK/Hebrew/Arabic/Cyrillic/Greek handled by default. |
| MiniSearch | 7.2.0 | 5.8 KB (5814 B) | 17.8 KB | 0 | Tokenization not Hebrew-tuned by default; needs custom `tokenize` |
| FlexSearch | 0.8.212 | 16.4 KB (16810 B) | 50.0 KB | 0 | Tokenization English-biased; needs custom encoder for Hebrew |
| Lunr | (not benchmarked) | ~28 KB | — | 0 | Needs stemmer plugin per language |

[VERIFIED: `curl -sL "https://bundlephobia.com/api/size?package=fuse.js@7.3.0"` → `{"gzip":8259, ...}` and matching calls for minisearch + flexsearch. Live API queries, 2026-05-22.]

### Why Fuse.js over the lighter MiniSearch

MiniSearch saves 2.5 KB gz but pays for it with:
1. **No bitap fuzzy matching.** MiniSearch supports prefix + fuzzy distance but ignoreLocation behavior differs — operator typos like `Pixxel` → `Pixel` work cleanly under Fuse but require explicit `fuzzy: { maxFuzzy: 0.2 }` tuning on MiniSearch.
2. **Hebrew tokenization is English-centric.** MiniSearch's default tokenizer splits on `\W+` which is fine for Latin scripts but treats Hebrew niqqud (vowel marks, if present) and English-Hebrew word boundaries unevenly. Fuse.js doesn't tokenize the query string by default at all — it does character-level fuzzy matching across the whole field which is what we want for "find this Hebrew phrase or this English brand term inside body text".
3. **CONTEXT.md §2 already locked Fuse.js by name.** No reason to break it for 2.5 KB.

### Recommended Fuse options for this codebase

```ts
import Fuse from 'fuse.js';

// Build the search corpus from the MDX AST (or from the rendered DOM
// post-mount — see Pattern #3 below). Each entry is one heading-bounded
// section.
type ManualSection = {
  id: string;        // matches the heading's rendered id (rehype-slug output)
  level: 1|2|3|4;    // heading level
  heading: string;   // heading text
  body: string;      // joined paragraph text + table cell text + list items, stripped
};

const fuse = new Fuse(sections, {
  keys: [
    { name: 'heading', weight: 0.7 },  // heading match beats body match
    { name: 'body',    weight: 0.3 },
  ],
  threshold: 0.35,        // default is 0.6 (too lax for a manual that's 2800 lines)
  ignoreLocation: true,   // match anywhere in the string, not just near the start
  includeMatches: true,   // returns matchIndices for inline <mark> highlighting
  minMatchCharLength: 2,  // single-character matches are too noisy
  useExtendedSearch: false,
});
```

`threshold: 0.35` is the most common "documentation-search" sweet spot in published examples; the default `0.6` is too lax for a Hebrew manual where short matches against generic words cause cascading false positives. Tune in Plan 3 with real operator queries.

### Highlighting via match indices

`includeMatches: true` returns `matches: [{ indices: [[start, end], ...], key, value }]` per result. The plan's task 3.3 should wrap the matched character ranges in `<mark>` at render time. **Do not regex-replace the source MD** — wrap the result of Fuse's match indices after the prose has been rendered to React nodes. Pattern: walk the rendered DOM via a ref, find text nodes that include the matched string, wrap with `<mark>` using `Range.surroundContents()`. Alternative (cleaner): pre-compute, at MDX-render time, a map of `sectionId → matchSubstrings` and inject `<mark>` directly into the body text in the MDX components map (override `p`, `li`, `td`, etc.). The DOM walk is simpler; the AST injection is more "React-idiomatic".

## 7. Pitfalls (this codebase, specifically)

Numbered list, in order of likely-to-bite-the-implementer:

### Pitfall #1 — Tailwind content glob doesn't see the manual file

**File:** `dashboard-web/tailwind.config.ts` line 14:
```
content: ['./src/**/*.{js,ts,jsx,tsx,mdx}'],
```

The manual lives at `/Users/dorperetz/script-roas/docs/ROAS-Dashboard-User-Manual.md` — **outside `dashboard-web/src/`**. The `.md` extension is also not in the glob. **Today this is fine** because the manual contains zero Tailwind classes ([VERIFIED: `grep "className=" docs/ROAS-Dashboard-User-Manual.md` returns nothing]). But if a future maintainer drops `<div className="text-roas-green">` inside the MDX, Tailwind will silently purge those classes from the production CSS and the styling will only work in dev. **Mitigation:** keep the manual class-free (rely on `.roas-manual-prose` rules in `globals.css`) AND optionally extend the content glob to `'../docs/**/*.md'` defensively. Document this rule in Plan 1.

### Pitfall #2 — `Dashboard.tsx` is `'use client'`; `<MDXRemote/>` from `/rsc` is async-server

Every file in `dashboard-web/src/components/` is a client component [VERIFIED: `grep -ln "'use client'" components/*.tsx | wc -l` returns 41 of 41]. `MDXRemote` from `next-mdx-remote-client/rsc` is an **async React Server Component** and cannot be rendered directly inside a `'use client'` boundary [CITED: README]. You must:

1. Render `<MDXRemote/>` in `app/page.tsx` (which is a Server Component today).
2. Capture the resulting JSX as a `ReactNode`.
3. Pass it as a prop into `<Dashboard manualSlot={node} />`.
4. `Dashboard` passes it down to `<ManualTab manualSlot={node} />`.
5. `ManualTab` renders `{manualSlot}` only when `activeTab === 'manual'`.

Failing to do this surfaces as a build-time error: `"async client Component"`. The mitigation must be in the plan from Plan 1 onwards.

### Pitfall #3 — `urlState.ts` TAB_VALUES Set is the silent gate

If you add `'manual'` to `Dashboard.tsx` but forget `urlState.ts:24-26`, the URL `?tab=manual` will be read by `readDashboardState`, fail the `TAB_VALUES.has(rawTab)` check, fall through to the default (`'home'`), and `setActiveTab('home')` will happen on mount. The bug presents as "I refresh the page on the manual tab and it bounces me to home." Affects: refresh, bookmark, share URL. This is the single highest-risk single-line change for a silent regression. **Add an explicit unit test** in Plan 1 that does `readDashboardState({...}, '?tab=manual')` and asserts `result.tab === 'manual'`.

### Pitfall #4 — `VERCEL_GIT_COMMIT_SHA` is server-only; client footer needs `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA`

[CITED: https://github.com/vercel/community/discussions/56 — Vercel system env vars are exposed to the server by default; to expose to the client bundle, set a separately-named `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` in the Vercel dashboard with the same value.] In dev (no Vercel), neither exists. const sha = process.env.NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA
  ?? process.env.VERCEL_GIT_COMMIT_SHA  // works if footer is server-rendered
  ?? 'dev';

### Pitfall #6 — `?tab=manual` initial URL with auto-focus on search input

UI-SPEC §Search Match Highlight ("On initial tab activation (`?tab=manual` URL), the search input gets `autofocus`") interacts with React 19's `useState(() => readDashboardState(...).tab)` initializer. The initializer runs SSR-disabled (it gates on `typeof window === 'undefined'`). When SSR renders, activeTab is `'home'`. When the client hydrates, activeTab flips to `'manual'`. If `<input autoFocus>` is on the search input, React 19 will auto-focus on the FIRST mount, which is AFTER hydration — so this works. BUT: setting `autoFocus` on an `<input type="search">` inside an RTL `<html dir="rtl">` parent has been historically buggy in Safari 16 [low-confidence anecdotal — no recent benchmark]. Mitigation: don't use the HTML `autoFocus` attribute; use `useEffect(() => { ref.current?.focus(); }, [])` inside `ManualSearchBar` so the focus runs after layout (and only when `activeTab === 'manual'`).

### Pitfall #7 — `process.cwd()` may differ between Vercel build and local dev

The proposed `app/page.tsx` does `path.join(process.cwd(), '..', 'docs', 'ROAS-Dashboard-User-Manual.md')`. On Vercel, `process.cwd()` at build/server-start time depends on the project's `Root Directory` setting in the dashboard. If the Vercel project is configured with `Root Directory: dashboard-web`, then `process.cwd()` is `/vercel/path0/dashboard-web/` and the `..` resolves to `/vercel/path0/` — correct. But if the operator ever changes that to `Root Directory: .` (root), the path breaks.

**Safer pattern:** put the manual symlink (or a copy at build time) under `dashboard-web/src/content/manual.md` and import the file with a relative path. Tradeoff: violates the existing "manual is at `docs/`" convention. **Recommended:** keep the manual where it is + add a build-time check that throws a clear error if the file can't be found:

```ts
const mdPath = path.join(process.cwd(), '..', 'docs', 'ROAS-Dashboard-User-Manual.md');
const source = await readFile(mdPath, 'utf-8').catch((e) => {
  throw new Error(
    `Manual file not found at ${mdPath} (cwd=${process.cwd()}). ` +
    `Check Vercel Root Directory setting — should be 'dashboard-web/'.`
  );
});
```

### Pitfall #8 — Search across 2800-line MD will block the main thread if naïve

Building the Fuse index from the FULL rendered prose at every keystroke would re-walk the DOM and re-tokenize the same 2800 lines repeatedly. Mitigation pattern (well-supported by Fuse):

1. **Build the index ONCE** on `ManualTab` mount (inside a `useMemo`), keyed by the rendered MD section list.
2. **Debounce search input by 120ms** before calling `fuse.search(query)`.
3. **Cap result render to top 50 sections** — for a 2800-line manual with the query `e` (a single char), every section matches.

Existing project pattern for debouncing: `dashboard-web/src/lib/utils.ts` does not export a debounce helper [VERIFIED via `grep -n debounce utils.ts` returns nothing]. Plan 3 needs to either inline a 5-line debouncer or add a `debounce()` to `utils.ts` (preferred — `safeDecode` was added there per Phase 2 patterns).
