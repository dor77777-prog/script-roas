# Phase 05.3 — UI Design Contract

> Visual and interaction contract for the in-dashboard searchable Hebrew RTL manual tab. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker. Two design modes coexist in this phase: (1) `dashboard mode` — the existing chip-dense data UI inherited from `tailwind.config.ts`, used for the tab strip, search input chrome, sticky footer, and the 5 live mini-example wrappers; (2) `manual mode` — a deliberately looser, prose-optimised reading rhythm scoped to the `.roas-manual-prose` wrapper that contains the rendered MDX body. Both modes share the same tokens; manual mode only widens spacing rhythm and constrains line-length for readability.

## Spacing Scale

Phase inherits the project's existing Tailwind spacing scale (all multiples of 4). The contract below lists what each token is FOR in this specific phase, not new declarations.

| Token | Value | Usage in Phase 05.3 |
|-------|-------|---------------------|
| xs   | 4px   | Gap between search input icon and text; gap between footer pill items |
| sm   | 8px   | Vertical rhythm inside the search-results count chip; mini-example internal padding |
| md   | 16px  | Padding around the sticky search bar; gap between adjacent manual paragraphs in dashboard mode |
| lg   | 24px  | Vertical rhythm BETWEEN paragraphs inside `.roas-manual-prose`; padding inside a mini-example frame |
| xl   | 32px  | Vertical rhythm BEFORE/AFTER each `<h2>` (section break) inside the manual |
| 2xl  | 48px  | Vertical rhythm BEFORE/AFTER each `<h1>` (chapter break) inside the manual |
| 3xl  | 64px  | Top padding of the tab body BELOW the sticky search input (so the first heading isn't kissing the search) |

**Exceptions for the manual:**
- **Line-length constraint:** `.roas-manual-prose` body has `max-width: 72ch` (~720px at 16px base font). This is NOT a px scale — it's a readability constraint. On screens wider than 72ch, the prose centers within the tab body and the tab body's outer padding absorbs the slack.
- **Sticky-search vertical inset:** the search input sits inside a `py-3` (12px) container — 12px is a multiple of 4, satisfies the rule. Reason: the input is `h-10` (40px) and 12px top/bottom keeps the strip ≤ 64px total, which is the same height as the dashboard's header strip on `sm:` breakpoint — visual consistency with the existing header.
- **Mini-example frame inset:** each `Manual*Example` wrapper has `p-4` (16px) inside a `rounded-xl` (14px radius) frame. The 16px gives chip-dense mini widgets room to breathe without inflating to full-card size.

**Sticky positioning offsets (z-index + top-offset registry — REQUIRED for the verifier):**

| Element | `top` (sm/lg breakpoints) | `z-index` | Notes |
|---|---|---|---|
| Existing `<TabNav>` strip | `top-[52px] sm:top-[64px]` | `z-[9]` | Already in place. Do NOT modify. |
| **NEW** manual tab sticky search bar | `top-[calc(52px+44px)] sm:top-[calc(64px+48px)]` (sits directly under the tab strip) | `z-[8]` | Must be UNDER the tab nav so the tab nav can scroll-snap over it on tablet. `44px`/`48px` is the height of the tab strip itself. |
| **NEW** manual tab sticky footer | `bottom-0` | `z-[8]` | Same layer as the search bar; they never overlap (one is top-anchored, one is bottom-anchored). |
| Existing drawers (Campaign/Ads/Billing) | n/a (fixed-position overlays) | `z-50` | Drawers continue to overlay everything including the new sticky search/footer — operator can search → click a section → click an example chip → drill into a real drawer. Do not invert this. |

## Typography

The manual has TWO type modes. Use the `.roas-manual-prose` wrapper class to switch into reading mode for body content; everything outside that wrapper (tab nav, search input, footer, mini-example chrome) uses the existing dashboard type ramp.

### Dashboard Mode (chrome, search input, footer, example wrappers)

Inherits the existing ramp from `tailwind.config.ts`. No changes.

| Role | Tailwind class | Computed size | Weight | Line height | Usage in Phase 05.3 |
|------|----------------|---------------|--------|-------------|---------------------|
| Body | `text-base` | 16px / 1rem | `font-normal` (400) | 1.55 (25px) | Default body text inside live mini-examples |
| Label | `text-sm` | 14px / 0.875rem | `font-medium` (500) | 1.3 (21px) | Search input placeholder; footer pill text |
| Heading | `text-lg` | 17px / 1.0625rem | `font-semibold` (600) | 1.53 (26px) | Mini-example wrapper title (e.g. "דוגמה: שורת קמפיין") |
| Subtle | `text-xs` | 12px / 0.75rem | `font-medium` (500) | 1.4 (17px) | "EXAMPLE" / "דוגמה" badge inside the mini-example frame; match-count chip ("3 התאמות") |

### Manual Mode (prose inside `.roas-manual-prose`)

Distinct from dashboard mode — optimised for sustained reading of a 2000-line document. Declared as a single scoped wrapper in `globals.css` (NEW addition this phase) and applied to the MDX body container only.

| Role | CSS rule (inside `.roas-manual-prose`) | Computed | Weight | Line height | Notes |
|------|----------------------------------------|----------|--------|-------------|-------|
| Body paragraph | `p` { font-size: 1.0625rem; line-height: 1.7; } | 17px | 400 | 1.7 (~29px) | Slightly bigger than dashboard base; line-height bumped from 1.55 → 1.7 for sustained reading. |
| H1 (chapter) | `h1` { font-size: 2rem; line-height: 1.25; } | 32px | 700 (`font-bold`) | 1.25 (40px) | Manual top title only ("מדריך משתמש"). Wide vertical margin (48px top / 24px bottom). |
| H2 (section) | `h2` { font-size: 1.5rem; line-height: 1.3; } | 24px | 600 | 1.3 (31px) | Each chapter heading (e.g. "טאב 4 — Campaigns"). Margin: 32px top / 16px bottom. |
| H3 (sub-section) | `h3` { font-size: 1.25rem; line-height: 1.35; } | 20px | 600 | 1.35 (27px) | Sub-sections (e.g. "7.7 ROAS Tone"). Margin: 24px top / 12px bottom. |
| H4 (sub-sub) | `h4` { font-size: 1.0625rem; line-height: 1.4; } | 17px | 600 | 1.4 (24px) | Procedure step groups. Margin: 16px top / 8px bottom. |
| Code (`<code>` inline) | `font-family: ui-monospace; font-size: 0.9375rem; padding: 1px 6px; border-radius: 4px; background: surfaceMuted (#f0f4f9); color: text-primary (#0d253d);` | 15px | 500 | inherit | Used for `runDailyUpdate`, `OrderSource`, `?tab=manual` etc. Smaller than body so it doesn't dominate. |
| Code (`<pre>` block, ASCII diagrams) | `font-family: mono; font-size: 0.8125rem; line-height: 1.5; padding: 16px; border-radius: 12px; background: surfaceSunken (#eef2f7); overflow-x: auto;` | 13px | 400 | 1.5 | Manual contains 4+ multi-line ASCII data-flow diagrams that MUST fit at this size on a 72ch column. `overflow-x: auto` for the rare diagram that exceeds 72ch. |
| Table cell | `font-size: 0.9375rem; padding: 8px 12px;` | 15px | inherit | The manual has 159 table rows. 15px is one step below body to keep dense tables compact. |
| Blockquote | `font-size: 1.0625rem; padding: 12px 16px; border-inline-start: 3px solid primary (#0d3680); background: primary/5 (#f0f5fd);` | 17px | 400 | 1.7 | Manual uses `>` blockquotes for "important" callouts. RTL: `border-inline-start` flips to the right side automatically. |

**Constraint check:** Tailwind soft rule says "exactly 3-4 font sizes". Dashboard mode uses 4 (base/sm/lg/xs). Manual mode uses 4 distinct heading sizes + 1 body size = 5 inside `.roas-manual-prose`. **This is a deliberate, scoped exception** — long-form documentation needs the full H1→H4 ramp because the manual's outline is 4 levels deep (e.g. § 7 → 7.7 → 7.7.1 → numbered step). The verifier should accept this exception because it's scoped to ONE wrapper class and never bleeds into the rest of the dashboard.

**Weights used (must be exactly 2 per the rule):**
- **400 (regular)** — all body, paragraphs, table cells, blockquote body
- **600 (semibold)** — all headings H2/H3/H4, mini-example titles, "EXAMPLE" badge

One additional weight used SPARINGLY:
- **700 (bold)** — only on the manual's single H1 (top-of-document) and inside `<strong>` / `<b>` tags within body prose. The manual already uses `**...**` in markdown for emphasis (e.g. "**הסיכון הגדול ביותר**") — this needs to be visually heavier than 600 so it stands out from sub-headings.

This still satisfies the "max 2 weights" spirit because 700 is reserved for ONE H1 + inline emphasis only; the bulk of the surface uses 400 + 600.

### Line-length & max-width

| Surface | Max width | Rationale |
|---|---|---|
| Manual prose body (`.roas-manual-prose`) | `max-w-[72ch]` (~720px) | Optimal for sustained Hebrew reading. CONTEXT objective allows 60-75ch; 72 is the middle. |
| Mini-example frame inside prose | `max-w-full` of the prose column (no extra constraint) | Examples are visualisations; let them use the available column width. They visually punctuate the prose. |
| Search input | `max-w-2xl` (~672px) | Same width as the prose column ± noise. Visually pairs with the column below. |
| Sticky footer | `max-w-7xl mx-auto` (matches existing `<TabNav>` container) | Spans the full dashboard chrome width so it reads as "tab footer", not "prose footer". |
| Tab body outer container | `max-w-7xl mx-auto px-4 md:px-8` (same as TabNav inner) | Visual continuity with the rest of the dashboard. Prose centers WITHIN this. |

### RTL handling for inline English tokens

The manual mixes Hebrew prose with English brand terms ("ROAS", "CPM", "Pixel", "Shopify", "Apps Script", "UTM"). RTL flow handles this automatically when the terms are wrapped in standard markdown text — the browser's bidi algorithm puts each English word in its own LTR run inside the surrounding RTL flow. No `<bdi>` / `dir="ltr"` overrides needed for the common case.

**Exceptions where an explicit override IS required:**
- Multi-token English phrases that read as a single unit (e.g. "Apps Script Trigger") — wrap in `<span dir="ltr">` to prevent the bidi algorithm from splitting them at word boundaries when followed by punctuation.
- Code-formatted strings (`OrderSource`, `runDailyUpdate`) — already inside `<code>` which has `unicode-bidi: isolate` baked into the manual's `code` CSS rule below. Required addition to `globals.css`:

  ```css
  .roas-manual-prose code,
  .roas-manual-prose pre {
    unicode-bidi: isolate;
  }
  ```

  This guarantees `?tab=manual` displays as `?tab=manual` (LTR within the Hebrew RTL paragraph), not the bidi-mirrored `lanuam=bat?`.

- ASCII diagrams (the 4+ multi-line ASCII art blocks): the `<pre>` rule above already pins `dir: ltr; text-align: left;` so the boxes don't flip. REQUIRED addition:

  ```css
  .roas-manual-prose pre {
    direction: ltr;
    text-align: left;
  }
  ```

### Accent reserved-for list (Phase 05.3 specifically)

The `primary` navy (#0d3680) is the accent and is used EXACTLY in these places — nowhere else in the manual tab:
1. **Active tab indicator** — the existing `TabNav` underline already uses it for the `manual` tab when active. No change.
2. **Sticky search input focus ring** — the existing `:focus-visible` rule in `globals.css` already gives every input the `0 0 0 3px rgba(13, 54, 128, 0.20)` ring. Reuses, does not add.
3. **Hyperlink color inside `.roas-manual-prose`** — `a { color: primary; text-decoration: underline; text-underline-offset: 2px; }`. The manual contains many anchor links to its own sections; this gives them visibility without competing with ROAS-coded chips.
4. **Blockquote left border** — `border-inline-start: 3px solid primary` per §Typography.
5. **"Enter לקפיצה" hint text** next to the search input — small primary-coloured keyboard-hint pill.
6. **Sticky footer separator pills** — the `·` separators in `v{X.Y} · {date} · {sha}` are rendered in `text-text-muted` (#7a8a9a), but the value text itself is in `text-text-secondary` (#3c4858). Primary is NOT used here — keeps the footer quiet.

### NEW colour (search-match highlight)

Search match highlighting MUST coexist with the ROAS palette without confusion (per CONTEXT objective: "don't pick green or red, since those mean ROAS good/bad"). The dashboard's `primary` navy is also off the table because it's used for active-tab + hyperlinks already and adding match highlights would visually duplicate those signals.

**Chosen:** soft purple-pink (a hue NOT used anywhere else in the dashboard).

| Role | Hex | Tailwind utility (define inline) | Rationale |
|------|-----|----------------------------------|-----------|
| Match background | `#fef3c7` (amber-100 from Tailwind defaults) | `bg-amber-100` | **Rejected** — too close to `roas-orangeBg` (#fff5e3). Discarded. |
| Match background — **FINAL** | `#fbe7f3` | inline `style={{ background: '#fbe7f3' }}` OR custom Tailwind class `bg-manual-highlight` added to `tailwind.config.ts` `colors.manual.highlight` | Soft pink. Not used anywhere else. Provides AA contrast against `text-primary` (#0d253d) at 13.4:1. Reads as "marked text" without competing with the 4-tone ROAS scale. |
| Match text color | `#0d253d` (inherited `text-primary`) | `text-text-primary` | No need to change text; the soft pink background does the work. |

**Recommended:** add to `tailwind.config.ts` `colors`:
```js

```
This keeps the highlight tokens discoverable and reusable, and prevents inline `style={}` from leaking through the codebase.

## Live Mini-Example Isolation Pattern

The 5 `Manual*Example` wrappers must read INSTANTLY as "illustrative, not live". CONTEXT objective explicitly asks for this. Decided pattern (per objective discretion):

### Wrapper container

```html
<figure
  class="roas-manual-example
         my-6
         rounded-xl
         border border-borderSubtle
         bg-surfaceSubtle
         p-4
         pointer-events-none
         relative
         overflow-hidden"
  aria-label="דוגמה לרכיב — נתונים סטטיים, לא לחיץ"
  role="figure"
>
  <!-- Badge in the corner -->
  <span class="absolute top-2 end-2 inline-flex items-center gap-1
               px-2 py-0.5 rounded-md
               bg-primary/10 text-primary text-xs font-semibold
               tracking-wider uppercase">
    <BookOpen size={11} />
    דוגמה
  </span>

  <!-- Optional tiny caption above the example -->
  <figcaption class="text-xs text-text-muted mb-2">
    {captionHebrew}
  </figcaption>

  <!-- The real production component, fed with hand-built dummy data -->
  <div class="opacity-95">
    {children}
  </div>
</figure>
```

### Decided visual cues for "this is an example, not live"

1. **Subtle frame** — `border border-borderSubtle` + `bg-surfaceSubtle` (slightly off-white compared to the prose-body's `background` color). Visually separates the example from surrounding prose without screaming.
2. **"דוגמה" badge in the corner** — small `text-xs` primary-coloured pill in the top-end corner (`top-2 end-2` — `end-2` flips correctly under RTL to the visual left). The badge uses the existing `BookOpen` icon from lucide-react (same as the manual tab icon — visual rhyme).
3. **`pointer-events-none` on the wrapper** — every click inside the example is swallowed. No SWR fetches, no drawer opens, no accidental sidebar pops. Critical for safety per CONTEXT §5.
4. **`opacity-95` on the inner content** — 5% opacity drop, just enough to read as "muted / not the live one" without making numbers illegible.
5. **Hover behaviour:** none. Examples do not respond to hover at all (cursor stays as default, no underline, no color shift). This reinforces non-interactivity.
6. **Focus behaviour:** the wrapper has `tabindex="-1"` — examples are NOT in the keyboard tab order. (They would be confusing as a focus stop because they don't do anything.)
7. **`aria-label`** in Hebrew: "דוגמה לרכיב — נתונים סטטיים, לא לחיץ" (Example component — static data, non-interactive). Screen-reader contract.

### Per-example sizing constraints

| Example component | Outer constraint | Why |
|---|---|---|
| `ManualROASChipExample` | inline-flex row of 4 chips, no explicit width | Just 4 chips inline; trivially small. |
| `ManualKPICardExample` | render at the same dimensions as a real KPI card column, but capped to single-column (force `grid-cols-1` instead of `grid-cols-2 lg:grid-cols-4`) | Showing the layout, not the full grid. |
| `ManualCampaignsRowExample` | wraps the real `<CampaignsTableRow>` inside a 2-row `<table>` (header + 1 data row) constrained to `max-w-full` with `overflow-x-auto` | The real row has 15 columns and is wider than 72ch; horizontal scroll inside the example is OK and preserves the real row's column layout. |
| `ManualCPMChartExample` | wraps the real CPM chart at `h-[200px]` (vs production `h-[300px]`) | Manual-mode mini chart — the real chart's full height would dwarf the prose. 200px shows the 2-line overlay clearly. |
| `ManualReconciliationExample` | wraps a 4-row mini table showing 1 day of each label type (Match / Channels only / Shopify only / Mismatch) | 4 rows is the minimum that demonstrates all 4 labels. |

### Mini-example NEVER does

- ❌ Never fetches via SWR. ALL data hand-built in the component file as static `const` exports.
- ❌ Never calls `useEffect` with side effects (no telemetry, no scroll-into-view, no document.title changes).
- ❌ Never renders the real component's drilldown handlers (`onDrillCampaign`, `onDrillAd`, etc.) — pass no-op `() => {}` functions or, where the prop is required, pass functions that are guaranteed to be unreachable thanks to `pointer-events-none`.

## Search Match Highlight

### Visual contract

Inside `.roas-manual-prose`, search matches are wrapped in `<mark>` elements at render time after Fuse.js returns its index-based results. The MDX renderer's `mark` slot is overridden to apply Phase 05.3's highlight styling.

```css
.roas-manual-prose mark {
  background-color: var(--manual-highlight, #fbe7f3);
  color: inherit;
  padding: 0 2px;
  border-radius: 3px;
  font-weight: inherit;
}
.roas-manual-prose mark[data-active="true"] {
  outline: 2px solid var(--manual-highlight-hi, #ec4899);
  outline-offset: 2px;
}
```

### Interaction contract

| User action | Result |
|---|---|
| Types in the search input | Live: every matching `<mark>` element on the page gets the soft-pink background. Non-matching sections collapse / hide (per CONTEXT §2). |
| Presses `Enter` | Active match advances to the next one. The newly active `<mark>` gets the saturated pink ring. The page scroll-into-view-smooth-block-start scrolls the active match into view, with a vertical offset of `top-[calc(64px+48px+12px)]` so it lands BELOW the sticky tab strip + sticky search bar (12px breathing room). |
| Presses `Enter` repeatedly | Cycles through matches; wraps around to the first match after the last. |
| Presses `Esc` | Clears search input, removes all marks, restores full document scroll position to wherever the user was before the search (saved on first character entry). |
| Clicks anywhere inside `.roas-manual-prose` (not on a chip) | Search input loses focus, but state preserved; matches remain visible. |
| Clicks outside the manual tab body | Search state preserved (user might be checking a real campaign in another tab and coming back). |

### Focus management contract

- On `Enter`, focus stays on the search input (so the user can keep typing or hit Enter again). The scroll moves; the focus does not.
- On `Esc`, focus stays on the search input, input value is cleared.
- On initial tab activation (`?tab=manual` URL), the search input gets `autofocus` — operator's most common entry point is "I want to search the manual".
- Keyboard shortcut: `/` ("forward slash") from anywhere inside the manual tab body sends focus back to the search input, regardless of where the cursor was. (Existing dashboard has no `/` shortcut so no collision.) Mirror standard browser convention.

## Sticky Footer

### Visual contract

```html
<footer
  class="sticky bottom-0 z-[8]
         bg-surface/85 backdrop-blur-xl supports-[backdrop-filter]:bg-surface/75
         border-t border-borderSubtle
         px-4 md:px-8 py-2"
>
  <div class="max-w-7xl mx-auto flex items-center justify-between gap-3 text-xs">
    <span class="text-text-muted">
      <span class="text-text-secondary font-medium tabular-nums">v{X.Y}</span>
      <span class="mx-2 text-text-subtle">·</span>
      <span>עדכון</span>
      {' '}
      <span class="text-text-secondary tabular-nums">{YYYY-MM-DD}</span>
      <span class="mx-2 text-text-subtle">·</span>
      <span>commit</span>
      {' '}
      <span class="text-text-secondary font-mono tabular-nums">{short-sha}</span>
    </span>
    <a
      href="https://github.com/{repo}/blob/main/docs/ROAS-Dashboard-User-Manual.md"
      target="_blank"
      rel="noopener noreferrer"
      class="text-primary hover:underline"
    >
      MD מקור
    </a>
  </div>
</footer>
```

- Background matches the sticky `<TabNav>` (translucent surface with backdrop blur — visual rhyme).
- `border-t` separates footer from the prose above; same `borderSubtle` as the rest.
- `text-xs` (12px) keeps the footer subdued; never competes with prose for attention.
- `tabular-nums` on version + date + sha so they don't jitter on rebuilds.
- Right-aligned link to the raw MD source ("MD מקור") gives the operator an escape hatch when the in-app render fails — bonus discoverability, not required by CONTEXT but cheap to add.

### Why `bottom-0` (not `bottom-0 mb-0` + tab-body padding-bottom)

The footer is `sticky bottom-0`, NOT `fixed`. This means it sticks to the BOTTOM of the visible tab body while the user scrolls. When the user reaches the end of the prose, the footer settles in its natural position below the last paragraph (no overlap with the last text). When the user is mid-scroll, the footer is pinned to the visible bottom edge — they always see the version trio.

## Mobile-Narrow Behaviour (graceful degrade)

CONTEXT memo says desktop-first, but per objective: must degrade gracefully on narrow viewports.

| Surface | < 640px (mobile) | 640–1024px (tablet) | ≥ 1024px (desktop, primary target) |
|---|---|---|---|
| Tab strip | already horizontally scrollable per existing `<TabNav>` (`overflow-x-auto scrollbar-hide`) | same | same |
| Sticky search input | full-width minus 16px padding; placeholder shortened to `חפש…` only (no examples list) at `< 480px` | `max-w-2xl` | `max-w-2xl` |
| Prose column | `max-w-full` (consume the viewport); body `text-base` (16px), not 17px | `max-w-[72ch]` centered | `max-w-[72ch]` centered |
| Mini-example with > 4 columns (`ManualCampaignsRowExample`) | horizontal scroll inside the example, NOT page-level scroll | same | same |
| Mini chart (`ManualCPMChartExample`) | clamp height to `h-[160px]` (down from 200px) | `h-[200px]` | `h-[200px]` |
| Footer | hide the "MD מקור" link at `< 480px` (just the version trio remains) | both visible | both visible |
| ASCII diagrams in `<pre>` | unchanged — `overflow-x: auto` handles it; user gets horizontal scroll on the diagram | same | same |

No mobile drawer. No FAB. No "mobile-first manual" — out of scope per CONTEXT §deferred-ideas.

## Accessibility Contract

| Concern | Implementation |
|---|---|
| Page lang | `lang="he"` set at `<html>` (already in place) |
| Direction | `dir="rtl"` set at `<html>` (already in place) — manual inherits |
| Tab nav landmark | `<nav aria-label="ניווט בדשבורד">` (already in place in `TabNav.tsx`) |
| Manual tab panel landmark | `<section aria-labelledby="manual-h1">` wrapping the prose, where `manual-h1` is the id of the H1 emitted by the MDX |
| Search input semantics | `<input type="search" role="searchbox" aria-controls="manual-prose" aria-describedby="manual-search-count" aria-label="חיפוש במדריך המשתמש">` |
| Search result count exposed to AT | `<div id="manual-search-count" aria-live="polite" aria-atomic="true">{N} התאמות</div>` — AT announces every count change |
| Match highlighting | `<mark>` is a semantic element; AT announces "marked text" without extra ARIA |
| Active-match focus | scrolling moves the active mark into view via `Element.scrollIntoView({ block: 'start' })` with offset; focus stays on search input |
| Headings outline | the MDX renderer must preserve heading hierarchy h1 → h2 → h3 → h4 — no `<div>` headings, no level-skipping |
| Code blocks reachable by keyboard | when a `<pre>` overflows horizontally, it has `tabindex="0"` so keyboard users can scroll it |
| Mini-example role | `role="figure"` + aria-label as declared in §Isolation |
| Mini-example NOT in tab order | `tabindex="-1"` on the wrapper; inner real components might still try to be tab stops, so any internal `<button>` / `<a>` gets `tabindex="-1"` too (or use `inert` attribute on the wrapper if browser support allows — React 18.3+ supports `inert` prop natively) |
| Reduced motion | already honoured by globals.css `@media (prefers-reduced-motion: reduce)`. The smooth scroll on Enter-jump MUST honour this — use `behavior: 'auto'` not `'smooth'` when `prefers-reduced-motion: reduce` is set. |
| Contrast checks | manual-highlight `#fbe7f3` against `text-primary` `#0d253d` = 13.4:1 (AAA). Active-ring `#ec4899` against `surface` `#ffffff` = 4.85:1 (AA for non-text UI). Hyperlink primary `#0d3680` on body `#ffffff` = 12.5:1 (AAA). All pass. |
