# Phase 05.3 — Implementation Decisions Locked

## Phase Goal (from ROADMAP.md)

Embed the operator manual (`docs/ROAS-Dashboard-User-Manual.md`) as a searchable tab inside the live dashboard at `https://roas-dashboard-smoky.vercel.app`, with inline live component examples (mini KPI cards, mini campaigns row, mini CPM chart, mini Reconciliation table) so the operator can learn the system without leaving the app.

**Why this phase exists:** Phase 05.2.2.1 shipped 55 commits of correctness fixes. The user requested that the freshly-written manual be reachable from the dashboard itself — easier to consult during real work than opening a separate file or browser tab. This is an operator-experience polish phase, not a correctness fix.

---

## Decisions (locked — downstream agents act on these without re-asking)

### 1. Tab position + label

| Decision | Value |
|---|---|
| **Position in nav** | Last tab, after `פירוט` (Detail) |
| **Label (Hebrew)** | `מדריך` |
| **Icon** | `BookOpen` (lucide-react) |
| **Route/key** | `manual` (matches existing 6 tab key pattern: `home`, `pnl`, `analysis`, `campaigns`, `products`, `detail`, **new:** `manual`) |
| **URL persistence** | `?tab=manual` via existing urlState pattern |

**Rationale:** Last position keeps the manual out of the way of daily work but discoverable. Hebrew "מדריך" is unambiguous in Hebrew-first nav (the other options "עזרה" and "מידע" felt like FAQ/glossary). `BookOpen` icon matches a printed-manual mental model.

**Not chosen:** sticky-to-home position (would crowd primary nav), header button (too hidden, no real estate for full manual rendering).

### 2. Search UX

| Decision | Value |
|---|---|
| **Search input position** | Sticky input at top of the tab body (NOT in header, NOT in Cmd-K) |
| **Behavior** | Inline filter — narrows visible content live as the user types |
| **Match algorithm** | Fuzzy match with typo tolerance |
| **Library** | `Fuse.js` (npm) — well-established, well-typed, ~20kb gzipped |
| **What's searchable** | Headings (h2, h3, h4) AND body paragraph text |
| **Result display** | Show matched sections in order; non-matching sections collapsed/hidden; highlight matched terms |
| **Navigation** | `Enter` jumps to next match; `Esc` clears search |

**Rationale:** Inline filter beats Cmd-K because the manual is a long document where the user wants to scroll-and-skim. Fuzzy matching handles English transliteration (`rias` → `ROAS`) and typos. Searching both headings + body covers operator queries like "פיקסל לא מסכים עם שופיפי" which might not match a heading verbatim but matches body text in the Reconciliation section.

**Not chosen:** Cmd-K only (loses spatial context — user wants to see the surrounding sections, not just jump). Exact-only (too brittle for Hebrew operators who mix English terms inconsistently).

### 3. Markdown → React rendering pipeline

| Decision | Value |
|---|---|
| **When** | Build-time |
| **How** | `next-mdx-remote` or `@next/mdx` — compile `docs/ROAS-Dashboard-User-Manual.md` to React at build |
| **Inputs** | The MD file itself + a registry of custom MDX components (the 4 live examples) |
| **Outputs** | A pre-rendered React component tree imported by the `manual` tab |
| **Update cycle** | Edit MD → commit + git push → Vercel auto-rebuild → new bundle |
| **Frontmatter** | YAML at top of MD (version, timestamp). Parsed at build, surfaced via the registry. |

**Rationale:** Build-time is simplest and fastest at runtime (no fs access, no API route, no extra hop). The manual is operator-facing reference content that changes infrequently (per the memory pre-push gate, only when user-visible behaviour changes). Rebuild on push is exactly the cadence that matches "manual stays in sync with code".

**Not chosen:** Runtime `/api/manual` route (extra latency, no build-time errors for broken MDX, complicates caching). Hybrid (overkill for the small benefit; dev-mode live-reload via `next dev` already works for the underlying MD file when developing).

### 4. Version display

| Decision | Value |
|---|---|
| **Where** | Sticky footer inside the tab |
| **Format** | `v{X.Y} · עדכון {YYYY-MM-DD} · commit {short-sha}` |
| **Data sources** | Version + date from MD frontmatter; commit sha from a build-time env var (`process.env.NEXT_PUBLIC_GIT_SHA` or `VERCEL_GIT_COMMIT_SHA`) |
| **Visibility** | Always-on small grey text bottom of tab body |

**Rationale:** Operator needs to know if they're reading a stale manual after a deploy. The trio (version / date / sha) gives both human-readable (date) and trace-back (sha) signals.

**Not chosen:** Frontmatter-only (invisible to user). Changelog tab/section (scope creep — separate phase if needed later).

### 5. Live component examples

Render mini, dummy-data-fed copies of these 4 existing dashboard widgets inline inside the markdown:

| Component | Where in manual | Why |
|---|---|---|
| `ManualROASChipExample` | Section 7.7 (ROAS Tone) | Show each color (🔴🟠🟢🔵) so operator learns the scale by seeing it |
| `ManualKPICardExample` | Section 4.2 (HeroOverview) | Show layout, delta arrows, formatting |
| `ManualCampaignsRowExample` | Section 7.6 (Campaigns Table) | Show Trust chip, CBO/ABO chip, FIX-26 off chip side by side |
| `ManualCPMChartExample` | Section 7.4 (CPM-vs-ROAS chart) | Show 2-line overlay + analysis box; toggle to demo half-over-half vs prev-period |
| `ManualReconciliationExample` | Section 12.3 (4 labels: Match/Channels only/Shopify only/Mismatch) | Show all 4 daily-row label types |

**Bonus deferred:** Could later add a Reconciliation pie/bar/sankey or a per-store summary card. NOT in scope of this phase.

**Data source for all examples:** **dummy data baked into the component file itself**. Static constants. Deterministic — same output every render, never depends on external state.

**Implementation pattern:** Each `Manual*Example` is a small wrapper that:
1. Imports the real production component (e.g., `<CampaignsTableRow />`).
2. Passes in hand-built dummy data shaped exactly like the real prop type.
3. Wraps in a `<div className="roas-manual-example pointer-events-none ...">` so clicks don't accidentally trigger drilldowns / SWR fetches in dummy mode.

**Rationale:** Dummy data is safer (no surprise SWR cascades when an operator opens the manual tab), deterministic (same screenshot every visit), and decoupled (works even if Apps Script is down). Real-data samples were considered but the risk of confusing dummy-vs-real outweighed the benefit.

## Out-of-scope (Deferred Ideas)

Captured per the discuss-phase scope-guardrail. Not implemented in 05.3, but noted for future phases:

- **Search analytics** — what operators search for. Useful for documentation gaps. Could go in a future observability phase.
- **Print-to-PDF button** inside the tab. Operator wants a hard copy? Use browser's native print. PDF generation is its own can of worms.
- **Mobile drawer / FAB** — manual on mobile. Out of scope (dashboard is desktop-first by design memory).
- **Per-section feedback button** — "was this section helpful?". Belongs in a feedback/observability phase.
- **Localized English copy** — manual is Hebrew-only. English version is a future phase if non-Hebrew operators are onboarded.
- **Real-data samples** — a future "advanced mode" toggle could swap dummy data for live, but the static path stays default.

## Pre-flight checks for downstream agents

**For the researcher (gsd-phase-researcher):**
- Investigate MDX libraries: `next-mdx-remote` vs `@next/mdx` (Next.js 14 App Router compatibility, RSC support, bundle size impact).
- Confirm `Fuse.js` is a reasonable choice OR identify a lighter alternative (`minisearch`?). Decision criterion: bundle size impact < 30kb gzipped.
- Identify how to expose the current git short-sha at build time (Vercel's `VERCEL_GIT_COMMIT_SHA` is already set automatically; no extra config needed).
- Scout the existing markdown extras the manual currently uses (tables, ASCII diagrams, emoji) and confirm they all render correctly through the chosen MDX pipeline.

**For the planner (gsd-planner):**
- Break the work into AT MOST 4 plans:
  - **Plan 1 — Manual tab skeleton.** New tab + nav + URL state + empty-state rendering of the markdown (no search, no examples yet).
  - **Plan 2 — Live component examples.** 5 `Manual*Example` wrappers with dummy data + MDX component registry.
  - **Plan 3 — Fuzzy search.** Inline sticky input + Fuse.js index + highlight + Enter/Esc navigation.
  - **Plan 4 — Version footer + polish.** Frontmatter parse, build-time sha exposure, footer component, accessibility pass (ARIA, focus management, RTL).
- Each plan ends with `npx tsc --noEmit` clean + at least one regression test (or smoke test for plans without easily-testable logic).

## Notes for the future

This phase introduces a new convention: **the manual lives both as a Markdown file (for PDF/print) and as a rendered React tab (for in-app reference)**. Any future operator-facing UX change must update the Markdown file (which then rebuilds the in-dashboard tab automatically). This consolidates the previous pre-push gate (already in memory) into a single source of truth.
