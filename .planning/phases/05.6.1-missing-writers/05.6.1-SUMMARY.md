## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Vitest fn type-inference for parameterless `vi.fn(async () => ...)`**
- **Found during:** Task 3 (Google Ads ad-level tests)
- **Issue:** Two new test spies declared as `vi.fn(async () => { ... })` caused `tsc` to infer the spy's mock-calls signature as `[]`, so accessing `spy.mock.calls[1][0]` produced TS2493 "Tuple type '[]' has no element at index '0'".
- **Fix:** Added explicit signature `vi.fn(async (_url: string | URL, _init?: RequestInit) => ...)` — matches the pattern already used by `buildOAuthThenGaqlFetchMock` at googleAds.test.ts:101.
- **Files modified:** `dashboard-web/src/lib/fetchers/__tests__/googleAds.test.ts`
- **Verification:** `tsc --noEmit` clean; vitest re-run 9/9 pass.
- **Committed in:** `3863e31` (part of Task 3 commit)

**2. [Rule 1 - Bug] Line-items proportional split fixture math**
- **Found during:** Task 1 (orders-attribution Test 5)
- **Issue:** Initially expected `r: 50` for each of two `$40`-gross lines in a `$100`-total order with a `$10` custom line. But Apps Script + my port compute subtotal BEFORE filtering custom lines (Shopify.gs:863), so subtotal = 90 and A's allocation = (40/90)×100 ≈ 44.44.
- **Fix:** Corrected the test expectation to `44.44` and added an inline comment explaining the subtotal-before-filter ordering.
- **Files modified:** `dashboard-web/src/lib/fetchers/__tests__/shopify.test.ts`
- **Verification:** Vitest 16/16 pass.
- **Committed in:** `0c688a3` (part of Task 1 commit, post-first-fail)

**3. [Rule 3 - Blocking] Missing node_modules in worktree**
- **Found during:** Task 1 (first vitest invocation)
- **Issue:** Fresh worktree had no `node_modules/` so vitest could not resolve `vitest/config` and aborted with `MODULE_NOT_FOUND`.
- **Fix:** Ran `npm install` (added 1016 packages); package.json itself unchanged.
- **Files modified:** none (lockfile drift reverted before commit — Section "Test plan" below documents the rationale).
- **Verification:** Vitest + tsc + next build all clean afterwards.
- **Committed in:** N/A (no source changes from this fix; lockfile reverted to avoid an unrelated 644-line lockfile bump in feature commits).

**4. [Rule 2 - Missing Critical] Prepend source_name='fb'/'google' branch to source classifier**
- **Found during:** Task 1 (designing classifyOrderAttribution)
- **Issue:** Apps Script Shopify.gs:910 omits this branch because Shopify's `source_name` is "web" for ~all storefront orders. But the plan's scope explicitly states the priority chain (item 1: `source_name === 'fb'` → 'facebook'), and orders from FB Channel SDK do carry `source_name='fb'`. Treating those as 'direct' would misattribute revenue.
- **Fix:** Added the two-line prepend branch before the existing UTM/click-ID/referrer chain. For the typical `source_name='web'` case the branch is a no-op so behavior is unchanged.
- **Files modified:** `dashboard-web/src/lib/fetchers/shopify.ts` (classifyOrderAttribution function)
- **Verification:** Orders Test 2 covers both `source_name='fb'` and `source_name='google'` paths.
- **Committed in:** `0c688a3` (part of Task 1 commit; documented in source comment block).

## Free-tier Impact

- `cron-daily-{storeId}` exec count: **6/run** (unchanged from Phase 05.6). 3 stores × 1 run/day × 30 days = 540 execs/month from cron-daily, well under the 50K/mo Inngest cap.
- Net API calls per cron-daily run:
  - Shopify: was 2 (orders × 2 windows), now 4 (orders × 2 + catalog + orders-attribution). Still issued in parallel inside one step.
  - Meta: was 2 (adset + spend-sum, with spend-sum reusing adset internally → really 1 unique call), now 2 (adset + ad-level in parallel inside one step; spend-sum still reuses adset internally).
  - Google Ads: was 1 OAuth + 2 GAQL (spend + ad-group), now 1 OAuth + 3 GAQL for uzoshop; **0 calls** for zolplus/usmile360 (short-circuit preserved).
- Wall-clock impact: roughly +20-30% per cron-daily run for uzoshop because each step's wall-clock is now bounded by its slowest parallel branch; for zolplus/usmile360 the impact is minimal (Shopify side adds 2 extra parallel calls).
