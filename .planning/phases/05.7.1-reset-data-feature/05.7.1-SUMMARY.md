## Decisions Made

1. **Two distinct tokens (not one shared "I CONFIRM"):** if both scopes shared a single token, a mis-clicked "wrong" button could still execute by typing the same literal. Distinct tokens force the operator to read the modal heading and type a scope-naming literal, making accidental cross-scope completion impossible.

2. **Universal filter `.not('store_id', 'is', null)`:** every one of the 7 DATA_TABLES has `store_id NOT NULL` (verified against `20260521063112_initial_schema.sql` + `20260521075741_add_constraints_and_grants.sql`). Other candidate columns (`id`, `updated_at`) aren't present on all 7 tables. `store_id` is the unique universally-present column, so the filter shape is identical across every table — no chance of one table silently being a no-op.

3. **Vitest covers the lib, not the component:** the project's `vitest.config.ts` uses `environment: 'node'` and the inline comment explicitly says adding JSDOM means wiring a second config + `@testing-library/react` deps. The most security-relevant code is in `operatorReset.ts` (table-disjointness invariants + the validator); covering it with 15 node-env tests delivers higher leverage than a JSDOM modal test for the same scope budget.

4. **PROTECTED_TABLES is a positive list, not an absence-test:** `stores`, `notification_config`, `dashboard_state` are documented explicitly in code with rationale per table. The vitest disjointness assertion is the runtime safety net.

5. **Partial-failure returns 200 with per-table breakdown:** the response carries `deleted` (per-table count, `-1` sentinel on failure) and an optional `errors` map. A 5xx would erase the per-table detail; the 200 path lets the UI amber-flag the partial-failure case while still showing the successes.
