Phase 12.1.2 — Ship the 3 aiReport cross-store cleanup fixes from AUDIT.md §Recommended Phase 12.1 Scope as one cohesive unit:

- ALG-04: statusByCampaign keyed by ${platform}::${campaignId} (no storeId) → in operator's default storeName='All' view, store A's status silently overwrites store B's for any colliding campaignId.
- ALG-05: ordersByCampaignId / ordersByCampaignName (and parallel detById / detByName maps further down) keyed without storeId → same utm_campaign='Brand' across stores merges revenue, double-counting at the row level. Feeds wrong gap/verdict columns in Pixel↔Shopify table AND inflated coverage/trust scores in Health Score.
- ALG-06: three suffix-match Array.from(map.keys()).find(k => k.endsWith(...)) patterns at lines 1124, 1492, 1588 return the FIRST match — for cross-store collisions, one campaign silently receives the other's data (daily series, ad-sets, creative drill-downs).

All three are MAJOR per AUDIT.md and fire in the OPERATOR'S DEFAULT VIEW (storeName='All'). They are conceptually one cluster — the unified fix is "thread storeId through campaignsList so every key construction is storeId-scoped". Per CONTEXT.md D-04, the Aggregated type in campaignsAggregator.ts ALREADY exposes storeId (verified in 12.1 Task 1 pre-flight), so no contract change is needed. The work is purely on the aiReport.ts side: surface storeId on the per-campaign aggregated rows it builds internally, and switch every map key to ${storeId}::${platform}::${campaignId} (or ${storeId}::${id} for the orders maps).

Per CONTEXT.md D-03, the cluster lands TDD-style with a single golden fixture (TG-02) pinning the contract.

Per CONTEXT.md D-08 the rule is one commit per fix, but since all three findings share one root cause (no-storeId in key construction), one file, and one test file, this plan ships ONE composite commit whose message references all three finding IDs. This is a documented exception — see Task 3 commit message body for the rationale.
