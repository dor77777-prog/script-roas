<objective>
Stand up the Inngest cloud account + Vercel marketplace integration. This is the ONE explicit operator-action gate in Phase 05.6 — every subsequent plan depends on the auto-injected env vars and the registered Inngest app.

Purpose: Inngest cloud is the cron + event scheduler (D-A1 / D-B1). The Vercel integration auto-injects both `INNGEST_EVENT_KEY` (used by `inngest.send()` from API routes) and `INNGEST_SIGNING_KEY` (used by `serve()` for webhook signature verification AND by the operator-console jobs proxy for REST `/v1/runs` Bearer auth). Without these, plan 02 cannot initialize the client, plan 04 cannot deploy the webhook, plan 11 cannot fire events from the operator console.

Output: 2 Vercel env vars marked Encrypted in Production + 1 registered Inngest App showing the operator's roas-dashboard project + (if applicable) a Vercel deployment-protection bypass configured.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Inngest cloud → Vercel webhook | Untrusted scheduler triggers a Vercel function; signing-key on body verifies authenticity |
| Operator → Inngest dashboard | Operator's Inngest login is the credentialed boundary; future operators rotate via Inngest's session UI |
| Vercel env-var store → Inngest serve() runtime | Encrypted at rest, decrypted only inside the serverless function process |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05.6-01-S1 | Spoofing | External attacker POSTs to /api/inngest with forged signature | mitigate | Plan 04 enables Inngest SDK's built-in signing-key verification (no custom code). The `serve()` handler rejects requests whose `X-Inngest-Signature` header does not validate against `INNGEST_SIGNING_KEY`. |
| T-05.6-01-T2 | Tampering | Replay of an old `inngest.send()` event | mitigate | Inngest tags events with internal IDs; the SDK rejects duplicates. + Phase 05.5 ON CONFLICT constraints make every persist step idempotent. |
| T-05.6-01-I3 | Info Disclosure | INNGEST_SIGNING_KEY bundled to browser | mitigate | Per RESEARCH §Security Domain — the key is only referenced server-side. Plans 06 + 11 use it ONLY in the API-route proxy; client code never imports it. Per-plan grep gate: `! grep -r "INNGEST_SIGNING_KEY" dashboard-web/src/components/ dashboard-web/src/app/operator/*.tsx` returns ZERO matches. |
| T-05.6-01-D4 | DoS | Vercel deployment protection blocks Inngest webhook | accept | Plan 04 verifies `/api/inngest` PUT works post-deploy. If 401/403, operator follows the bypass-secret path in Task 0. |
| T-05.6-01-E5 | Elevation of Privilege | Misuse of Inngest cloud account by anyone with the password | accept | Single-user URL-obscurity (D-D2). Future phase adds Supabase Auth + RLS; for 05.6 the operator's Inngest credentials are the trust boundary. |
