## Blockers (must fix before execution)

### C1 — Wave numbers violate `wave = max(dep_wave) + 1` for 9 plans

The orchestrator dispatches plans by wave: all plans in wave N start in parallel after all plans in wave N-1 complete. The current assignment puts dependents in the same wave as their dependencies, which means the orchestrator will fire them concurrently and they will race.

| Plan | Current wave | Dependencies (wave) | Should be wave | Reason |
|------|--------------|---------------------|----------------|--------|
| 10   | 4 | 08 (4) | **5** | eventBackfill+eventSyncNow import `runDailyForStore` from cronDaily |
| 11   | 4 | 08 (4), 09 (4), 10 (4) | **5** | serve() registers all 8 functions; must exist first |
| 13   | 5 | 12 (5), 11 (4) | **6** | JobsTable wires into page.tsx scaffold + needs route.ts deployed |
| 14   | 5 | 12 (5), 11 (4), 10 (4) | **6** | BackfillPicker wires into page.tsx + fires event/backfill |
| 15   | 5 | 12 (5), 02 (2) | **6** | ManualOverridesCrud wires into page.tsx |
| 16   | 5 | 12 (5), 14 (5) | **6** | SyncNowButtons wires into page.tsx + needs /api/operator/sync-now route |
| 19   | 6 | 17 (6), 18 (6) | **7** | Route branching uses postgresReaders + readFrom |
| 21   | 7 | 03..08 (3-4), 20 (7) | **8** | Algorithm-parity baseline runs against fetchers + needs imported overrides |
| 22   | 7 | 11..16 (4-5), 19 (6), 20 (7) | **8** | User Manual + smoke require everything else shipped |

**Fix:** Recompute waves with the standard `wave = max(deps[i].wave) + 1` rule. After renumbering, wave count becomes 8 (instead of 7). Concretely:

- Plan 10 → wave 5
- Plan 11 → wave 5
- Plan 12 → wave 3 (or stays 5; deps only on 02 — its current wave 5 is fine since it doesn't depend on anything in waves 3-4; but new dependents must be wave-of-12 + 1)
- Plans 13, 14, 15, 16 → wave 6
- Plans 17 → wave 3 (or stays 6 if planner wants it after fetcher completion)
- Plan 18 → wave 1 (or current 6; no deps)
- Plan 19 → wave 7
- Plan 20 → wave 7 (deps on 15 wave 6 — OK)
- Plan 21 → wave 8 (deps on 20 wave 7)
- Plan 22 → wave 8 (deps on 19 wave 7, 20 wave 7)

Alternatively, planner can elect to keep the loose wave grouping but the orchestrator MUST gate on `depends_on` (not on wave) — confirm orchestrator behavior before executing. If orchestrator gates only on wave, this is a hard blocker.

## Warnings (advisable to fix; not blocking)

### W1 — Plan 17 understates the read-source surface
Plan 17 says "postgresReaders.ts exports parallel functions matching **sheets.ts**" but production code splits the read layer across at least 5 modules: `@/lib/products`, `@/lib/campaigns`, `@/lib/ads`, `@/lib/ordersAttribution`, `@/lib/productCatalog`. Only 3 functions live in `sheets.ts` itself (`fetchDailyData`, `fetchStoreMeta`, `fetchDashboardState`). Plan 17's required-reading list also omits these 5 modules. The 9 reader signatures Plan 17 lists ARE the right surface, but the planner needs to read those 5 module files in addition to `sheets.ts` to ensure shape parity.

**Fix:** Append to Plan 17's `<read_first>` block: `@/lib/products.ts`, `@/lib/campaigns.ts`, `@/lib/ads.ts`, `@/lib/ordersAttribution.ts`, `@/lib/productCatalog.ts`.

### W2 — Plan 19 names wrong functions for 4 of 8 routes
Plan 19's mapping table says:
- `/api/products` → `fetchProducts` ↔ `fetchProductsFromPostgres`
- `/api/campaigns` → `fetchCampaigns` ↔ `fetchCampaignsFromPostgres`
- `/api/ads` → `fetchAds` ↔ `fetchAdsFromPostgres`
- `/api/orders-attribution` → `fetchOrdersAttribution` ↔ `fetchOrdersAttributionFromPostgres`
- `/api/product-catalog` → `fetchProductCatalog` ↔ `fetchProductCatalogFromPostgres`

But production code uses `fetchProductsData`, `fetchCampaignsData`, `fetchAdsData`, `fetchOrdersAttribution`, `fetchProductCatalog` (mixed `Data` suffix). The branching idiom is right, but execution will require re-reading each route to pick up the correct sheets-side function name. Defensible at execution time but the planner should pre-state this.

**Fix:** Update Plan 19's mapping table to use the actual sheets-side function names imported by each route. Cross-reference Plan 17 to ensure the postgres-side names match what Plan 19 expects to import.

### W3 — Plan 11's webhook `force-dynamic` claim is the inverse of what RESEARCH §Pitfall 11 says
Plan 11 asserts `! grep -c "force-dynamic"` AND `! grep -c "export const revalidate"` on `/api/inngest/route.ts`. RESEARCH §Pitfall 11 forbids `force-dynamic` + `revalidate` together. The current plan goes further and forbids both entirely. This may be correct for an Inngest invocation endpoint (POST-only, never cached). Confirm with Inngest docs — if `force-dynamic` is *required* for `serve()` to bypass static analysis, removing it could break the deploy.

**Fix:** Plan 11 should explicitly cite the Inngest documentation note (or RESEARCH excerpt) that `serve()` does not require `force-dynamic` for POST routes in Next.js app-router. If unconfirmed, add a smoke-test verify line in Plan 22 confirming POST to `/api/inngest` succeeds in production.

### W4 — Plan 09 cron-live mismatch between objective and step-budget claim
Plan 09's objective says ~3 step.runs per function, but the implementation in `runLiveForStore` makes nested calls inside `persist-rolling-3day` (3 dates × 2 UPSERTs per date = 6 admin calls in 1 step). Implementation is correct; the objective could note "2 step.run wrappers around N admin calls" for clarity.

**Fix:** Plan 09 SUMMARY note: "2 outer step.runs; persist-rolling-3day contains 3-day × 2-table UPSERT loop inside one step."

### W5 — Plan 08 step granularity claim vs RESEARCH §Pitfall 4
Plan 08's `runDailyForStore` has 5 outer step.runs (fetch-shopify, fetch-meta, fetch-google, apply-manual-overrides, persist-batch) but RESEARCH §Pitfall 4 recommends ~6 steps for free-tier budget headroom. The current plan is at the lower bound. If any step needs splitting (e.g., persist-batch into per-table UPSERTs for better retry granularity), the exec budget rises proportionally. Plan 08 should call out the trade-off.

**Fix:** Plan 08 SUMMARY note: "5 step.runs ÷ 6 recommended; if persist-batch fails repeatedly, split into 4 per-table UPSERT steps (8 total) — still 26% budget headroom."

### W6 — Plan 10 nested step.run inside eventBackfill loop
`eventBackfill`'s for-loop calls `step.run('backfill-{date}-{storeId}', () => runDailyForStore(...))`, but `runDailyForStore` itself uses `step.run('fetch-shopify', ...)` etc. Inngest's step ID uniqueness is per-function-invocation; if 6 backfill iterations all call `step.run('fetch-shopify')`, the IDs collide. The plan should either (a) qualify inner step IDs with `{date}-{storeId}-fetch-shopify`, OR (b) pass a `step` shim into `runDailyForStore` that prefixes IDs, OR (c) use `step.invoke()` to run `cronDaily` as a separate function.

**Fix:** Plan 10 Task 3 action block needs a note: "Verify `step.run('fetch-shopify')` inside runDailyForStore does not collide across iterations. If it does, either prefix step IDs or switch to step.invoke(eventSyncNow, {data: {storeId, date}})." Most likely fix: use `step.invoke()` from backfill into `eventSyncNow` instead of direct call.

### W7 — Plan 21 missing `key_links` in must_haves
Plan 21's `must_haves` block has `truths` + `artifacts` but no `key_links`. The other 21 plans all have it. The snapshot file is consumed by the algorithm-parity test; that linkage should be in `key_links`.
