# Plan 05.6-03 SUMMARY — Shopify fetcher (TS port)

Port the HTTP layer of `Shopify.gs` to a pure-TS module at
`dashboard-web/src/lib/fetchers/shopify.ts`. The fetcher paginates Shopify
Admin REST 2024-10 (orders + refunds + line_items), feeds the merged raw
order array into the EXISTING `computeRevenueWithCrossDayRefunds()`
algorithm from `dashboard-web/src/lib/shopifyRevenueRefunds.ts:150`, and
returns store-net + per-product net revenue in CAD plus a custom-item
refund diagnostic. The Phase 05.2.3.0 algorithm is REUSED, not re-derived
— this is the load-bearing constraint of the plan.

## What landed

### 1. `dashboard-web/src/lib/fetchers/shopify.ts` (427 lines)

Public entry point: `fetchShopifyDayRows(storeId, dateStr): Promise<ShopifyDayRows>`.

Key invariants preserved:

- **`SHOPIFY_API_VERSION = '2024-10'`** literal (line 73) — matches
  `Config.gs:12` exactly. Algorithm parity (D-C4).
- **`computeRevenueWithCrossDayRefunds` import** at line 58 — pulled from
  `@/lib/shopifyRevenueRefunds`. Called exactly once per invocation at
  line 412 (verified by Test 7 spy with `toHaveBeenCalledTimes(1)`).
- **Two-window fetch + merge deduped by id**:
  - Window A: `created_at_min/max=dateStr` (same-day orders → algorithm's
    `isSameDayOrder` path)
  - Window B: `updated_at_min/max=dateStr` (cross-day refunds — orders
    created earlier but refunded on D)
  - Merge via `Map<string, ShopifyOrderInput>` keyed on `String(o.id)`,
    window A inserted first, window B only inserts non-duplicates.
- **`isoLocalMidnight()` helper** (lines 130-178) — mirrors
  `Shopify.gs:56-83` `isoLocalMidnight_`. Resolves the Asia/Jerusalem
  offset from the actual date so DST transitions produce correct windows.
  Test 1 asserts the day-window starts at `2026-05-19T00:00:00+03:00`
  (IDT, May 2026).
- **`parseNextLink()`** (lines 211-216) — verbatim regex from
  `Shopify.gs:164`: `/<([^>]+)>;\s*rel="next"/.exec(link)?.[1]`.
- **Pagination cap of 50 pages** with `console.warn` matching
  `Shopify.gs:168-174`. Does NOT throw — additional orders beyond the
  cap are dropped silently with a warning (Pitfall 6).
- **`X-Shopify-Access-Token` header** (NOT Bearer) at line 277. Matches
  Apps Script convention.
- **Fields list** at line 246:
  `id,created_at,total_price,current_total_price,test,financial_status,line_items,refunds`
  — superset of both `getShopifyRevenue` (Shopify.gs:123) and
  `getShopifyProductSalesForDay` (Shopify.gs:222) so a single fetch
  satisfies both store-level + per-product algorithm needs.
- **`STORE_NAMES` map** at line 95 — `uzoshop`/`zolplus`/`usmile360`
  matches Phase 05.5-01 seed + `Config.gs:STORES`. No Supabase round-trip
  per fetch (out of scope; plan 13 owns stores-CRUD UI).
- **No `Math.max(0, ...)` clamping anywhere** (D-D3). Verified by
  `grep -c 'Math.max(0' src/lib/fetchers/shopify.ts == 0`.
- **No `.gs` files modified**. Verified by
  `git diff --name-only $(git merge-base HEAD d3c1348) HEAD | grep '\.gs$'`
  returning no matches.

Algorithm-parity confirmation:
- `shopifyRevenueRefunds.ts` is **UNTOUCHED** — `git diff` stat is empty
  across the plan commits.
- The 3 load-bearing invariants (CR-01/02/03 from 05.2.3.0-REVIEW.md)
  stay preserved by virtue of delegation. Re-deriving the algorithm
  would risk reintroducing the double-deduction bug Phase 05.2.3.0

## Notes for Plan 08 (cron-daily integration)

- `revenueCad` is in CAD already. All 3 Shopify accounts (uzoshop, zolplus, usmile360) are CAD-denominated per existing Apps Script config — no FX conversion needed in this layer. Plans 08-10 can write `revenueCad` directly to the Supabase `daily_data.revenue_cad` column without further math.
- `productRows[].product_id` is the stringified Shopify product_id (mirrors `shopifyRevenueRefunds.ts:144` `normalizeProductId`). Empty/null product_ids are diverted to `customItemRefundCad` and never appear in `productRows`.
- `customItemRefundCad` is a POSITIVE value (absolute deduction). Plans 08-10 should surface it as a diagnostic — typically zero but >0 indicates manual discount refunds or custom-item refunds that operators should investigate (matches Apps Script Shopify.gs:725-729 logging).
- The fetcher throws on non-200 responses — Inngest's 4-retry exponential backoff handles transient 5xx/429. Persistent 401 (token rotation needed) will dead-letter to the operator console's jobs table (matches D-B6 retry strategy + RESEARCH Pattern 2).
