# Phase 05.6: TS port + Inngest + Operator Console — Research

**Researched:** 2026-05-21
**Domain:** Inngest cloud (cron + event-driven background jobs) on Vercel + Next.js 15 app router, with TS ports of 5 Apps Script fetchers writing to Supabase via service-role client, plus a Hebrew operator-console tab and a one-off Sheets→Postgres importer for the 38 manual_overrides rows.
**Confidence:** HIGH on Inngest API surface + Supabase client patterns (verified against the official OpenAPI specs and supabase-js docs). MEDIUM on Inngest free-tier limits (verified via pricing page text but exact counting semantics are slightly ambiguous between "run" and "step"). HIGH on the Shopify refund algorithm parity (a complete pure-TS mirror already exists at `dashboard-web/src/lib/shopifyRevenueRefunds.ts:150` with vitest fixtures).

## Summary

This phase is a port-and-rebuild migration, not a greenfield feature. The 5 Apps Script fetchers (`Shopify.gs`, `MetaAds.gs`, `GoogleAds.gs`, `FX.gs`, `ManualOverrides.gs`) become pure-TS modules under `dashboard-web/src/lib/fetchers/`. Inngest cloud (free tier, ~50K executions/month allowance with **~9K/month forecast load = ~5× headroom**) replaces Apps Script triggers via 1 webhook route at `/api/inngest`, two cron-trigger function families (`cron-daily-{store}` at `0 5 * * *` UTC and `cron-live-{store}` at `*/15 * * * *`), and two event-trigger function families (`event/sync-now`, `event/backfill`). Writes use `getSupabaseAdmin()` — a new sibling to the existing `getSupabase()` factory — bound to the `SUPABASE_SERVICE_ROLE_KEY` env var (already seeded in Phase 05.5-02). All write paths use the Supabase JS client's `.upsert({...}, { onConflict: 'pkey-cols' })` builder against the UNIQUE / PRIMARY KEY constraints added in `20260521075741_add_constraints_and_grants.sql`. The operator console (`/operator`) polls Inngest's REST `/v1/events/{internalID}/runs` endpoint via signing-key Bearer auth every 15s for the jobs table, posts to internal API routes that re-fire `inngest.send()` for the sync-now / backfill buttons, and uses service-role-backed CRUD routes for the 38 manual_overrides rows. The cut-over flag (`READ_FROM=sheets|postgres`) lives in `dashboard-web/src/lib/featureFlags.ts` reading `process.env.READ_FROM` at request time (NOT module-load) and defaults to `'sheets'` — Postgres readers exist but are dormant.

**Primary recommendation:** Use `inngest@^4.4.0` with the Vercel marketplace integration (auto-injects both `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`). Use `@supabase/supabase-js@^2.106.1` (already installed) for writes via `.upsert()` with `onConflict` on the existing PKEY/UNIQUE constraints — no raw SQL needed. Use `inngest`'s default 4-retry exponential backoff (no custom retry config needed for 05.6). Use **Inngest API v1** for the operator-console jobs list because v1 uses the same signing key the SDK already needs (one secret, not two; v2 needs a separate API key — defer to a future phase). Mirror the existing `dashboard-web/src/lib/shopifyRevenueRefunds.ts` algorithm verbatim in the new fetcher — it is already a complete pure-TS port of the load-bearing Phase 05.2.3.0 refund-correction fix with vitest fixtures.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Cron triggers (daily 00:05 UTC + live every 15min) | Inngest cloud | Vercel-hosted `/api/inngest` handler | Inngest owns the schedule. Vercel just hosts the webhook handler the Inngest scheduler calls into. Replaces Apps Script time-based triggers. |
| Per-fetcher upstream API calls (Shopify/Meta/Google/FX) | API / Backend (Next.js server runtime invoked by Inngest webhook) | — | Pure HTTP+JSON; lives in `dashboard-web/src/lib/fetchers/*.ts` as side-effect-free async functions. Inngest function wrappers in `dashboard-web/src/inngest/*.ts` call them and persist results. |
| Supabase writes (UPSERT) | API / Backend (Inngest function step.run callback) | Service-role-backed `dashboard-web/src/lib/supabaseAdmin.ts` | Bypasses RLS (anon role only has SELECT per `20260521075741_add_constraints_and_grants.sql`). Strict server-only — file MUST never be imported by a client component. |
| Operator console UI (jobs table, backfill picker, manual_overrides CRUD, sync-now buttons) | Browser / Client (`/operator` route, client components) | API routes under `/api/operator/*` | UI in `dashboard-web/src/app/operator/page.tsx` + `dashboard-web/src/components/operator/*`. Reads from `/api/operator/jobs` (proxy to Inngest REST) and `/api/operator/manual-overrides` (proxy to Supabase). Writes via POST to those same routes. |
| Inngest jobs-table read (Inngest REST `/v1/events/.../runs`) | API / Backend (`/api/operator/jobs` route) | Signing-key Bearer auth | Signing key MUST NOT be sent to browser. The route proxies the Inngest API and returns clean JSON to the SWR-polling client. 15s polling per D-D3. |
| Manual_overrides CRUD | API / Backend (`/api/operator/manual-overrides` route) | Service-role client | Same trust model as the Inngest writer. POST/PATCH/DELETE all server-side; the client UI never talks to Supabase directly in 05.6 (per D-D2 URL-obscurity model). |
| Postgres readers (dormant in 05.6) | API / Backend (`dashboard-web/src/lib/postgresReaders.ts`) | anon-key client | `/api/data`, `/api/store-meta`, etc. branch on `readFrom()` and call either the existing Sheets reader OR the new Postgres reader. Both return the same shape so consumer code is unchanged. |
| Feature flag (`READ_FROM`) | API / Backend (`dashboard-web/src/lib/featureFlags.ts`, evaluated per request) | — | Pure function over `process.env.READ_FROM`. Read at request time so Vercel env-var changes take effect without redeploy (D-E2). |
| One-off importer (38 manual_spend rows from Sheets → Supabase) | CLI / Local script (`dashboard-web/scripts/import-manual-overrides.ts`) | Service-role client + existing `sheets.ts:getAuth` | Run once by operator via `npx tsx scripts/import-manual-overrides.ts`. Idempotent via UNIQUE (date, store_id, platform) constraint. NOT an Inngest function — single-shot. |

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Decision Set A — Architecture**
- D-A1 — Stack: Supabase Postgres + Inngest cloud + Vercel + Next.js. Locked. No alternatives.
- D-A2 — Rebuild from upstream APIs, not migrate Sheets rows.
- D-A3 — History scope: from 2026-05-01 forward.
- D-A4 — No dual-write. Apps Script keeps writing to Sheets independently.
- D-A5 — manual_overrides is load-bearing (38 rows). Cannot be re-derived from Meta API.

**Decision Set B — Inngest**
- D-B1 — Inngest cloud free tier (~50K executions/month).
- D-B2 — Function inventory: `cron-daily-{store}` (`0 5 * * *`), `cron-live-{store}` (`*/15 * * * *`), `event/sync-now`, `event/backfill`.
- D-B3 — Inngest function language: TypeScript.
- D-B4 — Service-role client for writes, anon-key client for reads.
- D-B5 — Idempotency: every write uses `ON CONFLICT (pkey) DO UPDATE`.
- D-B6 — Retries: rely on Inngest's default (4 retries, exponential backoff).

**Decision Set C — TS Fetcher Port**
- D-C1 — 5 fetcher modules under `dashboard-web/src/lib/fetchers/`.
- D-C2 — Each fetcher exports a single `fetchXForDay(storeId, date)` or `fetchXForRange(storeId, from, to)`. No singleton state, no PropertiesService.
- D-C3 — Fetcher modules are pure. Inngest wrappers persist.
- D-C4 — Algorithm parity required vs frozen Sheets snapshots for 2026-05-15..05-20 (modulo Phase 05.2.3.0 refund correction).
- D-C5 — No Apps Script references in new fetchers.

**Decision Set D — Operator Console**
- D-D1 — Route `/operator`, Hebrew tab "ניהול".
- D-D2 — Sub-views: jobs table (Inngest REST), backfill range picker, manual_overrides CRUD, sync-now buttons.
- D-D3 — No real-time. 15s polling.
- D-D4 — Match existing dashboard design system (Tailwind, RTL, Lucide icons).

**Decision Set E — Postgres readers**
- D-E1 — Build Postgres-reading equivalents, dormant in 05.6.
- D-E2 — `READ_FROM` env var, defaults `'sheets'`, read at request time.
- D-E3 — Every `/api/*` route gets 1-line branch.

**Decision Set F — manual_overrides importer**
- D-F1 — `dashboard-web/scripts/import-manual-overrides.ts` via `npx tsx`. Idempotent.
- D-F2 — Reads `manual-spend` Sheets tab via existing `sheets.ts:getAuth`. Writes via service_role client.
- D-F3 — Summary output: `imported N, skipped M, errored P`.

**Decision Set G — Branching/CI**
- D-G1 — All work on `main`.
- D-G2 — Vercel CI auto-deploys; Inngest-Vercel integration auto-syncs functions.

### Pattern 2 — Inngest cron function (factory pattern across stores)

**What:** One factory function emitting one `inngest.createFunction()` per store. Keeps the function code DRY across 3 stores.

**When to use:** For both `cron-daily-{store}` and `cron-live-{store}` families. The handler body differs in only one place: the per-day vs per-15-min window.

**Cron syntax (verified):** Inngest cron strings are unix-cron. **Default timezone is UTC.** For Israel-local time, prefix with `TZ=Asia/Jerusalem`. CONTEXT.md D-B2 specifies `0 5 * * *` (UTC) which equals 08:00 Asia/Jerusalem during winter or 08:00 Asia/Jerusalem during summer — **wait, no:** `0 5 * * *` UTC is `08:00` Israel during winter (IST = UTC+2) but `08:00` during summer (IDT = UTC+3 means UTC 5:00 = 08:00 IDT). The CONTEXT.md text says "00:05 daily" but the cron `0 5 * * *` is "05:00 UTC, every day at minute 0 of hour 5." **This needs operator clarification — see Open Questions.** [The number "00:05" in CONTEXT.md is ambiguous: is it 00:05 UTC or 00:05 Asia/Jerusalem? Apps Script's current trigger runs at the Israel-local hour configured in `Config.gs:TZ='Asia/Jerusalem'`.]

**Skeleton:**

```typescript
// dashboard-web/src/inngest/functions/cronDaily.ts
import { inngest } from '@/inngest/client';
import { fetchShopifyDayRows } from '@/lib/fetchers/shopify';
import { fetchMetaDayRows } from '@/lib/fetchers/meta';
import { fetchGoogleAdsDayRows } from '@/lib/fetchers/googleAds';
import { mergeOverridesFromSupabase } from '@/lib/fetchers/manualOverrides';
import { getSupabaseAdmin } from '@/lib/supabaseAdmin';

const STORES = ['uzoshop', 'zolplus', 'usmile360'] as const;

// Helper: yesterday's date in YYYY-MM-DD format, in Asia/Jerusalem TZ.
// Mirrors Apps Script's `yesterdayStr_()` in Config.gs.
function yesterdayJerusalem(): string {
  const fmt = new Intl.DateTimeFormat('en-CA', {
    timeZone: 'Asia/Jerusalem',
    year: 'numeric', month: '2-digit', day: '2-digit',
  });
  const now = new Date(Date.now() - 24 * 60 * 60 * 1000);
  return fmt.format(now); // 'YYYY-MM-DD'
}

function makeCronDaily(storeId: typeof STORES[number]) {
  return inngest.createFunction(
    {
      id: `cron-daily-${storeId}`,
      // 'TZ=Asia/Jerusalem 5 0 * * *' = 00:05 Asia/Jerusalem every day (matches
      // Apps Script trigger). The `5` is minutes, `0` is hour-of-day. UTC variant
      // is 'TZ=UTC 5 22 * * *' (winter) or 'TZ=UTC 5 21 * * *' (summer) — using
      // the TZ= prefix avoids the DST shift problem.
      // Use jitter to spread the 3 store crons over a 1-min window so they
      // don't all hit Shopify/Meta at the exact same second.
    },
    { cron: 'TZ=Asia/Jerusalem 5 0 * * *' },
    async ({ event, step, attempt }) => {
      const date = yesterdayJerusalem();

      // step.run wraps each side-effect so Inngest retries only the failing
      // step on error, not the entire function. Each step.run callback MUST
      // be deterministic across retries (the same step ID + same return value
      // = no re-execution).
      const shopify = await step.run('fetch-shopify', async () => {
        return await fetchShopifyDayRows(storeId, date);
      });

      const metaSpend = await step.run('fetch-meta-spend', async () => {
        return await fetchMetaSpendForDay(storeId, date);
      });

      const googleSpend = storeId === 'uzoshop'
        ? await step.run('fetch-google-spend', async () => {
            return await fetchGoogleAdsSpendForDay(storeId, date);
          })
        : { spend: 0, currency: 'CAD' };  // zolplus + usmile360 have no Google Ads

      // Apply manual overrides BEFORE persisting (D-A5 + D-F2 invariant).
      const merged = await step.run('apply-manual-overrides', async () => {
        return await mergeOverridesFromSupabase({
          storeId, date, metaSpend, googleSpend,
        });
      });

      // FX conversion (Meta is ILS, Google is CAD already, Shopify is CAD already).
      const fxIlsToCad = await step.run('fetch-fx', async () => {
        return await getFxRate('ILS', 'CAD', date);
      });

      // Persist all 5 tables in their own steps so each gets independent retries.
      await step.run('persist-data-daily', async () => {
        const { error } = await getSupabaseAdmin()
          .from('data_daily')
          .upsert({
            date, store_id: storeId, store_name: shopify.storeName,
            fb_spend_cad: merged.fbSpendCad,
            ga_spend_cad: merged.gaSpendCad,
            total_spend_cad: merged.totalSpendCad,
            revenue_cad: shopify.revenueCad,
            roas: merged.totalSpendCad > 0 ? shopify.revenueCad / merged.totalSpendCad : 0,
            gross_profit_cad: shopify.revenueCad - merged.totalSpendCad,
            cogs_cad: shopify.revenueCad * 0.25,
            net_profit_cad: shopify.revenueCad - merged.totalSpendCad - shopify.revenueCad * 0.25,
          }, { onConflict: 'date,store_id' });
        if (error) throw new Error(`data_daily upsert: ${error.message}`);
      });

      // ... similar step.run for products_daily, campaigns_daily, ads_daily,
      // orders_attribution. Each step independently retried by Inngest.

      return {
        storeId, date,
        shopifyRevenue: shopify.revenueCad,
        metaSpendCad: merged.fbSpendCad,
        googleSpendCad: merged.gaSpendCad,
      };
    },
  );
}

export const cronDailyFunctions = STORES.map(makeCronDaily);
```

**Source:** [VERIFIED: Cron syntax + TZ= prefix from https://www.inngest.com/docs/guides/scheduled-functions; step.run retry semantics from https://www.inngest.com/docs/features/inngest-functions/error-retries/retries; default = 4 retries / 5 attempts with exponential backoff + jitter]

### Pattern 3 — TS fetcher port (general shape)

**What:** Each `lib/fetchers/*.ts` module exports one or more pure async functions taking `storeId + date(s)` and returning typed row arrays. Side-effect-free — no DB writes, no PropertiesService, no globals.

**When to use:** For each of the 5 fetchers. The Inngest function code (Pattern 2) calls them and writes the results.

**Skeleton (Meta fetcher, simplified):**

```typescript
// dashboard-web/src/lib/fetchers/meta.ts

// META_API_VERSION: bump to current. v20.0 (Apps Script) deprecates Sept 2026.
// All <v24.0 deprecate June 9, 2026. Use v23.0 (or v24.0 — verify in PLAN).
// [VERIFIED 2026-05-21: https://developers.facebook.com/blog/post/2025/01/21/...]
const META_API_VERSION = 'v23.0';

export type MetaAdSetRow = {
  campaignId: string;
  campaignName: string;
  adSetId: string;
  adSetName: string;
  spend: number;          // in account currency (ILS for all 3 stores)
  currency: string;
  impressions: number;
  clicks: number;
  conversions: number;
  conversionValue: number;
};

export async function fetchMetaAdSetInsights(
  storeId: string,
  dateStr: string,
): Promise<MetaAdSetRow[]> {
  const token = process.env[`META_${storeId.toUpperCase()}_TOKEN`]
    || process.env.META_GLOBAL_TOKEN;
  if (!token) throw new Error(`Missing Meta token for ${storeId}`);

  const adAccountId = (process.env[`META_${storeId.toUpperCase()}_AD_ACCOUNT_ID`] || '')
    .replace(/^act_/, '');
  if (!adAccountId) throw new Error(`Missing Meta ad account id for ${storeId}`);

  const fields = 'campaign_id,campaign_name,adset_id,adset_name,spend,impressions,' +
                 'clicks,actions,action_values,account_currency';
  let url: string | null =
    `https://graph.facebook.com/${META_API_VERSION}/act_${adAccountId}/insights` +
    `?fields=${fields}` +
    `&time_range=${encodeURIComponent(JSON.stringify({ since: dateStr, until: dateStr }))}` +
    `&level=adset&limit=500` +
    `&access_token=${encodeURIComponent(token)}`;

  const out: MetaAdSetRow[] = [];
  let safety = 0;
  while (url && safety < 50) {
    const res = await fetch(url);
    if (!res.ok) {
      throw new Error(`Meta adsets ${storeId} ${dateStr} failed (${res.status}): ${await res.text()}`);
    }
    const body = await res.json() as {
      data?: Array<{
        campaign_id?: string; campaign_name?: string;
        adset_id?: string; adset_name?: string;
        spend?: string; impressions?: string; clicks?: string;
        actions?: Array<{ action_type: string; value: string }>;
        action_values?: Array<{ action_type: string; value: string }>;
        account_currency?: string;
      }>;
      paging?: { next?: string };
    };
    for (const r of (body.data ?? [])) {
      const spend = parseFloat(r.spend ?? '0') || 0;
      const impressions = parseInt(r.impressions ?? '0', 10) || 0;
      const conv = extractMetaPurchases(r.actions ?? [], r.action_values ?? []);
      if (spend === 0 && impressions === 0 && conv.count === 0) continue;
      out.push({
        campaignId: r.campaign_id ?? '',
        campaignName: r.campaign_name ?? '',
        adSetId: r.adset_id ?? '',
        adSetName: r.adset_name ?? '',
        spend,
        currency: r.account_currency ?? 'ILS',
        impressions,
        clicks: parseInt(r.clicks ?? '0', 10) || 0,
        conversions: conv.count,
        conversionValue: conv.value,
      });
    }
    url = body.paging?.next ?? null;
    safety++;
  }
  if (safety >= 50) {
    console.warn(`Meta adsets ${storeId} ${dateStr}: hit pagination cap of 50 pages`);
  }
  return out;
}

function extractMetaPurchases(
  actions: Array<{ action_type: string; value: string }>,
  values:  Array<{ action_type: string; value: string }>,
) {
  // Priority: omni_purchase (includes offline) → purchase → fb_pixel_purchase
  // Matches MetaAds.gs:85-98 exactly.
  const types = ['omni_purchase', 'purchase', 'offsite_conversion.fb_pixel_purchase'];
  function pick(arr: Array<{ action_type: string; value: string }>): number {
    for (const t of types) {
      const found = arr.find(a => a.action_type === t);
      if (found) return parseFloat(found.value) || 0;
    }
    return 0;
  }
  return { count: pick(actions), value: pick(values) };
}
```

```typescript
/**
 * Server-only Supabase admin client (service_role).
 *
 * Why service_role and not anon:
 *  - The `20260521075741_add_constraints_and_grants.sql` migration grants

 *     (`src/inngest/functions/*.ts`), API routes

 *     and the one-off importer (`scripts/import-manual-overrides.ts`).
 *   - There is no `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` and there never
 *     should be — even mentioning that env-var name in code outside of an
 *     explanatory comment is a planning defect (mirrors the supabase.ts
 *     T-05.5-03-S3 threat).
 *
 * Pattern: lazy factory matching `supabase.ts:30` (BL-01 fix from 05.5-03).
 * The throw happens inside the function so a missing env var manifests as
 * a caught Inngest step error (→ Inngest retries 4 times, then dead-letters
 * → operator sees in jobs table), NOT a module-load-time crash that
 * preempts every other Inngest function.
 */
import { createClient, type SupabaseClient } from '@supabase/supabase-js';

let cached: SupabaseClient | null = null;

export function getSupabaseAdmin(): SupabaseClient {
  if (cached) return cached;

  const url = process.env.SUPABASE_URL;
  const key = process.env.SUPABASE_SERVICE_ROLE_KEY;

  if (!url || !key) {
    throw new Error(
      'SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY missing — check Vercel env vars',
    );
  }

  cached = createClient(url, key, {
    auth: {
      persistSession: false,    // server-side; no user session
      autoRefreshToken: false,  // service_role doesn't need token refresh
      detectSessionInUrl: false,
    },
  });
  return cached;
}
```

- **Base URL:** `https://api.inngest.com` [VERIFIED: `https://api-docs.inngest.com/api-specs/v1.json`]
- **List events:** `GET /v1/events?received_after=<RFC3339>&received_before=<RFC3339>&name=<event_name>&limit=<1-100>&cursor=<event_id>` [VERIFIED: same spec]
- **List runs for one event:** `GET /v1/events/{internalID}/runs` (returns `{ data: [{ run_id, run_started_at, ended_at, status, output, function_id, function_version, environment_id, event_id, batch_id, original_run_id, cron, ... }] }`) [VERIFIED: same spec]
- **Get one run:** `GET /v1/runs/{runID}` [VERIFIED]
- **Get run steps/jobs:** `GET /v1/runs/{runID}/jobs` [VERIFIED]
- **Cancel a run:** `DELETE /v1/runs/{runID}` [VERIFIED]
- **Auth:** `Authorization: Bearer ${INNGEST_SIGNING_KEY}` (the signing key — same key the SDK already uses; do NOT create a separate API key for 05.6) [VERIFIED: `securitySchemes.your-signing-key` in v1 spec]

**Important caveat:** The v1 API does NOT expose a `/v1/runs` LIST endpoint that filters by `function_id` or `status` across all events. To build the operator jobs table, two approaches:

- **Approach 1 (recommended):** List recent events (`GET /v1/events?limit=100&received_after=<24h ago>`), then for each event, fetch runs (`GET /v1/events/{id}/runs`). Aggregate client-side. Works but is `N+1`.
- **Approach 2:** List events, then DEFER the per-event run fetch to the row click — show a basic "event received N runs" summary in the table, and only fetch the detailed runs when the operator expands a row. Better UX for 50+ events.

**Skeleton (Approach 1):**

```typescript
// dashboard-web/src/app/api/operator/jobs/route.ts
import { NextResponse } from 'next/server';
import { userFacingError } from '@/lib/apiErrors';

export const revalidate = 5; // client polls every 15s; server caches 5s

type InngestRun = {
  run_id: string;
  run_started_at: string;
  ended_at: string | null;
  status: 'Running' | 'Completed' | 'Failed' | 'Cancelled';
  function_id: string;
  event_id: string | null;
  output?: unknown;
};

type InngestEvent = {
  internal_id: string;
  name: string;
  received_at: string;
};

export async function GET(req: Request) {
  const key = process.env.INNGEST_SIGNING_KEY;
  if (!key) {
    return NextResponse.json(
      { runs: [], error: 'Missing INNGEST_SIGNING_KEY' },
      { status: 200 },
    );
  }
  const limit = parseInt(new URL(req.url).searchParams.get('limit') ?? '50', 10);

  try {
    // 1. List recent events.
    const since = new Date(Date.now() - 24 * 60 * 60 * 1000).toISOString();
    const evRes = await fetch(
      `https://api.inngest.com/v1/events?received_after=${encodeURIComponent(since)}&limit=${limit}`,
      { headers: { Authorization: `Bearer ${key}` } },
    );
    if (!evRes.ok) {
      throw new Error(`Inngest events list ${evRes.status}: ${await evRes.text()}`);
    }
    const evBody = await evRes.json() as { data: InngestEvent[] };

    // 2. Fan-out for runs (cap at 50 events to avoid quota burn).
    const events = evBody.data.slice(0, Math.min(limit, 50));
    const runs: Array<InngestRun & { event_name?: string }> = [];
    for (const ev of events) {
      const r = await fetch(
        `https://api.inngest.com/v1/events/${ev.internal_id}/runs`,
        { headers: { Authorization: `Bearer ${key}` } },
      );
      if (!r.ok) continue;
      const rb = await r.json() as { data: InngestRun[] };
      for (const run of rb.data) {
        runs.push({ ...run, event_name: ev.name });
      }
    }

    // Sort newest first.
    runs.sort((a, b) => b.run_started_at.localeCompare(a.run_started_at));
    return NextResponse.json({ runs, lastUpdated: new Date().toISOString() });
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    console.error('Inngest jobs proxy failed:', message);
    return NextResponse.json(
      { runs: [], error: userFacingError(message), lastUpdated: new Date().toISOString() },
      { status: 200 },
    );
  }
}
```

```typescript
 * shape so route handlers can branch on readFrom() without affecting consumers.

 * Dormant in 05.6 — only invoked when process.env.READ_FROM === 'postgres'

export async function fetchDailyDataFromPostgres(
  opts?: { range?: DateRange },
): Promise<DailyRow[]> {
  let q = getSupabase()
    .from('data_daily')
    .select('date, store_id, store_name, fb_spend_cad, ga_spend_cad, total_spend_cad, revenue_cad, gross_profit_cad, cogs_cad, net_profit_cad');

  if (opts?.range) {
    q = q.gte('date', opts.range.from).lte('date', opts.range.to);
  }

  const { data, error } = await q;
  if (error) throw new Error(`postgresReaders.fetchDailyData: ${error.message}`);

  for (const r of data ?? []) {
    const dateStr = String(r.date);
    if (opts?.range && !isInRange(dateStr, opts.range)) continue;
    const fbSpend = Number(r.fb_spend_cad ?? 0);
    const gaSpend = Number(r.ga_spend_cad ?? 0);
    const totalSpend = Number(r.total_spend_cad ?? 0) || fbSpend + gaSpend;
    const revenue = Number(r.revenue_cad ?? 0);
    const roas = totalSpend > 0 ? revenue / totalSpend : 0;
    rows.push({
      date: dateStr,
      storeId: String(r.store_id),
      storeName: String(r.store_name),
      fbSpend, gaSpend, totalSpend, revenue, roas,
      grossProfit: Number(r.gross_profit_cad ?? (revenue - totalSpend)),
      cogs: Number(r.cogs_cad ?? revenue * COGS_RATE_OF_REVENUE),
      netProfit: Number(r.net_profit_cad ?? (revenue - totalSpend - revenue * COGS_RATE_OF_REVENUE)),
      hasCogs: true,

  }
  return rows;
}
```

### Pattern 9 — Shopify refund algorithm (LOAD-BEARING — Phase 05.2.3.0 carry-forward)

**What:** The pure-TS port of the refund-net-of-refunds algorithm already exists at `dashboard-web/src/lib/shopifyRevenueRefunds.ts` (256 lines). It exports `computeRevenueWithCrossDayRefunds(orders, dateStr, tz)` which mirrors `Shopify.gs:90` (`getShopifyRevenue`) + `Shopify.gs:633` (`getShopifyRefundsForDay_`) + `Shopify.gs:208` (`getShopifyProductSalesForDay`) exactly. Has 8 vitest fixture-based tests at `dashboard-web/src/lib/__tests__/shopifyRevenueRefunds.test.ts`.

**When to use:** The new `dashboard-web/src/lib/fetchers/shopify.ts` MUST import and use this existing function, NOT reimplement the algorithm. The fetcher's responsibility is HTTP (paginate orders+refunds for the day) → call `computeRevenueWithCrossDayRefunds(...)` → return per-store + per-product totals.

**The three load-bearing invariants (DO NOT BREAK):**

1. **Store-level gross uses `total_price` (immutable per Shopify Admin REST 2024-10), NOT `current_total_price`.** Under `current_total_price`, every refund within 48h of order creation gets deducted TWICE once any backfill re-fetches the prior-day row. See CR-01 in 05.2.3.0-REVIEW.md.

2. **Refunds attribute to their `processed_at` day exactly ONCE — no cross-day filter.** Same-day and cross-day refunds both deduct on the refund day. Re-fetching prior-day rows no longer changes their value because `total_price` is immutable.

3. **Per-product intra-order refund map is built ONLY from refunds whose `processed_at` falls on the same day as the order.** A future-day refund on an order created on day D must NOT be deducted from day D's per-product net — it deducts on its processed_at day. See CR-02.

Plus: **No `Math.max(0, ...)` clamping ANYWHERE.** Per-line, per-product, and store-level nets can all go negative (D-D3). `transactions[].amount` is IGNORED (PROBE-EVIDENCE.md §Finding 1).

**Algorithm pseudocode (already implemented at `shopifyRevenueRefunds.ts:150`):**

```
function computeRevenueWithCrossDayRefunds(orders, dateStr, tz='Asia/Jerusalem'):
  sameDayGross = 0
  storeRefundDeduction = 0
  customItemRefundCad = 0
  byProduct = {}                            // product_id → { netRevenueCad }

  for each order o in orders:
    if o.test == true OR o.financial_status == 'voided': skip

    isSameDayOrder = (dayInTz(o.created_at, tz) == dateStr)

    // === Same-day order path ===
    if isSameDayOrder:
      sameDayGross += parseNum(o.total_price)   // INVARIANT 1: total_price

      // Per-product line gross.
      for each li in o.line_items:
        pid = String(li.product_id ?? '')
        if not pid: continue
        lineGross = parseNum(li.price) * parseNum(li.quantity)
        byProduct[pid].netRevenueCad += lineGross

      // INVARIANT 3: intra-order refundByLineId filtered to processed_at == dateStr.
      for each r in (o.refunds ?? []):
        if not r.processed_at: continue
        if dayInTz(r.processed_at, tz) != dateStr: continue   // SAME-DAY refunds only here
        for each rli in (r.refund_line_items ?? []):
          pid = String(rli.product_id ?? '')
          if not pid: continue
          byProduct[pid].netRevenueCad -= parseNum(rli.subtotal)

    // === Refund-day attribution path (INVARIANT 2) ===
    // EVERY refund processed on day D deducts here. No cross-day filter.
    for each r in (o.refunds ?? []):
      if not r.processed_at: continue
      if dayInTz(r.processed_at, tz) != dateStr: continue
      for each rli in (r.refund_line_items ?? []):
        amt = parseNum(rli.subtotal ?? rli.total ?? 0)
        pid = String(rli.product_id ?? '')
        storeRefundDeduction += amt
        if pid:
          byProduct[pid].netRevenueCad -= amt
        else:
          customItemRefundCad += amt

  // D-D3: NO Math.max(0, ...). Negative values are valid.
  return {
    storeNetCad: sameDayGross - storeRefundDeduction,
    byProduct,
    customItemRefundCad,
  }
```

### Pattern 11 — One-off manual_overrides importer

**What:** A standalone TypeScript script run via `npx --yes tsx scripts/import-manual-overrides.ts`. **When to use:** Exactly once. Outputs a summary line `imported N, skipped M, errored P`.

**Skeleton:**

```typescript
// dashboard-web/scripts/import-manual-overrides.ts
/**
 * One-off importer: 38 manual_spend rows from Google Sheets → Supabase.
 *
 * Run via: cd dashboard-web && npx --yes tsx scripts/import-manual-overrides.ts
 *
 * Idempotent — re-running is safe (UNIQUE constraint on (date, store_id, platform)
 * + ignoreDuplicates=true).
 *
 * Reads env from .env.local (Next.js dev convention). The script does NOT load
 * .env.local automatically — operator runs with `dotenv -e .env.local -- npx tsx ...`
 * OR exports env vars first. See User Manual update.
 */
import 'dotenv/config';  // OPTIONAL — if @next/env or dotenv not installed, skip
import { google } from 'googleapis';
import { getAuth } from '@/lib/sheets';
import { getSupabaseAdmin } from '@/lib/supabaseAdmin';

const MANUAL_SPEND_TAB = 'manual-spend';

type RowToInsert = {
  date: string;
  store_id: string;
  platform: 'meta' | 'google';  // lowercase to match CHECK constraint
  spend: number;
  currency: string;
  notes: string | null;
};

async function main() {
  const auth = getAuth();
  const sheets = google.sheets({ version: 'v4', auth });
  const spreadsheetId = process.env.SPREADSHEET_ID;
  if (!spreadsheetId) throw new Error('Missing SPREADSHEET_ID env var');

  console.log(`Reading from Sheets: ${MANUAL_SPEND_TAB} tab`);
  const res = await sheets.spreadsheets.values.get({
    spreadsheetId,
    range: `${MANUAL_SPEND_TAB}!A2:F1000`,
    valueRenderOption: 'UNFORMATTED_VALUE',
    dateTimeRenderOption: 'FORMATTED_STRING',
  });
  const values = res.data.values ?? [];

  const rows: RowToInsert[] = [];
  for (const row of values) {
    const date = parseDate(row[0]);
    if (!date) continue;
    const store_id = String(row[1] ?? '').trim();
    const platformRaw = String(row[2] ?? '').trim();
    if (!store_id || !platformRaw) continue;
    const platform = platformRaw.toLowerCase() === 'meta' ? 'meta'
                   : platformRaw.toLowerCase() === 'google' ? 'google'
                   : null;
    if (!platform) continue;
    const spend = parseFloat(String(row[3] ?? '0'));
    if (!Number.isFinite(spend)) continue;
    const currency = String(row[4] ?? 'ILS').trim().toUpperCase();
    const notes = row[5] ? String(row[5]) : null;
    rows.push({ date, store_id, platform, spend, currency, notes });
  }
  console.log(`Parsed ${rows.length} rows from Sheets`);

  // Batch upsert with ignoreDuplicates=true → ON CONFLICT (...) DO NOTHING
  const { data, error } = await getSupabaseAdmin()
    .from('manual_overrides')
    .upsert(rows, { onConflict: 'date,store_id,platform', ignoreDuplicates: true })
    .select();
  if (error) {
    console.error('Upsert failed:', error);
    process.exit(1);
  }
  const inserted = data?.length ?? 0;
  const skipped = rows.length - inserted;
  console.log(`Imported ${inserted} rows, skipped ${skipped} (already present), errored 0`);
}

function parseDate(v: unknown): string | null {
  if (v instanceof Date && !isNaN(v.getTime())) return v.toISOString().slice(0, 10);
  const s = String(v).trim();
  if (/^\d{4}-\d{2}-\d{2}/.test(s)) return s.slice(0, 10);
  return null;
}

main().catch((e) => {
  console.error('Fatal:', e);
  process.exit(1);
});
```

### Anti-Patterns to Avoid

- **Importing `supabaseAdmin.ts` from a client component.** ABSOLUTE rule. The service_role key would be bundled to the browser. Plans should `grep` for any import of `@/lib/supabaseAdmin` outside `src/inngest/`, `src/app/api/`, and `scripts/`.

- **Forgetting `onConflict` on the upsert.** Without it, a re-run of the same cron tick creates duplicate rows (or violates the PK constraint and throws). Each persist step.run callback MUST include `{ onConflict: '<pkey-cols-comma-separated>' }`.

- **Reading `process.env.READ_FROM` at module-load.** Defeats D-E2 — flipping the env var on Vercel would require redeploy. Always call `readFrom()` as a function inside the request handler.

- **Touching `.gs` files in 05.6.** Out of scope per CONTEXT.md `<specifics>`. Apps Script keeps running unchanged.

- **Direct DB writes from Next.js API routes that should go through Inngest.** A write triggered from the operator console (sync-now or backfill) MUST go via `inngest.send()` → Inngest function → write. Direct synchronous writes from the API route mean (a) no retry on transient failure, (b) the operator UI blocks for the full duration of the fetch, (c) the write doesn't appear in the jobs table. Manual_overrides CRUD is the ONE exception — those are user-driven row-level edits, fast, and there's no fetcher pipeline to retry. Everything else: route → `inngest.send()` → return 202.

- **Embedding the Inngest dashboard via iframe instead of the REST proxy.** D-D2 explicitly forbids this for the jobs table — "NOT iframe embed (better UX integration)".

- **Hand-rolling the Shopify refund algorithm in the new fetcher.** A complete pure-TS implementation already exists at `dashboard-web/src/lib/shopifyRevenueRefunds.ts:150` with vitest coverage. The new `dashboard-web/src/lib/fetchers/shopify.ts` MUST import and use that function, not re-derive the algorithm.

- **Using `force-dynamic` on GET routes with `revalidate`.** They conflict — `force-dynamic` overrides `revalidate` and the explicit Cache-Control header. See existing comment in `dashboard-web/src/app/api/data/route.ts:11-14`. Use one or the other based on cacheability: `force-dynamic` for CRUD/mutating routes (manual-overrides POST/PATCH/DELETE), `revalidate` for GET-only data routes.

- **Using a `MemberExpression` for the `revalidate` route segment config.** Next.js's static analyzer rejects `export const revalidate = CACHE_CONFIG.foo.revalidate` — it requires a literal. See Phase 05.5-03 Deviation #1. Always use a literal `export const revalidate = N;` with a sync-required comment.

- **Calling Inngest REST v2 with the signing key.** v2 uses a separate "API key" credential, NOT the signing key. v1 uses the signing key. For 05.6, use v1.

- **Mixing `process.env.NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` anywhere.** There is no such env var and there never should be. service_role MUST be server-only.

|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1 — Cron timezone confusion

**What goes wrong:** The operator's mental model is "00:05 daily" (local Israel time, matching the current Apps Script trigger). But Inngest's default timezone is UTC. A naive `cron: '5 0 * * *'` fires at 00:05 UTC = 02:05 / 03:05 Asia/Jerusalem (depending on DST) — 2 hours off the intended schedule, every day.

**Why it happens:** Cron strings have no built-in TZ awareness; Inngest defaults to UTC.

**How to avoid:** Always use the `TZ=Asia/Jerusalem` prefix when the intent is Israel-local time: `cron: 'TZ=Asia/Jerusalem 5 0 * * *'`. Confirms with `crontab.guru` — paste the cron string AND interpret the result against the right TZ.

**Warning signs:** First run lands at 02:05 / 03:05 Israel time instead of 00:05 Israel.

[VERIFIED: https://www.inngest.com/docs/guides/scheduled-functions]

### Pitfall 2 — Service-role key bundled to browser

**What goes wrong:** Importing `@/lib/supabaseAdmin` from a client component (`'use client';` file) causes Next.js to bundle the import — including the `process.env.SUPABASE_SERVICE_ROLE_KEY` reference — into the JS shipped to the browser. The key value isn't actually shipped (Next.js only inlines `NEXT_PUBLIC_*` vars), but the IMPORT graph includes server-side code, which can confuse Next.js's tree-shaking and may trigger "trying to use server module on client" errors at runtime — OR (worst case) leak the actual env var if the variable name is accidentally prefixed with `NEXT_PUBLIC_`.

**Why it happens:** Auto-import in the editor; copy-paste from an Inngest function into a UI component.

**How to avoid:**
1. NEVER use the `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` env-var name (it doesn't exist; renaming the existing `SUPABASE_SERVICE_ROLE_KEY` to add the prefix is the catastrophic mistake to guard against).
2. Per-plan grep gate: `! grep -rn "import.*supabaseAdmin" dashboard-web/src/components/ dashboard-web/src/app/operator/` should return ZERO matches.
3. The `supabaseAdmin.ts` file's JSDoc explicitly forbids client-side import.

**Warning signs:** Vercel build warning "trying to use server module on client" referencing supabaseAdmin.ts.

### Pitfall 3 — Step function not idempotent across retries

**What goes wrong:** A step.run callback that has side effects beyond Supabase writes — e.g., sends an email, posts to Slack, increments a counter — gets re-executed on retry. Inngest guarantees the RETURN VALUE is deterministic across retries (you observed the value once, you observe the same value again), but the SIDE EFFECT runs every retry attempt.

**Why it happens:** Mental model "step.run wraps a function call" → "function call is single-execution". But the retry mechanism re-invokes the function until it returns successfully.

**How to avoid:**
1. step.run callbacks MUST be idempotent. Supabase upserts with `onConflict` are naturally idempotent. fetch() reads are naturally idempotent. Email/Slack/counter increments are NOT.
2. For 05.6, every step.run does only: (a) HTTP fetch (idempotent), or (b) Supabase upsert with ON CONFLICT (idempotent). No side effects.
3. Logging via `console.log` is fine (re-emitted on retry, no semantic effect).

**Warning signs:** Supabase row count > expected after a transient API failure.

[VERIFIED: https://www.inngest.com/docs/features/inngest-functions/error-retries/retries]

### Pitfall 4 — Inngest free-tier execution overshoot

**What goes wrong:** Each step.run counts as an "execution." A function with 8 step.run calls = 9 executions per run (1 for the function + 8 for steps). 6 cron functions × 96 daily ticks × 3 stores × 9 execs = 15,552/day = 466,560/month — **exceeds the 50K free-tier limit**.

**Wait — recomputing more carefully.** Daily cron = 1 run/day per store. Live cron = 96 runs/day per store (every 15min × 24h). So per store:

- daily: 1 run × ~6 steps = 7 execs/day
- live: 96 runs × ~3 steps = 384 execs/day

× 3 stores = (7 + 384) × 3 = 1,173 execs/day = ~35,200/month for crons alone. Add ~50 event-triggered runs/day × ~6 steps = 9,000/month. **Total ~44,200/month — 88% of the free-tier limit.**

**Why it happens:** Initial estimate "9k/month" in CONTEXT.md D-B1 likely undercounted steps. Inngest's docs explicitly say "Each run or step in your code counts as one execution. For example, a run with 2 steps = 3 executions total (1 for the run + 2 for steps)." [VERIFIED: https://www.inngest.com/pricing]

**How to avoid:**
1. **Use FEWER step.run calls per function.** Instead of one step.run per Supabase table write, batch all 5 table writes into ONE step.run (with a try/catch that throws on any failure — Inngest retries the whole batch). Trade-off: a transient failure on one table re-runs the writes for all 5 (idempotent, so fine).
2. Move the live cron to every 30 minutes instead of every 15 if the headroom becomes critical. Operator would need to confirm — this is a behavior change.
3. Monitor the Inngest dashboard's monthly-usage counter in the first week post-launch.

**Recommended decomposition (gives ~6 execs/run for daily, ~3 for live):**
- daily: step.run('fetch-all') merged Shopify+Meta+Google fetch, step.run('fetch-fx'), step.run('persist-all') one batched UPSERT call per table = 5 + 1 = 6 steps + 1 function = 7 execs.
- live: step.run('fetch-shopify-rolling-3day'), step.run('persist-data-daily') = 2 steps + 1 function = 3 execs.

**Warning signs:** Inngest dashboard shows >40K execs/month in Week 2.

**Reconciliation with D-B1:** D-B1 claims "well under 50k executions/month free tier" — that estimate didn't account for the run-and-step counting model. Plans should target ≤30K/month execs to leave 40% headroom.

### Pitfall 5 — Meta API token expiry mid-job

**What goes wrong:** Meta's regular access tokens expire in 60 days (System User tokens are non-expiring). A regular token mid-rotation can suddenly start returning 401 — and the Inngest function throws, retries, and dead-letters.

**Why it happens:** Token expiry is a calendar event, not a system event. No warning.

**How to avoid:**
1. PROPS-MAP includes a rotation playbook (per Phase 05.5-02 SUMMARY). Operator's job to rotate before expiry.
2. The TS fetcher should NOT attempt token refresh — Meta tokens don't have a self-refresh flow like Shopify or Google Ads. If 401, throw a clear error including the storeId and the env-var name to update.

**Warning signs:** Daily cron starts failing for one store specifically (other stores OK) for >24h.

### Pitfall 6 — Shopify pagination cap of 50 hit silently

**What goes wrong:** Both `Shopify.gs` and the existing TS mirror cap pagination at 50 pages. For a store with >12,500 orders/day (50 pages × 250 limit), pages 51+ are silently dropped. Apps Script logs the warning to Logger.log; the TS port should match.

**Why it happens:** Defensive safety cap to prevent runaway loops. Shopify's typical 250-per-page × 50 = 12,500 orders/day is well above current store volume (~10-50 orders/day) so the cap is invisible.

**How to avoid:** Mirror Apps Script's safety cap of 50 + the `console.warn` exactly. If the cap is ever hit, fail-fast OR log loudly enough to be visible in Inngest's UI.

### Pitfall 7 — Sheets `manual-spend` tab Platform column case-sensitivity

**What goes wrong:** Apps Script writes `'Meta'` and `'Google'` (capitalized) to the Sheets `manual-spend` tab. The Supabase `manual_overrides.platform` column has a CHECK constraint requiring `'meta'` or `'google'` (lowercase) per the constraints-and-grants migration. The importer MUST lowercase during transformation.

**Why it happens:** Schema convention — Postgres columns prefer lowercase enums for indexing & CHECK matching.

**How to avoid:** In the importer (Pattern 11), `String(platformRaw).toLowerCase()` before the upsert. Test by running the importer twice — second run should report `skipped 38` (all already present).

**Warning signs:** Importer first run reports `errored N` with error message `new row for relation "manual_overrides" violates check constraint "manual_overrides_platform_check"`.

### Pitfall 8 — Google Ads token refresh race across Inngest function concurrency

**What goes wrong:** If 3 Inngest functions (one per store) all run concurrently and all hit `googleads.accessToken` cache miss simultaneously, they all fetch a refresh token in parallel. Google's OAuth endpoint will accept all 3 (rate-limit-permitting) but emit 3 access tokens — wasted work + 3 logged events.

**Why it happens:** Apps Script's `CacheService.getScriptCache()` (used at `GoogleAds.gs:194`) is process-shared. Inngest functions on Vercel are isolated invocations — no shared cache.

**How to avoid:**
1. Only uzoshop has Google Ads (per `Config.gs:23`). So in 05.6 only 1 Inngest function (`cron-daily-uzoshop`) ever calls Google Ads. Concurrent refresh is impossible.
2. If we later expand to multi-store Google Ads: use a module-level token cache scoped to the Inngest function lifetime (cheap; doesn't bridge invocations but reuses within one invocation).
3. Alternative: use Supabase as a token-cache row in `dashboard_state` or a dedicated `oauth_tokens` table — overkill for 05.6.

**Warning signs:** Not a concern in 05.6 (single store with Google Ads). Document for future.

### Pitfall 9 — Vercel max function duration vs Inngest payload size

**What goes wrong:** Vercel's free tier limits serverless functions to 10s (Hobby) / 60s (Pro). Inngest's `serve()` handler IS a Vercel function — if a step.run callback takes >10s, Vercel kills it. Shopify pagination for a large day could exceed this.

**Why it happens:** 10s default. Vercel can be configured via `export const maxDuration = N` in the route file.

**How to avoid:**
1. Set `export const maxDuration = 60` on `/api/inngest/route.ts`. Verify Vercel project's plan (Phase 05.5-02 indicated Production env Encrypted — operator should confirm if it's Hobby vs Pro).
2. Each step.run's callback should target ≤30s. For Shopify daily fetcher on a busy day: Shopify orders ≤12,500 orders/250 = 50 pages × ~500ms each = 25s. Cutting it close but workable.
3. Inngest's own step.sleep + step.run combination can fragment work into smaller pieces — if Vercel timeout becomes an issue, decompose further.

**Warning signs:** Inngest UI shows "function timeout" errors with specific step durations >10s.

[VERIFIED: https://www.inngest.com/docs/deploy/vercel — `maxRuntime` on client, `maxDuration` on `/api/inngest` route]

### Pitfall 10 — Vercel deployment protection blocking Inngest webhook

**What goes wrong:** Vercel deployment protection (password / SSO) blocks Inngest's HTTPS calls to `/api/inngest`. Inngest can't register functions, can't invoke them. Symptom: deploys succeed but no functions appear in Inngest dashboard.

**Why it happens:** Default Vercel preview-deployment protection is on for some accounts.

**How to avoid:** Per Inngest docs, either disable Vercel deployment protection OR enable "Protection Bypass for Automation" and paste the bypass secret into Inngest dashboard's Vercel integration settings.

**Warning signs:** Inngest dashboard shows the App as "registered" but with 0 functions, and PUT calls to `/api/inngest` return 401/403.

[VERIFIED: https://www.inngest.com/docs/deploy/vercel — deployment protection section]

### Pitfall 11 — `force-dynamic` vs `revalidate` conflict on routes

**What goes wrong:** A route declares both `export const revalidate = 60` and `export const dynamic = 'force-dynamic'`. They conflict; `force-dynamic` wins. The CDN never caches the route. Worse, the explicit `Cache-Control` header is also ignored.

**Why it happens:** Copy-paste from one route to another without checking.

**How to avoid:**
1. Use `revalidate` for GET-only data routes (CACHE_CONFIG-driven).
2. Use `dynamic = 'force-dynamic'` for CRUD routes only.
3. NEVER both in the same file.

[VERIFIED: existing comment at `dashboard-web/src/app/api/data/route.ts:11-14`]

### Pitfall 12 — `revalidate` requires a literal number

**What goes wrong:** `export const revalidate = CACHE_CONFIG.foo.revalidate` fails Next.js's static analyzer with "Unsupported node type MemberExpression at revalidate", aborting the build. Caught at Phase 05.5-03 Deviation #1.

**Why it happens:** Next.js parses route segment config statically and requires literal values.

**How to avoid:** Always use a literal `export const revalidate = N;` with a sync-required-comment referencing `CACHE_CONFIG.foo.revalidate`. Pattern verified in existing routes at `dashboard-web/src/app/api/data/route.ts:14`, `store-meta/route.ts:9`, `dashboard-state/route.ts:9`, `health/route.ts:23`.

[VERIFIED: Phase 05.5-03 SUMMARY Deviation #1]

### Pitfall 13 — Frankfurter API weekend-date behaviour

**What goes wrong:** Frankfurter (used by `FX.gs`) auto-shifts weekend dates to the prior business day. A Saturday `2026-05-23` returns Friday `2026-05-22`'s rate. The returned `body.date` differs from the requested URL date.

**Why it happens:** FX rates aren't published on weekends.

**How to avoid:** The Apps Script side relies on this auto-shift implicitly. The TS port should match — accept whatever Frankfurter returns, NOT validate that `body.date === requestedDate`.

**Warning signs:** Tests checking `body.date === '2026-05-23'` (Saturday) fail.

[CITED: FX.gs docstring `"אם נשאל על תאריך סוף שבוע/חג, ה-API מחזיר אוטומטית את שער יום העסקים הקודם"`] [PARTIAL VERIFY: https://frankfurter.dev/ confirms free + no key + rate-limited-not-quota — exact weekend-shift behavior not in fetched docs but matches Apps Script-implied semantics]

### Pitfall 14 — `process.env` evaluated at import-time

**What goes wrong:** Any module-level `const READ_FROM = process.env.READ_FROM` caches the value at module load. Vercel env-var changes need a redeploy to take effect.

**Why it happens:** Module-load-time evaluation is the natural JS idiom.

**How to avoid:** `readFrom()` (Pattern 10) is a function. Each call re-reads `process.env`. Same for any other env-var-gated behavior in 05.6.

### Pitfall 15 — Inngest `serve()` GET endpoint exposes function metadata

**What goes wrong:** `GET /api/inngest` returns JSON with function definitions (ids, triggers, retry config). Useful for Inngest's introspection — but anyone with the URL can see it.

**Why it happens:** Inngest's design choice — the metadata isn't secret, but exposing function IDs and trigger schedules is a fingerprint.

**How to avoid:** This is the URL-obscurity trust model (D-D2) for Phase 05.5/05.6. Not a real fix — just an acceptance. Document in User Manual §1.7.

[VERIFIED: https://www.inngest.com/docs/reference/serve — GET returns function metadata]

```typescript
// dashboard-web/src/lib/fetchers/fx.ts

/**
 * Mirrors FX.gs:getFxRate. Frankfurter is free, no API key, no rate limits
 * (per https://frankfurter.dev/). Returns the requested date's rate, OR
 * the prior business day's rate for weekends/holidays (Frankfurter handles
 * the shift automatically — server returns body.date as the actual lookup).
 */
export async function getFxRate(
  from: string,
  to: string,
  dateStr: string,
): Promise<number> {
  if (from === to) return 1;
  const url = `https://api.frankfurter.dev/v1/${dateStr}?base=${from}&symbols=${to}`;
  const res = await fetch(url);
  if (!res.ok) {
    throw new Error(`FX fetch failed (${from}->${to} on ${dateStr}): ${await res.text()}`);
  }
  const data = await res.json() as { rates?: Record<string, number>; date?: string };
  const rate = data.rates?.[to];
  if (!rate || !Number.isFinite(rate)) {
    throw new Error(`No FX rate ${from}->${to} for ${dateStr}`);
  }
  return rate;
}
```

## Open Questions

1. **Cron schedule timezone** — CONTEXT.md says "00:05 daily" but the cron string `0 5 * * *` is "05:00 UTC". Apps Script runs in `Asia/Jerusalem`. Is the operator's intent (a) 00:05 Israel local (matching Apps Script) → use `TZ=Asia/Jerusalem 5 0 * * *`, or (b) 05:00 UTC = 08:00 Israel (winter) / 08:00 Israel (summer with IDT) → use `0 5 * * *`?
   - **What we know:** Current Apps Script triggers run at 00:05 Israel local time (operator-confirmed in Phase 05.5-explore session); the bare cron `0 5 * * *` in Inngest is UTC.
   - **What's unclear:** Which the operator intends. CONTEXT.md's prose is ambiguous.
   - **Recommendation:** Default to `TZ=Asia/Jerusalem 5 0 * * *` to match existing Apps Script behavior exactly. Flag this in the PLAN's `<assumptions>` for operator confirmation in the first plan that creates the cron function.

2. **PROPS-MAP rows for fetcher credentials** — Per 05.5-03 SUMMARY "34 rows remaining" in PROPS-MAP. The new TS fetchers in 05.6 require Shopify domain + token, Meta access token + ad account ID, Google Ads dev token + client ID/secret + refresh token, in Vercel env vars. Are these already seeded as a part of 05.5-02, or pending in 05.6?
   - **What we know:** 05.5-02 SUMMARY ticked rows 41-43 (Supabase keys). Rows 14-40 (Shopify/Meta/Google per-store) remain.
   - **What's unclear:** Whether 05.6 includes a sub-plan to copy these from Apps Script's PropertiesService to Vercel.
   - **Recommendation:** Add an early plan in 05.6 (or a checkpoint:human-action task) that audits + seeds these. The Inngest crons can't run their first daily until the env vars are present.

3. **Per-fetcher step granularity** — The CONTEXT.md Open Question #3 asks the same. The 05.6 free-tier execution forecast (Pitfall 4) shows that fewer steps per function is better. Recommended decomposition: ~6 steps per cron-daily, ~3 per cron-live.
   - **What we know:** Inngest counts function runs + each step as 1 execution. Naive decomposition (one step per Supabase table) blows the free tier.
   - **What's unclear:** Whether the operator prefers per-table retry granularity (more steps) or fewer executions (fewer steps). Trade-off.
   - **Recommendation:** Start with the ~6 step / ~3 step decomposition. Monitor first-week usage. Refactor if needed.

4. **Operator "Sync now" semantics** — CONTEXT.md Open Question #4. Async (returns 202 immediately, operator watches jobs table) vs blocking (streams progress).
   - **Recommendation:** Async. The streaming pattern would require Server-Sent Events or WebSocket, adds complexity. The jobs table 15s poll already gives a clear "completed / failed" signal.

5. **manual_overrides CRUD authorization** — CONTEXT.md Open Question #5. URL-obscurity (current pattern) vs confirmation modals for destructive actions.
   - **Recommendation:** URL-obscurity + ONE confirmation modal on DELETE only. Add/edit are inline (no modal).

6. **Postgres reader query shape** — CONTEXT.md Open Question #6. supabase-js `.select()` builder vs raw SQL via `.rpc()`.
   - **Recommendation:** `.select()` builder for every reader. Our reads are SELECT-with-WHERE on indexed columns; no JOINs needed beyond what could be a server-side VIEW (also out of scope — the 10 tables are already shaped for direct reads). Builder is portable + typed; raw RPC is overkill.

7. **Vercel deployment protection status** — Pitfall 10. Is deployment protection ON or OFF on the operator's Vercel project?
   - **Recommendation:** Confirm in PLAN's Inngest-Vercel integration setup task. If ON, operator needs to add bypass-secret to Inngest dashboard during integration setup.

8. **Vercel function plan tier** — Pitfall 9. Hobby (10s) or Pro (60s)?
   - **Recommendation:** Confirm in PLAN. If Hobby, large-day Shopify pulls may timeout — decompose pagination across more step.runs.

9. **First-run backfill scope** — D-A3 says "history scope from 2026-05-01 forward". The first operator backfill needs to cover ~3 weeks (May 1 → research date). At ~6 steps/day × 3 stores × 21 days = ~380 executions for a one-shot backfill. Fits within free tier easily.
   - **What we know:** Free tier 50K execs/month covers it.
   - **Recommendation:** The first operator-initiated backfill is roughly the "smoke test" for the system. Include it as the last task in the phase.

10. **Local development workflow** — Out of scope per CONTEXT.md `<deferred>` but worth flagging: the Inngest Dev Server (`npx inngest-cli@latest dev`) is the recommended local-dev pattern.
