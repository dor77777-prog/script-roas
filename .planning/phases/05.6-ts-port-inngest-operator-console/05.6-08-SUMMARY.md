## Step Decomposition Detail

5 `step.run` calls per function (per RESEARCH §Pitfall 4 recommended ≤6 steps/run for free-tier budget headroom):

| Step ID | Action | Fetcher / DB | Retry-safe (idempotent)? |
|---------|--------|--------------|--------------------------|
| `fetch-shopify` | HTTP (Shopify REST) | `fetchShopifyDayRows(storeId, date)` | Yes — HTTP read |
| `fetch-meta` | HTTP × 2 (Promise.all) | `fetchMetaSpendForDay` + `fetchMetaAdSetInsights` | Yes — HTTP reads |
| `fetch-google` | HTTP × 2 OR short-circuit (Promise.all) | `fetchGoogleAdsSpendForDay` + `fetchGoogleAdsAdGroupInsights`; both return empty/zero for non-uzoshop | Yes — HTTP reads / pure |
| `apply-manual-overrides` | DB read + FX | `mergeOverridesFromSupabase` (reads `manual_overrides` for date×store, then `getFxRate`) | Yes — pure transform of inputs |
| `persist-batch` | DB writes (4 upserts) | `getSupabaseAdmin().from(t).upsert(rows, { onConflict })` × 4 | Yes — every upsert has `onConflict` matching PK |

**Total per run:** 5 steps + 1 function = **6 execs/run**.

**2. [Rule 1 - Bug in plan skeleton] PLAN.md skeleton used a 3-arg `inngest.createFunction()` API that does not exist in inngest@^4.4.0**
- **Found during:** Task 2 (during initial implementation matching PLAN.md skeleton line 414)
- **Issue:** PLAN.md line 414 + RESEARCH §Pattern 2 line 414 both show `inngest.createFunction({ id }, { cron: '...' }, async ({ step }) => { ... })` — three arguments. inngest@^4.4.0's actual API (verified at `node_modules/inngest/components/Inngest.cjs:550`) is a 2-arg signature: `createFunction(opts, handler)`. The SDK throws verbatim: `"createFunction" expected a handler function as the second argument. Triggers belong in the first argument: createFunction({ id, triggers: { event: "..." } }, handler)`. Calling with the PLAN skeleton's 3-arg form would have crashed at function-construction time (load-time, before any cron tick), preventing serve() registration in plan 11.
- **Fix:** Used the 2-arg form: `createFunction({ id, triggers: [{ cron: '...' }] }, handler)`. The triggers array shape is the canonical form (single-trigger input is normalized to array by `sanitizeTriggers` per Inngest.cjs:561-565).
- **Files modified:** `dashboard-web/src/inngest/functions/cronDaily.ts` (factory `makeCronDaily` function)
- **Commit:** `6e9ecd8` (bundled with the GREEN implementation)

**3. [Rule 1 - Type incompatibility] Strict `Promise<T>` generic on `RunDailyStep.run` conflicted with both real Inngest StepTools and test mocks**
- **Found during:** Task 2 (first tsc run, 6 errors)
- **Issue:** Initial signature `run<T>(id: string, callback: () => Promise<T>): Promise<T>` failed type-checking at two callsites:
  - The real Inngest SDK's StepTools.run returns `Promise<Jsonify<Awaited<T>>>` (because the SDK serialises step return values to JSON for cross-worker memoization — Date → string, undefined stripped, etc.); the wrapped type is NOT the same as `T`.
  - Test mocks return plain `Promise<unknown>` (no Jsonify pipeline) — also not the same as `T`.
- **Fix:** Relaxed signature to `run(id: string, callback: () => Promise<unknown>): Promise<unknown>` — `unknown` is the lowest common denominator that both real and mock shapes satisfy. Each call site narrows the result via `as Awaited<ReturnType<typeof fetcher>>` immediately after the await (e.g. line 156: `(await step.run('fetch-shopify', ...)) as Awaited<ReturnType<typeof fetchShopifyDayRows>>`). The cast is type-safe because the runtime shape is enforced by the fetcher's own return-type contract (verified by plan 03-07 fetcher test suites).
- **Files modified:** `dashboard-web/src/inngest/functions/cronDaily.ts` (RunDailyStep type + 4 step.run callsites)
- **Commit:** `6e9ecd8` (bundled with GREEN implementation)
