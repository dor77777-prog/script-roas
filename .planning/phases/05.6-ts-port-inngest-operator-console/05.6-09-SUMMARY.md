## Decisions Made

- **SDK v4.4 2-arg `createFunction`** — The PLAN's `<action>` snippet used the deprecated 3-arg form `inngest.createFunction({ id }, { cron }, handler)`. The 4.4.0 SDK throws on that shape (`Inngest.js:551`: "Triggers belong in the first argument: createFunction({ id, triggers: { event: '...' } }, handler)"). Implementation uses `inngest.createFunction({ id, triggers: [{ cron: '...' }] }, handler)`.
- **Inline cron literal** — The cron string is the literal `'TZ=Asia/Jerusalem */15 * * * *'` (not built via template `\`TZ=${TZ} */15 * * * *\``). The PLAN's `<verify>` block greps for the exact substring in source bytes, so a template-built string would fail the verify even though runtime behavior is identical.
- **`data_daily` UPSERT preserves spend via column omission** — On the UPDATE-existing path, the payload contains only `revenue_cad` + derived columns (recomputed against the preserved `total_spend_cad` from a prior SELECT) plus `store_name`. The 3 spend columns are absent from the payload, so the ON CONFLICT DO UPDATE SET clause never touches them. On the INSERT-new-row path, the payload adds `fb_spend_cad: 0`, `ga_spend_cad: 0`, `total_spend_cad: 0` so subsequent SELECTs read numeric zeros instead of NULLs.
- **`products_daily` UPSERT minimal payload** — Only `date`, `store_id`, `store_name`, `product_id`, `net_revenue_cad`. Schema columns owned by daily (`units NOT NULL DEFAULT 0`, `orders NOT NULL DEFAULT 0`, `gross_revenue_cad NUMERIC NULL`, `product_title TEXT NULL`) are preserved on UPDATE (omitted from SET clause) and take their defaults on INSERT.
- **Sequential per-date persistence in one step.run** — The persist step iterates the 3 rolling-window dates serially rather than `Promise.all`-ing 3 SELECT+UPSERT pairs. Justification: (a) keeps the Supabase pool unsaturated, (b) aligns with cron-daily's per-date pattern (plan 08), (c) Inngest counts the whole persist as one step regardless of inner parallelism so there's no exec-count win from concurrency here.
- **Rolling-window dedup guard** — `rollingWindowDates` returns `Array.from(new Set(...))` to defend against the theoretical case where a DST-transition tick compresses two ticks onto the same local day. Never expected to fire for daysBack=3 in Asia/Jerusalem but cheap insurance.
- **Cast `step as unknown as StepRunner` at the factory boundary** — Inngest's typed `step.run<T>` returns `Promise<Jsonify<T>>` (the SDK strips Date/Map for cross-worker serialization). For the primitive return types `runLiveForStore` uses (Record<string, number/string>, string[]), `Jsonify<T> ≡ T`, so the cast is sound. The cast is isolated to a single line in `makeCronLive` and documented inline.
