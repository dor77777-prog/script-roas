<domain>
## Phase Boundary

This is the active migration phase: port the 5 Apps Script fetchers to TypeScript, stand up Inngest cloud, build an operator-console UI in the dashboard, and import the 38 historical `manual_overrides` rows.

Apps Script keeps running unchanged in parallel writing to Sheets — the two systems are independent (NO dual-write). They both read from the same upstream APIs (Shopify Admin / Meta Marketing / Google Ads / Open Exchange Rates). The dashboard's read path stays on Sheets via the `READ_FROM=sheets` feature flag default; flipping to `postgres` is Phase 05.7's job, not 05.6's.

**What lands in this phase:**
- `dashboard-web/src/lib/fetchers/*.ts` — 5 TS modules mirroring the 5 `.gs` fetchers
- `dashboard-web/src/inngest/*` — Inngest function definitions (crons + on-demand events)
- `dashboard-web/src/app/operator/page.tsx` — new "ניהול" tab with jobs table, backfill picker, manual_overrides CRUD, sync-now buttons
- `dashboard-web/src/app/api/inngest/route.ts` — Inngest webhook endpoint
- `dashboard-web/src/lib/supabaseAdmin.ts` — server-only service_role client for writes
- `dashboard-web/src/lib/postgresReaders.ts` — Postgres equivalents of `sheets.ts` fetchers (READ side, used only when feature flag is flipped — defaults inactive in 05.6)
- `dashboard-web/src/lib/featureFlags.ts` — `READ_FROM` flag
- Inngest cloud account + Vercel integration (operator-side setup)
- One-off importer: 38 `manual_spend` rows from existing Sheets tab → Supabase `manual_overrides`

**What does NOT land here (out of scope, deferred to 05.7):**
- Flipping `READ_FROM` default to `postgres`
- Apps Script trigger removal
- `clasp` CI workflow deletion
- Sheets archive freeze
- 14-day verification harness (it's part of 05.7's gate, not 05.6)

</domain>

<decisions>
## Implementation Decisions

### Decision Set A — Architecture (locked in `/gsd-explore` 2026-05-21)

- **D-A1** — Stack: **Supabase Postgres + Inngest cloud + Vercel + Next.js**. Locked. No alternatives.
- **D-A2** — **Rebuild from upstream APIs**, not migrate Sheets rows. Source of truth is Shopify / Meta / Google Ads / OXR. Algorithm corrections (Phase 05.2.3.0) propagate to history automatically.
- **D-A3** — **History scope: from 2026-05-01 forward**. ~3-7 weeks at migration time. <2 hours of Inngest backfill jobs.
- **D-A4** — **No dual-write**. Apps Script keeps writing to Sheets independently. New system writes to Supabase independently. Both read from the same upstream APIs. Two systems must converge on the same numbers (verified in Phase 05.7).
- **D-A5** — `manual_overrides` is **load-bearing** (38 rows of operator-entered spend for uzoshop May 1-8). Cannot be re-derived from Meta API. Must have CRUD UI + one-off importer.

### Decision Set B — Inngest (locked)

- **D-B1** — **Inngest cloud free tier**. Estimated load: ~96 cron runs/day × 3 stores + ~50 events/day = well under 50k executions/month free tier.
- **D-B2** — Function inventory:
  - `cron-daily-{store}` — `0 5 * * *` (00:05 UTC, mirrors current Apps Script daily trigger)
  - `cron-live-{store}` — `*/15 * * * *` (mirrors current 15-min live trigger)
  - `event/sync-now` — triggered from operator console "Sync now" buttons (per-store or global)
  - `event/backfill` — triggered from operator console backfill range picker
- **D-B3** — **Inngest function language: TypeScript** (no Python). Functions live in `dashboard-web/src/inngest/` alongside the dashboard's existing TS code. Single deployment unit via Vercel.
- **D-B4** — **Service-role client for writes**, anon-key client for reads. Writer client is server-only (`process.env.SUPABASE_SERVICE_ROLE_KEY`, already seeded in Phase 05.5-02).
- **D-B5** — **Idempotency keys**: every fetcher write uses `ON CONFLICT (pkey) DO UPDATE` so a re-run of the same cron tick is safe. Phase 05.5 added the necessary UNIQUE + PKEY constraints; 05.6 just needs to use them in the writers.
- **D-B6** — **Retries**: rely on Inngest's built-in retry-on-throw (default 4 retries with exponential backoff). Fetcher errors throw; Inngest handles the rest.

### Decision Set C — TS Fetcher Port (locked)

- **D-C1** — 5 fetcher modules under `dashboard-web/src/lib/fetchers/`:
  - `shopify.ts` — port of `Shopify.gs` (revenue, products, refunds, orders attribution)
  - `meta.ts` — port of `MetaAds.gs` (campaigns, ads, insights, conversions)
  - `googleAds.ts` — port of `GoogleAds.gs` (campaigns, ads, conversions; only uzoshop has Google Ads per `Config.gs:STORES`)
  - `fx.ts` — port of `FX.gs` (Open Exchange Rates, CAD/USD/ILS conversion)
  - `manualOverrides.ts` — port of `ManualOverrides.gs` (applies overrides to fetched spend data; reads from Supabase `manual_overrides` table now, not the Sheets `manual-spend` tab)
- **D-C2** — Each fetcher exports a single `async function fetchXForDay(storeId, date)` or `fetchXForRange(storeId, from, to)` signature. No singleton state. No PropertiesService references.
- **D-C3** — Fetcher modules are **pure** (in/out, no side effects). The Inngest functions wrap them: fetcher returns rows → Inngest writes to Supabase via service_role client → commits step.
- **D-C4** — **Algorithm parity required**. Each fetcher's output for a given (store, date) MUST match the corresponding Sheets row produced by Apps Script (modulo the Phase 05.2.3.0 refund algorithm correction, which applies to Postgres only). Per-fetcher unit tests compare against frozen Sheets snapshots for 2026-05-15 onward.
- **D-C5** — **No Apps Script references** in the new fetchers (no global state, no event triggers, no PropertiesService). Pure HTTP + JSON.

### Decision Set D — Operator Console (locked)

- **D-D1** — New top-level dashboard tab: **"ניהול"** (Hebrew for "Management"). Route: `/operator`. Auth: same URL-obscurity as the rest of the dashboard (no login).
- **D-D2** — Sub-views:
  - **Jobs table** — recent Inngest runs (status, duration, step list, error if failed). Implemented via Inngest REST API (`/v1/runs`) — NOT iframe embed (better UX integration).
  - **Backfill range picker** — date-range + store-selector → triggers `event/backfill`
  - **Manual overrides CRUD** — table view + add/edit/delete rows; writes to Supabase `manual_overrides` via service_role API route
  - **Sync now buttons** — global + per-store; triggers `event/sync-now`
- **D-D3** — **No real-time updates** in 05.6. Operator console polls Inngest API every 15s. Real-time via Supabase Realtime deferred to a future phase.
- **D-D4** — **Visual style**: match existing dashboard design system (Tailwind classes, RTL layout, dark sidebar). No new design tokens. Lucide icons.

### Decision Set E — Postgres readers (deferred-active)

- **D-E1** — Phase 05.6 builds the Postgres-reading equivalents of `sheets.ts` (`fetchDailyDataFromPostgres`, `fetchStoreMetaFromPostgres`, etc.) but does NOT use them yet. They live behind the `READ_FROM=postgres` feature flag.
- **D-E2** — **Feature flag**: `READ_FROM` env var with values `sheets` (default) or `postgres`. Implementation in `dashboard-web/src/lib/featureFlags.ts`. Read at request-time (not module-load) so flipping the env var on Vercel takes effect on next request without redeploy.
- **D-E3** — Every `/api/*` route gets a 1-line branch: `if (readFrom() === 'postgres') return readFromPostgres(...); else return readFromSheets(...);`. Both branches return the same shape.

### Decision Set F — manual_overrides importer (locked)

- **D-F1** — One-off importer task: `dashboard-web/scripts/import-manual-overrides.ts`. Run once by operator (`npx tsx scripts/import-manual-overrides.ts`). Idempotent (uses `ON CONFLICT (date, store_id, platform) DO NOTHING` per the UNIQUE constraint added in Phase 05.5 + WR fixes).
- **D-F2** — Reads the existing `manual-spend` Sheets tab via the EXISTING `sheets.ts:getAuth` (no Apps Script call). Writes to Supabase `manual_overrides` table via service_role client.
- **D-F3** — Importer outputs a summary: `imported N rows, skipped M (already present), errored P`. Operator confirms = 38 rows imported on first run.

### Decision Set G — Branching/CI (locked)

- **D-G1** — All work on `main` (no feature branch). Phase commits use `feat(05.6-XX): ...` / `fix(05.6-XX): ...` conventions.
- **D-G2** — Vercel CI deploys on every push to main (already configured for the dashboard). Inngest cloud auto-syncs functions from the Vercel deployment via the Inngest-Vercel integration.

### Claude's Discretion

- **Detailed Inngest step decomposition** — how many Inngest `step.run()` calls per fetcher, error-boundary placement, sleep/retry semantics for rate-limited APIs
- **Operator console layout details** — exact column order, label wording, button placement
- **Postgres reader query shape** — JOIN strategy, view vs raw SQL, supabase-js select() vs raw RPC
- **One-off importer error handling** — what to do if Sheets read fails mid-way, dedup strategy beyond ON CONFLICT
- **Test coverage scope** — which fetchers get unit tests, which integration tests, which manual smoke tests

## Specifics & Constraints

- **Phase order is sequential**: 05.6 has 5 fetchers + 4 Inngest function types + operator console + importer + Postgres readers + feature flag. Realistic estimate: 8-15 plans, multi-session execution.
- **The Inngest account setup is the ONE operator-action gate** in 05.6. Plan it as an explicit `checkpoint:human-action` task with a 5-minute time estimate and a clear resume-signal (the operator's Inngest event-key and signing-key, pasted into Vercel).

- **No production behavior change**. The dashboard read path stays on Sheets (`READ_FROM=sheets` default). Postgres readers exist but are dormant. The cut-over is 05.7's responsibility.
- **`Config.gs:STORES` is the source of truth for store list** (uzoshop / zolplus / usmile360). The Inngest functions enumerate stores via `Config.gs:STORES` semantics ported into the `stores` Supabase table (already seeded in Phase 05.5).

- **Inngest free tier safety**: 50k executions/month. Current load ~96 daily × 3 stores + ~50 events/day = ~9k/month. We have ~5× headroom. If the operator wants to add a 5-min cron tier in 05.6, recompute headroom.
- **Operator console URL**: `/operator`. Add to the dashboard sidebar with a single new entry. RTL-aware label (Hebrew "ניהול").

<open_questions>
## Open Questions for Researcher / Planner

These are NOT blockers for planning — they're flagged so the researcher can scope them in `RESEARCH.md`:

1. **Inngest cloud Vercel integration** — exact env-var names Inngest injects (`INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`?). Required for the `checkpoint:human-action` task spec.
2. **Inngest REST `/v1/runs` auth** — Bearer token? Vercel env var? Required for the operator console jobs table.
3. **Per-fetcher step granularity** — should `shopify.ts` be a single Inngest function with one `step.run`, or multiple steps (orders → refunds → products)? Trade-off: more steps = better Inngest UI visibility + smaller retry units; fewer steps = simpler code.
4. **Operator console "Sync now" semantics** — does the button trigger an Inngest event and return immediately (async — operator watches the jobs table for completion), or does it block and stream progress? Trade-off: async = simpler; blocking = better UX for one-shot syncs.
5. **`manual_overrides` CRUD UI authorization** — same URL-obscurity? Or add a confirmation-modal pattern to prevent accidental deletes?
6. **Postgres reader queries — supabase-js vs raw SQL** — for the cut-over, do we use the supabase-js client's `.select()` builder or write raw SQL via `supabase.rpc()`? Trade-off: builder = portable + typed; raw = full SQL power + view-friendly.

</open_questions>
