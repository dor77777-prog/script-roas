# Phase 05.6 Plan 15: manual_overrides CRUD subsystem Summary

One-liner: 4-verb CRUD route (`/api/operator/manual-overrides`) backed by service_role + a client component that adds/lists/deletes rows with an accidental-wipe confirmation modal, replacing the plan-12 placeholder.

## What landed

- **CRUD route** `dashboard-web/src/app/api/operator/manual-overrides/route.ts`:
  - GET / POST / PATCH / DELETE — all 4 verbs
  - `getSupabaseAdmin()` service_role for writes (anon has SELECT only per Phase 05.5 WR-04)
  - POST upserts on `(date, store_id, platform)` matching the UNIQUE constraint
  - Platform / currency normalised before reaching Postgres CHECK constraint (Pitfall 7 defense in depth)
  - Validation rejects unknown stores / platforms / currencies with predictable error strings
  - GET uses S-2 soft-fail (HTTP 200 + `{rows: [], error}`); POST/PATCH/DELETE return 4xx/5xx so the client catch-block fires
  - `force-dynamic` only (no `revalidate`) per Pitfall 11
- **Client component** `dashboard-web/src/components/operator/ManualOverridesCrud.tsx`:
  - `'use client'` + SWR fetch of `/api/operator/manual-overrides`
  - Inline add-row form (date / store / platform / spend / currency / notes)
  - Table view with delete buttons
  - **Confirmation modal on DELETE** — resolves RESEARCH §Open Question 5 ("URL-obscurity + add a confirmation pattern to prevent accidental deletes")
  - Hebrew copy with RTL flow; `dir="ltr"` on numeric/date fields
  - **No service-role import** — all DB access through the server-only route (T-05.6-15-I2 mitigation)
- **page.tsx wire** — the plan-12 placeholder section "(CRUD על manual_overrides יופיע כאן — ממומש בשלב הבא)" is replaced with `<ManualOverridesCrud />`.
- **cacheConfig.ts** — added `manualOverrides: { revalidate: 0, swr: 0 }` so the cache contract is documented centrally even though the route itself is `force-dynamic`.

- **Confirmation modal on DELETE only:** `grep -c "אישור מחיקה" ManualOverridesCrud.tsx` → 1 occurrence (the modal title). ADD has no confirmation step (low blast radius); only the destructive verb is gated.

- **Threat model:**
  - T-05.6-15-T1 (Tampering — capitalised platform): mitigated by client + server lowercase before upsert (defense in depth); CHECK is the last-resort backstop.
  - T-05.6-15-I2 (Info Disclosure — service_role key in browser): mitigated; `grep` confirms no admin client in the component.
  - T-05.6-15-T3 (Tampering — XSS via notes): mitigated by React auto-escape (`{r.notes ?? '—'}`); no `dangerouslySetInnerHTML`.
  - T-05.6-15-I5 (Info Disclosure — raw Postgres error): mitigated by `userFacingError()` on every error path; raw `console.error` server-side only.

## Deviations from Plan

### Auto-fixed during execution

**1. [Rule 3 - Verify regex collision] Reworded comments to avoid grep false positives**
- **Found during:** Task 1 + Task 2 verify steps
- **Issue:** The plan's verify chains use `grep -c "export const revalidate"` and `grep -c "import.*supabaseAdmin\|SUPABASE_SERVICE_ROLE_KEY"`. My initial inline comments mentioned both literal strings (in "intentionally NOT exported" / "intentionally does NOT import" explanatory prose). The greps don't distinguish comment from code, so they fired on the comments and reported the route/component as failing the contract.
- **Fix:** Reworded both comments to describe the intent without naming the literal symbol — same security/clarity, no regex collision. Both `grep -c` checks now return `0` correctly.
- **Files modified:**
  - `dashboard-web/src/app/api/operator/manual-overrides/route.ts` (1 comment block)
  - `dashboard-web/src/components/operator/ManualOverridesCrud.tsx` (1 comment block)
- **Commit:** included in `b7e5e79` (Task 1) and `e077e86` (Task 2) — pre-commit fix

**2. [Rule 2 - Missing critical functionality] PATCH validation widened to per-field**
- **Found during:** Task 1
- **Issue:** The plan skeleton's `PATCH` accepted `{id, ...patch}` and forwarded `patch` to Supabase verbatim (after normalising `platform`/`currency` if present). That left undefined behavior for the case where the operator submits e.g. `{id: 7, spend: "not-a-number"}` — the malformed value would reach Postgres and either be silently coerced (NUMERIC accepts some strings) or trigger a raw Postgres error that `userFacingError` would scrub but in an unhelpful generic way ("שגיאה לא צפויה").
- **Fix:** Per-field validation in PATCH mirrors POST (date format, store enum, platform/currency enum, spend numeric). Returns specific 400 error string per field. No DB roundtrip on bad input.
- **Files modified:** `dashboard-web/src/app/api/operator/manual-overrides/route.ts`
- **Commit:** `b7e5e79`

**3. [Rule 2 - Missing critical functionality] cacheConfig.manualOverrides entry added**
- **Found during:** Task 1
- **Issue:** The plan itself did not require this — the route is `force-dynamic` and never calls `cacheControl()`. However, the user's invocation criteria explicitly required `cacheConfig.ts extended with manual_overrides entry`. Adding it preserves the "every route has a documented cache contract" pattern (S-3) and makes the explicit `revalidate=0` a tripwire against future drift.
- **Fix:** Added `manualOverrides: { revalidate: 0, swr: 0 }` with an inline comment explaining why both are zero (force-dynamic only — any accidental `cacheControl('manualOverrides')` use on the CRUD route becomes a no-op rather than a silent staleness bug).
- **Files modified:** `dashboard-web/src/lib/cacheConfig.ts`
- **Commit:** `b7e5e79`

### Other deviations from the plan skeleton

- **Error logging on every catch path** — the plan's skeleton had `console.error` only on POST/PATCH/DELETE catch blocks, not on the error branches of `supabase.from().select()` returning `{ error }`. I added `console.error('… failed: ...', error.message)` on every error path so ops can correlate sanitized user messages to the raw Postgres / Supabase message in logs. Mirrors the `dashboard-state/route.ts:41` precedent.

- **Deleted modal field-overload pattern dropped** — the skeleton stored the delete-error inside `confirmDelete.notes` (re-using the row's notes field for the error string). That was a clever hack but it conflated row data with modal state; I split them into separate `confirmDelete: Row | null` + `deleteError: string | null` state slots. Easier to reason about and the modal renders the error in its own line with `role="alert"`.

- **`<label>`s with column headers in the form** — the skeleton used bare `<input>`s with placeholders. Adding `<label>` wrappers makes the form keyboard-accessible (each field is a known landmark) and aligns with the dashboard's existing form patterns (see `Filters.tsx`).

- **`spend` as string in form state** — the skeleton typed `spend: number` in form state, but `<input type="number">` returns a string mid-typing (e.g. "12." while user is entering "12.5"). Keeping it as string in state + `parseFloat` at submit avoids the React-warning class of bugs where the controlled input re-renders with `NaN`.

- **Empty-table message** — added a `<tr colSpan={7}>` row with "אין רשומות. הוסף את הראשונה למעלה." for the empty case. Without it the table renders headers only, which looks broken on the live `/operator` page until the importer (Plan 20) populates rows.
