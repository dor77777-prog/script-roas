- **`eventSyncNow`** (id `event-sync-now`, trigger `event/sync-now`) — single-store, single-date wrapper that delegates to `runDailyForStore` from plan 08. Payload `{storeId, date?}`; `date` defaults to today in Asia/Jerusalem via the same Intl.DateTimeFormat(en-CA) helper pattern as cronDaily.ts:yesterdayJerusalem.

- **Per-pair fault tolerance** — try/catch around each iteration so a single failure (post Inngest's 4× retry policy per D-B6) records to `results[]` and the loop continues. Operator sees partial progress on the jobs table rather than a hard abort.
- **TS strict-null clean** (`tsc --noEmit` exit 0) + **7 new events tests pass** (320 total in suite, +7 vs baseline 313).

## Step Decomposition Detail (per backfill click)

For each `(date, storeId)` pair, 5 prefixed step.run calls (per `runDailyForStore` body):

| Prefixed Step ID | Action | Idempotent? |
|------------------|--------|-------------|
| `${date}-${storeId}-fetch-shopify` | HTTP read (Shopify orders × 2 windows) | Yes — HTTP read |
| `${date}-${storeId}-fetch-meta` | HTTP × 2 (Meta spend + insights, Promise.all) | Yes — HTTP read |
| `${date}-${storeId}-fetch-google` | HTTP × 2 OR short-circuit (Google Ads spend + ad-groups) | Yes — HTTP read / pure |
| `${date}-${storeId}-apply-manual-overrides` | DB read + FX | Yes — pure transform |
| `${date}-${storeId}-persist-batch` | DB writes (4 ON CONFLICT upserts) | Yes — onConflict matches PK |

**Per pair:** 5 step.runs. **Per backfill invocation:** 5 × pairs + 1 function = 5N + 1 execs.

For the maximum-scope D-A3 backfill (2026-05-01 → 2026-05-21 × 3 stores = 63 pairs):
- 63 × 5 + 1 = **316 execs per backfill click** = 0.6% of 50K/month free-tier cap
- Operators rarely run more than 1-2 backfills per month; forecast ~1K execs/month from backfill

For sync-now: 5 step.runs + 1 function = **6 execs per click**. At 100 clicks/month: 600 execs ≈ 1.2% of cap.

Total event-trigger budget (sync-now + backfill) tracks the CONTEXT.md forecast of ~9K execs/month — comfortably within the 50K cap.

## W6 Mitigation Detail

**Threat (per CHECK.md §W6):** The naïve shape

```typescript
step.run(`backfill-${date}-${storeId}`, () =>
  runDailyForStore(storeId, date, { step }),
);
```

would cause 6 backfill iterations to all issue `step.run('fetch-shopify', ...)` via the inner `step` arg — Inngest step IDs must be unique per function invocation; collision.

**Fix applied:** `makePrefixedStep(outer, '${date}-${storeId}')` returns a step shim whose `.run(id, cb)` delegates to `outer.run('${prefix}-${id}', cb)`. The shim is passed into `runDailyForStore` as `{step: prefixedStep}`. The inner step.run calls go through the prefix; no outer `step.run('backfill-...')` wrapper is needed.

**Why this over `step.invoke`:**
- `step.invoke(eventSyncNow, {data: {storeId, date}})` would route each pair to a separate Inngest function invocation — collision-proof because each invocation has its own step namespace.
- But: requires both functions registered in serve() first (plan 11 territory — chicken/egg).
- And: Test 5 mocks `runDailyForStore` directly via `vi.mock('../cronDaily')`. `step.invoke` would bypass that mock (it goes through Inngest's transport layer), breaking the test contract.
- The prefix-shim approach is fully contained in plan 10, preserves the test mock, and adds zero coupling to plan 11.

**Trade-off accepted:** physically 5 step.runs per pair (not 1), so a 21-day × 3-store backfill issues 315 step.runs instead of 63. Free-tier budget still has massive headroom (0.6% of cap) — non-issue.

## Threat Flags

None. The plan's `<threat_model>` covers the full attack surface for the two event functions:

- **T-05.6-10-T1 (Tampering — backfill payload with pre-history dates):** Validation block throws BEFORE any upstream fetch (`if (from < HISTORY_BOUNDARY) throw ...`). Error message names the boundary date.

No new threat surface introduced: no new network endpoints (plan 14 territory), no new auth paths, no schema changes. Both files are pure additions in `src/inngest/functions/`.
