## Locked Meta API version

**`META_API_VERSION = 'v23.0'`.**

Reasoning:
- v20.0 (Apps Script) deprecates **2026-09-24** (~4 months from research date).
- All Marketing API versions **<v24.0 deprecate 2026-06-09** (~3 weeks from research date).
- RESEARCH §State of the Art (line 188) recommended "v23.0 OR v24.0" with v23.0 as the explicit skeleton constant (line 508).
- v24.0 was an option, but v23.0 has the longer settled-stability track record and the SAME insights field shape as v24.0 — no behavioral upside to bumping to v24 over v23, but slightly higher field-shape stability risk if Meta tweaks v24 in a point release.

### Curl spot-check (assumption A2 mitigation)

**Status: deferred to operator runtime gate.**

The plan's `<action>` step 1 noted the executor "SHOULD" curl the live uzoshop ad account at v23.0 to confirm field-shape stability before locking in. The execute-time worktree has no Meta token (the production token rides in Vercel env vars; no token is committed to the repo or available to the agent). The mitigation is:

1. **Algorithm-parity tests at the snapshot layer (plan 21)** will detect any drift — the snapshot fixtures are frozen at 2026-05-15..05-20 against the Apps Script v20.0 output; a v23.0 field-shape change would cause the diff to fail loudly.
2. **First-run cron failure surface** — if v23.0 returns a different shape than the TS code expects, the first `cron-daily-uzoshop` run after plan 08 lands will throw with a clear error message (`Meta adsets uzoshop YYYY-MM-DD failed (...)` or a TS narrowing TypeError), bubbling into Inngest's retry → dead-letter → operator console (plan 14).
3. **Operator can manually curl from a dev machine** at any point between now and the plan-08 cron go-live by pasting their token into a one-shot `curl https://graph.facebook.com/v23.0/act_26442930835313109/insights?fields=spend,impressions,actions,action_values,account_currency&time_range=%7B%22since%22%3A%222026-05-20%22%2C%22until%22%3A%222026-05-20%22%7D&level=adset&access_token=$TOKEN`. The fields-shape check is a 30-second visual diff against the v20.0 response.

The risk if A2 is falsified is bounded: any mismatch fails closed (throw), never silently corrupts data. The threat register T-05.6-04-T1 explicitly accepts this trade-off (mitigate-not-prevent: rely on plan 21 algorithm-parity tests).

## Note for plan 08

Meta spend is in **ILS** (Israel Shekel) — the `currency` field of `fetchMetaSpendForDay` will be `'ILS'` for all three Phase 05.5 seed stores. Plan 08 wires the FX-conversion step (ILS → CAD) by calling `fetchFxRate` (from plan 06, FETCH-FX) and multiplying:

```typescript
const metaSpend = await fetchMetaSpendForDay(storeId, date);  // { spend: 19.75, currency: 'ILS', ... }
const ilsToCad = await fetchFxRate('ILS', 'CAD', date);
const metaSpendCad = metaSpend.spend * ilsToCad;
```

The dashboard's `data_daily` table stores all-CAD values, so the FX step is non-negotiable on the write path. The fetcher itself stays currency-agnostic (returns whatever Meta reports) for two reasons: (1) keeps the fetcher pure with no FX-API dependency, and (2) supports future non-ILS accounts without code change.

## Deviations from Plan

### Rule 1 (auto-fix bug) — test mock callcount

**Found during:** Task 2 GREEN-step verification.
**Issue:** The "non-200 throws with status+body" test (originally line 416) used `mockResolvedValueOnce` for the error response, but the test asserted `expect(...).rejects.toThrow(...)` twice — each call invokes the SUT, so the second invocation got an undefined response and the assertion failed with "Cannot read properties of undefined (reading 'ok')".
**Fix:** Switched to `mockResolvedValue` (persistent mock) so both invocations see the same error response. The two assertions still serve their original purpose (validate that the thrown message contains BOTH the status code "400" AND the storeId "uzoshop" — done as separate regex assertions because Jest/Vitest's `toThrow` matches the first matching regex per call).
**Files modified:** `dashboard-web/src/lib/fetchers/__tests__/meta.test.ts` lines 412-419.
**Commit:** `305d4dc`.

### Vitest config widening (anticipatory infra, not a deviation per se)

**Why:** The fetchers test directory `src/lib/fetchers/__tests__/` was outside the existing `include` glob `src/lib/__tests__/**/*.test.{ts,tsx}`. Without the widening, `npm run test` would silently skip the new tests — the IN-03 finding that vitest config comments warn about ("a .tsx test ... used to be silently skipped"). The widened glob `src/lib/**/__tests__/**/*.test.{ts,tsx}` keeps the existing `src/lib/__tests__/` path picked up AND auto-discovers all sibling fetcher dirs (the upcoming `src/lib/fetchers/__tests__/` for shopify, googleAds, fx, manualOverrides as well).

This is one-line infra setup, not a behavioral deviation from the plan — the plan explicitly verifies via `npx vitest run src/lib/fetchers/__tests__/meta.test.ts` which works whether the glob matches or not, but `npm run test` (operator's normal pre-push gate) needs the wider glob.
