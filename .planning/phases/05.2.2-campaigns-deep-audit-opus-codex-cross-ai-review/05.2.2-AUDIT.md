# Phase 05.2.2 — Campaigns Tab Deep Audit

## Summary

Deep, line-by-line audit of every campaign-related file (8 components, 2 hooks, 6 lib modules, 1 API route — 7,094 lines total) following the 05.2.1.1 fix batch. The math is healthier than it was in 05.2.1 — `pearson` returns null correctly, `ORGANIC_SOURCES` is now an inverted predicate, Bessel correction is in place, etc. — but there are still **five P0 silent data corruption defects** that ship wrong numbers as truth, plus four P1 contract violations that misrepresent reality.

Top 3 must-fix items:

1. **AUDIT-P0-01** — `useCampaignTrueRevenue.ts:264-281` `dailyMeta` IIFE walks `data.rows` (unfiltered global response — every store, every platform, every campaign) and re-filters by (storeId, platform, campaignId). Cross-store campaignId collisions still possible if the legacy `setNumberFormat('@')` migration was never run on a given sheet. More importantly: this is the same dailyMeta series fed into `analyzeAttribution → detectOutlierDays → computeWindowStability`, so a polluted series cascades into outlierDays + windowStability for the wrong campaign. Plain bug — `data` not used to filter the IIFE.
2. **AUDIT-P0-02** — `MetaShopifyReconciliation.tsx:218-230` `isOrganicSource` predicate is `true` for the empty-string source (`''`) and for `other-paid`. The OrderSource union includes `''` ("unknown / missing") at `ordersAttribution.ts:75` AND `other-paid` ("UTM-tagged but unrecognised paid source" at line 72). Both flow into the Organic bucket today, inflating the organic series with TikTok/Influencer paid orders and with classifier-failure orders. This is the AUDIT-P0-01 reversal — we over-corrected.
3. **AUDIT-P0-03** — `MetaShopifyReconciliation.tsx:243-251` Organic series still has the `if (mappedRevenue <= 0) continue;` refund-day skip — the 05.2.1 P0-03 was claimed fixed for the Shopify series (`=== 0` at line 186) but NOT for Organic (still `<= 0` at line 250). Refund days drop from Organic, inflating dark-traffic %.

Beyond the P0s: the AdsDrawer fetches `/api/orders-attribution` without `?from=&to=` so it gets the **default 90-day window** while passing `rangeFrom/rangeTo` to the analyzer — when the user picks a date >90 days back, attribution silently shows zero (P1-01). The CPM chart's smart-analysis baseline labels show `cpmDaily[halfMidIdx - 1]` slices without a guard for `halfMidIdx === 0` (P2-04). `prevRange` is computed with `Date.UTC` then `.toISOString().slice(0,10)` — a TZ pinhole that drops a day on some boundaries (P1-09). And `dailyMetaPrev`/`prevRange` use `localRange.from.slice(0,4)` numeric parsing that silently returns NaN on malformed input.

Phase 5.2.1.1 fixes are mostly intact but two regressed silently:
- The `localRange` reference-equality contract documented at `useCampaignTrueRevenue.ts:157-167` is violated by `CampaignsTable.tsx:299` which creates a NEW `localRange` object on EVERY render via `useState<DateRange>(range)` initializer **only on first mount**, then setLocalRange creates a new ref on user action — that's fine, BUT the parent's `range` object identity is not stabilized; if the parent passes a fresh `{ from, to }` literal on every render, `useEffect([range.from, range.to])` only updates on value change but the dep array `[range]` would invalidate. This is OK in current callers but fragile.
- `AdsDrawer.tsx:265` defensive guard `if (!rangeFrom || !rangeTo) return null;` happens AFTER all the useSWR + useMemo hooks fire — these violate React's rules-of-hooks contract by short-circuiting after the hooks (allowed) but they STILL run the SWR fetch even when ranges are invalid (would 400 the API).

Recommended fix priority: P0-01..05 before any new feature ships. P1-01..09 before Phase 6 (security hardening). P2-* + P3-* can batch into a single "cleanup" plan.

## Severity Legend

- **P0** — Silent data corruption (wrong number displayed as truth, no error visible)
- **P1** — Wrong math / contract mismatch (loud failure OR contradicts a spec)
- **P2** — Missing edge case or defensive gap (works on happy path, fails on unusual input)
- **P3** — Test gap, stale comment, minor UX

### AUDIT-P0-01 — useCampaignTrueRevenue dailyMeta IIFE walks the FULL CampaignsResponse (`data.rows`) instead of the already-filtered `allCampaignRows`

**File**: `dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:270-281`
**Severity**: P0

**Issue**: The inner IIFE at lines 270-281 builds `dailyMeta` for the per-campaign attribution analysis. It walks `data.rows` (line 273 — the entire CampaignsResponse the SWR fetch returned, covering ALL three stores' campaigns) then filters via `r.storeId !== a.storeId || r.platform !== a.platform || r.campaignId !== a.campaignId`. The fix in 05.2.1.1-FIX-05 was to use `allCampaignRows` for `campaignSpend` (lines 189-193) — but the dailyMeta IIFE at line 273 was not migrated to use `allCampaignRows`. Both data sources can be different:
- `data.rows` = full SWR response, no filters
- `allCampaignRows` = filtered by `localRange.from..to` AND `localStore` (see `CampaignsTable.tsx:440-447`)

```ts
// useCampaignTrueRevenue.ts:270-281
const dailyMeta = (() => {
  const byDate = new Map<string, number>();
  if (!data) return [];
  for (const r of data.rows) {            // ← unfiltered (all stores)
    if (r.storeId !== a.storeId) continue;
    if (r.platform !== a.platform) continue;
    if (r.campaignId !== a.campaignId) continue;
    if (r.date < localRange.from || r.date > localRange.to) continue;
    byDate.set(r.date, (byDate.get(r.date) ?? 0) + r.conversionValue);
  }
  return Array.from(byDate.entries()).map(([date, value]) => ({ date, value }));
})();
```

**Why it matters**: When the user has the localStore filter set to "All", `allCampaignRows` = `data.rows` filtered by date range, and the IIFE's behavior is identical. BUT — when the migration `migrateProductMapKeys` runs and a campaignId is mapped to a Google platform, the post-migration check `r.platform !== a.platform` works correctly. The actual silent corruption path: in the rare case where Meta's campaignId 17-19-digit string was lossy-rounded by Sheets (the 05.2.1 AUDIT-P0-02 scenario, fixed by setNumberFormat('@') for new writes BUT existing sheets need the migration run), `r.campaignId !== a.campaignId` returns FALSE for two different campaignIds that lossy-compressed to the same JS Number value. The cross-store filter `r.storeId !== a.storeId` saves most of those cases (the cross-store collisions still get filtered out by storeId), but **same-store, same-platform** collisions silently pass through. This is rare but real if existing sheets haven't been re-migrated.

The bigger issue is that `data` is destructured from `opts` but the `useMemo` dependency lists `data` (line 314) — so the IIFE has a stable closure over `data` ref. But the analysis is computed PER `a` in the `aggregated` loop, walking `data.rows` for every campaign. For N campaigns × M rows = O(N*M) work where it should be O(M) (build a multi-key map once outside the loop).

**Recommended fix**:
1. Replace `data.rows` with `allCampaignRows` (already filtered by store + date).
2. Hoist the dailyMeta walk out of the per-campaign loop. Build a `Map<string, Array<{date, value}>>` keyed by `${storeId}::${platform}::${campaignId}` ONCE, then look up per campaign:

```ts
const dailyMetaByCampaign = useMemo(() => {
  const out = new Map<string, Map<string, number>>();
  for (const r of allCampaignRows) {
    const k = campaignKey(r.storeId, r.platform, r.campaignId);
    let m = out.get(k);
    if (!m) { m = new Map(); out.set(k, m); }
    m.set(r.date, (m.get(r.date) ?? 0) + r.conversionValue);
  }
  return out;
}, [allCampaignRows]);
```

Then inside the loop: `const dailyMeta = Array.from(dailyMetaByCampaign.get(campaignKey(a.storeId, a.platform, a.campaignId)) ?? [], ([date, value]) => ({date, value}));`. Fixes both correctness and the O(N*M) wart in one shot.

### AUDIT-P0-02 — `isOrganicSource` predicate buckets `'other-paid'` AND empty-string source into Organic

**File**: `dashboard-web/src/components/MetaShopifyReconciliation.tsx:218-230`
**Severity**: P0

**Issue**: After 05.2.1.1-FIX-01 inverted the predicate, the new `isOrganicSource` reads:

```ts
function isOrganicSource(order: { source: OrderSource | string; fbclidPresent?: boolean; gclidPresent?: boolean }): boolean {
  if (order.fbclidPresent) return false;
  if (order.gclidPresent) return false;
  if (order.source === 'meta-paid') return false;
  if (order.source === 'google-paid') return false;
  return true;
}
```

The OrderSource union at `ordersAttribution.ts:66-75`:
```ts
| 'meta-paid' | 'google-paid' | 'meta-organic' | 'google-organic'
| 'email' | 'other-paid' | 'other-referral' | 'direct' | '';
```

`other-paid` is documented as "UTM-tagged but unrecognised paid source" (line 72). For uzoshop/zolplus the TikTok / influencer / native ads campaigns that don't emit fbclid or gclid land here. Today those are counted as **organic**. This is the inverse of the 05.2.1 P0-01 problem: we over-corrected the whitelist by adding `'other-paid'` to the organic bucket.

Equally problematic: `''` (line 75 — "unknown / missing"). An order with no UTM and no referrer where the writer couldn't classify ends up with `source = ''`. By the inverted predicate, `'' === 'meta-paid' → false`, `'' === 'google-paid' → false`, falls through → `return true`. Every classifier-failure order is counted as organic.

**Why it matters**:
- For zolplus/usmile360 (active TikTok / influencer): TikTok orders inflate the Organic series. When the user looks at "Organic vs Shopify" they think they have a healthy organic flow when really half is paid TikTok.
- For ANY store: a classifier failure on the Apps Script side (a UTM the writer didn't anticipate, a referrer string Shopify didn't normalize) silently becomes organic. The classifier failure mode is invisible.
- `darkTrafficPercent` is correspondingly under-counted (organic is fatter than real).

**Repro**: Set up a Shopify order with `source = 'other-paid'`, `fbclidPresent = false`, `gclidPresent = false`, containing a mapped product. Run `buildReconciliation`. Expected: order should NOT contribute to organic (it's a paid order). Actual: order's `mappedRevenue` adds to `organicByDate`.

**Recommended fix**: Explicitly enumerate the organic set with both inclusion and exclusion:

```ts
function isOrganicSource(order: { source: OrderSource | string; fbclidPresent?: boolean; gclidPresent?: boolean }): boolean {
  if (order.fbclidPresent) return false;
  if (order.gclidPresent) return false;
  if (order.source === 'meta-paid') return false;
  if (order.source === 'google-paid') return false;
  if (order.source === 'other-paid') return false;          // ← add
  // unknown / missing source = ambiguous. Default to NOT organic so a
  // classifier failure doesn't silently inflate the organic series.
  if (order.source === '') return false;                     // ← add
  return true;
}
```

Lock with a test that sweeps every OrderSource union member through `isOrganicSource` and pins the expected bucket (see also AUDIT-P3-01).

### AUDIT-P0-03 — Organic-series accumulator drops refund days (still `<= 0` skip), inconsistent with the Shopify-series fix

**File**: `dashboard-web/src/components/MetaShopifyReconciliation.tsx:243-252`
**Severity**: P0

**Issue**: The 05.2.1 audit's P0-03 finding was "refund days silently dropped." The fix was applied to the Shopify series at line 186 (`if (mappedRevenue === 0) continue;`) — but the Organic series (lines 244-252) STILL uses the buggy gate:

```ts
let mappedRevenue = 0;
for (const li of order.lineItems) {
  if (wantedIds.has(li.productId)) {
    mappedRevenue += li.revenueCad;
  }
}
if (mappedRevenue <= 0) continue;  // ← still buggy
organicByDate.set(order.date, (organicByDate.get(order.date) ?? 0) + mappedRevenue);
```

The fix pattern from the Shopify series (line 186) was deliberately `=== 0` (skip only orders with NO mapped products) but for Organic the `<= 0` was preserved. This means: a Shopify-direct order on date D that contains a mapped product AND was fully refunded (negative `revenueCad`) is:
- Counted in `shopifyByDate[D]` with negative value (correct)
- NOT counted in `organicByDate[D]` (wrong — refund should reduce organic too)

The two series are then on inconsistent bases: Shopify includes refunds, Organic doesn't. The chart shows Shopify dipping on refund days while Organic stays flat, making it look like the organic flow has zero variability — which then drives `r(Organic)` toward 0 (no variance → null per the pearson contract).

**Why it matters**: For stores with frequent refunds (any DTC) the operator sees an inflated organic baseline. `darkTrafficPercent` calculation `Math.round((1 - sumChannels / sumShopify) * 100)` is biased: on refund-heavy days, `sumShopify` shrinks but `sumChannels` doesn't shrink (organic kept inflated, paid platforms have their own claim numbers), so the ratio looks artificially healthy.

**Repro**: Direct organic order on 2026-05-10 with one mapped product, line item refunded after sale → `revenueCad = -50`. Expected: `organicByDate.get('2026-05-10') = -50`. Actual: order skipped entirely, no Organic contribution.

**Recommended fix**: Change line 250 from `if (mappedRevenue <= 0) continue;` to `if (mappedRevenue === 0) continue;` — same change that was applied to Shopify at line 186. The skip should only happen when there's NO contribution (no mapped product in this order), not when there's a refund contribution.

### AUDIT-P0-04 — `analyzeAttribution` filter doesn't enforce `o.storeId === campaign.storeId` at the boundary; relies on the matcher

**File**: `dashboard-web/src/lib/attributionAnalysis.ts:329-333`
**Severity**: P0

**Issue**: The campaign-level `analyzeAttribution`'s `matchedOrders.filter` at lines 329-333:

```ts
const matchedOrders = orders.filter(o => {
  if (o.date < dateFrom || o.date > dateTo) return false;
  if (!Number.isFinite(o.totalCad)) return false;
  return orderMatchesCampaign(o, campaign);
});
```

The filter does NOT check `o.storeId === campaign.storeId`. It relies on `orderMatchesCampaign` (line 238) to do that — and `orderMatchesCampaign` does check storeId at line 238 (`if (order.storeId !== campaign.storeId) return false`). So today the storeId match is enforced — but ONLY via the matcher's internal guard.

Compare to `analyzeAttributionForAdSet` at lines 729-734 (which has explicit storeId check at line 731) and `analyzeAttributionForAd` at lines 779-784 (storeId check at line 781). Those analyzers have defense-in-depth: filter AT the boundary, then matcher does its own check. The campaign-level analyzer is missing the boundary check.

Why does this matter:
1. The Bayesian CI block (lines 354-386) uses `matchedOrders.map(o => o.totalCad)` for variance computation. If `orderMatchesCampaign` ever drops the storeId check (refactor regression), wrong-store orders would leak in.
2. `computeWindowStability` (line 567) and `detectOutlierDays` (line 641) iterate the same `matchedOrders` — same exposure.
3. Distinct from those: `dailyMetaSeries` parameter at line 317 has NO storeId enforcement at all. The caller (`useCampaignTrueRevenue.ts:288-301`) builds dailyMeta from `data.rows` filtered by storeId/platform/campaignId — but as documented in AUDIT-P0-01, that filter relies on the field equality which can falsely match on lossy-rounded Meta IDs.

**Why it matters**: This is a latent contract violation. The matcher is doing two jobs (boundary filter + matching). If a future PR splits the matcher (e.g., extracts the storeId check, or adds a different match path), the campaign-level analyzer silently widens to cross-store. Defense-in-depth would catch the regression at the boundary.

**Repro**: Comment out line 238 (`if (order.storeId !== campaign.storeId) return false;`) and `analyzeAttribution` for `uzoshop`'s campaign starts including `zolplus` orders with the same campaignId. The ad-set/ad analyzers still filter correctly because they have explicit storeId checks.

**Recommended fix**: Add an explicit storeId guard at the filter:

```ts
const matchedOrders = orders.filter(o => {
  if (o.storeId !== campaign.storeId) return false;
  if (o.date < dateFrom || o.date > dateTo) return false;
  if (!Number.isFinite(o.totalCad)) return false;
  return orderMatchesCampaign(o, campaign);
});
```

Mirrors the ad-set/ad analyzers' pattern.

### AUDIT-P0-05 — `analyzeProductChannel` does NOT filter by platform; Google + Meta orders both feed `facebookShare`

**File**: `dashboard-web/src/lib/attributionAnalysis.ts:1025-1103`
**Severity**: P0

**Issue**: `analyzeProductChannel` computes `facebookShare = facebookOrders / totalOrders` (line 1102). The denominator `totalOrders` is the count of orders containing ANY mapped product (line 1071-1072). The numerator counts orders where `o.source === 'meta-paid' || o.source === 'meta-organic' || o.fbclidPresent === true` (lines 1085-1088).

The caller (`CampaignDrawer.tsx:336-352`, `productChannelBreakdown` useMemo) gates on `summary.platform === 'Meta'` (line 337). So when we call this for a Meta campaign with mapped products P1, P2, the result tells us "of orders containing P1 or P2, X% came from Facebook." Sounds right.

BUT — the mapped products are SHARED with Google PMax campaigns too. Today, when zolplus's Meta campaign and Google PMax both have P1 in their mapping, `analyzeProductChannel` counts EVERY order containing P1 in the denominator (regardless of platform attribution), while the numerator filters to Facebook-only. The result is biased low: a P1 order that came from Google PMax shows up in `totalOrders` but not in `facebookOrders`, so `facebookShare` drops.

The UI then renders "רק 35% מהמכירות הגיעו מפייסבוק → ייתכן שהקמפיין לא הוא המניע" (`ProductChannelBreakdown.tsx:101-108`) — but actually 100% of the FB-driven sales of P1 came from this Meta campaign; the 65% Google portion is irrelevant to the Meta campaign's attribution.

**Why it matters**:
- Operator viewing the Meta campaign drawer sees "this campaign isn't driving sales of P1" (amber warning) when actually it's driving 100% of the Facebook portion. They pause the Meta campaign. Google then has no support, P1 sales drop.
- Mirror problem: if Meta were dominant, the operator sees "60% Facebook" (healthy green) and doesn't realize the Google halo on the same product is the real driver.

**Repro**:
1. Map product P1 to Meta campaign M and Google PMax campaign G.
2. Run a period where: Meta P1 sales = 10 orders (all fbclid), Google P1 sales = 20 orders (all gclid).
3. Open Meta campaign M's drawer. Expected `facebookShare` for the Meta-relevant slice: 100% (all 10 FB sales are FB). Actual: 33% (10 FB / 30 total). Amber warning fires.

**Recommended fix**: The function is doing too much. Two paths:

a) **Scope by platform at the caller**: Pass a `expectedPlatform: 'Meta' | 'Google'` parameter and filter orders to only those with the expected attribution before computing share. Then `facebookShare` becomes "of the Meta-relevant orders, X% are FB-attributed" — useful for cross-check (should be near 100% for a Meta campaign with utm tracking).

b) **Rename the metric**: Keep the function unchanged but rename `facebookShare` → `crossChannelFacebookShare` and update the UI copy to reflect "of all sales of this campaign's products, X% came via Facebook (any campaign, paid+organic)" — which is the current behavior. The amber/green threshold logic in ProductChannelBreakdown.tsx (lines 93-108) then needs to be re-thought because it's framed as "Facebook drove the sale" but actually means "Facebook drove SOME share of cross-channel sales."

Option (a) is the cleaner fix and matches the user's mental model of "is this Meta campaign actually the source."

**Issue**:


Same change applies to `/api/ads` at line 78-82: it has no range params either, so the AdRow filter at line 156-159 filters in-memory after fetching the full ads tab. That's a P2 (memory waste, not correctness) — see AUDIT-P2-01.

### AUDIT-P1-02 — `parseDate` in campaigns.ts uses `new Date(string)` fallback path which interprets dates in LOCAL timezone, not UTC

**File**: `dashboard-web/src/lib/campaigns.ts:71-88`
**Severity**: P1

**Issue**: The `parseDate` helper has three paths:
1. Numeric (Sheets serial date) — correct, uses `(v - 25569) * 86400 * 1000` ms-since-epoch.
2. Regex match `/^\d{4}-\d{2}-\d{2}/` — correct, slices the first 10 chars.
3. Regex match `/^\d{1,2}\/\d{1,2}\/\d{4}$/` — assumes DD/MM/YYYY (Israeli format), correctly constructs `${y}-${m}-${d}`.
4. **Fallback**: `const d = new Date(s); if (!Number.isNaN(d.getTime())) return d.toISOString().slice(0, 10);` — this is the bug.

`new Date(string)` for non-ISO strings is implementation-defined. For ambiguous strings like `"5/10/2026"` (already handled by path 3, so fine), but for unexpected formats it can interpret as local TZ:
- Vercel's serverless functions run in UTC by default — `new Date("2026-05-10 12:30")` parses as UTC noon → `.toISOString().slice(0,10) = "2026-05-10"`.
- A developer running locally in IDT (UTC+3) gets `new Date("2026-05-10 23:30")` → 20:30 UTC → still `"2026-05-10"`. But `new Date("2026-05-10 02:30")` IDT → 23:30 UTC on **2026-05-09** → `.toISOString().slice(0,10) = "2026-05-09"`. **Off by a day.**

The same flaw exists at `ordersAttribution.ts:107-122` (mirror parseDate).

**Why it matters**: If Apps Script ever writes a non-standard date format (e.g., a tab written with `setNumberFormat('yyyy-mm-dd hh:mm')` for the date col, then the API returns formatted strings via `dateTimeRenderOption: 'FORMATTED_STRING'`), the date can shift by a day. Currently the writer uses `setNumberFormat('yyyy-mm-dd')` so path 2 matches and the fallback is unreached. But it's a load-bearing assumption with no test.

**Recommended fix**: Either delete the fallback (refuse non-standard dates explicitly) OR construct UTC-anchored:

```ts
const d = new Date(s);
if (Number.isFinite(d.getTime())) {
  // Force UTC parsing semantics by normalizing through Date.UTC.
  return new Date(Date.UTC(d.getUTCFullYear(), d.getUTCMonth(), d.getUTCDate()))
    .toISOString().slice(0, 10);
}
return null;
```

Better: log a warning so we know when the fallback path is hit.

### AUDIT-P1-03 — `cpmRoasAnalysis.pearson_` uses population variance (divisor N), not sample variance (N-1) — inconsistent with `attributionAnalysis.pearson` which uses the correct full population formula but on filtered finite pairs

**File**: `dashboard-web/src/lib/cpmRoasAnalysis.ts:54-77`
**Severity**: P1

**Issue**: `cpmRoasAnalysis.pearson_` (lines 54-77) computes correlation with no Bessel correction. Note that for correlation specifically, this is mathematically OK — both numerator and denominator are scaled by the same factor, so the result is identical to the sample-variance form. BUT — the function does NOT filter non-finite values (`NaN`, `Infinity`). The companion in `attributionAnalysis.pearson` (lines 158-186) does:

```ts
// attributionAnalysis.ts:158-186
for (let i = 0; i < n; i++) {
  const x = xs[i];
  const y = ys[i];
  if (!Number.isFinite(x) || !Number.isFinite(y)) continue;   // ← filter
  pairs.push([x, y]);
}
if (pairs.length < 2) return null;
// ...
if (vx === 0 || vy === 0) return null;
const denom = Math.sqrt(vx * vy);
if (!Number.isFinite(denom) || denom === 0) return null;
```

`cpmRoasAnalysis.pearson_` doesn't filter non-finite, doesn't check NaN denom, and returns the raw `cov / Math.sqrt(varA * varB)` — which can be NaN/Infinity if inputs aren't sanitized.

Today, `analyzeCpmVsRoas` at line 130 filters `d.cpm > 0 && d.roas > 0` before passing into `pearson_`, which incidentally filters NaN (NaN > 0 is false). So the bug is masked. But:
1. The contract of `pearson_` (per docstring) is "returns null when... zero variance or n<3." It does NOT promise to reject NaN. So a future caller bypassing the `> 0` filter would silently get NaN out.
2. The function has TWO copies — `pearson_` (cpmRoasAnalysis.ts) and `pearson` (attributionAnalysis.ts). They have different contracts, different signatures (`number | null`) but only one is rigorous. DRY violation.

### AUDIT-P1-04 — `prevRange` computation in CampaignsTable and CampaignDrawer uses `new Date(prevToMs).toISOString().slice(0, 10)` — off-by-one near month boundaries due to UTC vs local-anchored Date.UTC math

- `dashboard-web/src/components/CampaignsTable.tsx:532-550`

**Issue**: Both files compute the previous-period range with this pattern:

```ts
  Number(localRange.from.slice(5, 7)) - 1,
  Number(localRange.from.slice(8, 10)),
```

- `Date.UTC(y, m-1, d)` returns milliseconds at UTC midnight — correct.
- Subtracting `86400000` is "go back 24 hours" — correct, hits the previous UTC midnight.
- `new Date(prevToMs).toISOString().slice(0, 10)` is the actual UTC date string. Correct.

More subtle: in `Date.UTC(2026, 0, 1)` and a span of 90 days that crosses a DST boundary (Israel goes IDT → IST in October, IST → IDT in March), the millisecond delta is exactly `90 * 86400000` because UTC has no DST. The `Math.round` is a safety net for double-precision arithmetic noise. So spanDays is correct.

What's wrong: in the rare edge case where the user enters a range whose `from` slice is malformed (e.g., `"2026-03-3"` instead of `"2026-03-03"`), `Number("3-")` returns NaN, `Date.UTC(2026, 2, NaN)` returns NaN, `prevToMs = NaN - 86400000 = NaN`, `new Date(NaN).toISOString()` THROWS `RangeError: Invalid time value`. If the parent ever passes a non-validated range, the crash propagates.

**Recommended fix**: Validate or default-coalesce the slice math:

```ts

  if (!validateIsoDate(rangeFrom) || !validateIsoDate(rangeTo)) {
```
