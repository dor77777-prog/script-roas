# Phase 05.2.2 — Codex Peer Review of Opus Audit

## Summary

Opus found several real defects, especially the AdsDrawer range mismatch, drawer budget recency bug, stale CBO/ABO budget display, missing `/api/ads` pagination, and the remaining organic refund skip. The audit is high-signal on edge cases, but the P0 count is inflated: most P0/P1 claims are defensive hardening, performance, or ambiguous-channel semantics rather than "wrong number with no error" defects.

The biggest disagreements are `AUDIT-P0-05` and `AUDIT-P1-07`. `analyzeProductChannel` is documented as cross-channel product-source analysis, so filtering out Google orders would remove the signal it was built to show. The blended CPM calculation is also a valid portfolio CPM; zero-impression sub-rows do not make the aggregate formula wrong.

I found four additional issues Opus missed. The most important: campaign drilldown state drops the `storeId` namespace, so an all-stores view can open a drawer that merges two stores' rows for the same campaign ID. Two sibling namespace drops exist in CPM previous-period drawer analysis and AdsDrawer. I also found a signed-revenue visual defect in `AttributionAnalysisPanel`'s deterministic/modeled bar.

## Verdict Legend

- **AGREE** — Opus's finding is real, severity is correct
- **PARTIAL** — finding is real but severity is wrong (specify what you'd change it to) OR fix recommendation needs adjustment
- **DISAGREE** — Opus is wrong (be specific: false positive, fix would break something, etc.)
- **EXTEND** — Opus identified part of the issue; the real problem is bigger / has more affected sites

## Verdicts on Opus's 36 findings

### AUDIT-P0-01 — useCampaignTrueRevenue dailyMeta IIFE walks the FULL CampaignsResponse (`data.rows`) instead of the already-filtered `allCampaignRows`

**Verdict**: PARTIAL

**Reasoning**: The code does walk `data.rows` inside the per-campaign loop (`dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:270-281`), while `campaignSpend` correctly uses `allCampaignRows` (`dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:184-193`). That is inefficient and inconsistent, but the alleged cross-store corruption is not demonstrated: the loop explicitly checks `r.storeId`, `r.platform`, `r.campaignId`, and the date range (`dashboard-web/src/lib/hooks/useCampaignTrueRevenue.ts:273-278`). Also, replacing `data.rows` with `allCampaignRows` would not fix same-store lossy-ID collisions; both arrays would contain the same lossy IDs.

**Adjustment**: Downgrade to P2 performance/defense. Build a `dailyMetaByCampaign` map once from `allCampaignRows`, but do not frame this as a current P0 data-corruption path.

### AUDIT-P0-02 — `isOrganicSource` predicate buckets `'other-paid'` AND empty-string source into Organic

**Verdict**: PARTIAL

**Reasoning**: This is real: `isOrganicSource` only excludes click IDs, `meta-paid`, and `google-paid` (`dashboard-web/src/components/MetaShopifyReconciliation.tsx:224-230`), while `OrderSource` explicitly includes `other-paid` and `''` (`dashboard-web/src/lib/ordersAttribution.ts:66-75`). Counting unrecognized paid and unknown-classifier rows as "Organic / Direct" can inflate that line. But 05.2.1.1 deliberately moved to an inverted paid-exclusion model, so the business policy is ambiguous: either exclude `other-paid`/unknown, or rename the bucket to "non-Meta/non-Google".

**Adjustment**: Downgrade to P1. Fix by making the channel policy explicit and testing every `OrderSource` bucket through `buildReconciliation`.

### AUDIT-P0-03 — Organic-series accumulator drops refund days (still `<= 0` skip), inconsistent with the Shopify-series fix

**Verdict**: EXTEND

**Reasoning**: The organic accumulator still drops non-positive mapped revenue (`dashboard-web/src/components/MetaShopifyReconciliation.tsx:236-251`), while Shopify actual allows negative values by only skipping `mappedRevenue === 0` (`dashboard-web/src/components/MetaShopifyReconciliation.tsx:174-187`). So a signed organic refund can be omitted from organic while included in Shopify. Opus's one-line `=== 0` fix is still not precise enough, because zero-net orders with mapped products are semantically different from orders with no mapped product.

**Adjustment**: Use `hitMapped` in both Shopify and Organic accumulators: skip only when no mapped product was present, then add the signed `mappedRevenue` even when it is zero or negative. Severity should be P1/P2 unless production refund rows are confirmed to be common.

### AUDIT-P0-04 — `analyzeAttribution` filter doesn't enforce `o.storeId === campaign.storeId` at the boundary; relies on the matcher

**Verdict**: PARTIAL

**Reasoning**: The boundary filter lacks an explicit store guard (`dashboard-web/src/lib/attributionAnalysis.ts:329-333`), but `orderMatchesCampaign` immediately enforces `order.storeId !== campaign.storeId` (`dashboard-web/src/lib/attributionAnalysis.ts:226-239`). The current output is store-isolated. The ad-set and ad analyzers do have redundant boundary guards (`dashboard-web/src/lib/attributionAnalysis.ts:729-733`, `dashboard-web/src/lib/attributionAnalysis.ts:779-783`), so adding one here is reasonable consistency.

**Adjustment**: Downgrade to P3/P2 defense-in-depth. Add the explicit guard for symmetry, not because this is a P0.

### AUDIT-P0-05 — `analyzeProductChannel` does NOT filter by platform; Google + Meta orders both feed `facebookShare`

**Verdict**: DISAGREE

**Reasoning**: The current behavior matches the documented contract. `analyzeProductChannel` asks what fraction of all orders containing the mapped products came from a Facebook surface, independent of `utm_id` campaign matching (`dashboard-web/src/lib/attributionAnalysis.ts:985-989`, `dashboard-web/src/lib/attributionAnalysis.ts:1025-1103`). The component also labels the panel as sales by channel for the mapped products (`dashboard-web/src/components/ProductChannelBreakdown.tsx:37-42`). Filtering out Google orders would destroy the cross-channel product-source signal.

### AUDIT-P1-02 — `parseDate` in campaigns.ts uses `new Date(string)` fallback path which interprets dates in LOCAL timezone, not UTC

**Verdict**: PARTIAL

**Reasoning**: The fallback exists (`dashboard-web/src/lib/campaigns.ts:71-88`), and sibling parsers repeat it (`dashboard-web/src/lib/ads.ts:63-78`, `dashboard-web/src/lib/ordersAttribution.ts:107-122`). ### AUDIT-P1-03 — `cpmRoasAnalysis.pearson_` uses population variance (divisor N), not sample variance (N-1)

**Verdict**: PARTIAL

**Reasoning**: Bessel correction is irrelevant for Pearson correlation because the common scale cancels out. The real point is the local helper does not filter non-finite pairs or guard a non-finite denominator (`dashboard-web/src/lib/cpmRoasAnalysis.ts:54-76`), unlike the shared `pearson` helper (`dashboard-web/src/lib/attributionAnalysis.ts:158-185`). Current callers filter `d.cpm > 0 && d.roas > 0` first (`dashboard-web/src/lib/cpmRoasAnalysis.ts:130-132`), so the bug is masked today.

**Adjustment**: Downgrade to P3 hardening. Port the finite-pair filtering while preserving the CPM helper's intentional 3-point minimum.

### AUDIT-P1-04 — `prevRange` computation in CampaignsTable and CampaignDrawer uses `new Date(prevToMs).toISOString().slice(0, 10)` — off-by-one near month boundaries

**Verdict**: PARTIAL

**Reasoning**: The timezone/off-by-one claim is wrong: both implementations use `Date.UTC`, subtract whole UTC days, and serialize UTC dates (`dashboard-web/src/components/CampaignsTable.tsx:532-550`, `dashboard-web/src/components/CampaignDrawer.tsx:149-167`). That is stable across DST. The only real issue is malformed `rangeFrom`/`rangeTo` causing `new Date(NaN).toISOString()` to throw, but current range values come from validated route params or `<input type="date">`.

**Adjustment**: Downgrade to P3 validation hardening. Centralizing `getPreviousPeriod(range)` would still be a useful cleanup.

### AUDIT-P1-06 — `aggregate()` latest budget comparison uses `>=`, making duplicate-date tie-breaking non-deterministic

**Verdict**: PARTIAL

**Reasoning**: The `>=` tie-break exists for campaign budget, ad-set budget, and budget type (`dashboard-web/src/components/CampaignsTable.tsx:176-195`). ### AUDIT-P1-07 — `cpmDaily` mixed zero-impression rows distort CPM

**Verdict**: DISAGREE

**Reasoning**: The code computes a blended portfolio CPM as total daily spend divided by total daily impressions (`dashboard-web/src/components/CampaignsTable.tsx:492-516`). If one ad set has spend and zero impressions while another has impressions, including both spend and impressions is a valid aggregate CPM. Dropping spend from zero-impression rows would understate actual spend. The drawer uses the same portfolio formula (`dashboard-web/src/components/CampaignDrawer.tsx:250-299`, `dashboard-web/src/components/CampaignDrawer.tsx:572-585`).

## New findings (Opus missed)

### CODEX-NEW-P1-01 — Campaign drawer drilldown drops `storeId`, so all-stores view can merge same campaign ID across stores

**File**: `dashboard-web/src/components/CampaignsTable.tsx:418-420,1266-1280`; `dashboard-web/src/components/CampaignsTableRow.tsx:72-76`
**Severity**: P1

**Issue**: The row click passes only `(campaignId, platform)` to the parent (`CampaignsTableRow.tsx:72-76`). `CampaignsTable` stores only `drillCampaignId` and `drillPlatform` (`CampaignsTable.tsx:418-420`), then builds drawer rows by filtering `campaignId`, `platform`, date, and optional `storeName` (`CampaignsTable.tsx:1266-1280`). When `localStore === 'All'`, there is no `storeId` filter.

**Why Opus missed it**: Opus focused on analyzer-level store guards, not the UI state transition that loses the row's composite key.

**Why it matters**: If two stores have the same platform campaign ID, the drawer aggregates both stores into one summary. `CampaignDrawer` then derives `storeId` from `rows[0]` (`dashboard-web/src/components/CampaignDrawer.tsx:232-233,354-357`), so reconciliation and product mapping use the first store while spend/value include both stores.

**Recommended fix**: Carry the full row namespace through drilldown: store `{ storeId, platform, campaignId }`, pass `storeId` from `CampaignsTableRow`, and filter drawer rows by all three fields.

### CODEX-NEW-P2-01 — CampaignDrawer previous-period CPM baseline filters only by `campaignId`

**File**: `dashboard-web/src/components/CampaignDrawer.tsx:591-610`
**Severity**: P2

**Issue**: The previous-period CPM series filters `campaignsDataPrev.rows` with only `r.campaignId === campaignId` (`CampaignDrawer.tsx:591-594`). It does not filter `storeId` or `platform`, even though current drawer rows are scoped to one store/platform.

**Why Opus missed it**: Opus audited the previous-range date math but not the namespace filter used after the extra SWR fetch.

**Why it matters**: A same campaign ID in another store or platform can contaminate the "vs previous period" CPM/ROAS baseline. The chart then compares current campaign performance against a previous-period series that is partly from a different campaign.

**Recommended fix**: Filter previous rows by `r.storeId === storeId`, `r.platform === summary.platform`, and `r.campaignId === campaignId`. Also keep the date guard against `prevRange`.

### CODEX-NEW-P2-03 — AttributionAnalysisPanel bar widths can become negative or exceed 100% on signed revenue

**File**: `dashboard-web/src/components/AttributionAnalysisPanel.tsx:81-97`
**Severity**: P2

**Issue**: The deterministic/modeled breakdown bar uses `analysis.deterministicRevenue / value` and `analysis.modeledRevenue / value` directly, only capping the upper bound with `Math.min(100, ...)` (`AttributionAnalysisPanel.tsx:81-97`). Signed revenue is explicitly supported by the analyzer, so deterministic revenue can be negative after refunds, and modeled revenue can exceed the platform value when `deterministicRevenue < 0`.

**Why Opus missed it**: Opus found a similar zero-total width issue in `ProductChannelBreakdown`, but did not check the signed-revenue path in the attribution panel.

**Why it matters**: Refund-heavy campaigns can render invalid negative CSS widths or bars whose combined widths exceed the container, even though the numeric analysis is valid.

**Recommended fix**: Clamp each visual segment to `[0, 100]`, and for signed revenue either render a separate refund marker or hide the proportional bar when deterministic revenue is negative.
