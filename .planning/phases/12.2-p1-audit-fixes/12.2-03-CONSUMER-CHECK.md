### Rationale

Per CONTEXT D-07 decision matrix, this technically maps to "**type-only carve-out**" (M=7 type-only, N=0 runtime). However, per the planner's `<done>` clause on Task 3.1 ("Per known-state (Oracle: 4 non-test consumers exist...), the verdict will be **fix path**") and the operator's pre-confirmation in the plan body, we proceed with **fix-path**:

1. The `ProductRow` type is the shared schema contract across 7 files. Even if `fetchProductsData` is unused today, the type definition lives in the same module and any future re-enable of the Sheets path (e.g., Postgres outage fallback) would re-introduce the latent bugs.
2. The fixes are small (one parseDate replacement + one filter expression alignment).
3. The regression tests pin the bug shapes so they cannot recur if someone resurrects the Sheets-path call.
4. **Type-only carve-out is more invasive** (requires extracting `ProductRow` to its own module + updating 7 imports) than the in-place fix.
5. STA-46/47 do NOT modify the `ProductRow` type, so type-only consumers are unaffected.

**Proceeding to Tasks 3.2 + 3.3 + 3.4.**
