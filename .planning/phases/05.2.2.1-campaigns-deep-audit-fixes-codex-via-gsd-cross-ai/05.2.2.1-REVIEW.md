### WR-01: FIX-19 banner fires prematurely while previous-period data is still loading

**File:** `dashboard-web/src/components/CampaignDrawer.tsx:793-798`, `dashboard-web/src/components/CampaignsTable.tsx:934-939`
**Issue:** The banner condition is `cpmAnalysisMode === 'prev' && analysis.mode === 'half-over-half'`. When the user toggles to `prev`, `campaignsDataPrev`/`cpmPrevData` is `undefined` for ~100-500ms while SWR fetches. During that window `prevDaily` returns `undefined`, the analyzer is called without `{ prev }`, `havePrev=false`, and `analysis.mode='half-over-half'` -> the banner fires immediately. The banner copy promises the operator that the previous period had fewer than 3 active days, but the analyzer never actually evaluated the prev data. The banner self-corrects when data arrives, but if data is genuinely sufficient (>=3 days), the user briefly sees an incorrect explanation. `isLoadingPrev` is already computed (line 629 / 776) and could gate the banner.
**Fix:**
```tsx
{cpmAnalysisMode === 'prev' && !isLoadingPrev && analysis.mode === 'half-over-half' && (
  <div className="text-[10px] text-amber-700 bg-amber-50 px-2 py-1 rounded mt-1">
    תקופה קודמת לא הספיקה (פחות מ-3 ימים פעילים) — חזרנו להשוואת חצי-חצי.
  </div>
)}
```
This keeps the banner suppressed until SWR resolves, then fires only on the real fallback condition.

### WR-04: parseDate accepts `'DD/MM/YYYY'` strings without validating real calendar dates

**File:** `dashboard-web/src/lib/dateRange.ts:160-164`
**Issue:** The DMY branch matches `/^(\d{2})\/(\d{2})\/(\d{4})$/` and reformats to `${yyyy}-${mm}-${dd}` without checking that the day/month numbers are valid. A malformed legacy cell `'31/02/2026'` parses to the string `'2026-02-31'`, which is not a real calendar date. Downstream lexicographic comparisons (`r.date < range.from`, `r.date > range.to`) accept it, and the row is included with a fake date. `parseRangeParams` validates query params with `isRealDate`, but `parseDate` doesn't apply the same gate. This is a defense-in-depth gap that survives only because the Apps Script writer currently emits ISO-formatted strings — the DMY fallback is a legacy path for older sheets.
**Fix:**
```ts
const dmy = /^(\d{2})\/(\d{2})\/(\d{4})$/.exec(str);
if (dmy) {
  const [, dd, mm, yyyy] = dmy;
  const candidate = `${yyyy}-${mm}-${dd}`;
  // Round-trip via Date to validate month/day boundaries (matches isRealDate).
  const d = new Date(`${candidate}T00:00:00Z`);
  if (!Number.isFinite(d.getTime()) || d.toISOString().slice(0, 10) !== candidate) {
    console.warn(`parseDate: invalid DD/MM/YYYY "${str}"`);
    return null;
  }
  return candidate;
}
```

### WR-05: getPreviousPeriod does not validate that range.from <= range.to before computing length

**File:** `dashboard-web/src/lib/dateRange.ts:203-223`
**Issue:** The helper validates ISO format via regex but not the from/to ordering. If callers pass `{ from: '2026-05-31', to: '2026-05-01' }` (e.g., from a corrupted localStorage or a future caller that doesn't enforce ordering), `lengthMs = toMs - fromMs` is negative, `prevFromMs = prevToMs - lengthMs = prevToMs + |lengthMs|` -> the returned `prevFromMs > prevToMs`, an inverted range. Downstream `r.date >= prevRange.from && r.date <= prevRange.to` becomes impossible -> empty results silently. CampaignsTable's date inputs enforce ordering (line 657-659 swaps when needed), so the input today is always sorted, but the helper's contract should validate or fail loudly.
**Fix:**
```ts
export function getPreviousPeriod(range: DateRange): DateRange {
  if (!ISO_DATE.test(range.from) || !ISO_DATE.test(range.to)) {
    console.warn('getPreviousPeriod: malformed range, returning as-is', range);
    return range;
  }
  if (range.from > range.to) {
    console.warn('getPreviousPeriod: from > to, returning as-is', range);
    return range;
  }
  // ... existing math
}
```
