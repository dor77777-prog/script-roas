## Summary

Reviewed the FIX-01..15 + TEST-01..08 surface area. The focus-area fixes work in the common case but ship with several latent defects in edge cases:

- **`computeLineItemsCad` (TS mirror) does not match `Shopify.gs` for orders containing a mix of standard + custom items** — the test that explicitly claims parity asserts the wrong contract. This is the highest-impact finding (BLOCKER for the documented "KEEP IN SYNC" promise, even though the TS function isn't yet consumed in production code).
- The **product-map migration** is "one-shot per session," ranges only as wide as the active SWR fetch (default 90 days), and silently leaves legacy 2-segment keys behind for campaigns inactive outside that window. Consumer code that uses `startsWith(storeId::)` then double-counts them for the shared-campaigns heuristic and may produce double allocations.
- Several `buildReconciliation` parameters (`productsData`, `summary.dailyArr`, `summary.campaignId`) are accepted on the public API but never read — call sites and tests still pass them, and one test even documents the absence of `productsData` semantics as intentional.
- The negative-`metaClaim` and refund paths in `analyzeAttribution` are partially guarded (signed-input fix landed for coverage) but still emit nonsense `trust.score` (negative ints) and reason strings ("רק -200% מההמרות") when `deterministicRevenue` is large negative.
- One `default:` branch in `CampaignsTable.sortAggregated` throws inside an `Array.prototype.sort` comparator. If TypeScript exhaustiveness ever drops out (e.g., upstream type widens), this becomes a runtime crash that takes the entire campaigns table down.

No security vulnerabilities found at this depth. The lock around `writeProductSalesForDay_` and `isoLocalMidnight_`'s DST handling are both correct as written.

## Warnings

### WR-01: TS `computeLineItemsCad` mirror diverges from `Shopify.gs:computeLineItemsCad_` on mixed-item orders

**File:** `dashboard-web/src/lib/lineItems.ts:42-75`
**Issue:** The module docstring (lines 2-21) claims "KEEP IN SYNC with Shopify.gs" and lists the behavior contract, but the two implementations compute subtotal differently:

- **`Shopify.gs:658-662`** reduces subtotal over the **unfiltered** `items` array (includes custom items with empty `product_id`).
- **`lineItems.ts:53-59`** reduces subtotal over `valid` only (after filtering empty productIds).
- Same divergence applies to the flat-spread denominator (`.gs` uses `items.length`, TS uses `valid.length`).

Concrete example: order total $100, line items `[{p:'p-1', price:50, qty:1}, {p:'', price:50, qty:1}]`:
- `.gs` writer emits `{p:'p-1', r: round2((50/100)*100) = 50}`
- TS mirror emits `{productId:'p-1', revenueCad: round2((50/50)*100) = 100}`

The test at `computeLineItemsCad.test.ts:78-90` asserts the TS value (100), so the test suite happily validates the divergent behavior. Today the impact is bounded — only the test consumes `lineItems.ts` — but the moment any production code starts using this helper to recompute or verify line-item splits, dashboard-vs-sheet numbers will silently disagree.

**Fix:** Match the .gs semantics in `lineItems.ts` so the parity claim is real, then update the test:

```typescript
export function computeLineItemsCad(
  orderTotal: number,
  lineItems: LineItemInput[],
): LineItemSplit[] {
  if (!lineItems || lineItems.length === 0) return [];

  // Mirror Shopify.gs:658 — subtotal includes ALL items, including
  // custom/empty-productId. This matters when an order mixes a real
  // product with a custom item.
  const subtotal = lineItems.reduce(
    (s, li) => s + (Number(li.price) || 0) * (Number(li.quantity) || 0),
    0,
  );
  const useFlatSpread = !(subtotal > 0);
  const denom = lineItems.length;

  const out: LineItemSplit[] = [];
  for (const li of lineItems) {
    if (!li.productId || li.productId.length === 0) continue; // skip custom
    const qty = Number(li.quantity) || 0;
    const lineGross = (Number(li.price) || 0) * qty;
    const lineCad = useFlatSpread
      ? (denom > 0 ? orderTotal / denom : 0)
      : (lineGross / subtotal) * orderTotal;
    out.push({ productId: li.productId, units: qty, revenueCad: round2(lineCad) });
  }
  return out;
}
```

And update `computeLineItemsCad.test.ts:78-90` to assert the .gs behaviour:
```typescript
expect(split[0].revenueCad).toBeCloseTo(50, 2);  // (50/100) * 100 — matches .gs
```

### WR-02: Product-map migration leaves legacy keys behind for campaigns inactive in current SWR window

**File:** `dashboard-web/src/lib/campaignProductMap.ts:75-107`, `dashboard-web/src/components/CampaignsTable.tsx:332-342`
**Issue:** The migration runs exactly once per session (`productMapMigrationRan.current = true`) and only inspects `campaignsData.rows` for the currently-active date range (default 90 days). If a user has a legacy 2-segment key for a campaign that has been paused or hasn't had spend in 90+ days:

1. `rows.filter(r => r.storeId === storeId && r.campaignId === campaignId)` returns `[]`
2. `platforms.size !== 1` triggers the warning branch
3. The legacy key is preserved untouched
4. The migration is marked complete and never retries — even if the user widens their date range to include the inactive campaign's history

Downstream consequences:

1. **Forward lookup is silent UX failure.** `CampaignDrawer.tsx:267` and `CampaignsTableRow.tsx:198`/`306`/`320` build keys via `campaignKey(storeId, platform, campaignId)` (3-segment). The legacy 2-segment key is never matched — the drawer's "Mapped products" section shows empty / picker reads `initial=[]` even though the user's mapping is intact in localStorage.

2. **Reverse-lookup double-counts.** `useCampaignTrueRevenue.ts:259` and `campaignProductMap.ts:152` use `startsWith('${storeId}::')`. This matches BOTH the legacy 2-segment AND any new 3-segment key the user creates for the same campaign, so:
   - `allocateProductRevenue` builds `mappedKeys` containing BOTH keys
   - `campaignSpend.get(legacyKey)` returns 0 (spend keys are 3-segment), so `totalSpend` from the new key alone drives the proportional split — but `mappedKeys.length` is 2 → the `share = 1/mappedKeys.length` fallback fires when `totalSpend === 0`, halving the share
   - The shared-campaigns heuristic counts the legacy entry as a "shared other campaign" → biases confidence toward `medium`/`low`

**Fix:** Run migration on every change to `data` (drop the ref guard), or migrate based on a static union of `STORES × {Meta, Google}` from config rather than from `campaignsData`:

```typescript
useEffect(() => {
  if (data) {
    setProductMap(migrateProductMapKeys(data));
  } else {
    setProductMap(readProductMap());
  }
  // ...
}, [data]);
```

Migration must be idempotent (current implementation is — once a key is migrated it doesn't match the 2-segment regex). Re-running on each `data` refresh handles the "user widens range" case at marginal cost. Optionally, when `platforms.size === 0` AND every campaign for that store in the entire system is single-platform (i.e., it's safe to attribute to the only platform present in `data`), opportunistically migrate using the store's available platforms.

### WR-03: Negative-coverage path in `analyzeAttribution` emits nonsensical `trust.score` and reason text

**File:** `dashboard-web/src/lib/attributionAnalysis.ts:429-441`
**Issue:** The TEST-03 signed-revenue test (analyzeAttribution.test.ts:253-270) demonstrates that `deterministicRevenue` can go negative (refunds exceed sales) and `coverage` is then negative (clamped only on the upper bound by `Math.min(2, ...)`). When this hits the `} else {` branch at line 429:

- `pct = Math.round(coverage * 100)` → e.g., `-200` for coverage=-2
- `trust = { level: 'low', label: 'לא אמין', score: pct }` → `score: -200`
- `reasons.push(\`רק ${pct}% מההמרות... תויגו לקמפיין הזה\`)` → renders `"רק -200% מההמרות (1 הזמנות) תויגו לקמפיין הזה"` to the user

The type contract for `AttributionTrust.score` says "0..100 — useful as a confidence score for any downstream system" (line 75). A negative score breaks any downstream comparator (`Math.max`, range checks, color thresholds).

**Fix:** Clamp the score and rephrase the reason when coverage is negative:

```typescript
} else {
  const pct = Math.round(coverage * 100);
  const safePct = Math.max(0, pct);
  trust = { level: 'low', label: 'לא אמין', score: safePct };
  if (pct < 0) {
    reasons.push(
      `החזרים גדולים מההזמנות (${deterministicOrders} פעולות, CAD ${deterministicRevenue.toFixed(0)} נטו)`,
    );
  } else {
    reasons.push(
      `רק ${pct}% מההמרות (${deterministicOrders} הזמנות) תויגו לקמפיין הזה`,
    );
  }
  // ... rest unchanged
}
```

### WR-04: `sortAggregated` default branch throws inside `Array.prototype.sort` comparator

**File:** `dashboard-web/src/components/CampaignsTable.tsx:231-238`
**Issue:** The exhaustiveness check uses `throw new Error(...)` inside the `default:` branch of `valueOf` (called from the sort comparator at line 242). At compile time the `_exhaustive: never` assignment catches unhandled keys, BUT if anything causes `sortKey` to widen at runtime (e.g., a stale `localStorage` value, a future hot-reload glitch, or a user-controlled SortKey from URL params if that's ever added) — the comparator throws, which propagates out of `Array.prototype.sort` and unmounts the entire table tree via React's error boundary (or worse, an uncaught error if no boundary).

Inconsistent with the equivalent default in `CampaignDrawer.tsx:345-354` (AdSetTable sort) which returns `0` for the same scenario and explicitly documents the "collapses sort to stable" rationale.

**Fix:** Mirror the drawer's safer pattern — log to console once for diagnostics, return 0 to keep the table alive:

```typescript
default: {
  const _exhaustive: never = sortKey;
  void _exhaustive;
  // Defensive: TS exhaustiveness already catches new keys at compile
  // time, but a runtime widening shouldn't take down the whole table.
  return 0;
}
```

### WR-07: `migrateProductMapKeys` regex assumes neither `storeId` nor `campaignId` contains a colon

**File:** `dashboard-web/src/lib/campaignProductMap.ts:81-82`
**Issue:** The 2-segment detection uses `/^[^:]+::[^:]+$/`. If a campaignId in the wild ever contains a single colon (Meta IDs are numeric, so unlikely; Google IDs are also numeric in production; but Apps Script reads from a sheet that could be edited by hand), the regex would fail to match. Worse: if a 3-segment key has a storeId/platform/campaignId combination that happens to look like a 2-segment string (e.g., empty platform), `oldKey.split('::')` returns `['storeId', '', 'campaignId']` and destructuring gets `[storeId, '']` — the `''` campaignId would never match any row and the legacy key stays orphaned.

Also: `split('::')` on a key with literal `::` in storeId (`'foo::bar::Meta::camp-1'`) would silently mis-parse. Defensive coding would compute the segment count explicitly:

```typescript
for (const oldKey of Object.keys(map)) {
  const parts = oldKey.split('::');
  if (parts.length !== 2) continue;  // explicit segment count, not regex
  const [storeId, campaignId] = parts;
  if (!storeId || !campaignId) continue;  // skip malformed
  // ... rest unchanged
}
```

**Fix:** Replace the regex with an explicit segment-count check (above). Same change applies to `campaignsForProduct`'s storeId-prefix matching if storeId can ever contain colons (currently all storeIds are alphanumeric — `uzoshop`, `zolplus`, `usmile360` — so this is defense-in-depth).

### WR-08: `shopify` series in `buildReconciliation` is not directly comparable to `meta + google + organic` channels

**File:** `dashboard-web/src/components/MetaShopifyReconciliation.tsx:124-144`, `255-262`
**Issue:** The `shopify` series sums mapped-product line-item revenue across ALL orders regardless of source. The `meta` and `google` series sum the platforms' self-reported `conversionValue` (post-conversion-window, may include modeled/view-through), and `organic` sums line-item revenue ONLY from non-paid orders.

This means:
- A meta-paid order contributes `lineItem.revenueCad` to `shopify` AND `campaign.conversionValue` to `meta`. These are two different numbers reported on different bases.
- The `darkTrafficPercent = 1 - (meta + google + organic) / shopify` ratio treats `meta + google + organic` as if it sums to the same denomination as `shopify`. It doesn't — `meta` and `google` are platform claims (which can over- or under-report relative to actual Shopify revenue), and `organic` is Shopify-actual, so the mix is denomination-inconsistent.

When platform claims under-report (typical post-iOS-14), `darkTrafficPercent` overstates organic gap. When platforms over-report (view-through, modeled), `darkTrafficPercent` can go negative — but the current implementation only warns when `sumChannels / sumShopify < 0.8`, never the converse, so over-attribution is invisible in this signal.

**Fix:** Either (a) use deterministic click-id revenue for `meta` and `google` (matching `organic`'s line-item basis), or (b) rename `darkTrafficPercent` to something honest like `unreportedShopifyPercent` and document that "channels" here means "what the platforms claim plus what organic accounts for, which is a mix of bases." Suggested:

```typescript
// Use deterministic paid-channel revenue (line-item basis, click-id gated)
// instead of platform conversionValue, so all four series are denomination-
// consistent and the ratio is meaningful.
const metaLineItemByDate = new Map<string, number>();
const googleLineItemByDate = new Map<string, number>();
if (ordersData?.rows) {
  for (const order of ordersData.rows) {
    if (order.storeId !== storeId) continue;
    if (order.date < rangeFrom || order.date > rangeTo) continue;
    if (!order.lineItems?.length) continue;
    let mappedRev = 0;
    for (const li of order.lineItems) {
      if (wantedIds.has(li.productId)) mappedRev += li.revenueCad;
    }
    if (mappedRev <= 0) continue;
    if (order.fbclidPresent || order.source === 'meta-paid') {
      metaLineItemByDate.set(order.date, (metaLineItemByDate.get(order.date) ?? 0) + mappedRev);
    } else if (order.gclidPresent || order.source === 'google-paid') {
      googleLineItemByDate.set(order.date, (googleLineItemByDate.get(order.date) ?? 0) + mappedRev);
    }
  }
}
```

(Note: this is a design-correctness comment, not a single-line patch. The Meta/Google channels currently surface "what the platform claims" which is the user's primary lens — replacing them silently would change the chart's meaning. At minimum, document the denomination mismatch in the panel's explainer copy.)
