## Notes

### Finding 1 — D-B2 / D-C1 are empirically wrong: `refund.transactions[].amount` is NOT the deduction-from-revenue field

The plan's D-B2 math invariant `current_total_price == total_price − Σ refund.transactions[].amount` fails on all 3 stores by a large margin (delta 80–468 CAD). The probe captures enough evidence to identify the correct invariant:

| store | total_price | Σ `refund_line_items[].subtotal` | total_price − Σ subtotal | current_total_price | matches? |
|---|---|---|---|---|---|
| uzoshop | 68.80 | 68.80 | **0.00** | 0.00 | ✓ exact |
| zolplus | 65.28 | 65.28 | **0.00** | 0.00 | ✓ exact |
| usmile360 | 136.43 | 81.08 + 55.35 = 136.43 | **0.00** | 0.00 | ✓ exact |

**The correct invariant is `current_total_price == total_price − Σ refund_line_items[].subtotal`**, not `Σ transactions[].amount`. This implies `refund_line_items[].subtotal` is the canonical "merchandise refunded" field that Shopify itself uses to compute `current_total_price`. The `transactions[].amount` field captures something else — most likely the full money-out at the payment-gateway layer, including shipping refunds, gateway fees, currency-conversion adjustments, or (in the usmile360 case) duplicate-transaction artifacts from a double-refund flow.

### Finding 2 — `refund_line_items[].total` is consistently `undefined` in the live response

The plan's D-B2 fields list included `refund_line_items[].total`, but the field is absent on every refund_line_items entry across all 3 stores (Logger prints `undefined`). The existing per-product code at [Shopify.gs:228](Shopify.gs#L228) already defensively falls back: `parseFloat(rli.subtotal || rli.total || 0)` — i.e. `subtotal` is consumed first, `total` only used as fallback. The `total` field MUST be removed from the contract — the Vitest fixtures (Plan 04) should not encode an `undefined` field, and the TS mirror should accept `subtotal` as the single source.

### Finding 3 — `transactions[].amount` ≫ order total on multi-currency or duplicate-refund paths

For all 3 stores `transactions[].amount` is dramatically higher than the underlying order's `total_price`:
- uzoshop: 149 vs 68.80 (2.17× the order)
- zolplus: 149 vs 65.28 (2.28× the order)
- usmile360: 302.10 × 2 = 604.20 vs 136.43 (4.43× the order, with **2 refund objects** both reporting transaction.amount=302.10 on the same day)

The probe didn't capture `transactions[].currency`, `transactions[].kind` (refund / void / authorization), `transactions[].gateway`, or order-level `currency` / `presentment_currency`. The most likely explanations:
1. **Currency mismatch**: order `total_price` is in display/presentment currency (e.g. ILS), while `transactions[].amount` is in the merchant's payout/transaction currency (e.g. CAD or USD via Stripe).
2. **Double-refund artifact**: in the usmile360 case the merchant likely clicked "refund" twice (or a refund was voided then re-issued), producing two refund objects with full-amount transactions but only one real money movement.

Either way, **`transactions[].amount` is not safe to subtract from `current_total_price`-based revenue** without first reconciling currencies and filtering by `transactions[].kind`. Switching to `refund_line_items[].subtotal` sidesteps both issues — that field is always in the order's display currency (same as `total_price`) and represents merchandise-only.

### Finding 4 — STRIDE-I PII redaction held

The probe's `fields=` parameter excluded the documented PII set (see [05.2.3.0-01-PLAN.md:125-127](05.2.3.0-01-PLAN.md#L125-L127) for the prohibited-fields list — kept in the plan, not duplicated here). The captured log contains zero identifying tokens from that list and no e-mail-shaped strings. The committed evidence file inherits the redaction. **PII gate: PASS.**

### Finding 5 — All 3 sample orders happen to be tax-free (total_tax=0)

Empirical sample didn't include a tax-bearing order, so the invariant `current_total_price = total_price − Σ refund_line_items[].subtotal` is not yet validated for orders where tax was refunded. The 3-store invariant holds for tax-free orders; a follow-on probe (or production observation) is recommended to either confirm extends-to-tax-orders or document a tax-refund gap.
