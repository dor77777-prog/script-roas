# Phase 05.2.3.0: shopify-revenue-refunds-bug-fix - Context

**Gathered:** 2026-05-20
**Status:** Ready for planning (probe-gated — see D-B1..D-B4)

<domain>
## Phase Boundary

Fix the load-bearing data-integrity bug where store-level Shopify revenue does NOT reflect refunds processed on a different day than the original order ("cross-day refunds"). After this phase: a refund processed today on yesterday's order MUST appear as a deduction in today's revenue row across every dashboard surface (home KPIs, PerStoreCards, GoalTracker, daily P&L, data-daily sheet). Refund-day attribution model: refunds count on the day their `refund.processed_at` falls (in Asia/Jerusalem TZ), not on the order's creation day. Prior-day rows stay frozen with their pre-refund total — cross-day refunds appear as today's deduction.

**Critical correction from the failed first attempt (rolled back 2026-05-20):** Prior planning assumed `current_total_price` was gross at order-creation time, then subtracted ALL refunds processed on day D. This caused double-deduction of same-day refunds (because `current_total_price` IS net of refunds applied to that order — confirmed by AUDIT-P0-03). The corrected algorithm subtracts only refunds whose underlying order was created on a different day.

</domain>

<decisions>
## Implementation Decisions

### Area A — Revenue field source & deduction scope

- **D-A1:** Store-level revenue uses `current_total_price` (NOT `total_price`). This field IS net of refunds applied to the order — confirmed empirically by [.planning/phases/05.2.1-algorithm-correctness-audit-opus-codex-cross-ai-review/05.2.1-AUDIT.md](.planning/phases/05.2.1-algorithm-correctness-audit-opus-codex-cross-ai-review/05.2.1-AUDIT.md) AUDIT-P0-03 which observed `current_total_price` going negative when refunds exceed the initial total. The 15-min sync lag is mitigated by the rolling 3-day backfill (D-D1).
- **D-A2:** Cross-day refund detection: query `orders.json` with `updated_at_min/max` covering day D (Asia/Jerusalem 00:00–23:59), then iterate each order's `refunds[]` client-side and keep only refunds where `refund.processed_at` falls on day D AND `order.created_at` does NOT fall on day D. This catches refunds processed on D against orders created on any prior day, since refunding an order advances its `updated_at`.
- **D-A3:** Per-product path (`getShopifyProductSalesForDay`) reuses the SAME `updated_at`-windowed HTTP call as the store-level cross-day fetch. One fetch, two consumers: store-level sums `transactions[].amount`; per-product accumulates `refund_line_items[].subtotal` by `product_id` into `byProduct[pid].netRevenueCad`. Avoids duplicate API calls and API quota burn.
- **D-A4:** All "day" comparisons use `Asia/Jerusalem` timezone (consistent with the existing `isoLocalMidnight_` helper in `Shopify.gs`). A refund processed at `2026-05-20T22:30:00Z` (UTC) is attributed to day `2026-05-21` (IL); document this in the User Manual.

### Area B — Empirical validation probe (CR-04 fix from rolled-back review)

- **D-B1:** Build a read-only Apps Script probe BEFORE writing any TS mirror or main implementation. The probe is **Plan 01** of this phase; the rest of the plans (TS mirror, runtime wiring, manual update) only get written after the probe outputs are confirmed.
- **D-B2:** Probe scope: one order with a refund from each of 3 stores (uzoshop / zolplus / usmile360). For each, dump these fields: `order.id`, `order.created_at`, `order.total_price`, `order.current_total_price`, `order.subtotal_price`, `order.total_tax`, `order.refunds[].processed_at`, `order.refunds[].transactions[].amount`, `order.refunds[].refund_line_items[].subtotal`, `order.refunds[].refund_line_items[].total`. Verify the math: `current_total_price == total_price − Σ refund.transactions[].amount`.
- **D-B3:** Probe runtime: Apps Script menu item `probeRefundContract_()` in `Main.gs`. Output via `Logger.log` (visible in Execution Log). Operator runs the menu item, copies the log to `05.2.3.0-PROBE-EVIDENCE.md` in this phase directory. No secrets in the file — tokens stay in Script Properties.
- **D-B4:** **CHECKPOINT GATE between Plan 01 and Plan 02:** `plan-phase` writes ONLY Plan 01 initially. After Plan 01 runs and `PROBE-EVIDENCE.md` is populated, return to `/gsd-plan-phase 05.2.3.0` to write Plans 02..N based on the empirically confirmed contract. This is the structural mechanism that prevents another fictional-fixture trap (the rolled-back review's CR-04). If the probe reveals the contract differs from this CONTEXT.md, this file gets revised before planning continues.

### Area C — Refund magnitude field & reconciliation invariant

- **D-C1:** Store-level deducts `refund.transactions[].amount` (tax-inclusive, includes shipping refunds). This matches `current_total_price` semantics (tax-inclusive, post-discount, includes shipping). The amount used is the one that makes `current_total_price` match Shopify Admin > Reports > Total Sales for day D.
- **D-C2:** Per-product deducts `refund_line_items[].subtotal` (tax-exclusive, per-line). This matches `line_items[].price` semantics used in the per-product gross calculation. Existing per-product refund logic at `Shopify.gs:200-250` already uses `rli.subtotal || rli.total` — that pattern stays. The cross-day branch (D-A3) follows the same field.
- **D-C3:** Four test invariants are MANDATORY:
  1. **Store-level:** `revenue(D) = Σ current_total_price(orders.created_at=D, excl test/voided) − Σ transactions[].amount(refunds.processed_at=D AND order.created_at≠D)`
  2. **Per-product:** `Σ byProduct[pid].netRevenueCad(D) = (Σ per-line gross for orders.created_at=D after intra-order refund deduction) − Σ refund_line_items.subtotal(refunds.processed_at=D AND order.created_at≠D, grouped by product_id)`
  3. **Cross-path documentation:** store-level ≈ Σ per-product, with a documented gap = `total_tax_refunded(D) + shipping_refunded(D)`. The gap is documented in CONTEXT.md, User Manual, and as a code comment on the per-product function.
  4. **Full reconciliation:** `store_net(D) == Σ per-product[pid].netRevenueCad(D) + total_tax_refunded(D) + shipping_refunded(D)` — exact equality (within float rounding ±0.01 CAD). This invariant catches drift between store-level and per-product paths.
- **D-C4:** Tests live in `dashboard-web/src/lib/__tests__/shopifyRevenueRefunds.test.ts` and use **fixtures derived from PROBE-EVIDENCE.md** (real data from real stores). NO fictional fixtures.

### Area D — Backfill cadence & negative-revenue policy

- **D-D1:** Live trigger (every 15 min via `runLiveUpdate`) runs a rolling 3-day backfill: D-2, D-1, D for each store in sequence. Estimated runtime ~46s (well under the 6-min Apps Script cap). Covers the 15-min `current_total_price` sync lag and catches cross-day refunds processed in the prior 48h.
- **D-D2:** Manual cleanup menu in `Main.gs`: 3 separate per-store menu items, each refreshes 20 days for that store. Wording (exact Hebrew, used verbatim in code and manual): `רענן הכנסות (20 ימים) — uzoshop` / `Zol Plus` / `360usmile`. Operator runs them one at a time with a wait between clicks (to avoid concurrent Apps Script executions exceeding quota).
- **D-D3:** Negative daily revenue is shown as-is (no clamping to 0). Consistent with `current_total_price` going negative per AUDIT-P0-03. Document in User Manual: a day with heavy refunds against prior-day orders can legitimately show negative revenue — this is correct accounting, not a bug. Dashboard surfaces (PerStoreCards, KPIs) display the negative number with the existing red-for-negative color.
- **D-D4:** Same algorithm across all 3 stores (uzoshop, zolplus, usmile360). No per-store knobs — Shopify Admin REST is the same contract for every shop on the same API version (2024-10). Cross-store differences (currency, plan name) are handled by existing helpers (`FX.getFxRate`, `getShopifyPlan`); the refund attribution model is shop-agnostic.

### Claude's Discretion

- Helper naming (e.g., `getShopifyRefundsForDay_` vs `getShopifyRefundsByProcessedDay_`) — pick a clear name during planning.

## Existing Code Insights

### Reusable Assets
- `Config.gs:nextDayStr_(dateStr)` — date-string helper using `Date.UTC` shape. Mirror as `previousDayStr_(dateStr, n=1)` for the rolling 3-day backfill (D-D1).
- `Config.gs:fetchWithRetry_` — wraps `UrlFetchApp.fetch` with 429-retry and exponential backoff. Use for the new updated_at-windowed fetch.
- `Shopify.gs:tryAutoBootstrapShopify_` — handles 401 auto-refresh via Client Credentials Grant. The new fetcher MUST reuse this (don't reinvent token refresh).
- `Shopify.gs:isoLocalMidnight_` — Asia/Jerusalem TZ-aware midnight conversion. Reuse for the `updated_at_min/max` window construction in D-A2.
- `FX.getFxRate(currency, dateStr)` — converts shop-currency to CAD. Refund amounts in shop currency must be CAD-converted before deduction.
- `computeLineItemsCad_` (`Shopify.gs:618-649`) — existing proportional CAD split. Per-product refund subtractions must be applied AFTER this split (so the math sums correctly to the order total).
- `Logger.log` — Apps Script's logging primitive. The probe (D-B3) and new fetcher use it consistently with existing patterns.
- `dashboard-web/src/lib/utils.ts` — TS utility surface. The new TS mirror should follow this file's conventions.

### Established Patterns
- **Date strings as `YYYY-MM-DD`** — never as Date objects across function boundaries. All comparisons string-equal.
- **`storeId` lookup pattern** — `getProp(${storeId}.shopify.token)` always, never hardcoded.
- **50-page pagination safety cap** — every paginated fetch in `Shopify.gs` has it (search `safety > 50`). The new updated_at-windowed fetch follows the same cap.
- **`test` and `voided` order exclusion** — applied uniformly in both store-level and per-product paths. The new cross-day refund extractor MUST honor this filter (a refund against a `test` order does NOT deduct from revenue).
- **`_` suffix for private** — `getShopifyRefundsForDay_` (private, called only by `getShopifyRevenue` and `getShopifyProductSalesForDay`).
- **Vitest mirror pattern** — TS mirror files end in `.ts` (no `.gs` extension), live in `dashboard-web/src/lib/`, tested via Vitest. Existing pattern: `analyzeAttribution.ts` ⇄ `Shopify.gs` attribution logic.

### Integration Points
- **`runLiveUpdateUzoshop` / `Zolplus` / `Usmile`** (`DailyUpdate.gs`) — entry points the 15-min trigger calls. These get wrapped with the rolling 3-day loop (D-D1). Existing helper `runUpdateForSingleStore_(storeId, dateStr)` is the one to call in the loop.
- **`backfillRangeForStores(dateFrom, dateTo, storeIds)`** (`DailyUpdate.gs`) — the helper the 20-day cleanup menu items call (D-D2). Already handles per-day pagination and Sheets-write batching.
- **`Main.gs onOpen`** — menu construction. The 3 new menu items get inserted between the existing `מילוי היסטורי (טווח)…` item and the trigger-management group, sandwiched by `addSeparator()`.
- **`data-daily` tab** — the Sheets tab that surfaces `revenue` per `(store, dateStr)`. The new fix writes via existing `writeDataDailyRow_` (no schema change).
- **Dashboard surfaces** — `HomeTab`, `PerStoreCards`, `GoalTracker`, `PnLTab`, `MetaShopifyReconciliation` all read from `data-daily` via the `/api/data` route. NO dashboard code changes — the fix is server-side (Apps Script) and the dashboard reads whatever the sheet contains.
