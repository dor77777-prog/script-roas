## Area A — Revenue field source & deduction scope

### Q1: Which field to sum at store level?

| Option | Description | Selected |
|--------|-------------|----------|
| `current_total_price` (net, kept) | Sum `current_total_price` for orders with `created_at` on D. Per AUDIT-P0-03 this field IS net of refunds (incl. same-day refunds, may go negative). Cross-day refunds added explicitly. 15-min lag mitigated by rolling backfill. | ✓ |
| `total_price` (gross, explicit deduct all) | Sum `total_price`, then subtract all refunds on D (same-day + cross-day). Cleaner conceptually but requires more deduction code and risks the double-count trap that broke the first attempt. | |

**User's choice:** `current_total_price` (recommended)
**Notes:** Confirmed by codebase evidence (AUDIT-P0-03 shows `current_total_price` going negative).

### Q2: How to detect cross-day refunds for day D?

| Option | Description | Selected |
|--------|-------------|----------|
| `updated_at_min/max` around D + client-side filter | Query `orders.json?updated_at_min=D 00:00 IL&updated_at_max=D 23:59 IL` then iterate `refunds[]` keeping only `refund.processed_at` on D AND `order.created_at` NOT on D. Refunds advance the order's `updated_at`, so this window catches them. | ✓ |
| `processed_at_min/max` on refunds endpoint | Shopify Refunds endpoint doesn't expose `processed_at` filters cross-shop — would need a per-shop refunds endpoint that doesn't exist for this purpose. | |
| Look-back window (e.g., D-30 to D) | Query a wide `created_at` window and filter client-side. Wasteful and risks the 50-page safety cap. | |

**User's choice:** `updated_at_min/max` + client-side filter
**Notes:** This is the only Shopify-supported way to bracket "refunds processed today regardless of order age."

### Q3: Per-product path under the new model

| Option | Description | Selected |
|--------|-------------|----------|
| Add cross-day refund extractor parallel to store-level | Same `updated_at`-windowed fetch, but the extractor maps `refund_line_items[].subtotal` per `product_id`. For cross-day refunds (`order.created_at != D`), decrements `byProduct[pid].netRevenueCad` for day D (gross untouched — item wasn't sold today). One HTTP call shared between store and product paths. | ✓ |
| Separate fetch for per-product | Two API calls per day per store. Doubles API/runtime cost. | |
| Leave per-product as-is | Keeps the existing same-day refund handling but leaves the cross-day bug in per-product path. | |

**User's choice:** Shared fetcher (recommended)
**Notes:** Cost-efficient and avoids drift between store and product paths.

### Q4: Timezone for refund.processed_at comparison

| Option | Description | Selected |
|--------|-------------|----------|
| Asia/Jerusalem | Convert `refund.processed_at` to IL TZ, compare to D. Consistent with how `order.created_at` is bucketed (existing `isoLocalMidnight_`). User-facing days match operator's clock. | ✓ |
| UTC | Use UTC for both ends. Would cause off-by-one days for refunds processed in the IL evening (UTC = same day, IL = next day). Doesn't match Shopify Admin > Reports which displays in shop TZ. | |

**User's choice:** Asia/Jerusalem (recommended)
**Notes:** Operator-facing days must match what `Shopify Admin > Reports` shows.

## Area C — Refund magnitude field & reconciliation invariant

### Q1: Store-level refund magnitude

| Option | Description | Selected |
|--------|-------------|----------|
| `refund.transactions[].amount` (tax-incl) | Matches `current_total_price` semantics (also tax-incl, includes shipping, includes Shopify fees that were refunded). Matches Shopify Admin > Reports > Total Sales. | ✓ |
| `refund_line_items[].subtotal` (tax-excl) | Doesn't match `current_total_price`. Would create asymmetry between store-level revenue (tax-incl) and store-level refund (tax-excl). | |
| Defer to PROBE-EVIDENCE | Decide after probe. | |

**User's choice:** `transactions[].amount` (recommended)

### Q2: Per-product refund magnitude

| Option | Description | Selected |
|--------|-------------|----------|
| `refund_line_items[].subtotal` (tax-excl) | Matches `line_items[].price` semantics. Existing per-product path already uses `rli.subtotal || rli.total`. | ✓ |
| Switch to tax-inclusive | Would require per-line tax computation (line_item.price + Σ tax_lines/line). Complex. | |
| Defer to PROBE-EVIDENCE | Decide after probe. | |

**User's choice:** `refund_line_items[].subtotal` (recommended)

### Q3: Test invariants (multi-select)

| Option | Description | Selected |
|--------|-------------|----------|
| Store-level invariant | `revenue(D) = Σ current_total_price(orders.created_at=D) − Σ transactions[].amount(refunds.processed_at=D, order.created_at≠D)` | ✓ |
| Per-product invariant | `Σ byProduct[pid].netRevenueCad = (gross for day_orders) − Σ refund_line_items.subtotal(cross-day)` | ✓ |
| Cross-path documentation (no test) | Document store ≈ Σ per-product gap in CONTEXT.md and manual. | ✓ |
| Full reconciliation test | store_net == Σ per-product netRevenueCad + total_tax_refunded + shipping_refunded (exact equality, ±0.01 CAD) | ✓ |

**User's choice:** All four — store, per-product, doc, and full reconciliation (recommended for regression prevention)
**Notes:** Strong correctness guarantees given the financial-accounting nature of the bug.

### Q4: Recon scope confirmation

| Option | Description | Selected |
|--------|-------------|----------|
| All 4 invariants | Confirm scope from Q3. | ✓ |
| Only 1+2+3, defer full recon | Lighter MVP. | |

**User's choice:** All 4 (recommended)
