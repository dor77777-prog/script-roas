# Phase 05.2.3.0 Plan 06: Per-Store 20-Day Revenue Cleanup Menu Items Summary

3 per-store ROAS-menu items + 3 thin handlers + 1 shared 20-day backfill implementation in Main.gs, fulfilling D-D2's operator-facing cleanup path for cross-day refunds beyond the rolling 3-day live backfill.

## Outcome

The ROAS menu now has a 4th cluster (between `מילוי היסטורי (טווח)…` and `התקן טריגר יומי…`) containing exactly the 3 items mandated by D-D2:

```
רענן הכנסות (20 ימים) — uzoshop      →  refreshRevenue20DaysUzoshop_
רענן הכנסות (20 ימים) — Zol Plus     →  refreshRevenue20DaysZolplus_
רענן הכנסות (20 ימים) — 360usmile    →  refreshRevenue20DaysUsmile_
```

Each wrapper calls `refreshRevenue20DaysImpl_(storeId, storeLabel)`, which:

1. Computes `today = todayStr_()` and `start = previousDayStr_(today, 19)` → 20-day inclusive window.
2. Logs to `Logger.log` AND opens a modal start alert (Hebrew — see the operator-facing strings below).
3. Calls `backfillRangeForStores(start, today, [storeId])`.
4. On success: logs completion and opens a modal completion alert advising the operator to wait ~30 seconds before clicking the next store's item.
5. On error: logs the message and opens a modal error alert pointing the operator at the Apps Script Executions log.

Apps Script's concurrent-execution quota (30 per script) plus the modal start alert practically eliminate the risk of 3 simultaneous backfills (T-05.2.3.0-06-01 mitigation per the plan's threat model).
