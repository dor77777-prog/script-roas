## Deviations from Plan

### Deviation D1 — Function rename for Run-dropdown visibility (`probeRefundContract_` → `probeRefundContract`)

**What:** Renamed the probe function from `probeRefundContract_` to `probeRefundContract`. Removed the trailing underscore. Updated the `addItem(..., 'probeRefundContract')` menu wiring to match. Doc-comment line "Run: ROAS menu → ... OR Apps Script editor → Run dropdown" remains accurate post-rename.

**Why:** Apps Script Editor's Run dropdown filters out functions with `_` suffix as a hard-coded convention (consistent with the project's other `_`-suffix functions: `showVerifyConfig_`, `showSpreadsheetUrl_`, `promptBackfill_`, `promptRunForDate_` — none of which appear in the dropdown). The plan's D-B3 requirement that the probe "MUST be invocable both via the Apps Script Run dropdown AND via the menu item" was unsatisfiable with the `_` suffix. The plan's separate guidance "DO NOT add a wrapper without `_`" was overridden in favor of a clean rename, since the probe is operator-invoked (matching the convention used by `setupAll`, `installDailyTrigger`, `bootstrapAllShopifyTokens`).

**Impact:**
- Plan 01 Task 1 acceptance criterion `grep -c 'function probeRefundContract_' Main.gs == 1` no longer passes verbatim; corrected gate is `grep -c 'function probeRefundContract' Main.gs == 1` (matches the renamed definition).
- Plan 01 Task 2 acceptance criterion `addItem('בדיקת חוזה החזרים (Shopify probe)', 'probeRefundContract_')` no longer matches verbatim; corrected gate uses the un-suffixed name.
- D-B3 satisfied (probe runs from Run dropdown and from menu).
- No downstream effect on Plans 02–07 — they don't reference `probeRefundContract` by name.

### Deviation D2 — D-B2 invariant empirically falsified → CONTEXT.md / Plans 02, 04 revised before Wave 2 dispatch

**What:** Probe ran on 3/3 stores. The math invariant `current_total_price == total_price − Σ refund.transactions[].amount` (D-B2) failed on all 3 by 80–468 CAD per order. The corrected invariant `current_total_price == total_price − Σ refund_line_items[].subtotal` matched all 3 exactly. CONTEXT.md decisions D-B2, D-C1, D-C3 were revised in the same commit batch as Wave 2 dispatch.

**Why:** D-B4 (the CHECKPOINT GATE between Plan 01 and Plan 02) was explicitly designed for this failure mode. The plan body line 396 says: "If at any step you see MATH MISMATCH on all 3 stores, STOP — that invalidates D-A1. Type `MISMATCH FOUND` instead of `approved` and we will revise 05.2.3.0-CONTEXT.md before continuing." This deviation IS the structural mechanism (D-B1..D-B4) doing its job — empirical evidence overriding a hypothesis before downstream code locks the wrong contract in.

**Impact:**
- CONTEXT.md D-B2, D-C1, D-C3 revised (see commit batch)
- Plan 02 Task 2 code body: store-level summing switched from `r.transactions[].amount` to `r.refund_line_items[].subtotal` (single field, single loop, matches per-product path D-C2)
- Plan 04: D-C3 invariant 3 collapsed (no `transactions − subtotal` gap to test); invariant 4 simplified (`custom_item_refunds(D)` replaces `total_tax_refunded + shipping_refunded`)
- D-A1 (`current_total_price IS net of refunds`) is **NOT** invalidated by this finding — it's confirmed by the corrected invariant (`current_total_price == total_price − Σ subtotal == 0` on all 3 stores, exactly matching observed `current_total_price`)

### Deviation D3 — usmile360 order had two refund objects (probable double-refund artifact)

**Observed:** usmile360 order 4697724059855 has `refunds[0]` and `refunds[1]` both with `processed_at` on 2026-05-20 and `transactions[0].amount = 302.10` each. Sum = 604.20. But `refund_line_items` subtotal sum is 136.43 (= order total), and `current_total_price = 0`.

**Interpretation:** Either (a) the merchant clicked "refund" twice (one was voided), or (b) the second refund object represents a no-op (e.g., refund-without-restock that didn't actually move money). The `current_total_price = 0` constraint confirms that Shopify did NOT actually take 604 CAD from the merchant — only the merchandise (136.43) flowed back.

**Mitigation:** The corrected algorithm uses `refund_line_items[].subtotal` (which sums to the correct 136.43, not the inflated 604.20), so this artifact is harmless for revenue accounting. The `transactions[].amount` field is unsafe and intentionally NOT used at the store level after this revision.

**Follow-up (deferred):** A future probe variant capturing `transactions[].kind` and `transactions[].gateway` could disambiguate void-vs-real-refund, but is not necessary for D-C1's correctness.
