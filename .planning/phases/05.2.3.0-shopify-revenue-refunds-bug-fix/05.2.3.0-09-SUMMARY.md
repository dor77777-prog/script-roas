## Expected Period Sum (Invariant 5)

Under the Plan 08 algorithm, period sum = `Σ storeNetCad over all 5 unique days = 85.00 CAD`. Derivation:

| Day | total_price for day | refunds on day | storeNetCad |
|---|---|---|---|
| 2026-03-09 | 65.28 (zolplus) | 0 | 65.28 |
| 2026-04-11 | 136.43 (usmile360) | 0 | 136.43 |
| 2026-05-02 | 68.80 (uzoshop) | 0 | 68.80 |
| 2026-05-10 | 60.00 (customItem) | 0 | 60.00 |
| 2026-05-20 | 50.00 (sameDay) | 68.80+65.28+81.08+55.35+20.00+5.00 = 295.51 | 50.00 − 295.51 = −245.51 |
| **Σ** | **380.51** | **295.51** | **85.00** |

Cross-check via period identity: `Σ total_price − Σ refund_line_items.subtotal = 380.51 − 295.51 = 85.00 ✓` (matches per-day sum).

Under the **pre-Plan-08 algorithm** (current_total_price + cross-day filter), period sum would have been:

| Day | current_total_price | cross-day refunds | storeNetCad |
|---|---|---|---|
| 2026-03-09 | 0.00 | 0 | 0 |
| 2026-04-11 | 0.00 | 0 | 0 |
| 2026-05-02 | 0.00 | 0 | 0 |
| 2026-05-10 | 55.00 | 0 | 55.00 |
| 2026-05-20 | 30.00 | 275.51 (no same-day intra-order) | −245.51 |
| **Σ** | | | **−190.51** |

Pre-Plan-08 period sum (−190.51) − Plan 08 period sum (85.00) = **−275.51** — exactly the cross-day refund double-deduction magnitude for the fixture set. Invariant 5 would have been RED against pre-Plan-08 main, GREEN against Plan 08 HEAD. The DUAL-ALGORITHM RED GATE comment block in the test body documents this hand-derivation so future readers can verify by hand without checking out historical code.

## Invariant 6 Verification (Synthetic Fixture)

Synthetic fixture `sameDayOrderWithFutureRefund` — same-day order on 2026-05-20, refund processed on 2026-05-25.

Plan 08 algorithm:

| Day under test | byProduct['prod-future-refund'] | storeNetCad |
|---|---|---|
| 2026-05-20 (order day) | +100.00 (line gross, no deduction — refund's processed_at != today, intra-order map empty) | 100.00 (total_price gross − 0 refunds today) |
| 2026-05-25 (refund day) | −40.00 (refund-day attribution applies the refund_line_item subtotal) | −40.00 (no orders created today − 40.00 refund) |
| **Period sum** | (period sum not computed at per-product level) | **60.00** |

Period identity: `total_price (100) − refund_subtotal (40) = 60 ✓`.

Pre-Plan-08 algorithm (refundByLineId unfiltered): on 2026-05-20 the future refund of 40 would have leaked into per-product net = 60 (= max(0, 100 − 0 − 40)). On 2026-05-25 the refund attributes again = −40. Period sum (per-product attribution) = 60 + (−40) = 20 — **wrong by 40.00** (same-day per-product over-counted the deduction).

Invariant 6 locks Plan 08 Task 3's `if (processedDay !== dateStr) continue` filter on the intra-order refundByLineId map in place.
