<objective>
Apply the cross-day refund deduction at the two existing callsites that surface revenue to `data-daily` (the home-tab / KPI feed) and `products-daily` (the per-product feed). After this plan, a refund processed today on yesterday's order appears as today's deduction across every dashboard surface — without any client-side change (dashboard reads from the same Sheets tabs).

Per D-A1, `current_total_price` is the source field — already net of same-day refunds (proven by AUDIT-P0-03). We add ONLY cross-day refunds via `getShopifyRefundsForDay_` (Plan 02). The double-deduction trap that rolled back the prior attempt is structurally avoided because the fetcher's filter (`refund.processed_at on D AND order.created_at NOT on D`) excludes refunds that `current_total_price` already accounts for.

Per D-D3, negative daily revenue is shown as-is — no clamping. A day with heavy refunds against prior-day orders legitimately shows negative revenue, consistent with `current_total_price` going negative per AUDIT-P0-03.

Per D-A3, BOTH callsites consume the SAME fetcher — each call site invokes it at most once per (store, day) inside its own function body. (We do NOT introduce a higher-level orchestrator caching layer in this plan — that would require restructuring DailyUpdate.gs. The "one fetch, two consumers" efficiency invariant is bounded by "one fetch per consumer function call", which is the natural granularity matching the existing DailyUpdate orchestrator that calls each function once per (store, day).)

Output: a refactored Shopify.gs where the two existing functions deduct cross-day refunds without changing their signatures (callers in DailyUpdate.gs / SheetBuilder.gs continue to receive the same shapes — number from `getShopifyRevenue`, array from `getShopifyProductSalesForDay`).
</objective>
