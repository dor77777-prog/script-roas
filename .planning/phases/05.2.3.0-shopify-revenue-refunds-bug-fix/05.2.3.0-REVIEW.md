# Phase 05.2.3.0: Code Review Report

**Reviewed:** 2026-05-21T15:30:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The phase ships a thorough refactor: an empirical probe (`probeRefundContract`), a shared cross-day refund fetcher (`getShopifyRefundsForDay_`), per-store rolling 3-day live wrappers, 3 per-store 20-day cleanup menu items, a pure-TS mirror with 4 invariant tests, and a comprehensive User Manual §16.11 section. The PROBE-EVIDENCE feedback loop (D-B4 gate) clearly worked — it caught the `transactions[].amount` falsification before fixtures were locked in.

**However, the core attribution model has a critical double-deduction bug that is triggered by the very mechanisms the phase introduced (rolling 3-day backfill, 20-day cleanup):**

The framework's assumption "`current_total_price` already nets same-day refunds" (D-A1 in comments at `Shopify.gs:176-178`) is true but incomplete — empirically (PROBE-EVIDENCE.md uzoshop/zolplus/usmile360) `current_total_price` reflects **ALL refunds applied to the order, including cross-day refunds**, not just same-day ones. Once any prior-day row is **re-fetched and overwritten** (which the rolling 3-day backfill and 20-day cleanup explicitly do), that row's stored revenue silently drops to reflect the future refund — AND the same refund is independently subtracted from the refund-processing day via `getShopifyRefundsForDay_`. The result: every cross-day refund within 48h of order creation is **deducted twice** in normal operation, and the 20-day cleanup menu (advertised as the operator's tool for fixing stale rows) **introduces the double-deduction for the entire 20-day window**.

Per-product breakdown has the same structural bug plus an additional drift (Apps Script's `refundByLineId` at `Shopify.gs:251-259` does NOT filter by `processed_at`, so it conflates same-day with cross-day refunds — TS mirror does filter and so they diverge).

In addition: a `Math.max(0, ...)` clamp at `Shopify.gs:274` violates the documented D-D3 "no clamping" policy for the per-product same-day path. The User Manual claim "שורת D-3 תישאר עם הסכום שהיה לפני ההחזר" (`docs/ROAS-Dashboard-User-Manual.md:1512`) is also factually incorrect once any backfill rewrites the row.

The phase also has the smaller (correctness-adjacent) issues called out as Warnings below: the test suite never exercises a multi-day reconciliation that would catch the double-deduction; the 3-day per-store loop has no inter-day sheets-quota breathing; `refreshAllStoresNow` per-shot trigger spacing is now too tight given the new ~46s/store estimate.

## Critical Issues

### CR-01: Double-deduction of cross-day refunds when prior-day rows are re-fetched

**File:** `Shopify.gs:111-185` (`getShopifyRevenue`), `Shopify.gs:624-729` (`getShopifyRefundsForDay_`), `DailyUpdate.gs:96-116` (per-store live wrappers), `Main.gs:368-397` (`refreshRevenue20DaysImpl_`), `dashboard-web/src/lib/shopifyRevenueRefunds.ts:154-241`

**Issue:** The store-level revenue model is:
```
row[D] = Σ current_total_price(orders.created_at=D)  −  Σ refund_line_items[].subtotal(refunds.processed_at=D AND order.created_at!=D)
```
Per `PROBE-EVIDENCE.md` Finding 1, the empirically validated invariant is `current_total_price == total_price − Σ refund_line_items[].subtotal` across **every** refund on the order, regardless of when it was processed. So `current_total_price` is a **live field that reflects all refunds applied so far** (this is also confirmed by `AUDIT-P0-03`'s observation that the field can go negative when refunds exceed the initial total).

Concretely with uzoshop's probe data (`PROBE-EVIDENCE.md` lines 11-21):
- Order created `2026-05-02`, `total_price=68.80`, refund processed `2026-05-20T15:27:19+03:00` with `refund_line_items[0].subtotal=68.80`, `current_total_price=0.00`.
- Trigger run on `2026-05-20`:
  - Day D=2026-05-20 row: cross-day deduction catches the refund → `-68.80`.
  - Day D-2=2026-05-18 row: re-fetched; no relevant orders (order X was created on 2026-05-02, outside the `created_at` window). OK.
- 20-day cleanup runs on 2026-05-21 → backfills `2026-05-02..2026-05-21`:
  - `2026-05-02` row re-fetched. `current_total_price` for order X is now `0.00` (refund applied). Gross = `0.00`. Cross-day deduction for May 2: `0` (refund's `processed_at=2026-05-20`, not May 2). **Row written as `0`** (was `68.80` originally).
  - `2026-05-20` row re-fetched: cross-day deduction still applies → `-68.80`.
- Sum over period: `0 + (-68.80) = -68.80`. True revenue: `68.80 - 68.80 = 0`. **Off by $68.80** (the refund counted twice).

The same bug fires **without** the 20-day cleanup whenever the refund happens within 48h of order creation, because the live trigger's rolling 3-day backfill (`runLiveUpdate{Uzoshop,Zolplus,Usmile}`, `DailyUpdate.gs:96-116`) re-fetches D-2 and D-1 on every 15-min cycle. Worked example:
- Order created `2026-05-18` for `$100`.
- Refund processed `2026-05-19 12:00` for `$30`.
- Live trigger fires `2026-05-19 12:15`: backfills May 17, 18, 19 sequentially.
- May 18 row re-written: `current_total_price=70` (refund already applied 15 min ago). Cross-day for May 18: nothing matches. Row = `$70`.
- May 19 row written: gross of May 19 orders + cross-day catches `$30` refund. Row = `(May 19 gross) − $30`.
- Sum: `$70 + (May 19 gross) − $30 = (May 19 gross) + $40`.
- True: `$100 (May 18 order) + (May 19 gross) − $30 (May 19 refund) = (May 19 gross) + $70`.
- **Off by $30, every time** — the refund is double-counted.

The TS mirror at `dashboard-web/src/lib/shopifyRevenueRefunds.ts:136-241` has the exact same shape (uses `parseNum(o.current_total_price)` for same-day gross AND subtracts cross-day `refund_line_items[].subtotal`), so the bug is replicated in the dashboard's pure-TS path that gets exercised by `computeRevenueWithCrossDayRefunds`.

Note that the existing 4 invariant tests at `dashboard-web/src/lib/__tests__/shopifyRevenueRefunds.test.ts:264-353` **cannot catch this bug** — they all run against a single day (`DAY_D = '2026-05-20'`) and assert that DAY_D's net is `-245.51`. They never trace the same fixtures across the order's creation day (e.g. May 2 for uzoshop) where `current_total_price=0.00` would silently produce a phantom `$68.80` loss against the May 2 row.

**Fix:** This requires a model change, not a patch. Two viable directions:

1. **Use `total_price` as gross + deduct ALL refunds at refund-processing day** (no cross-day filter, just attribute every refund to its `processed_at`):
   ```js
   // getShopifyRevenue
   total += parseFloat(o.total_price || 0);  // gross
   // getShopifyRefundsForDay_: drop the order.created_at != D filter; sum every refund whose processed_at falls on D.
   ```
   Net for the period now correctly equals `Σ total_price − Σ refund_line_items.subtotal`, distributed across the gross day and the refund day. Re-fetching prior-day rows no longer changes their value (`total_price` is immutable).

2. **Lock the original day's row** — never re-fetch a row once written. Use `total_price`-based gross for the original-day write only, and accept that cross-day refunds will only ever apply to refund-day rows. Then the 20-day cleanup menu becomes a contradiction (its purpose is to re-fetch); it would need to be replaced with a refund-day-only recompute.

Either fix demands updating the TS mirror, the test fixtures (which currently encode `current_total_price=0.00` as gospel — fine for cross-day day's net but not for same-day) and the User Manual claim at `docs/ROAS-Dashboard-User-Manual.md:1512` ("שורת D-3 תישאר עם הסכום שהיה לפני ההחזר").

### CR-02: Per-product `refundByLineId` deducts ALL refunds without `processed_at` filter — double-deducts cross-day refunds from original-day rows

**File:** `Shopify.gs:251-274`

**Issue:** Inside `getShopifyProductSalesForDay`'s same-day order loop, the per-line-item refund map is built from **every** refund on the order, with no `processed_at` filter:
```js
const refundByLineId = {};
for (const refund of (o.refunds || [])) {
  for (const rli of (refund.refund_line_items || [])) {
    const liId = String(rli.line_item_id || '');
    if (!liId) continue;
    const amount = parseFloat(rli.subtotal || rli.total || 0);
    refundByLineId[liId] = (refundByLineId[liId] || 0) + amount;
  }
}
// ...
const lineRefund = refundByLineId[String(li.id || '')] || 0;
const net = Math.max(0, gross - lineDiscount - lineRefund);
```

So for an order created on day D with a future refund processed on day D+5, when day D's `products-daily` row is rebuilt (e.g. during the rolling 3-day backfill on D+1/D+2, or the 20-day cleanup), the future refund is subtracted from day D's per-product `netRevenueCad`. The cross-day mechanism at `Shopify.gs:313-330` then subtracts the same refund from day D+5's per-product `netRevenueCad` (since `order.created_at=D ≠ D+5`).

This is also a **KEEP-IN-SYNC drift** from the TS mirror: `shopifyRevenueRefunds.ts:182-194` filters intra-order refunds by `processedDay === dateStr` before deducting from `byProduct`. Apps Script does not.

**Fix:**
```js
// Filter intra-order refunds to processed_at == dateStr only.
const refundByLineId = {};
for (const refund of (o.refunds || [])) {
  if (!refund.processed_at) continue;
  const processedDay = Utilities.formatDate(new Date(refund.processed_at), TZ, 'yyyy-MM-dd');
  if (processedDay !== dateStr) continue;
  for (const rli of (refund.refund_line_items || [])) {
    const liId = String(rli.line_item_id || '');
    if (!liId) continue;
    const amount = parseFloat(rli.subtotal || rli.total || 0);
    refundByLineId[liId] = (refundByLineId[liId] || 0) + amount;
  }
}
```
This restores parity with the TS mirror and removes the per-product double-deduction. CR-01 still needs its own model-level fix because the store-level path uses `current_total_price` (not line-level gross), so this patch alone isn't sufficient.

### CR-03: `Math.max(0, …)` clamp on per-product same-day net violates documented D-D3 "no clamping" policy

**File:** `Shopify.gs:274`

**Issue:** `getShopifyProductSalesForDay` enforces a non-negative floor on the per-product same-day net:
```js
const net = Math.max(0, gross - lineDiscount - lineRefund);
```
CONTEXT.md D-D3 (re-stated in `Shopify.gs:30-32` and `User-Manual.md:1556-1564`) explicitly says: "negative revenue should be shown as-is, no clamping to 0". The Phase comment at `Shopify.gs:307-312` adds: "Refund-only products (no day-D sales but a cross-day refund hit) surface with `netRevenueCad < 0` so the operator sees the deduction." That works only for the **cross-day-only** path at lines 320-326 (which uses `netRevenueCad: -refundCad`). The same-day path is clamped, so a same-day order whose intra-order refund exceeds gross still floors at 0 instead of going negative — exactly the opposite of D-D3.

The User Manual at line 1563 even claims: `הקוד ב-Shopify.gs (getShopifyRevenue + getShopifyProductSalesForDay) אינו מבצע Math.max(0, …) על הסכום הסופי`. This is factually wrong for `getShopifyProductSalesForDay`.

**Fix:** Drop the floor:
```js
const net = gross - lineDiscount - lineRefund;
```
Then audit `writeProductSalesForDay_` and the dashboard's product breakdown panel to confirm they render a negative `netRevenueCad` correctly (the dashboard already handles store-level negative revenue per D-D3, so this should be a small surface).

### CR-04: `getShopifyProductSalesForDay` same-day per-product net DRIFTS from TS mirror because Apps Script unfilters intra-order refunds and clamps to 0

**File:** `Shopify.gs:251-274` vs `dashboard-web/src/lib/shopifyRevenueRefunds.ts:182-194`

**Issue:** This is the explicit KEEP-IN-SYNC violation called out in CR-02 + CR-03 wrapped together, but worth surfacing as its own finding because the file headers at `shopifyRevenueRefunds.ts:1-9` and the test header at the test file's lines 1-10 declare a strict KEEP-IN-SYNC contract: "Any change to the algorithm must be applied to BOTH files in the same commit." Two divergences exist today:

| Aspect | Apps Script `getShopifyProductSalesForDay` | TS mirror `computeRevenueWithCrossDayRefunds` |
| --- | --- | --- |
| Intra-order refund filter on `processed_at` | **None** — sums every refund on the order | Filters `processedDay === dateStr` (line 186) |
| Negative net floor | `Math.max(0, …)` clamp at line 274 | No floor — accumulator is signed (D-D3 honored) |
| Fallback `rli.subtotal \|\| rli.total \|\| 0` | Yes at line 256 | No (TS only uses `rli.subtotal` in the same-day path) |

Each of these is a behavior-affecting drift. The test suite would not catch any of them because tests run against a single day where the same-day order's intra-order refund happens on that day (so the `processed_at` filter happens to be a no-op for the test fixture), and the same-day order's net is positive (so the clamp doesn't fire).

**Fix:** Apply CR-02 and CR-03 to Apps Script; then add a test case to `shopifyRevenueRefunds.test.ts` that exercises a same-day order with a future-day refund_line_item to lock the parity in.

## Warnings

### WR-01: Test suite never exercises a multi-day reconciliation — the 4 D-C3 invariants pass even with the CR-01 double-deduction bug

**File:** `dashboard-web/src/lib/__tests__/shopifyRevenueRefunds.test.ts`

**Issue:** All 4 invariant tests call `computeRevenueWithCrossDayRefunds(fixtureOrders, DAY_D='2026-05-20', PROBE_TZ)` against a single calendar day. The fixtures (uzoshop/zolplus/usmile360 from the probe) have orders created on `2026-05-02`, `2026-03-09`, `2026-04-11` respectively — but the tests never call the function with those dates to verify what the original-day net would be when re-computed.

Per the bug trace in CR-01: re-running on uzoshop's creation day (`2026-05-02`) would return `storeNetCad=0` because `current_total_price='0.00'` is the live (post-refund) value. So `sum over period (May 2 .. May 20)` from these fixtures alone would be `0 + (-245.51) = -245.51`, against a real expected `0 (all orders fully refunded; net=0 over the period)`. The tests don't catch this because they don't sum days.

**Fix:** Add a fifth invariant that sums `computeRevenueWithCrossDayRefunds(fixtureOrders, day, PROBE_TZ).storeNetCad` for each unique `created_at` day AND the refund day, then asserts the sum equals the period's true `Σ total_price − Σ refund_line_items.subtotal`. With current data this would fail and surface the CR-01 model bug.

### WR-02: Per-store live wrappers iterate 3 days with no inter-day Sheets API breathing

**File:** `DailyUpdate.gs:96-116`

**Issue:** `runLiveUpdateUzoshop` / `runLiveUpdateZolplus` / `runLiveUpdateUsmile` each loop `for (let n = 2; n >= 0; n--)` calling `runUpdateForSingleStore_` per iteration. `runUpdateForSingleStore_` writes campaigns + ads + daily-flat + products-daily + orders-attribution = thousands of cells. The legacy `runUpdateForDate` / `runUpdateForDateForStores_` inserts `Utilities.sleep(1500)` between **stores** specifically because the Sheets API short-window quota throttles multi-store runs; there is no analogous breathing between **days** in the new wrappers, even though the workload per day is comparable to a single store's workload.

Three days × ~10k cells across a single execution is the same magnitude as the multi-store cascade that motivated Phase 5 / 5.1's trigger split. The risk: a noisy day on uzoshop could time out before day 2 or day 3 finishes.

**Fix:** Add `if (n < 2) Utilities.sleep(1500);` (or equivalent) inside the loop to mirror the inter-store pause:
```js
function runLiveUpdateUzoshop() {
  const today = todayStr_();
  for (let n = 2; n >= 0; n--) {
    if (n < 2) Utilities.sleep(1500);
    const dateStr = previousDayStr_(today, n);
    runUpdateForSingleStore_('uzoshop', dateStr);
  }
}
```

### WR-03: `refreshAllStoresNow` one-shot trigger spacing (+5s/+30s/+55s) is now too tight given the 3-day rolling backfill ~46s/store estimate

**File:** `DailyUpdate.gs:134-139`

**Issue:** Before Phase 05.2.3.0, each per-store wrapper handled one day in ~15s, so 25s spacing was a safe margin. Now each wrapper handles 3 days in ~46s (per the docstring at `DailyUpdate.gs:84-85`). The current spacing produces overlap:

| wrapper | start | est. end | overlaps with |
| --- | --- | --- | --- |
| uzoshop  | +5s  | +51s | zolplus 30..51 (21s) |
| zolplus  | +30s | +76s | usmile 55..76 (21s) |
| usmile   | +55s | +101s | — |

Apps Script's 30-concurrent-execution ceiling won't be breached, but the Sheets API short-window quota is account-wide and is the very quota Phase 5 / 5.1 split apart. With 21s of overlap on EACH transition, two wrappers writing the same daily-flat tab concurrently can hit `Service Spreadsheets timed out`.

**Fix:** Widen spacing to `+5s / +60s / +120s` (or longer) so the 46s windows don't overlap.

### WR-04: `getShopifyRefundsForDay_` is called twice per store-day (once by `getShopifyRevenue`, once by `getShopifyProductSalesForDay`) — contract claims "one HTTP call, two consumers"

**File:** `Shopify.gs:180` (called from `getShopifyRevenue`) and `Shopify.gs:313` (called from `getShopifyProductSalesForDay`); contract assertion in comment block at `Shopify.gs:583-597` and CONTEXT.md D-A3.

**Issue:** The fetcher contract says: "Per D-A3: ONE HTTP call, TWO consumers." In practice `getShopifyRefundsForDay_` is invoked independently from both consumers — each invocation paginates the `updated_at` window from scratch. So per store-day the daily run executes `getShopifyRefundsForDay_` **twice**, doubling the Shopify Admin REST burn for the refund window. Combined with the rolling 3-day backfill that calls each consumer 3× per cycle = 6 refund-window fetches per store per 15-min cycle.

This is not a correctness bug, but it contradicts a documented design intent and adds 4× the Shopify API calls vs. the contract. At Shopify's default rate of 4 calls/sec (40 burst), this stacks but probably stays within budget; nonetheless the contract should match reality.

**Fix:** Pass the refund result from `getShopifyRevenue` (or compute it once at the call site in `updateStoreForDate_`) and feed it into `getShopifyProductSalesForDay` as an argument. Alternatively, drop the "one HTTP call" claim from the contract.

### WR-05: User Manual §16.11.1 incorrectly claims the original order's row is preserved

**File:** `docs/ROAS-Dashboard-User-Manual.md:1512`

**Issue:** The text says (Hebrew): `שורת D-3 תישאר עם הסכום שהיה לפני ההחזר (פר D-D3 — לא משכתבים שורות עבר)` — translation: "The D-3 row will stay with the amount it had before the refund (per D-D3 — we don't rewrite past rows)."

This is **factually incorrect**:
- The rolling 3-day backfill (`DailyUpdate.gs:96-116`) explicitly rewrites D-1 and D-2 every 15 minutes.
- The 20-day cleanup menu (this phase's `refreshRevenue20DaysImpl_`, `Main.gs:368-397`) rewrites the last 20 days when invoked.
- The user-facing `backfillRange` and `backfillRangeForStores` (`DailyUpdate.gs:525-595`) rewrite arbitrary ranges.

The User Manual ships this to operators as a guaranteed property of the system, and the property does not hold. Operators reading this section will conclude that the only thing that changes between D-3 and D is "the cross-day refund row gets added on D", and won't suspect that re-running cleanup re-attributes prior-day revenue.

**Fix:** Rewrite §16.11.1 to either (a) call out that prior rows DO get rewritten by backfills and the cleanup menu (and surface the resulting double-deduction risk per CR-01), or (b) once CR-01 is structurally fixed, change the model so the claim becomes true.

### WR-07: `probeRefundContract` 401 retry path doesn't increment `safety` — bounded only by `bootstrapTried` flag

**File:** `Main.gs:262-267`

**Issue:** The pagination loop in the probe:
```js
while (url && safety < 50 && !found) {
  const res = fetchWithRetry_(url, { … });
  const code = res.getResponseCode();
  if (code === 429) { Utilities.sleep(2000); safety++; continue; }
  if (code === 401 && !bootstrapTried) {
    bootstrapTried = true;
    const fresh = tryAutoBootstrapShopify_(store.id);
    if (fresh) { token = fresh; continue; }
  }
  // ...
  safety++;
}
```
On a 401 + successful bootstrap, `continue` is reached without bumping `safety`. Because `bootstrapTried = true` is set before continue, a second 401 in the same store can't loop, so this is bounded — but the comment "safety < 50" suggests the cap should be evenly enforced. Same pattern exists in `getShopifyRevenue` (`Shopify.gs:143-151`), `getShopifyProductSalesForDay` (`Shopify.gs:233-237`), `getShopifyRefundsForDay_` (`Shopify.gs:655-660`), `getShopifyOrdersAttribution` (`Shopify.gs:782-786`) — these are pre-existing patterns but the new probe adopts them.

**Fix:** Move `safety++` before the `continue` in the 401-success branch (or restructure the loop to always increment at the top):
```js
if (code === 401 && !bootstrapTried) {
  bootstrapTried = true;
  const fresh = tryAutoBootstrapShopify_(store.id);
  if (fresh) { token = fresh; safety++; continue; }
}
```

### WR-08: `getShopifyOrdersAttribution` doesn't subtract refunds from `totalCad`, leaving the attribution tab on gross-of-refunds revenue while `data-daily` is net

**File:** `Shopify.gs:754-831`

**Issue:** `getShopifyOrdersAttribution` writes `totalCad: parseFloat(o.current_total_price || 0)` per order, then `writeOrdersAttributionForDay` lands it in `{storeId}-orders-attribution`. The dashboard's reconciliation joins this tab to attribute per-channel revenue. Since the per-order rows reflect `current_total_price` (which is live), an order with a future refund will have its `totalCad` go down whenever the row is rewritten by a backfill — but only on the original day. The cross-day attribution flow doesn't add a separate "refund-day" row for cross-day refunds. So:

- The `orders-attribution` tab's per-day sum != `data-daily.revenueCad` for the same day, by the cross-day deduction amount.
- The dashboard's `dark traffic` calculation (`MetaShopifyReconciliation`) uses both sources and can show systematic mismatch on heavy-refund days.

This isn't strictly introduced by Phase 05.2.3.0 (the gross-of-refunds attribution row was pre-existing), but the phase's changes to `data-daily` opened a NEW gap between the two tabs that didn't exist before (when both tabs were on `current_total_price` only).

**Fix:** Either (a) reconcile the orders-attribution tab to also reflect cross-day refunds (insert a synthetic "refund row" with negative `totalCad` and channel inherited from the original order's row), or (b) document the new gap in the User Manual and in the dashboard's reconciliation block.

### IN-01: `previousDayStr_(date, 0)` returns yesterday, not the same day — surprising default

**File:** `Config.gs:94-99`

**Fix:** Allow `n>=0`:
```js
const offset = (typeof n === 'number' && Number.isFinite(n) && n >= 0) ? Math.floor(n) : 1;
```
