## Summary

**Phase 05.5 is a runway phase** — it establishes infrastructure (Postgres schema, env-var classification, dashboard supabase-js wiring) without changing any production behavior. The only user-visible change is the `sync OK` indicator going from binary to ternary. All locked decisions in `<user_constraints>` are pure scaffolding work — they do not interact with the existing Apps Script → Sheets pipeline, which continues running unchanged through Phase 05.6.

**The research surface is small and well-bounded.** The Supabase CLI, supabase-js client, Vercel CLI, and Postgres schema design are mature, documented, and have canonical workflows. The riskier parts of v2.0 (Inngest, TS fetchers, feature-flag flip) are explicitly out of scope for 05.5. The one architectural question that needs a discretion call from the planner is **how to handle the dashboard health endpoint**, since the current dashboard has no `/api/health` route — only `SyncIndicator` reading client-side `cloudSync.ts` state derived from `/api/dashboard-state` calls (see §Architecture Patterns).

**Primary recommendation:** Use `supabase init` at the **repo root** (not inside `dashboard-web/`) since migrations are an Apps-Script-and-Next.js-spanning concern; pin `@supabase/supabase-js@^2.106.1` in `dashboard-web/package.json`; use the **legacy anon/service_role keys** (functional through end-of-2026, new `sb_publishable_*` / `sb_secret_*` keys are operator-discretion); create a brand-new `dashboard-web/src/app/api/health/route.ts` for the connectivity ping (parallel `Promise.allSettled` checks against Sheets + Supabase, ~10s `Cache-Control`); seed Vercel env vars via stdin-piped `vercel env add` for reproducibility. Write `docs/PROPS-MAP.md` as a 43-row table (40 existing + 3 new Supabase keys) sorted by service grouping (Sheets → Notifications → Google Ads → uzoshop → zolplus → usmile360 → Supabase) to match `.env` Section ordering.

### Supporting

| Tool / Pattern | Purpose | When to Use |
|----------------|---------|-------------|
| `Promise.allSettled` (Node built-in) | Run sheets + supabase health checks in parallel without one failure aborting the other | `/api/health` route — both checks must complete to derive the ternary state |
| `JSONB` Postgres column type | Store `dashboard_state.value` as flexible JSON | The 7 existing `ALLOWED_STATE_KEYS` payloads have wildly different shapes (recurring billing array vs single goal number vs annotations record); JSONB preserves that without per-key columns |
| `TIMESTAMPTZ` (timestamp with time zone) | Audit columns (`updated_at`, `created_at`) | Supabase databases are UTC by default; TIMESTAMPTZ stores instant + lets queries project to any TZ |
| `TEXT` (not VARCHAR(N)) | Variable-length string columns | Postgres community convention (Postgres Wiki "Don't Do This") — TEXT and VARCHAR have identical storage/performance; arbitrary length caps cause production breakage. **This overrides the generic PostgreSQL docs recommendation of VARCHAR(N) which is misleading for Postgres specifically.** |
| `NUMERIC(p, s)` | Monetary columns (revenue, spend, COGS) | Exact-precision; ad-platform conversion-value math accumulates floating-point error otherwise. `NUMERIC(14, 4)` gives 10 integer digits + 4 fractional — plenty for any realistic CAD amount |

### Pattern 1: Supabase CLI cloud-only workflow

**What:** Run `supabase init`, `supabase link --project-ref <ref>`, then `supabase db push` to apply migrations to the cloud project. Skip the Docker local stack entirely (D-B2).

**When to use:** Phase 05.5 ships migrations 0001 + 0002. Future migrations during 05.6 follow the same flow.

**Source:** `[CITED: supabase.com/docs/guides/deployment/database-migrations]` + `[CITED: supabase.com/docs/reference/cli/supabase-db-push]`

```bash
# One-time, repo-root
supabase init                                       # creates supabase/config.toml + supabase/migrations/
supabase login                                      # interactive; or set SUPABASE_ACCESS_TOKEN for CI
supabase link --project-ref <ref-from-dashboard>   # binds to the cloud project (free tier)

# Per migration
supabase migration new initial_schema               # generates 20260521000001_initial_schema.sql skeleton
# ... edit the SQL file ...
supabase db push                                    # applies all unapplied migrations to the cloud
supabase migration list                             # verify cloud + local agree
```

**Non-TTY workaround (if a future GitHub Action wants to push automatically):**
```bash
export SUPABASE_ACCESS_TOKEN="$SUPABASE_ACCESS_TOKEN_SECRET"
supabase link --project-ref <ref>  # works without interactive login
supabase db push --include-all     # apply everything
```

### Pattern 2: Migration filename convention

**What:** Supabase CLI generates files named `YYYYMMDDHHMMSS_<short_name>.sql` in **UTC** time. The 14-digit timestamp is what enforces chronological ordering across collaborators. `[CITED: supabase.com/docs/guides/local-development/overview + community confirmation]`

**Recommendation:** Let the CLI generate timestamps (don't hand-name files). Example outputs from `supabase migration new`:
- `supabase/migrations/20260521143022_initial_schema.sql`
- `supabase/migrations/20260521143055_seed_stores.sql`

Never use `0001_` / `0002_` style prefixes — they break chronological merging when two collaborators create migrations on different branches.

### Pattern 3: Cloud-only Migration discipline (D-B4 — Claude's discretion call)

**Recommendation: additive-only by default; explicit `-- DESTRUCTIVE` comment exception.**

**Rationale:**
- Single Supabase project means every migration runs against production data. A bad `DROP TABLE` cannot be rolled back (D-B3 accepted: no staging).
- Additive migrations (`CREATE TABLE`, `ALTER TABLE ADD COLUMN`, `CREATE INDEX`) are safe to re-run via the migration-history check; they can't lose data.
- A `DROP COLUMN` / `DROP TABLE` / `TRUNCATE` requires the operator to add `-- DESTRUCTIVE: <reason>` as the first line of the migration. This is a tripwire — the planner / reviewer / Discord can grep for `^-- DESTRUCTIVE` in any PR.
- Convention: **never edit an already-pushed migration file.** If a migration was wrong, write a new corrective migration. Use `supabase migration repair` only as a last resort.

**Concrete convention to lock in 05.5:**
1. Default: additive operations only. No `DROP`, `TRUNCATE`, `RENAME`, or `ALTER COLUMN TYPE`.
2. Exception: prepend `-- DESTRUCTIVE: <one-line reason>` if destructive operation is unavoidable.
3. Never edit a pushed migration (per `supabase migration list` showing it as applied) — write a new one.
4. Migration commit message format: `feat(supabase): <migration purpose>` matching repo's commit-prefix style.

### Pattern 4: `@supabase/supabase-js` minimal Next.js server-side client

**What:** Use `createClient()` (NOT `@supabase/ssr.createServerClient()`) since 05.5 does not need cookie-based auth — we only do anon-key reads from server-side route handlers. `[VERIFIED: supabase-js v2.106.1 GitHub README + Context7-equivalent docs review]`

**Source:** `[CITED: supabase.com/docs/reference/javascript/initializing]`

```ts
// dashboard-web/src/lib/supabase.ts (NEW)
import { createClient } from '@supabase/supabase-js';

/**
 * Server-only Supabase client. Uses the anon key — Phase 05.5 only does
 * SELECT count(*) FROM stores (D-D2), which is allowed even with RLS off.
 *
 * Why anon and not service_role:
 *  - Lower blast-radius if the key ever leaks (anon can SELECT/INSERT/UPDATE/
 *    DELETE but is rate-limited by Supabase; service_role bypasses RLS entirely)
 *  - D-D2 locks the ping as `SELECT count(*) FROM stores` — read-only — so anon
 *    is sufficient
 *  - Phase 05.6 will introduce a SECOND client using service_role for the
 *    Inngest writer; that's the right place to add the elevated client
 *
 * Note on env-var names:
 *  - `SUPABASE_URL` and `SUPABASE_ANON_KEY` (server-side only — no NEXT_PUBLIC_
 *    prefix) are sufficient for Phase 05.5. If we later need browser-side
 *    queries (e.g., realtime), promote them to `NEXT_PUBLIC_SUPABASE_URL` and
 *    `NEXT_PUBLIC_SUPABASE_ANON_KEY` — but defer that to 05.6 when the read-
 *    path actually flips to Postgres.
 */
const url = process.env.SUPABASE_URL;
const key = process.env.SUPABASE_ANON_KEY;

if (!url || !key) {
  // Fail fast at module load if env vars are missing — same pattern as
  // dashboard-web/src/lib/sheets.ts which requires GOOGLE_PRIVATE_KEY at boot.
  throw new Error('SUPABASE_URL or SUPABASE_ANON_KEY missing — check Vercel env vars');
}

export const supabase = createClient(url, key, {
  auth: { persistSession: false },  // server-side, no user session
});
```

### Pattern 5: Parallel health check (`/api/health`)

**What:** Both checks run in parallel via `Promise.allSettled`. One failing doesn't break the other. Total latency = max(sheets latency, supabase latency).

**Source:** Inspired by existing soft-fail pattern in `dashboard-web/src/app/api/orders-attribution/route.ts:28-44` (catches errors, returns shape-compliant response with `error` field).

```ts
// dashboard-web/src/app/api/health/route.ts (NEW)
import { NextResponse } from 'next/server';
import { supabase } from '@/lib/supabase';
import { getAuth } from '@/lib/sheets';  // existing — service-account auth probe
import { google } from 'googleapis';

export const revalidate = 10;  // matches /api/dashboard-state cadence

type HealthStatus = 'ok' | 'down';
type HealthResponse = {
  sheets: HealthStatus;
  supabase: HealthStatus;
  lastChecked: string;
  errors?: { sheets?: string; supabase?: string };
};

async function pingSheets(): Promise<void> {
  // Cheapest possible verification — Spreadsheet metadata get + assert the
  // SPREADSHEET_ID env var resolves. Matches the existing reader scope.
  const auth = getAuth();
  const sheets = google.sheets({ version: 'v4', auth });
  await sheets.spreadsheets.get({
    spreadsheetId: process.env.SPREADSHEET_ID!,
    fields: 'spreadsheetId',
  });
}

async function pingSupabase(): Promise<void> {
  // D-D2: SELECT count(*) FROM stores — should be 3 after seeding.
  // Use head: true to avoid transferring row data — only metadata.
  const { error } = await supabase
    .from('stores')
    .select('id', { count: 'exact', head: true });
  if (error) throw new Error(error.message);
}

export async function GET() {
  const [sheetsRes, supabaseRes] = await Promise.allSettled([
    pingSheets(),
    pingSupabase(),
  ]);

  const errors: HealthResponse['errors'] = {};
  const sheetsStatus: HealthStatus = sheetsRes.status === 'fulfilled' ? 'ok' : 'down';
  const supabaseStatus: HealthStatus = supabaseRes.status === 'fulfilled' ? 'ok' : 'down';

  if (sheetsRes.status === 'rejected') {
    errors.sheets = String(sheetsRes.reason?.message ?? sheetsRes.reason);
  }
  if (supabaseRes.status === 'rejected') {
    errors.supabase = String(supabaseRes.reason?.message ?? supabaseRes.reason);
  }

  return NextResponse.json(
    {
      sheets: sheetsStatus,
      supabase: supabaseStatus,
      lastChecked: new Date().toISOString(),
      ...(Object.keys(errors).length > 0 ? { errors } : {}),
    } satisfies HealthResponse,
    {
      headers: { 'Cache-Control': 's-maxage=10, stale-while-revalidate=60' },
    },
  );
}
```

### Anti-Patterns to Avoid

- **Hand-naming migration files (`0001_*.sql`, `0002_*.sql`):** Breaks merge ordering. Always use `supabase migration new <name>` to get a UTC timestamp.
- **Editing a migration that's already been pushed:** Even if the project is single-user, `supabase migration list` will flag the divergence between the cloud's `schema_migrations` table and the local file. Always write a corrective migration.
- **Using `@supabase/ssr` for the simple anon-key ping:** Adds cookie-auth complexity that 05.5 explicitly doesn't need. Save it for when Phase 05.6 introduces operator-action writes.
- **Calling `supabase.from('stores').select('*')` for the ping:** Transfers full row data on every poll. Use `{ count: 'exact', head: true }` to get only the count.
- **Setting `force-dynamic` on `/api/health`:** Same trap as documented in `ARCHITECTURE.md` Anti-Patterns — conflicts with the explicit `Cache-Control` header. Use `revalidate` + explicit `Cache-Control` (matches the `/api/dashboard-state` pattern).
- **Adding `NEXT_PUBLIC_` prefix to Supabase env vars:** Promotes the value to the browser bundle. For 05.5 (server-only ping), use plain `SUPABASE_URL` / `SUPABASE_ANON_KEY`. Defer the `NEXT_PUBLIC_*` versions to 05.6 if the feature flag needs browser-side queries.
- **Committing `.env` to git:** It's already in `.gitignore` — keep it there. The PROPS-MAP file in `docs/` references value placeholders, not actual values. `docs/PROPS-MAP.md` itself is safe to commit as long as the "Source value" column shows abbreviated tokens (e.g., `EAAVHQVcWlXMBRhT...`).
- **Per-store split tables (`uzoshop_campaigns_daily`):** Locked rejected by D-A4 — single `campaigns_daily` table with `store_id` PK column.
- **`VARCHAR(N)` instead of `TEXT`:** Postgres community convention `[CITED: wiki.postgresql.org/wiki/Don't_Do_This]` — TEXT is the right default. VARCHAR(N) provides no performance benefit and risks production breakage on edge-case inputs. **This is non-obvious because some Postgres generic docs recommend VARCHAR.**
- **`DOUBLE PRECISION` for currency columns:** Use `NUMERIC(14, 4)`. Conversion-value accumulation across thousands of orders accumulates floating-point error.

|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: Forgetting to `supabase login` before `supabase link`
**What goes wrong:** `supabase link --project-ref X` fails with `Error: please log in first`.
**Why it happens:** First-time CLI use on a fresh machine.
**How to avoid:** Plan includes an explicit `supabase login` step before the link step. Mention that browser-based device auth is the path.
**Warning signs:** `link` fails immediately with auth error.

### Pitfall 2: Pushing migrations to the wrong cloud project
**What goes wrong:** `supabase db push` applies the schema to a different project than expected because `supabase/config.toml` had the wrong project_id.
**Why it happens:** `supabase link` was run once with the wrong `--project-ref`, then never re-linked.
**How to avoid:** After `supabase link`, immediately run `supabase status` to confirm project_id. Plan includes "operator confirms project_id matches the freshly-created project" as a checkpoint:human-verify.
**Warning signs:** `supabase db push` succeeds but the dashboard UI doesn't show the new tables.

### Pitfall 3: Postgres `RLS Disabled in Public` lint warning blocks operator confidence
**What goes wrong:** Supabase dashboard Security Advisor surfaces lint code `0013_rls_disabled_in_public` on every one of the 10 tables. Operator might panic and enable RLS prematurely, breaking D-D2's anon-key ping. `[CITED: github.com/orgs/supabase/discussions/26584]`
**Why it happens:** Supabase defaults assume public REST access requires RLS — but our single-user URL-obscurity model deliberately skips RLS (per `/gsd-explore` 2026-05-21).
**How to avoid:** Plan documents the lint warning as expected; consider adding a `docs/SECURITY-POSTURE.md` (or a section in User Manual) explaining the trust model. **One mitigation: remove `public` from "exposed schemas" in API settings** — kills the lint at the cost of disabling the auto-generated REST API. But this conflicts with D-D2 (anon-key REST read of `stores`). For 05.5, accept the lint and document the deferral.
**Warning signs:** Operator opens Supabase dashboard, sees 10 red badges, considers enabling RLS without policies → all reads break.

### Pitfall 4: Long Shopify product IDs corrupted in `products_daily.product_id`
**What goes wrong:** Shopify product IDs are 17-19 digit numerics. If stored as `BIGINT`, they overflow JS Number precision (16 safe digits) when the dashboard reads them. `[VERIFIED: SheetBuilder.gs:1163-1168 has explicit comment about this]`
**Why it happens:** `BIGINT` survives Postgres-side, but JSON-encoded responses from Supabase REST go through JS Number on the dashboard side.
**How to avoid:** `product_id TEXT` in all 4 tables that reference product IDs (`products_daily`, `product_catalog`, plus any future references in `orders_attribution.line_items` JSON values). Apps Script side already forces text format on these columns (`SheetBuilder.gs:1169`); Postgres side mirrors that.
**Warning signs:** `productMap` lookups fail; product mapping breaks silently.

### Pitfall 5: `vercel env add` for development env defaults to "encrypted", not "sensitive"
**What goes wrong:** Production seeds are auto-marked `sensitive` (can't be viewed in dashboard later); development seeds are marked `encrypted`. Operator pulls dev env vars expecting to see the value; they're hidden.
**Why it happens:** Vercel CLI policy as of 2026-03-17 — production+preview default to `sensitive`; development is `encrypted`. `[CITED: vercel.com/docs/cli/env]`
**How to avoid:** For 05.5, seed only `production` (the dashboard runs on Vercel production for the operator). Don't seed development env vars unless needed for local dev (defer to 05.6 if needed).
**Warning signs:** Operator runs `vercel env pull` and sees `***` instead of values.

### Pitfall 6: Migration file edited after push, losing track of cloud state
**What goes wrong:** Operator edits `20260521143022_initial_schema.sql` after running `supabase db push`. Next `db push` reports nothing to apply (timestamp already in `schema_migrations`), but the local file disagrees with the cloud.
**Why it happens:** Confusion between "edit a migration" and "write a follow-up migration."
**How to avoid:** Plan locks the convention: **never edit a pushed migration; always write a new one**. Add a `supabase/MIGRATION-DISCIPLINE.md` (~30 lines) documenting the rule.
**Warning signs:** `supabase migration list` shows "Local" column ≠ "Remote" for any timestamp.

### Pitfall 7: Existing `/api/dashboard-state` cache busted by SyncIndicator polling `/api/health`
**What goes wrong:** Adding a second 30s-poll endpoint doubles the Sheets API request rate; if the new endpoint's `pingSheets()` is too aggressive (e.g., calls `values.get` on a large range), it eats quota.
**Why it happens:** The existing `revalidate=10` on `/api/dashboard-state` already polls Sheets every 10s × the SWR interval. Adding `/api/health` with the same cadence approximately doubles read pressure.
**How to avoid:** `pingSheets()` uses `sheets.spreadsheets.get` (metadata only, returns spreadsheet ID — costs 1 unit of read quota) NOT `values.get`. Verified pattern in the route code skeleton above. Also: cache `/api/health` for 10s + SWR `dedupingInterval` of 30s gives effective 1 call per 30s.
**Warning signs:** `Quota exceeded` errors in Vercel logs around the time SyncIndicator was deployed.

### Pitfall 8: SyncIndicator's existing yellow state conflicts with new yellow meaning
**What goes wrong:** D-D1 mandates yellow = "Sheets OK but Supabase down". The current `SyncIndicator` may already use an in-flight / pending state that's also yellow-ish (`bg-white/15`).
**Why it happens:** Reusing color tokens across semantic states.
**How to avoid:** Inspect current colors: existing `error` uses `bg-red-500/85`, `ok` uses `bg-emerald-500/30`, `syncing` uses `bg-white/15`, idle uses no special bg. **No existing yellow.** D-D1 yellow is a new state; use Tailwind's `bg-amber-500/30` or similar. Verified by reading SyncIndicator.tsx:34-57.
**Warning signs:** Visual ambiguity between "still saving" and "Supabase down."

### Known Threat Patterns for {Postgres + Supabase + Next.js}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SQL injection via supabase-js | Tampering | supabase-js uses parameterized queries via PostgREST; injection requires explicit `.rpc()` with concatenated SQL. **No raw SQL in 05.5 code.** |
| Anon key leak via browser exposure | Information Disclosure | Anon key in `SUPABASE_ANON_KEY` (no `NEXT_PUBLIC_` prefix); server-only. Vercel marks `sensitive` so it can't be retrieved via dashboard later. |
| Service-role key leak | Elevation of Privilege | `SUPABASE_SERVICE_ROLE_KEY` server-only, never logged, never passed to browser. supabase-js client in `lib/supabase.ts` uses anon — service role NOT loaded in 05.5. |
| RLS bypass | Elevation of Privilege | RLS disabled by design. Mitigation: anon key has only the privileges granted to `anon` role in Postgres (SELECT on `public` tables by default). No row-level filtering needed because we have only 1 user. |
| Time-of-check-time-of-use in health endpoint | Tampering | Endpoint is read-only; no TOCTOU risk. |
| Open redirect / SSRF via health endpoint | Tampering | Endpoint takes no input. |
| Excessive querying (DDoS via SyncIndicator polling) | Denial of Service | 30s SWR interval + 10s `Cache-Control` + Vercel rate-limits. Single-user system has no DDoS surface. |
