## Area 1 — Schema scope

### Q1: How many tables to create in 05.5?

**Options presented:**
- Full: 7 tables upfront (`stores`, `manual_overrides`, `data_daily`, `products_daily`, `campaigns_daily`, `ads_daily`, `notification_config`)
- Half: 3 load-bearing tables (`stores` + `manual_overrides` + `data_daily`)
- Minimal: `stores` + `health_check` only

**User answered (freeform):** "יש רשימה גדולה יותר של טבלאות לפי מה שאני רואה בקובץ roas אני רוצה שכל הטבלאות הרלוונטיות שצריכות להווצר כדי לעמוד בכל מה שהדבשורד עושה ומציג כרע בצורה אמיתית" — i.e. "the actual list is bigger than 7; I want all the tables needed for the dashboard to display real data."

**Orchestrator action:** Scanned the codebase (`grep` for `getSheetByName`, `insertSheet`, `_TAB`) to find ALL Sheets tabs currently in use:
- Global tabs: `data-daily`, `products-daily`, `manual-spend`, `store-meta`, `סיכום` (Summary), `dashboard-state`
- Per-store dynamic tabs: `{storeId}-campaigns`, `{storeId}-ads`, `{storeId}-orders-attribution`, `{storeId}-products-catalog`

**Updated proposal:** 10 tables total (not 7), with the 4 per-store entity sets collapsing to 4 unified tables with `store_id` column. The `סיכום` tab becomes a materialized view (deferred to 05.6).

**Decision (D-A1, D-A5):** Full 10-table schema upfront. Phase 05.6 has zero DDL surface area.

### Q2: Column granularity per table

**Options:** Mirror 1:1 / Mirror + cleanup / Normalize aggressively (3NF + FKs)

**Selected:** **Mirror 1:1** (Recommended). Trivial schema mapping; easy to verify in Phase 05.7 diff. Cost: includes unused columns from Sheets, cleaned up in a post-cut-over hygiene pass.

**Decision (D-A2):** Mirror 1:1 column granularity. Cleanup deferred.

### Q3: Archive policy for 18-month retention

**Options:** Don't archive — single table forever / Soft archive (`is_archived` flag) / Hard archive (separate `*_archive` table)

**Selected:** **Don't archive** (Recommended). Postgres handles 1M+ rows fine with composite indexes; the Sheets archive was a cell-cap workaround. Estimated load (100 orders/day × 3 stores × 5 years ≈ 500k orders) is well within single-table comfort zone.

**Decision (D-A3):** No archive — single table per entity forever. Defer Postgres partitioning to future phase if row counts cross ~10M.

### Q4: Per-store consolidation strategy

**Options:** Unified (one table per entity with `store_id` column) / Per-store (12 separate tables: `campaigns_uzoshop`, `campaigns_zolplus`, etc.)

**Selected:** **Unified** (Recommended). Cross-store queries via `WHERE store_id IN (...)` instead of `UNION` across 3 tables. Mirrors the natural Postgres multi-tenant pattern.

**Decision (D-A4):** Unified per-entity tables. The 4 entities currently split across 3 per-store tabs each collapse to 4 unified tables.

**Continue?** Selected "לעבור ל-Setup approach" — moved to Area 2.

## Area 2 — Setup approach

### Q1: How to create the Supabase schema?

**Options:** Supabase CLI + git migrations / Web UI (Studio) / Hybrid

**Selected:** **CLI + SQL migrations in git** (Recommended). Schema is git-tracked code. `supabase init` at repo root; migrations in `supabase/migrations/{timestamp}_{name}.sql`. `supabase db reset` reproduces from scratch.

**Decision (D-B1):** Supabase CLI + git-tracked migrations.

### Q2: Local-dev with Docker?

**Options:** Local Supabase (Docker) for development / Cloud only

**Selected:** **Cloud only** — all migrations run directly against the cloud project. No Docker, no staging.

**Decision (D-B2):** Cloud-only. Trade-off accepted: every migration is "production" (no staging). Mitigation: migrations are git-tracked + reviewable before push.

### Q3: Single Supabase project vs dev/prod separation?

**Options:** Single project for all environments / Two projects (dev + prod)

**Selected:** **Single project** (Recommended). Single-user system, no team. Local dev + Vercel Preview + Production all share the same Supabase project.

**Decision (D-B3):** Single Supabase cloud project for all environments. Risk accepted: local dev work shows live data.
