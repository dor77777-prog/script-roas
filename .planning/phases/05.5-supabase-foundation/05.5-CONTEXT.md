# Phase 05.5: Supabase Foundation + PROPS-MAP - Context

**Gathered:** 2026-05-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Stand up Supabase Postgres (free tier, single cloud project) with the full v2.0 data model (10 tables); classify all 40 properties from `.env` into SECRET / CONFIG / DATA + seed them into Vercel env vars / Supabase tables; write `docs/PROPS-MAP.md` as the operator checklist gating cut-over (Phase 05.7); extend the dashboard's existing `sync OK ☁️` indicator with a Supabase connectivity ping so the operator gets a one-glance "is the new stack alive?" signal at the end of the phase.

**No fetcher work, no production behavior change.** This phase is the runway — it lays the foundation Phase 05.6 builds on. The only user-visible change is the `sync OK` indicator going from binary (Sheets only) to ternary (Sheets / Supabase / both).

This phase explicitly excludes:
- Inngest setup → Phase 05.6
- TS port of Apps Script fetchers → Phase 05.6
- Operator console UI (sync now button, jobs table, backfill picker, manual_overrides CRUD) → Phase 05.6
- Importer of 38 `manual_spend` rows → Phase 05.6
- Dashboard feature flag (`READ_FROM=sheets|postgres`) → Phase 05.6 (only the read path; flip default in 05.7)
- Apps Script decommission → Phase 05.7
- Supabase Auth + RLS policies → deferred to a future phase (single-user URL-obscurity stays, per `/gsd-explore` 2026-05-21)
- Token rotation playbook → deferred to a future phase

</domain>

<decisions>
## Implementation Decisions

### Area A — Schema scope & fidelity

- **D-A1:** Create the **full v2.0 data model upfront in 05.5** — 10 tables, not a minimal smoke-test schema. Operator's request: "all relevant tables needed for the dashboard to display real data." This locks the schema design as a Phase-05.5 deliverable so Phase 05.6's Inngest port has zero DDL surface area and can focus entirely on porting fetcher logic.
- **D-A2:** **Mirror Sheets 1:1 at the column level.** Every column visible in Apps Script's writes to a tab maps to a Postgres column with the same semantics (snake_case rename). Empty / unused columns from Sheets carry over as-is — even if they look obsolete, removing them risks breaking a downstream read path nobody remembers. Cleanup of dead columns is deferred to a post-cut-over hygiene pass.
- **D-A3:** **No archive — single table per entity forever.** Postgres handles 1M+ rows in a single table comfortably with composite `(store_id, date)` indexes. The Sheets-era 18-month archive workbook was a Sheets-cell-cap workaround, not a Postgres requirement. Defer partitioning to a future phase only if row counts cross ~10M (current trajectory: ~500k orders over 5 years across 3 stores — well under).
- **D-A4:** **Unified per-entity tables with `store_id` column, NOT per-store split tables.** The 4 entities currently split as 3 per-store tabs each (`{store}-campaigns`, `{store}-ads`, `{store}-orders-attribution`, `{store}-products-catalog`) collapse to **4 unified tables** (`campaigns_daily`, `ads_daily`, `orders_attribution`, `product_catalog`) with `store_id` as the first PK column. Cross-store dashboard queries become `WHERE store_id IN (...)` instead of `UNION ALL` across 3 tables.
- **D-A5:** **10-table schema:**
  1. `stores` — store metadata (id, name, currency, hasGoogleAds, plan, etc.) — replaces `store-meta` tab + STORES constant in Config.gs
  2. `manual_overrides` — operator-typed spend overrides — replaces `manual-spend` tab
  3. `data_daily` — per-(store, date) aggregate — replaces `data-daily` tab
  4. `products_daily` — per-(store, date, product_id) — replaces `products-daily` tab
  5. `campaigns_daily` — per-(store, date, campaign_id, platform) — replaces 3 × `{storeId}-campaigns` tabs
  6. `ads_daily` — per-(store, date, ad_id) — replaces 3 × `{storeId}-ads` tabs
  7. `orders_attribution` — per-(store, order_id) classification — replaces 3 × `{storeId}-orders-attribution` tabs
  8. `product_catalog` — per-(store, product_id) names/types — replaces 3 × `{storeId}-products-catalog` tabs
  9. `dashboard_state` — per-key state for cloud-sync — replaces `dashboard-state` tab
  10. `notification_config` — operator-editable notification settings (templates, phones, email) — extracted from PropertiesService `notify.*` / `metacloud.*` / `twilio.*` values
- **D-A6:** **The Hebrew `סיכום` (Summary) tab is NOT mirrored as a table.** That tab uses Sheets-native VLOOKUP formulas to aggregate. In Postgres, the dashboard's API routes do the aggregation in SQL (or via a `data_daily_summary` materialized view if performance demands). Materialized view design is deferred to Phase 05.6 where actual query patterns crystallize.

### Area B — Setup approach

- **D-B1:** **Supabase CLI + version-controlled SQL migrations** in `supabase/migrations/{timestamp}_{name}.sql`. Schema is git-tracked code, not external state. PR review can catch schema drift. `supabase db reset` reproduces the entire state from scratch on demand. Init via `supabase init` at the repo root.
- **D-B2:** **Cloud-only — no local Docker Supabase** during 05.5–05.6. All migrations run directly against the cloud project. Trade-off accepted: every schema change is "production" (no staging), but the single-user system has no concurrent users to disrupt. Mitigation: migrations are git-tracked + Discord-reviewable before push.
- **D-B3:** **Single Supabase cloud project for all environments** (`roas-dashboard`, or operator-chosen name). No dev/prod project split. Single-user system, no team. Vercel Preview deployments share the same Supabase project. Risk accepted: local dev work shows live data.
- **D-B4 (claude's discretion — deferred to planning):** Migration discipline during 05.5–05.6 — additive-only (never DROP) vs flexible (DROP/recreate OK during iteration). Recommend: additive-only by default; explicit DROP migration with `-- DESTRUCTIVE` comment if absolutely needed. Lock convention in 05.5 planning step.

### Area C — PROPS-MAP format

- **D-C1:** **Single markdown table at `docs/PROPS-MAP.md`** with 5 columns: `Property key | Type | Destination | Source value | Seeded?`. Operator-readable, grep-able, checkbox-based progress (`[ ]` → `[x]` as each row gets seeded). All 40 rows in one place.
- **D-C2:** **Preserve original `lowercase.with.dots` key names** in the "Property key" column. The translation to UPPER_SNAKE_CASE (Vercel convention) lives in the "Destination" column. Example row:
  ```
  | uzoshop.shopify.token | SECRET | VERCEL_ENV: UZOSHOP_SHOPIFY_TOKEN | shpat_... | [ ] |
  ```
- **D-C3:** **Type taxonomy (3 values):** `SECRET` (Vercel env var, sensitive — Shopify tokens, Meta access tokens, refresh tokens, etc.) / `CONFIG` (Vercel env var, low-sensitivity — domains, ad account IDs, customer IDs) / `DATA` (Supabase row — operator-editable via UI in Phase 05.6 — notification_config.template_name, stores.currency, etc.).
- **D-C4:** **Rotation playbook is deferred to a future phase.** PROPS-MAP focuses on classification + seeding status in 05.5. Incident-response steps for rotating Shopify/Meta/Google/Twilio tokens get their own `docs/SECRET-ROTATION.md` in a later phase, not now.
- **D-C5 (Claude's discretion — planning):** Add 2 new Supabase-side properties to `.env` and PROPS-MAP during this phase:
  - `supabase.url` → CONFIG → `VERCEL_ENV: SUPABASE_URL`
  - `supabase.anon.key` → SECRET → `VERCEL_ENV: SUPABASE_ANON_KEY`
  - (and possibly `supabase.service.role.key` → SECRET → `VERCEL_ENV: SUPABASE_SERVICE_ROLE_KEY` for server-side writes)

### Area D — Connectivity smoke test

- **D-D1:** **Extend the existing `sync OK ☁️` indicator** in the dashboard header. The indicator becomes ternary:
  - 🟢 Green = both Sheets API + Supabase are reachable (the post-05.5 happy path)
  - 🟡 Yellow = Sheets OK but Supabase fails (Supabase project down or env vars wrong)
  - 🔴 Red = Sheets unreachable (current `sync OK` red behavior, unchanged)
- **D-D2:** **Ping payload: `SELECT count(*) FROM stores`** via the supabase-js client. This single query validates:
  - Network connectivity (reaches the Supabase REST endpoint)
  - Auth (Vercel-injected `SUPABASE_ANON_KEY` works)
  - Schema (the `stores` table exists from D-B1's migrations)
  - Permissions (anon role can read — confirms RLS-off configuration intended for 05.5)
  - The `count(*)` should return `3` (uzoshop, zolplus, usmile360) after the seeding step completes.
- **D-D3 (Claude's discretion — planning):** Implementation detail — extend the existing `/api/health` (or equivalent) route to add a `supabase` field alongside the current `sheets` field. The indicator component reads both. Refresh cadence stays the same as current `sync OK` (likely every 30s when tab visible).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`.env` at project root** — already inventoried 40 properties grouped by service (Sheets / Notifications / Google Ads / per-store credentials × 3). Section 5 has a draft type classification. PROPS-MAP.md takes this draft and turns it into the actionable checklist with Destination + Seeded columns.
- **`Config.gs:STORES` constant** (3 entries: uzoshop, zolplus, usmile360 with `name`, `hasGoogleAds`) — direct mapping to the `stores` table seed (D-A5 row 1). Single source of truth for store identity.
- **`SheetBuilder.gs`** — creates the 8 Sheets tabs today. Reading the tab schemas (column headers, types) is the canonical reference for the 1:1 mirror in D-A2.
- **Existing `sync OK ☁️` indicator in the dashboard** — a known UI surface that already polls a health endpoint at 30s cadence. D-D1 extends it; no new UI component needed.

### Established Patterns
- **Per-store dimensional naming** — Apps Script uses `{storeId}-{entity}` for tab names; v2.0 collapses to single tables with `store_id` column (D-A4). Test that the dashboard's queries are filtered by `store_id` consistently.
- **`storeId` lookup pattern** — code uses `getProp(${storeId}.shopify.token)` against PropertiesService. In v2.0, this becomes `getSupabaseSecret(${storeId}, 'shopify_token')` (Phase 05.6) or `process.env.UZOSHOP_SHOPIFY_TOKEN` (Vercel env var direct). PROPS-MAP locks the Destination column for each.
- **`spreadsheet.id` + `spreadsheet.canonical-id` duplicate** — both point to the same workbook today (legacy). Migrate both to `VERCEL_ENV: SPREADSHEET_ID`; do NOT carry the duplicate over.

### Integration Points
- **Vercel env vars are already the existing dashboard's secret store** for some keys (e.g., `GOOGLE_SERVICE_ACCOUNT_*`). PROPS-MAP D-C1 doesn't introduce a new mechanism — just extends the existing Vercel-env-vars pattern with another 25-30 entries.
- **Supabase free tier limits:** 500MB DB, 2GB egress, 50k MAU (irrelevant for single-user), 500MB file storage. Estimated current load: <1MB schema + ~30MB/month data growth = well under for 1-2 years.
- **`@supabase/supabase-js`** is the standard client. Install path: `dashboard-web/package.json` (NOT root — Apps Script side stays untouched).

</code_context>

<specifics>
## Specific Ideas

- The `notification_config` table (D-A5 row 10) is a small operator-editable settings table. Rows include: `notify.provider` (metacloud), `metacloud.template_name` (roas_daily_summary), `metacloud.template_lang` (he), `notify.dashboard_url`, `notification.email`, `notify.phone1`, `notify.phone2`. Twilio fields (currently DATA in PROPS-MAP but legacy per `.env` Section 2.3) get rows too — flagged as `provider = 'twilio' AND active = false` (kept for fallback). The CRUD UI for `notification_config` comes in Phase 05.6.
- The `dashboard_state` table (D-A5 row 9) ports from the existing `dashboard-state` Sheets tab. Schema: `key TEXT PRIMARY KEY, value JSONB, updated_at TIMESTAMPTZ`. The 8 ALLOWED_STATE_KEYS from `dashboard-web/src/app/api/dashboard-state/route.ts` are the canonical key set.
- For **Phase 05.6** planning context: the TS port of fetchers should NOT introduce new Supabase tables — every read/write maps to the 10 tables locked here. If 05.6 discovers a table is needed that 05.5 didn't create, that's a planning bug to flag back to 05.5 (re-open the schema decisions).

</specifics>
