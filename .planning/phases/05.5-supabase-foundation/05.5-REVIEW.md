## Summary

Phase 05.5 introduces a server-only Supabase client, a soft-fail `/api/health` route, a ternary `SyncIndicator`, the v2.0 10-table schema + seed migrations, the PROPS-MAP operator checklist, and a User Manual update. Security posture is clean overall: no `NEXT_PUBLIC_*` leakage, no `service_role` key used in 05.5 code, and PROPS-MAP truncates every sensitive token to ~8 characters. Migrations are additive and consistent with the locked discipline doc.

One **BLOCKER** stands out: the module-load fail-fast in `supabase.ts` breaks the soft-fail promise of `/api/health` when `SUPABASE_URL` / `SUPABASE_ANON_KEY` are missing — and the inline justification cites `sheets.ts:getAuth` as precedent, which is factually inverted (sheets.ts throws lazily inside the function, supabase.ts throws eagerly at import). This is the exact failure mode (amber state) that D-D1 is supposed to surface to the operator; instead the whole endpoint 500s and the SyncIndicator shows the `idle` neutral pill.

Six WARNINGs cover: SyncIndicator branches that swallow `idle` and initial-load supabase-down conditions, missing `UNIQUE (provider)` on `notification_config`, an unverified-but-claimed default Postgres SELECT grant for the anon role after RLS-off, mismatched `revalidate` literal vs. constant (acknowledged in spec but worth a sync-comment hardening), seed migrations that aren't idempotent on re-run, and the absence of FOREIGN KEYs from `*_daily.store_id` to `stores.id`.

No critical security issues. No SQL injection (all seed values are literals). No `NEXT_PUBLIC_*` env vars introduced. `service_role` is correctly absent from 05.5 code, mentioned only as a deferred 05.6 concern in comments. PROPS-MAP previews are all truncated.

## Blockers

### BL-01: `supabase.ts` throws at module load, defeating `/api/health` soft-fail and amber-state D-D1 detection [RESOLVED]

**Status:** RESOLVED in commit `6bcc0f5` (2026-05-21) — `supabase.ts` converted to lazy `getSupabase()` factory; `health/route.ts:pingSupabase()` updated. Local build with empty env vars now succeeds end-to-end; vitest 242/242 passing; production curl with cache-bust returns `{"sheets":"ok","supabase":"ok"}` from the post-fix deploy.

**File:** `dashboard-web/src/lib/supabase.ts:25-29`
**Issue:** The supabase client module throws at top-level if env vars are missing:

```ts
const url = process.env.SUPABASE_URL;
const key = process.env.SUPABASE_ANON_KEY;

if (!url || !key) {
  // Fail fast at module load if env vars are missing — same pattern as
  // dashboard-web/src/lib/sheets.ts which requires GOOGLE_PRIVATE_KEY at boot.
  throw new Error('SUPABASE_URL or SUPABASE_ANON_KEY missing — check Vercel env vars');
}
```

The justification claims parity with `sheets.ts:getAuth`, but this is factually inverted:

- `sheets.ts:getAuth` (line 45) is a **function**. The throw on line 50 only fires when `getAuth()` is *called* — i.e., lazily, inside `pingSheets()` at `route.ts:38`. The `Promise.allSettled` wrapper at `route.ts:61` then captures it, marks `sheetsRes` as `rejected`, and the response is 200 with `sheets: 'down'`. Soft-fail works as designed.
- `supabase.ts:25` throws at **module evaluation**. Importing `supabase` at `route.ts:14` is synchronous; if env vars are missing the entire route module fails to load and Next.js returns **500 Internal Server Error** to the SyncIndicator, **not** the 200/`supabase: 'down'` soft-fail.

Downstream consequences:
1. The soft-fail comment at `route.ts:5-7` ("Returns shape-compliant JSON with HTTP 200 always") is broken — `/api/health` 500s when SUPABASE env vars are absent.
2. The D-D1 amber state in `SyncIndicator.tsx:79-84` (`status === 'ok' && health?.supabase === 'down'`) is unreachable in this scenario — the fetcher receives non-2xx, returns `null` (line 26 of SyncIndicator), `health?.supabase` is `undefined`, and the user sees the neutral `idle` pill instead of amber. The User Manual §1.7 instructs the operator to "check SUPABASE_URL / SUPABASE_ANON_KEY ב-Vercel" when they see yellow — but they will never see yellow when those env vars are the exact thing missing.
3. The User Manual table row at §2.1 (line 197 of the manual) promises 🟡 yellow when "Supabase לא נגיש או env vars שגויים ב-Vercel" — directly contradicted by the actual behavior of throwing 500 in that case.

This is the inverse of fail-fast: it fails the route entirely instead of degrading gracefully, in exactly the operator-facing scenario the ternary indicator was designed to surface.

**Fix:** Make the throw lazy. Either:

(a) Mirror `getAuth()` — export a factory and call it inside the ping:
```ts
// supabase.ts
import { createClient, type SupabaseClient } from '@supabase/supabase-js';

let cached: SupabaseClient | null = null;

export function getSupabase(): SupabaseClient {
  if (cached) return cached;
  const url = process.env.SUPABASE_URL;
  const key = process.env.SUPABASE_ANON_KEY;
  if (!url || !key) {
    throw new Error('SUPABASE_URL or SUPABASE_ANON_KEY missing — check Vercel env vars');
  }
  cached = createClient(url, key, { auth: { persistSession: false } });
  return cached;
}
```
and then in `route.ts:53-58`:
```ts
async function pingSupabase(): Promise<void> {
  const { error } = await getSupabase()
    .from('stores')
    .select('id', { count: 'exact', head: true });
  if (error) throw new Error(error.message);
}
```
The throw now lands inside `pingSupabase`, gets captured by `Promise.allSettled`, and the route returns 200 with `supabase: 'down'` and the proper `errors.supabase` field. The User Manual's amber-state instructions become reachable and accurate.

(b) Less invasive: keep module-load behavior but provide a null fallback:
```ts
export const supabase = (url && key)
  ? createClient(url, key, { auth: { persistSession: false } })
  : null;
```
and check `if (!supabase) throw new Error(...)` inside `pingSupabase`. Same lazy-throw semantics, fewer call-site changes.

Either fix also requires correcting the misleading "same pattern as `sheets.ts`" comment at `supabase.ts:26-27` so it doesn't mislead future maintainers.

## Warnings

### WR-01: SyncIndicator `idle` state hides supabase outage at first paint

**File:** `dashboard-web/src/components/SyncIndicator.tsx:64-95`
**Issue:** The ternary ordering at lines 69-95 only checks `health?.supabase === 'down'` when `status === 'ok'`. The initial `SyncState.status` is `'idle'` (per `cloudSync.ts:104`). On first paint, before `hydrateFromCloud` has fired, the component falls through to the final `else` branch (line 93), showing the neutral `bg-white/12` pill with title `ממתין לסנכרון ראשוני` — even if `/api/health` returns `{ supabase: 'down' }`. The amber state is therefore tied to a successful sheets hydrate, not to the actual supabase health, which is the opposite of the D-D1 goal of "Sheets OK, Supabase down → amber".

Also: when SWR has not yet returned (`health` is `undefined`), `health?.supabase === 'down'` evaluates `false`, so even a `status === 'ok'` user briefly sees green during the first 30s SWR window if supabase is down. Acceptable but worth documenting.

**Fix:** Extract the supabase check so it also applies during `idle`:
```ts
const supabaseDown = health?.supabase === 'down';

if (status === 'syncing') { /* unchanged */ }
else if (status === 'error') { /* unchanged */ }
else if (supabaseDown) {
  // amber regardless of sheets sync status (idle, ok, anything not error)
  icon = <Cloud size={13} />;
  label = 'sync OK';
  tone = 'bg-amber-500/30 text-white hover:bg-amber-500/40';
  title = 'Sheets תקין, Supabase לא זמין — בדוק SUPABASE_URL / SUPABASE_ANON_KEY ב-Vercel';
}
else if (status === 'ok') { /* green, unchanged */ }
else { /* neutral idle */ }
```
Tradeoff: amber will show during idle even before sheets has been confirmed reachable, which means the label "sync OK" is slightly inaccurate (sheets state unknown, not "ok"). Consider relabeling the amber pill to `Supabase Down` or splitting `label` from `title`. Pair with BL-01 fix — once `/api/health` reliably returns 200, the amber path is the only honest signal of supabase outage.

### WR-02: `notification_config` lacks `UNIQUE (provider)` — duplicate rows risk on re-seed or future upserts

**File:** `supabase/migrations/20260521063112_initial_schema.sql:166-178`
**Issue:** `notification_config` uses `id BIGSERIAL PRIMARY KEY` and `provider TEXT NOT NULL`, with no `UNIQUE` constraint on `provider`. The seed migration inserts two rows (`metacloud` + `twilio`). Two issues:

1. **Re-run hazard:** the seed migration is not wrapped in `ON CONFLICT DO NOTHING`. The MIGRATION-DISCIPLINE.md does forbid re-pushing immutable migrations, but `supabase db reset --linked` is a documented escape hatch in Supabase tooling and would re-apply the seed; without unique-on-provider, this would yield 4 rows, 2 per provider. Future Phase 05.6 writers reading "the active metacloud row" would have to pick one arbitrarily.
2. **Phase 05.6 prep:** the Writer in 05.6 will need to update `notification_config.template_name` etc. from the dashboard UI. Without `UNIQUE (provider)`, an `ON CONFLICT (provider)` upsert clause is impossible — the writer would have to read-then-update-or-insert, which is racy.

**Fix:** Add a UNIQUE constraint on `provider` in a follow-up migration (do NOT edit the pushed 05.5 migration — see MIGRATION-DISCIPLINE.md rule 3):
```sql
-- supabase/migrations/<new-ts>_notification_config_unique_provider.sql
-- ADDITIVE
ALTER TABLE notification_config ADD CONSTRAINT notification_config_provider_unique UNIQUE (provider);
```
Then the seed migration becomes idempotent with a one-line change going forward:
```sql
INSERT INTO notification_config (...) VALUES (...)
ON CONFLICT (provider) DO NOTHING;
```

### WR-03: Seed migration is not idempotent — duplicate `stores` PK violation on re-apply

**File:** `supabase/migrations/20260521063301_seed_stores.sql:6-19`
**Issue:** Both `INSERT` statements lack `ON CONFLICT` handling:

```sql
INSERT INTO stores (id, name, has_google_ads, meta_ad_account_id, google_ads_customer_id) VALUES
  ('uzoshop',   'uzoshop',   TRUE,  '26442930835313109', '4014537400'),
  ('zolplus',   'Zol Plus',  FALSE, '800776975668368',   NULL),
  ('usmile360', '360usmile', FALSE, '981695850074160',   NULL);
```

If the seed migration is re-applied (e.g., `supabase db reset --linked` mid-development, or an operator manually re-runs the file to re-seed after a partial wipe), the second run errors on `stores_pkey` (duplicate `id`). The migration is "pushed and immutable" per discipline doc, but defensive `ON CONFLICT (id) DO NOTHING` would harden the file against operator error without changing observable behavior on a clean apply.

Same concern for `notification_config` once WR-02 lands.

**Fix:** In a follow-up migration (not edit-in-place), backfill idempotent seeding for any future re-apply. Alternatively, accept the risk and document in the phase summary that re-running the seed is unsupported — both are valid trade-offs.

### WR-04: Anon-role grants assumed — verify `SELECT` on `stores` works without RLS policies

**File:** `dashboard-web/src/lib/supabase.ts:1-19` and `supabase/migrations/20260521063112_initial_schema.sql` (header)
**Issue:** The schema comment says "RLS deliberately NOT enabled — single-user URL-obscurity (per /gsd-explore 2026-05-21)". With RLS off in Supabase, the default `anon` role grants depend on PostgREST defaults plus any role grants in the `extensions`/`graphql_public` config. In a fresh Supabase project, `anon` *does* by default have `SELECT` on tables in `public`, but this is config-dependent and not guaranteed across project tiers/regions/recent platform changes.

If for any reason the `anon` role does not have `SELECT` on `stores`, the D-D2 ping returns a permission error and the SyncIndicator goes amber **forever** even when the project is healthy. Worse, the operator would follow the User Manual's instruction to "check SUPABASE_URL / SUPABASE_ANON_KEY" — neither of which is the real cause.

**Fix:** Add a defensive explicit grant in a follow-up migration so the access surface is committed to git rather than implicit:
```sql
-- supabase/migrations/<new-ts>_anon_role_grants.sql
-- ADDITIVE
GRANT USAGE ON SCHEMA public TO anon;
GRANT SELECT ON stores TO anon;
-- Phase 05.6 will add INSERT/UPDATE/DELETE grants on the writer tables via service_role
```
Even if these grants are already implicitly applied, the explicit grant in source-of-truth migrations protects against project-config drift and surfaces the security model in code review for future phases.

Also recommend adding a one-line VALIDATION step: run `psql -c "SELECT has_table_privilege('anon', 'stores', 'SELECT');"` against the linked project as part of the 05.5 acceptance check.

### WR-05: `export const revalidate = 10` literal mismatched-by-design with `CACHE_CONFIG.health.revalidate`

**File:** `dashboard-web/src/app/api/health/route.ts:19-24` and `dashboard-web/src/lib/cacheConfig.ts:32`
**Issue:** The route comment correctly acknowledges Next.js's MemberExpression limitation forces a literal, and that the literal "MUST stay in sync with CACHE_CONFIG.health.revalidate". This is the same pattern as the other routes — fine as a workaround, but the synchronization is fragile because nothing enforces it at build time. A future maintainer who bumps `CACHE_CONFIG.health.revalidate` from `10` to `20` won't get a TypeScript or runtime error if the literal on line 24 isn't also bumped — the symptom would be subtle (CDN s-maxage=20 but Next ISR re-runs every 10s, doubling read-quota traffic).

**Fix:** Add a build-time assertion to catch drift. The cleanest approach is a `type` brand that fails to compile if the literal disagrees:
```ts
// route.ts (after CACHE_CONFIG import)
export const revalidate = 10;
// Guard against drift between literal and config — fails compile if they diverge.
const _check: typeof revalidate = CACHE_CONFIG.health.revalidate;
void _check;
```
Or simpler — a one-line vitest in `cacheConfig.test.ts`:
```ts
import { revalidate as healthRevalidate } from '@/app/api/health/route';
import { CACHE_CONFIG } from '@/lib/cacheConfig';
test('health route literal matches CACHE_CONFIG', () => {
  expect(healthRevalidate).toBe(CACHE_CONFIG.health.revalidate);
});
```
This is preventative — the pattern repeats across `dashboard-state/route.ts:10`, `store-meta/route.ts:10`, etc., so it's worth investing in once.

### WR-06: No FOREIGN KEYs from `*_daily.store_id` to `stores.id`

**File:** `supabase/migrations/20260521063112_initial_schema.sql` (all CREATE TABLE statements)
**Issue:** The schema declares `store_id TEXT NOT NULL` on `manual_overrides`, `data_daily`, `products_daily`, `campaigns_daily`, `ads_daily`, `orders_attribution`, `product_catalog`, and `notification_config` (implicitly via `phone1`, etc.), but **never** declares `REFERENCES stores(id)`. This mirrors Sheets's lack of referential integrity, but Postgres can enforce it cheaply and protects against:

1. Typo-introduced orphan rows during 05.6 backfill (e.g., `'uzo-shop'` vs `'uzoshop'`).
2. Future `DELETE FROM stores WHERE id = 'usmile360'` orphaning rows in 6 tables.
3. Backfill from the Sheets export accidentally including a store_id that's not in the canonical `stores` table.

The 05.6 phase will be the easiest time to discover such drift; without FKs the dashboard happily renders rows for a non-existent store.

**Fix:** Add FKs in a follow-up migration (cannot edit 05.5 migration per discipline rule 3):
```sql
-- supabase/migrations/<new-ts>_store_id_fks.sql
-- ADDITIVE
ALTER TABLE data_daily          ADD CONSTRAINT data_daily_store_fk          FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE products_daily      ADD CONSTRAINT products_daily_store_fk      FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE campaigns_daily     ADD CONSTRAINT campaigns_daily_store_fk     FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE ads_daily           ADD CONSTRAINT ads_daily_store_fk           FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE orders_attribution  ADD CONSTRAINT orders_attribution_store_fk  FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE product_catalog     ADD CONSTRAINT product_catalog_store_fk     FOREIGN KEY (store_id) REFERENCES stores(id);
ALTER TABLE manual_overrides    ADD CONSTRAINT manual_overrides_store_fk   FOREIGN KEY (store_id) REFERENCES stores(id);
```
Note: this must run AFTER all 05.6 backfill data has been validated; running it before 05.6 imports would error if any imported row references a missing store. Consider deferring until 05.6 acceptance — but flag it in the 05.6 plan so it doesn't get forgotten.

### WR-07: `manual_overrides.platform` is unconstrained TEXT — accept set or enum needed

**File:** `supabase/migrations/20260521063112_initial_schema.sql:31`
**Issue:** `platform TEXT NOT NULL` accepts any value. The Sheets `manual-spend` tab has a constrained enum-like set (`meta`, `google`, etc.). Without a CHECK constraint or enum type, future Phase 05.6 imports could land `'Meta'` vs `'meta'` vs `'facebook'` and the dashboard would render them as separate platforms. Same concern applies to `campaigns_daily.platform`, `ads_daily.platform`.

**Fix:** Add a CHECK constraint in a follow-up migration:
```sql
-- supabase/migrations/<new-ts>_platform_check.sql
-- ADDITIVE
ALTER TABLE manual_overrides  ADD CONSTRAINT manual_overrides_platform_check  CHECK (platform IN ('meta', 'google'));
ALTER TABLE campaigns_daily   ADD CONSTRAINT campaigns_daily_platform_check   CHECK (platform IN ('meta', 'google'));
ALTER TABLE ads_daily         ADD CONSTRAINT ads_daily_platform_check         CHECK (platform IN ('meta', 'google'));
```
Or use a Postgres ENUM type, which is more invasive but self-documenting. Defer if the canonical platform set isn't yet locked — but document the decision.

## Out-of-scope Observations (not findings — context only)

These are NOT findings but are recorded so future reviewers don't re-discover them:

- **`HealthResponse` cross-import from a route file by a client component.** `SyncIndicator.tsx:8` does `import type { HealthResponse } from '@/app/api/health/route'`. This is the codebase convention (used 8 places, e.g., `CommandPalette.tsx`, `InsightsBoard.tsx`, `ProductsTable.tsx`). Because `import type` is erased at compile time, no runtime cycle exists and the route's `googleapis` + `next/server` imports do not get bundled into the client. Safe pattern, no finding.
- **`service_role` key absent from 05.5 code.** Grep confirms only documentation references (planning, PROPS-MAP row 43 marked as `[x]` seeded into Vercel env), never imported by any source. Correctly deferred to 05.6 per the supabase.ts comment.
- **PROPS-MAP token previews are all ≤8 characters + `...`** — no full secret leakage. PROPS-MAP §"Notes" item 4 explicitly documents this discipline. Good.
- **No `NEXT_PUBLIC_*` env vars introduced in 05.5.** The supabase.ts comment correctly defers to 05.6 if browser-side queries are needed. Good.
- **Cache-Control: `public` on /api/health** means browsers/CDN cache for 10s. This can delay supabase-outage detection by up to ~10s + 30s SWR interval = ~40s worst case. Acceptable trade-off for read-quota economy on a 30s poller; not a bug.
- **`head: true` + `count: 'exact'` in pingSupabase** issues `HEAD /rest/v1/stores?select=id` with `Prefer: count=exact`. Bandwidth ~0, count returned in `Content-Range`. Correctly the cheapest verification per RESEARCH.md Pitfall 7.
- **User Manual §1.7 + §2.1 are sound** when paired with the BL-01 fix. The Hebrew translation is consistent with the rest of the manual; the RLS-disabled rationale matches the URL-obscurity trust model in MEMORY.
